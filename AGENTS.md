# Working on WitOS

## Project direction

The core objective is standard upstream .NET above a minimal native kernel and a hardware-independent system layer. Shells and applications eventually run on that .NET platform. [ADR 0024](@Docs/Implementation/ADR-0024-Three-Layers-and-Unix-Form-Runtime.md) (2026-10-06) fixes the architecture: a nano-kernel of mechanisms whose hardware part (`Kernel.Arch.*`, `Kernel.Platform.*`) is the UHI; a user-space system layer that owns loading, process state and the runtime substrate; unchanged upstream .NET in its Unix form (`TargetOS=witos`), whose POSIX-shaped substrate is private to the system layer. Neither Win32 nor POSIX is an external contract of WitOS. The specifications are [RFC 0011 v3](@Docs/RFC-0011-Kernel-Architecture-and-ABI.md) (kernel architecture, ABI-1 between the kernel and the system layer, ABI-2 between the system layer and .NET) and [RFC 0015 v2](@Docs/RFC-0015-DotNet-Runtime-Port-and-Compatibility-Contract.md) (the runtime port and the compatibility contract); the Implementation Strategy §157 maps the milestones to the plan. Current guest code includes the kernel's ABI-1 mechanisms on the three ISAs (ABI-1 1.4; threads on every processor of the board since phase P), the system layer of phases S and D (the libc, libwitos, the root task and the NativeAOT services of ADR 0025 — devices and storage, the terminal, the display and the network — ABI-2 1.1 since V2.3) and upstream .NET in its Unix form: NativeAOT and CoreCLR pass the M3 acceptance, `dotnet App.dll` runs an application published by the stock SDK without a RID on Windows or Linux as those bytes, .NET 10 and 8 run side by side, PowerShell and base applications run on the terminal and the screen, the network service gives sockets, HTTP, HTTPS, ASP.NET Core, local sockets and IPv6, and one x64 kernel boots QEMU's q35 and pc machines and VMware, where a USB keyboard on an xHCI controller is driven (R2–R8, N1–N4, C, V, P, W, H1, H2.1; the audits of 2026-10-14 and 2026-10-20 in `@Docs/Implementation/`). Phase H takes WitOS to real hardware: VMware first, then the Raspberry Pi 4 and, as its goal, the PocketTerm35 with a Raspberry Pi 5, booted by UEFI or by the Linux arm64 boot protocol to one boot contract (ADR 0028, ADR 0029, ADR 0030); the author's aim is computers, phones and tablets on current ARM and x86 processors and embedded systems with substantial hardware; the Windows-form runtime line was removed at plan step K8.2, and the kernel policy it needed (native PE loading, the DLL lifecycle, files, process state) left at K8.4a. Host-side C# tooling must not be described as guest .NET support.

The application compatibility target is unchanged portable managed binaries under upstream CoreCLR/JIT, standard TFMs/SDK/NuGet and optional additive WitOS APIs. NativeAOT is an early system implementation/deployment tool, not the application compatibility contract; do not replace upstream CoreLib or managed semantics.

Original vision documents live in `@Docs/`. Concrete implementation status and deliberate limitations live in `@Docs/Implementation/`. Preserve original drafts unless the task calls for revising them.

Track the program in the root PLAN.md: phases A, K, T, S, R, D, N, C, V, P, W and H with steps such as `K2.1`. Name a slice, its commit and its PR by its step; mark a step complete only when its guest acceptance passes on every supported ISA — x64, ARM64 and, since V3 (`@Docs/Implementation/V3-Three-ISAs.md`), riscv64: a rule below that says "both ISAs" was written for x64 and ARM64 and holds on riscv64 as well, except the NuGet libraries' own suites (N2.2) and .NET 8 beside .NET 10 (N3), which stay on x64 and ARM64 as caveats until a RISC-V board is a release target (the first release's are x64 and ARM64, ADR 0028; the author's decision of 2026-10-23) — and in the same PR move its entry with its evidence to `@Docs/Implementation/Plan-Completed.md` and update the plan's phase table and next step: PLAN.md holds only current work (the audit of 2026-10-14, `@Docs/Implementation/Program-Audit-2026-10-14.md`). ## Rules of the new direction

These follow RFC 0011 v3 and RFC 0015 v2 and bind every new slice in phases K, T, S, R, D, N, C, V, P, W and H.

- The kernel keeps mechanisms only. Nothing in `src/Kernel` learns an image format, a file, a path, a directory, a name of a thread or process, an environment variable, a library or symbol, a language's exception format, a service or a device class. A call enters ABI-1 only when no composition of existing calls provides the mechanism and a layer-2 consumer with a test needs it (RFC 0011 §5). The kernel policy RFC 0011 §8 marks "leaves" was removed at step K8.4a (the PE loader, libraries, files and the package's parser, the environment and current directory, thread names, stack leases, software exception scopes and fatal reports, calls 207–222); the version 1 thread form, raw and compiler TLS and `INT 0x80` left at K8.4b; the startup block leaves at K8.4c and is never extended.
- Every system call validates its whole input, including every byte of a destination buffer, before it changes any state or writes any byte; a failed call changes nothing; an object is published only after all of its resources exist. Request structures start with `Version` and `Size`; an unknown version is `UNSUPPORTED`, a wrong size `INVALID_ARGUMENT`, and the kernel never pretends success. After step K1 a call number, a status value and a rights bit are never reused; `QUERY` reports the ABI-1 version and the feature mask of the families present (RFC 0011 §10.1). ABI-1 is 1.0 since K8.4d, 1.1 since R7.2b (`PROCESS_QUERY`'s `BUDGET` state and `THREAD_CREATE`'s `STACK_ADJACENT` flag), 1.2 since D1.2 (a device handle that is its process's last reference reaches another process) 1.3 since C2.1 (`DEVICE_MEMORY`'s window: the region's page an object of at most 64 pages starts at, so that a framebuffer is reached window by window) 1.4 since P1.4 (`THREAD_QUERY`'s version 6 with the thread's processor; version 5 still served) 1.5 since H1.2a (a device table of up to 64 descriptors in as many pages as they take, and the root task's reset status `WIT_ROOT_EXIT_RESET`; ADR 0029) and 1.6 since H1.2b (`INTERRUPT_BIND_MESSAGE` and `WIT_ABI_FEATURE_MESSAGE_INTERRUPTS`; ADR 0029): the version is `(major << 16) | minor` (`WIT_ABI_VERSION_MAJOR`, `WIT_ABI_VERSION_MINOR`), a change is additive (a call, an operation, an appended field under a new structure version, a feature bit) and raises the minor, removing or changing the meaning of anything needs a new major and an ADR, and the libc's `crt1` refuses another major. `@Docs/Implementation/ABI-Reference.md` stays equal to the headers, which a host test checks; a change to RFC 0011 §7 that is not in the headers is a plan step, not a fact.
- Handles are capabilities: no ambient authority, generation-bearing tokens, attenuation only downward on `HANDLE_DUPLICATE`, transfer over channels by move with the `TRANSFER` right, and closing never terminates an object's activity except a channel endpoint's. One wait (`OBJECT_WAIT`) serves every waitable object with absolute monotonic deadlines; an activation interrupts a wait or sleep with `INTERRUPTED` and is delivered through the fault callback with the interrupted context (RFC 0011 §7.4–§7.5).
- Only the register block of a thread context and the calling convention differ between ISAs; everything else in ABI-1 is identical, and layer 2 is recompiled, not rewritten. A new platform adds `Kernel.Arch.<isa>` and `Kernel.Platform.<board>` and nothing in `src/Kernel`. Devices stay unknown to the kernel: the platform enumerates regions and lines, the kernel publishes descriptors and mints capabilities on request (RFC 0011 §7.7); no board describes a PCI bridge (H1.2a).
- The system layer's substrate is taken from pinned open code, never written: musl, LLVM libunwind, libc++abi and libc++, `ld.so`, patched only through `UpstreamPatches`. WitOS adds no symbols to the libc namespace; everything WitOS-specific is `libwitos` and `OutWit.OS.*`. ABI-2 is 1.0 since N3.3 and 1.1 since V2.3 (RFC 0011 §10.2; 1.1 added riscv64's names, which are arm64's and `__riscv_flush_icache`, `riscv_flush_icache` and `__longjmp`, without changing x64's or arm64's): `build/abi2.json` records the libraries a runtime links (`libc.so`, `libc++.so.1`, `libc++abi.so.1`, `libunwind.so.1`) and the names `libc.so` exports on each ISA, less the system layer's private `__wit_` names its libwitos reaches; every sysroot build (`SystemLayerAbi`, the exports read by `ElfExports`) requires `libc.so` to export exactly those names, so a removal or a change of meaning needs a new major and an ADR, and an addition is recorded with a new minor; libwitos stays static and outside ABI-2 1.0 until it ships shared to a consumer outside the system layer. The substrate is never an application API: applications see .NET and WitOS capability APIs (RFC 0011 §9).
- Layer 2 is built by the pinned clang and lld (`Toolchain.LLVM_VERSION`, extracted by `setup` from the hash-verified LLVM installer, never a system compiler) for the triples `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` and, since V2.1, `riscv64-unknown-linux-musl` (T1; riscv64 with `-mcmodel=medany -mno-relax`, since the image window lies above 2 GiB and nothing may address through `gp`, which a thread the kernel starts or a callback it enters never sets, and without `-fno-plt`, which clang refuses for RISC-V — `KernelArchitecture.PltOptions`): ELF, the SysV convention, the Itanium C++ ABI. A layer-2 source is one for both ISAs and, until the libc of S1 exists, compiles freestanding (`-ffreestanding -nostdlib -nostdlibinc -fPIE -Wall -Wextra -Werror`; x18 is an ordinary register on ARM64 since R3.3 (the kernel stopped resetting it to its compiler TLS at K8.4b, and neither layer 2 nor the runtime's toolchain patch passes `-ffixed-x18`)). The sysroot `src/Sysroot/include` holds what layer 2 adds to the kernel's ABI-1 headers, starting with the transport `witos/syscall.h`; the ABI-1 headers stay the kernel's and compile under MSVC and clang alike, so an MSVC-only construct needs a `_MSC_VER` branch. The root task is `tests/User/root.c` with `root_mechanisms.c` (their shared declarations hidden, so that calls between them need no GOT), linked by `tests/User/root.ld` at the image window as a static `ET_EXEC` with page-aligned RX, RO and RW segments and converted by `FlatImage.FromElfAsync`, which refuses an interpreter, a dynamic section, TLS, a writable executable segment and an unaligned or a fifth segment; the kernel still knows no ELF. Its first log line names the compiler and the ISA; then it checks the mechanisms no other part of layer 2 uses yet (K8.2: waits on several objects, a suspended thread's context read and replaced, an activation of a thread that has not run, the memory-pressure event, `MEMORY_RESET`) on threads of the one form, and `boot-128` of both suites requires both lines. The kernel, its loader and every fixture are clang's since T3 and K8.4a (see the kernel rules).
- The libc is musl at the pinned release (`MuslLibc.VERSION`, the tarball by SHA-256, extracted by `setup`), built by WitOS.Dev after musl's own Makefile rules and options for the three triples (plus `-ffp-contract=off`, the meaning GCC gives `-std=c99` and clang does not, S7.2; upstream files change only through `patches/musl` (WitOS's hooks, musl's own later fixes backported unchanged with their commits, S7.2, and the C linkage guards `sys/membarrier.h` lacks, R1.3, which the libc build writes beside its generated headers and the sysroot installs), and the assembly that issues Linux system calls is left out in favour of musl's generic C; the library's mapping table holds 8192 mappings, the kernel's reservations of a system layer process (R7.3, N2.2); a file never crosses a process. Descriptors (R2.3a): `dup`, `dup2`, `dup3` and `F_DUPFD` share the open file description (one position and `O_NONBLOCK`, `FD_CLOEXEC` per descriptor); a duplicate of a standard stream writes to the log; descriptors 0–2 are slots of the same table, a standard stream until closed, then free for the lowest descriptor an `open` or a `dup` takes, and `dup2` may put a file, a pipe or another stream there within the process. Pipes (`pipe.c`) are within the process until a `posix_spawn` file action gives an end to a child: a ring buffer of anonymous memory per pipe with its own lock, a reader or writer parking on a futex word outside the table lock (`__wit_syscall` takes it only to find the pipe and hold a reference), the end of the file once no writer is left, `EPIPE` after `SIGPIPE` once no reader is, atomic writes of `PIPE_BUF`, `O_NONBLOCK`'s `EAGAIN` and `FIONREAD`; a pipe between processes (N4.2, `@Docs/Implementation/N4.2-Processes.md`) is the same ring in a memory object of five pages (a header with the readers' head and the writers' tail, free-running counts read with acquire and written with release, then the 16 KiB) and one channel whose two endpoints are the ends' wakeups: a holder of an end maps the object, sends an empty message on its end's endpoint after each change (a full queue carries the wakeup already) and, with nothing to do, drains its endpoint, looks at the ring and waits on the endpoint (`OBJECT_WAIT`), so that no wakeup is lost; the last local descriptor of an end closes that end's endpoint, and the kernel's `PEER_CLOSED` is the end of the file for a reader and `EPIPE` for a writer once every process let that end go; a child receives an end as a `WitStreamMessage` (`witos/start.h`: the object with `MAP|WRITE|DUPLICATE|TRANSFER`, the endpoint with the endpoint rights) on the channel its grant is, and `start.c` installs it at its standard descriptor before `main`; one process reads an end, and one writes it, at a time; `poll` looks again every 10 ms while a shared pipe lives, since another process's change bumps no word of this one; `epoll` (N4.2, `epoll.c`) serves pipe ends and, since W2.1b, sockets: what System.IO.Pipes' asynchronous reads and System.Net.Sockets' asynchronous operations need under CoreCLR (its socket engine registers each pipe or socket edge-triggered with an epoll port): an instance is a descriptor (`KindEpoll`) over an interest list of 32 entries, 8 instances, a wait computes readiness as `poll` does with an edge token (`__wit_pipe_edge`: the local ring's sequence, a shared ring's counts and open ends; `flock` (R4.1) locks the open file description as Linux does (descriptions of one file conflict, duplicates share, the last descriptor ends it; without `LOCK_NB` a conflict parks outside the table lock on a word every unlock bumps), `lstat` is `fstatat` (no symbolic links), `mkdir` is `EEXIST` for a name and `EROFS` otherwise; `select` is `ENOSYS`. Threads (S2) are the kernel's: musl's `__clone` is a suspended `THREAD_CREATE` of the one form entered through `__wit_thread_entry` (the thread pointer is the request's TLS base on x64 and written to TPIDR_EL0 by the trampoline on ARM64), a thread's `SYS_exit` and `__unmapself` are `THREAD_EXIT` with the exit request naming the clear word and its futex event, and `__unmapself` first takes the stack out of the mapping table, since the kernel releases that reservation itself (R2.2), and futex waits park in sixty-four slots (K5.3, R6, P2), as many as the kernel's threads of a process, with their own auto-reset kernel events under one lock, so that a wake reaches that word's waiters alone and none is lost (the exit word's waiters share the one event the exit request sets); thread ids are the library's, the kernel handle is closed after the resume, and musl's `clone.c`, `__unmapself.c` and the x64 `__set_thread_area.c` leave the build. Signals (S3) are the kernel's faults and activations made POSIX by `signal.c`: the one fault callback (`__wit_signal_entry`, entered with the token, the vector and the address in the argument registers, the SysV ones on x64 since K8.4d, `a0`–`a2` on riscv64, whose causes classify as Linux's handler classifies them — misaligned addresses `SIGBUS`, access faults `SIGSEGV`/`SEGV_ACCERR`, page faults `SIGSEGV`/`SEGV_MAPERR` with `stval`, an illegal instruction `SIGILL`, a breakpoint `SIGTRAP` — into musl's riscv64 `ucontext_t`, `__gregs[0]` the program counter and `__fpregs.__d` the D registers with `fcsr`, V2.1) classifies a fault by its vector or exception class into the synchronous signal and `si_code` Linux gives it and an activation by the marker callback into the signal it carries; dispositions, each thread's mask, pending set and `sigaltstack` are the library's, kept with the thread records (an alternate stack whose bottom pages the kernel refuses, a guard page CoreCLR's PAL makes `PROT_NONE`, gives the kernel the writable part above them while enough is left, R3.2a; the range's base rounds down to 16 bytes, since the kernel and the library write at its top alone, so that a stack of exactly `SIGSTKSZ` bytes, the kernel's minimum on x86_64 and riscv64, keeps its size whatever its alignment, V2.3); a handler runs after `EXCEPTION_CONTINUE` into the trampoline with a frame (the saved context, a `ucontext_t` in musl's layout, a `siginfo_t`) on the thread's stack or the alternate stack, and returns through `__wit_sigreturn`, which resumes the saved context through a delivery of its own (K8.1: `THREAD_CONTEXT_RESTORE` leaves ABI-1): with the thread's signals held it leaves the frame in the thread's record and raises an activation of its own thread with the marker `__wit_sigreturn_activation`, from the interrupted stack below its red zone when the handler ran on the alternate stack, since the callback needs `WIT_EXCEPTION_STACK_MINIMUM` of room; the callback recognizes the marker before any mask or hold, ends the hold, re-arms what arrived meanwhile and continues the frame's transfer with `EXCEPTION_CONTINUE`; layer 2 uses no call that K8 removes; - The services of phase D (ADR 0025) are NativeAOT programs of the boot package that `runtime-witos` publishes with the SDK's targets after the M3 acceptance (`RuntimeDevices`, D1.1), compiling the source folders of `src/OutWit.OS` (`Native`, `Resources`, `Communication`, `Hardware`, `Execution`, `Storage`) into each and linking the sysroot's `libwitos.a` through `DirectPInvoke`; `runtime-services` repeats that step alone on the tree an earlier `runtime-witos` built. `OutWit.OS` is the services' managed API over libwitos's capability API (`witos/capabilities.h`: a function returns 0 or an errno value, and no call number or status appears above layer 2), built and tested on the host (`tests/OutWit.OS.Tests`, in CI), never published or an application API until phase N, and it grows only by what a service uses. A process may start with one capability its creator grants: start message version 4 names its optional capabilities in `Capabilities` (the process manager's endpoint, then the grant, since a message's handles leave no gaps; the initial directory has 224 bytes), spawn request version 3 carries the grant in a third handle slot, and `witos_spawn_options.grant` is moved on success and closed on failure. A service's grant is the end of a channel to its creator, over which its capabilities arrive, and the process manager starts services before its first process (`witos_manager_run_services`), serving requests until each answers a `WitServiceStatus` or ends. The device manager `/system/DeviceManager` (`src/Services/DeviceManager`) receives the root task's own handle of the device table (`witos/device_manager.h`: `HANDLE_DUPLICATE` keeps `ACQUIRE` out of a memory object's rights, so the root task moves rather than attenuates and keeps no device authority), validates the table, translates each PCI descriptor into a UHI record (a virtio device by its type's contract, `BlockStorageController`, `EntropySource`; every other function by its PCI class), prints a discovery line for each and answers before `/bin/init` starts; the `runtime-devices` scenario requires the block and entropy devices' lines, the summary and the root task's report of a ready device manager on both ISAs. The device manager starts the driver its table names for a device (D1.2: Virtio's `BlockStorageController` is `/system/Drivers/VirtioBlock`, `src/Services/Drivers`) through `witos_manager_spawn`, the process manager's client that grants the new process a capability (`witos/spawn.h`): it acquires the device, sends the driver's start (`witos/driver.h`: the descriptor in the bytes, the device handle, its last reference, in the one slot) and then starts the driver with the other end as its grant; the kernel delivers a device handle to another process only when the message holds its origin's last reference (no handle, binding or pin of the origin's left; the holder changes at delivery, ABI-1 1.2, `User.DeviceMove`), otherwise it stays queued with `UNSUPPORTED`, and interrupt bindings and pins stay process-bound; the driver maps the device's configuration region through `DEVICE_MEMORY`, requires the identity its descriptor names and answers a `WitServiceStatus`, and the `runtime-devices` scenario requires its line and the device manager's report of it on both ISAs. The driver then drives the disk (D2): libwitos and `OutWit.OS` give memory objects, events and the one wait (`witos_object_wait`, an absolute deadline an activation does not end), interrupt bindings, DMA pins with their physical ranges, `witos_device_barrier` (MFENCE, DSB SY) and `MmioRegion` (a writable mapping of a device region, one volatile access of each width at a time, bounds and alignment checked, never inlined, since the x64 JIT narrows an inlined volatile load tested against a byte's mask to a one-byte read, which QEMU's xHCI answers with zero, H2.1); `src/Services/Drivers/VirtioBlock/Virtio` sets up the modern virtio PCI transport through the regions it received, queue 0 on five pages it pins, its INTx line bound to an auto-reset event, and reads sector 0, which the scenario requires as the boot disk's FAT16 boot sector on both ISAs. The block layer (D3.1) is `OutWit.OS.Storage`: `IBlockStorage` addresses bytes by offset aligned to `Info.RequiredAlignment`, serves several requests at once, makes a flush a durability barrier (storage document §45, §48), takes `WriteOptions.Durable` as FUA and discard as optional, and carries no filesystem's rule in `BlockStorageInfo` (§10); `BlockStorageBase` checks every request before a provider serves it; `MemoryBlockStorage`, `PartitionBlockStorage` (a partition's holder has authority over its range alone), `CachedBlockStorage` (least recently used blocks, writing through or back, a flush writing dirty blocks in ascending order then flushing below) and `GptPartitionTable` (headers and entries checked by CRC-32, the backup when the primary fails, no overlaps) are tested on the host by one conformance suite over every provider (§113); nothing of OutWit.Common is copied in, and D4 reaches `OutWit.Common.Fat` through an adapter (§14–15). The block protocol (D3.2, `witos/block.h`) is what a block driver serves on the block channel whose other end moves with its ready answer: `ATTACH` moves a duplicate of the client's memory object (`MAP`, `WRITE`, `TRANSFER`), which the driver pins and closes, so that the device reads and writes the window in place; `INFO`, `READ`, `WRITE` (`DURABLE`: this write and every completed one durable when it completes) and `FLUSH` are served one at a time, each checked whole by `BlockMessages.Check` before anything reaches the device, errors are errno values (`EINVAL`, `EROFS`, `EOPNOTSUPP`, `EPROTO`, `EIO`), and the transfer limit is the device's segments less one in pages within the 64-page window. The virtio driver negotiates `VIRTIO_F_VERSION_1` with what the device offers of `SIZE_MAX`, `SEG_MAX`, `RO`, `BLK_SIZE` and `FLUSH`, reads its configuration until the generation holds still, sets up a queue of up to 128 entries on one pin, gives a request the window's physical runs (`DmaPin.RunAt`) cut at `SIZE_MAX`, makes a durable write `OUT` then `FLUSH`, and waits on both its channels with one `OBJECT_WAIT`. `ChannelBlockStorage` is the contract over a session (`IBlockSession`, `ChannelBlockSession`), in transfers of the driver's limit within the window, and `GptPartitionTable.WriteAsync` writes a table and reads it back. The `runtime-devices` scenario boots with a second, writable disk the tool writes anew with that writer (`BootRequest.DataDisk`: 8 MiB, the "WitOS test" partition), the device manager's probe reads both disks' tables through their drivers, sees the read-only boot disk refuse a write with `EROFS` and writes 320 KiB durably to the test partition and reads it back, and the tool requires those bytes in the image after the boot, on both ISAs. The filesystem contract (D4.1) is `OutWit.OS.FileSystems`: `IFileSystem` (paths absolute within the volume with '/', lookup, listing without "." and "..", open by `FileMode` and `FileAccess` but `Append`, directories with their parents, delete of a file or an empty directory, rename to a free destination, flush, a check that changes nothing) and `IFileHandle` (bytes by offset with no shared position, a write past the end leaving zeros), each failure a `FileSystemException` whose `FileSystemError` is the same for every provider, for D5 to map to errno. `FatFileSystem` is FAT through `OutWit.Common.Fat` from nuget.org, pinned in `OutWit.OS.csproj` and the test projects' lock files and never copied (its `OutWit.Common` dependency comes with it; WitOS code uses neither outside `FileSystems/Fat`): the library's device over an `IBlockStorage` whose block is a power of two of 512–4096 bytes, mount (read-only on a read-only resource), format, detection, the library's failures translated, one operation at a time behind one lock, and UTC times on the host and in the guest; a service compiles `FileSystems` and `FileSystems/Fat` only when it needs them, with OutWit.OS's package references read from its project (`RuntimeDevices.PackageReferences`). `RuntimeDataDisk` writes the data disk anew (16 MiB: "WitOS test" and "WitOS FAT", formatted on the host by the same provider with `/hello.txt`); the device manager's `FileSystemProbe` mounts the boot disk's FAT16 read-only (its root, the loader's `MZ`, a clean check) and the FAT partition (the host's file read, `/guest` with a file of several clusters and a note written, flushed, checked, mounted again and read back), and the tool requires the guest's files and a clean check of that volume in the image after the boot, on both ISAs. The ext4 provider (D4.2, `OutWit.OS.FileSystems.Ext4`) reads the on-disk format, never Linux's VFS (§19): ext4, ext3 and ext2, mounted read-only until D4.3 writes through the journal; the superblock is checked whole first (magic, CRC-32C with `metadata_csum`, geometry, and the incompatible features it serves: `filetype`, `extents`, `64bit`, `flex_bg`, `ea_inode`, `csum_seed`, `largedir`; anything else, a journal that needs recovery among them, is `Unsupported` with its reason), then the group descriptors (CRC-32C or CRC-16), and each inode, extent block (depth at most 5, each child one less than its parent) and directory leaf by its checksum when it is read; the checksums are the kernel's raw CRC-32C update and CRC-16/ARC; directories are read linearly (an htree's root and index nodes hold no entries a linear reader sees); a lookup never follows a link (`ReadLinkAsync`, `FileSystemError.NotALink`), and an entry's `Kind` and `FileSystemUnixMetadata` (mode, owner, links, number) are recorded data, not authority. Its references are volumes the host's e2fsprogs makes (`mkfs -d` then `e2fsck -fD`, six variants in `tests/OutWit.OS.Tests`, which also check that the htree, the extent index and the index nodes they claim are there; hosts without e2fsprogs skip them, CI's `linux-host` runs them), and the `runtime-devices` data disk (32 MiB) carries a third partition, "WitOS ext4", that `RuntimeExt4Volume` makes the same way, which the device manager's `Ext4Probe` reads through the block channel. The provider writes (D4.3) on a writable resource whose volume has `extents` and only the read-only compatible features it writes (`sparse_super`, `large_file`, `huge_file`, `gdt_csum`, `dir_nlink`, `extra_isize`, `metadata_csum`; anything else, ext2 and ext3 among them, mounts read-only): the mount replays a journal that needs recovery (`Ext4Journal`, as the kernel does: the committed transactions from `s_start`, revoke records, descriptor, commit and data checksums v2 and v3, escapes, 64-bit tags, the wrapping log) and sets `needs_recovery` until a clean unmount; every change is one transaction (`Ext4Writer`): its metadata blocks copied into `Ext4Transaction`, which the volume's reads see, its data written to their blocks first, then the commit — the log with `CSUM_V3`, the journal's superblock pointing at it, the blocks in place, the journal empty, a flush after each — so the log never holds more than one transaction and no revoke is written; a failed change restores the descriptors and the superblock the mount holds. `Ext4Allocator` takes and frees blocks and inodes by the checked bitmaps with every count (no allocation in `BLOCK_UNINIT` groups, an empty bitmap for `INODE_UNINIT`), `Ext4ExtentWriter` writes a tree anew (four extents in `i_block`, four leaves below one index beyond), and `Ext4DirectoryWriter` inserts where an entry has room or in a new block, removes by joining, and makes an htree linear before inserting into it. Its judge is e2fsprogs: `e2fsck -fn` clean and `debugfs dump` byte for byte after changes on four ext4 variants, every cut of a change recovered clean with the file whole or absent, `e2fsck -fy` replaying the provider's journal and the provider replaying a debugfs journal with a revoke; the `runtime-devices` probe writes the ext4 partition through the journal and reads it back after a second mount, and after the boot the host's `e2fsck -fn` must find it clean and `debugfs` must read the guest's files, on both ISAs. ## Kernel and UHI rules

These describe the kernel as it is and are carried into phase K. Where RFC 0011 §8 changes a mechanism (join becomes a wait, `THREAD_COMPLETE` merges into `THREAD_EXIT`, APCs become activations, the delivered-tick clock goes), the rule holds until the K step that changes it, and that step rewrites the rule.

- The kernel and its EFI loader (T3: x64 in T3.1, ARM64 in T3.2) are C17 compiled by the pinned clang for the architecture's `KernelArchitecture.KernelTriple`, `x86_64-unknown-windows` or `aarch64-unknown-windows` (PE/COFF, the Microsoft conventions; x18 stays the platform register clang never allocates on ARM64): freestanding with `-nostdinc`, `-fno-stack-protector`, `-O0` as MSVC's `/Od` was, `-Wall -Wextra -Werror`, CodeView records, linked by the pinned `lld-link` with `link.exe`'s options; MSVC builds no part of the kernel. Its assembly is GNU syntax (`.S`; `.intel_syntax noprefix` on x64) through clang's integrated assembler. The x64 privileged, port and identification instructions are the inline functions of `witos/x64_instructions.h`, each that changes processor state or reaches a device a compiler barrier; never declare an MSVC intrinsic; ARM64's system registers are read and written in its assembly. Each architecture's `compiler.S` holds `memcpy`, `memset` and `__chkstk`. No part of a kernel image, release or self-test, needs MSVC since K8.4a. `release --arch arm64` checks the ARM64 release kernel with the release suite, as CI does.
- The RISC-V kernel (phase V; V1.1 `@Docs/Implementation/V1.1-RISC-V-Loader.md`, V1.2 `@Docs/Implementation/V1.2-RISC-V-Kernel.md`, V1.3 `@Docs/Implementation/V1.3-RISC-V-User-Mode.md`, V1.4 `@Docs/Implementation/V1.4-RISC-V-Harts.md`) is the exception the pinned LLVM forces: `lld-link` knows no RISC-V machine and UEFI loads PE32+ alone, so the same loader and common kernel are compiled for `riscv64-unknown-elf` (`-march=rv64gc -mabi=lp64d -mcmodel=medany -mno-relax -fPIE`, no unwind tables, DWARF in place of CodeView) and linked by `ld.lld` as one position-independent ELF with `src/Kernel.Arch.RV64/kernel.ld` (`-pie --no-dynamic-linker -z separate-loadable-segments`, the first page left to the headers, `__ImageBase` section-relative, relative relocations alone), which `ElfToPe` converts into the PE32+ EDK II loads (machine 0x5064, the segments as sections with their rights, `R_RISCV_RELATIVE` as `DIR64` base relocations with the addends in place; a writable and executable segment, a relocation with a symbol or an entry outside code is refused). Traps enter `wit_rv64_trap_vector` (`stvec` direct, `entry.S`) and save a full frame (x1–x31, sepc, sstatus, scause, stval, f0–f31, fcsr; 560 bytes) on the interrupted stack: in S-mode `tp` points to the hart's record (`processor.c`, P1.1) and `sscratch` is zero, while U-mode runs `sscratch` holds that record, whose first word is the running thread's kernel stack top and whose second keeps the thread's sp across the switch, so one entry serves both modes: a trap swaps `tp` with `sscratch`, a zero names S-mode and takes the kernel's `tp` back, and the frame keeps the interrupted `tp` in X[4]; an exception taken in S-mode prints `[EXCEPTION] cause= sepc= stval= sstatus= sp= stack=` and panics by the cause's name (`exceptions.c`); a trap from U-mode (`frame.c`, V1.3) is a system call when its cause is `ECALL` (a7 the number, a0–a2 the arguments, the status in a0 and the value in a1, `sepc` moved past the instruction before anything else) and otherwise a fault whose vector and error are `scause` and whose address is `stval` for the memory faults (the `[USER-FAULT]` line carries `sepc`, `sstatus`, `scause` and `stval`, and the judge requires SPP clear); `wit_rv64_run_user` saves the host's callee-saved state, switches `satp` and resumes the frame, `wit_rv64_leave_user` returns from it, every U-mode resume clears the load reservation with a store-conditional to a kernel word, and a frame is resumed only at the top of the selected kernel stack; `tp` (x4) is the thread's, as TPIDR_EL0 is on ARM64: the kernel writes it once, from the request's TLS base, when a frame that has never run is first resumed (`WIT_RV64_FRAME_FRESH`), `THREAD_SET_TLS` is `UNSUPPORTED`, and a context carries it like every other register; a context is the RISC-V block (X1–X31, PC, F0–F31, FCSR; profile `FPREGS`, `CONTEXT_PROFILE` reports `WIT_CPU_CONTEXT_FPREGS` with the FCSR bits), validated by FCSR within its eight bits and a rounding mode of at most 4; the idle path is `wfi` then `csrsi sstatus, 2` at `wit_rv64_idle_resume`, since WFI honours the individual enables while SIE is clear. The scheduler tick is the supervisor timer interrupt, armed through `stimecmp` where the boot hart's ISA string or extension list names `sstc` (QEMU's `rv64` does) and through SBI `set_timer` otherwise (`witos/rv64_sbi.h`, `sbi.c`: one `ecall` with the extension in a7), at 100 Hz of the `timebase-frequency` the device tree names (`fdt.c`, 10 MHz on virt); the external interrupt is the PLIC, whose sources 1–95 are the device lines (`interrupts.c`: the enable bit of the boot hart's supervisor context `2 × hart + 1` and then priority 1, since QEMU's PLIC raises a source that asserted while masked on a write of a priority, never of an enable word (V2.4), claimed and completed through its claim register before the trap masks it, since the PLIC ignores the completion of a source not enabled, three pages mapped on demand); UTC is the goldfish RTC's nanoseconds; the processors are the harts of `/cpus`, the boot hart the one SBI HSM reports started, since S-mode reads neither `mhartid` nor `misa` and the features word stays zero; the device table is the PCI functions behind the device tree's generic ECAM bridge (`pci.c`, V1.3: the bridge found at any depth, since this board's lies under `/soc`; the INTx line of a function is the PLIC source its interrupt map names under the mask, one interrupt cell and no address cell, lines 32–35 on virt) and then the firmware's framebuffer. - The alternate stack (S3.1): `THREAD_STACK_ALTERNATE` records for the calling thread one 16-byte aligned range of at least `WIT_EXCEPTION_STACK_MINIMUM` bytes inside one committed writable reservation of the caller and apart from its stack, validated whole before the record changes, cleared by a zero request and `BUSY` while the caller's stack pointer is inside it; `validate_return`, the context validation and the fault delivery accept the thread's stack pointer in either range (`wit_user_thread_stack_range`), and a delivery whose interrupted stack has no room for the callback frame enters the callback at the top of the alternate stack when the thread is not on it already. On x64 the callback frame leaves the 128-byte SysV red zone below the interrupted stack pointer (`RED_ZONE_BYTES`), since layer-2 leaf functions keep data there. The kernel knows no signal, no `SA_ONSTACK` and no handler: the libc switches stacks itself for ordinary signals and needs the kernel only where the interrupted stack is exhausted.
- Processes: the registry has thirty-two slots in both kernels since P1.5 (`WIT_PROCESS_CAPACITY`; twelve and eight before, when every slot held the static kernel stacks of its 32 threads in the image and sixteen slots made the x64 release image 52.5 MiB, which the firmware refused to load with 128 MiB): a user thread's kernel stack lies in the stack window of the kernel half (`@Docs/Implementation/P1.5-Allocated-Kernel-Stacks.md`, `witos/kernel_stacks.h`: top-level entry 320 above the package and the root task image, whose subtree every user root shares, 64 KiB a stack with a guard page below and above that is never mapped), whose tables each architecture makes at boot before any user root and whose pages a stack takes from the allocator when a thread of its slot and index is created (`wit_kernel_stack_ensure`, refused with `NO_MEMORY`), keeps for the slot's next thread, and gives back once released (its thread reaped, its slot torn down) and no processor runs on it (`wit_kernel_stacks_collect` at a kernel entry, in the idle loop, after a run and after a destroy; each processor names the stack it runs on, `wit_kernel_stack_running`, and every processor drops the pages' translations before they go back); a slot costs the image its record alone, some 360 KiB in the pool, and `PROCESS_CREATE` takes records from the pool of as many; a new process is an empty address space with one capability, the endpoint the request names (moved with its rights), the full profile's quotas bounded by the page quota asked and the creator's tick budget, the system layer's reservation table (S5.4) and its threads, handles and events (K5.3), no thread, and it is scheduled from creation. `THREAD_CREATE` version 3 names the process (`MANAGE`): the stack lies in the target's reservations, the entry is executable there, the handle stays with the caller and serves `OBJECT_WAIT` and `THREAD_QUERY` alone across processes. The dispatcher round-robins the live components and their threads, switching the address space, kernel stack and TLS (`wit_arch_space_switch`): a tick or a yield begins with the next component and reaches the current one last, so that a thread that keeps running, or spins on a lock whose holder waits for another component, never keeps the processor from the others (D5.2), while a wait, an exit or a device line begins with the current one; deadlines and pressure expire for every component on one clock read; a device line reaches its binding's owner. A created process that ends is settled, torn down at once with its space left for the kernel root, taken off the registry and its waiters woken; if it was running, the dispatcher resumes another frame directly (`wit_arch_resume_frame`) and its kernel stack is abandoned; its record lives for `PROCESS_QUERY` until the last handle; a threadless process whose last handle goes ends. The root's end ends every created process; nothing of the pool survives a run. Never run a created process's teardown while its space is active, never charge a tick to a component that is not running, and never let events, bindings or pins cross a process boundary until their records leave the process, and a device only as its origin's last reference (D1.2).
- Clocks: UTC is the board's real-time clock read once at boot (`wit_platform_realtime_seconds`: the CMOS RTC on q35, the PL031 at the virt profile's fixed base) plus the monotonic time since, converted in whole seconds and remainder so that no product overflows; its frequency is 10^9 and a board without a real-time clock reports `UNSUPPORTED`, never an invented time. `CLOCK_SET` needs the clock capability (kind `CLOCK`, the handle itself, no record), sets UTC alone, refuses a value before the boot or beyond 2^63, and the root task alone receives it, as its fourth initial handle. The monotonic domain is `CLOCK_READ`'s and `CLOCK_FREQUENCY`'s; `MONOTONIC_QUERY` was retired at K8.4a.
- Processors: the platform enumerates them once at boot (`wit_platform_processors`: the MADT reached from the loader's RSDP on q35 with every table's signature, length and checksum verified and nothing else of ACPI read; the `/cpus` nodes of the device tree on virt) and the common kernel keeps a table of eight with the boot processor first, panicking on a table without it or with a repeated identity; every present processor is started at boot (K7.2) and `wit_processors_online()` counts the started ones, `wit_processors_current()` is the caller's number from its own register (P1.1: the selector of its own task state on x64, TPIDR_EL1 on ARM64, the record `tp` points to on RISC-V, each written once at the processor's start and required to name its hardware identity), the dispatcher keeps its component, thread and idle state per processor, and `wit_processors_scheduling()` is the online count since P1.3b (`@Docs/Implementation/P1.3b-Threads-on-Every-Processor.md`): threads run on every online processor, `MEMORY_QUERY` and `THREAD_QUERY` report it and the libc's `sched_getaffinity` with them; `CODE_PUBLISH` publishes on every processor, a suspension or an activation kicks a target another processor runs, and `THREAD_CONTEXT_GET`/`SET` of a suspended target still leaving another processor run again once the caller is dispatched anew (`WIT_USER_CALL_RESTART`, `wit_arch_frame_restart_call`), while `GET` of an unsuspended one is `BUSY` (RFC 0011 section 7.3). `PROCESSOR_QUERY` has the record form alone, with the caller's version and size (the 4-byte form left at K8.4d); features and cache sizes are reported for online processors, each by itself at its start. `THREAD_AFFINITY` reads (`QUERY`) and sets (`AFFINITY`) a mask the dispatcher honours since P1.4 (`@Docs/Implementation/P1.4-Affinity-and-Balance.md`): nonzero, within the table, with an online processor; every processor of the table by default; `pick` skips a thread whose mask leaves the processor out, a running thread the new mask leaves out is kicked off its processor (the caller at its call's end), and a processor that leaves the kernel or goes idle kicks one idle processor a ready thread may run on; the libc's `sched_getaffinity` and `sched_setaffinity` are `THREAD_AFFINITY` of the thread a tid names, the processors beyond the online ones ignored and an empty rest `EINVAL`. A scenario asks for processors through `BootRequest.Processors`; `boot-smp2` and `boot-smp4` (P1.4) must keep passing on the three boards with `Processors present/online: 2/2` and `4/4`; the riscv64 board's device tree walk keeps an interrupt controller a hart and the PLIC (`CONTROLLER_CAPACITY`). The runtime on several processors (P2, `@Docs/Implementation/P2-Runtime-on-Several-Processors.md`): the x64 trampoline page is claimed before the first page table, since the allocator hands out the lowest pages first and a larger memory's tables took every usable page below 1 MiB; the dispatcher's walks over a process's threads end at its `ThreadTop`, one past its highest thread that is not empty, and its memory-pressure events are counted, so that a capacity costs nothing a process does not use; `THREAD_YIELD` writes its value into the caller's frame before its dispatch, which sets it to zero when it picks the caller again, since that dispatch delivers a pending activation into the same frame and the value register is the callback's vector register on ARM64 and riscv64 (its address register on x64) — never write a call's result after a dispatch that may have resumed the caller; the `runtime-processors` scenario (`RuntimeProcessors`, after `runtime-libraries` in `runtime-witos`) publishes `tests/Runtime.Witos/Processors`, an ordinary console project, with the stock SDK and no RID once as it is and once with `ServerGarbageCollection`, runs both through `dotnet` beside the device services on four processors and requires `[P2] 4 processors, workstation GC: 11 of 11 checks passed` and its server GC line on the three ISAs (the processor count, `Thread.GetCurrentProcessorId` naming every processor, a heap per processor under the server collector, the thread pool's minimum, exact results of interlocked, locked, parallel, allocating and queued work on every processor at once); the scenarios of applications under load, N1's and N2's (`runtime-compatibility`, `runtime-libraries`, `runtime-nuget-suites`, `runtime-published`), boot on four processors (`RuntimeProcessors.PROCESSORS`).
- Secondary processors (K7.2): `cpus.c` starts every processor of the table at boot through the architecture (`wit_arch_secondary_prepare`, `wit_arch_secondary_start`: INIT and two start-up interrupts through the local APIC in xAPIC mode with a trampoline in a page claimed below 1 MiB on q35, PSCI `CPU_ON` through `hvc` on virt) and waits for each to report itself ready within a bounded monotonic time, panicking otherwise; a started processor idles with interrupts enabled. The kernel lock and the requests (P1.2, `@Docs/Implementation/P1.2-Kernel-Lock-and-Requests.md`): every entry into the kernel's state takes the one kernel lock (`wit_cpus_lock`: a call, a tick, a device line or a fault through `user.c`'s `enter()`, the root task's start) and the processor gives it up only when it leaves for a frame or halts (`leave()`, before `wit_arch_resume_frame`, `wit_arch_run_user`, `wit_arch_leave_user` and the idle halt); its holder takes it again for nothing, and a processor serves its requests while it spins for it. Any processor sends any other a request, and only while it holds the lock: the kinds FENCE, INVALIDATE (with its address), RESCHEDULE, STOP and RUN (a function, for the self-tests) are bits of the target's pending set, and the one inter-processor interrupt, the doorbell (`WIT_IPI_DOORBELL`: vector 0xF0 by the interrupt command register on x64, SGI 0 through ICC_SGI1R_EL1 on virt, the supervisor software interrupt on riscv64), tells the target to serve its set — from the doorbell, which the boot processor takes too once others are online (`wit_platform_ipi_enable_boot`), or while it spins for the lock or waits for an acknowledgement of its own, so that a holder waiting for a processor that spins for the lock is answered; each kind is acknowledged by a counter (`wit_cpus_acks`) its sender waits for within a bounded monotonic time, RUN before its function runs; RESCHEDULE has a processor that runs a thread enter its dispatcher (`wit_user_reschedule` from a doorbell that interrupted user mode) and an idle one look again; STOP is reserved; PUBLISH runs the architecture's code publication (P1.3b). Every spin-wait takes a step of `wit_arch_spin_pause` per round (PAUSE on x64, YIELD on ARM64, a WFI with the hart's own software interrupt pending on riscv64, whose PAUSE QEMU does not yield on), since under `-icount` QEMU runs the processors round-robin and the awaited one runs only when the spinning one ends its slice; the q35 HPET's last value is raised by compare-and-exchange, since every processor reads the clock. `PROCESS_WRITE_BARRIER` fences the caller and every online processor through `wit_cpus_fence_all`. A secondary processor runs threads since P1.3b: once ready it lives in `wit_user_processor_main`'s idle loop on its own stack, joins each run when `wit_user_run` sends it a RESCHEDULE, starts its tick and dispatches, and parks between runs (no component, its tick stopped); the boot processor ends a run (`finish_run`) once every secondary parked, waiting without the lock. It loads its own task register on x64 (P1.1), whose selector names it, and a kernel exception there is a panic. The kernel lock goes in the architecture's return to a frame once the stack pointer is the frame's (`wit_cpus_release` in `wit_x64_restore_context`, `wit_a64_resume_frame`, `wit_rv64_resume_frame`), never before, since the processor otherwise still runs on a kernel stack another may take; a holder that released the lock while others waited takes it again only after one of them took it. A component ends on one processor while others run it in three steps: a RESCHEDULE to every other processor that has it active, acknowledged once the target took the doorbell, so that none runs its user code any more; then its threads and references go (`settle`); its address space goes when the last processor leaves it (`drop_component`, `retire`), and an entry into the kernel for a component that ended under the processor is abandoned (`abandon()`). A shootdown follows every invalidation of a space another processor has active (`wit_user_space_shootdown`: INVALIDATE requests on x64 and riscv64; ARM64's TLBI VAAE1IS is broadcast). The platform maps and enables a processor's interrupt frames (`wit_platform_processor_prepare`, `wit_platform_processor_interrupts_enable`) and sends and completes its inter-processor interrupts (`wit_platform_ipi`, `wit_platform_ipi_complete`); the PC keeps the boot processor's local APIC on whatever the number of processors since H1.2b (message interrupts), and the PIC's line enters through LINT0 as ExtINT. Each processor has a tick of its own (P1.3a, `@Docs/Implementation/P1.3a-Processor-Entry-and-Tick.md`): `wit_platform_timer_start`, `stop` and `acknowledge` act on the calling processor — on q35 the boot processor's PIT and a secondary's local APIC timer on the PIT's vector, measured once against the monotonic clock (`witos/x64_local_timer.h`), on virt each processor's virtual timer through its own redistributor, on riscv64 each hart's `stimecmp` or SBI timer — and each architecture counts ticks per processor, `wit_arch_clock_ticks()` the caller's; the selected kernel stack top (ARM64, riscv64) and the fresh frame's TLS base (riscv64) are per processor too. Keep the request kinds, the rule that only the lock's holder sends, the serving while spinning and the bounded waits explicit; a pending set holds a kind once, never a queue, and never let a request's acknowledgement be assumed.
- `THREAD_ACTIVATE` validates the handle's `ACTIVATE` right, the callback (executable, not writable), the registered fault callback and the per-thread quota before it marks the target. An activation is delivered only at the target's return to user mode, through the one fault callback with the interrupted context and the activation vector; a thread inside a delivery or suspended keeps its activations pending in order, `EXCEPTION_REGISTER` is `BUSY` while one is pending, and a stack with no room for the callback frame ends the component as a fault of the thread. Never run an activation's callback in CPL0 and never add a user-space dequeue.
- Memory-pressure events are kernel-controlled, wait-only manual events sharing existing quotas. Derive pressure from settled physical/quota headroom, count no-access backing and private tables, preserve explicit hysteresis, expire deadlines before notifying, and never publish transient failed-allocation pressure. Purge closed generations before reuse; kernel notification authority must not leak to user Set/Reset. Dispatch a caller made Ready by the final expiration pass.
- Keep native initializer execution in user space. Kernel image descriptors are readonly; ReadyToRun/TypeManager/GC-table initialization belongs to the actual runtime, not the kernel.
- Keep __chkstk in the x64 layer and follow its special compiler ABI: RAX supplies size and is preserved; do not allocate/move the caller stack or clobber argument/nonvolatile/SIMD registers. Probe downward one 4 KiB step at a time plus the final partial span; never skip a guard page via an endpoint-only check or wrapped size. Fixed-stack overflow remains a contained user fault, not automatic growth or managed exception handling.
- Treat the boot handoff and experimental user ABI as evolving contracts, not a frozen public SDK.

## Removed: the kernel policy of RFC 0011 §8

The PE loader with its imports, exports, static TLS and unwind validation, libraries and their lifecycle, the file namespace over the boot package and the package's parser, the kernel-held environment and current directory, thread names, stack leases, software exception scopes and fatal reports left the kernel at plan step K8.4a with calls 207–222, statuses 11 and 17, the thread flag `LIBRARY_NOTIFICATIONS` and handle kinds 6–9, together with `src/Runtime.Native`, the PE fixtures of `tests/User.X64` and `tests/User.A64`, their self-tests and markers and the host harnesses that tested them (`@Docs/Implementation/K8.4a-Policy-Calls-Removal.md`). The system layer owns all of it: the libc reads the package (`files.c`), keeps the current directory, the environment and thread names, and libwitos and musl's `ld.so` load programs and libraries. Never bring a call of that list back, and never let the kernel parse the package again: the host test's `PackageReader.c` is the format's reference reader for `AssemblyPackage`, not kernel code.

## Removed: the Windows-form user space

The runtime line of P6.4 — the NativeAOT adapters written against the Windows PAL, the guest C++ runtime, UCRT subset and pinned STL, the guest host build, `coreclr-guest`, the Win32 and COM binding surface, with their fixtures, self-tests, experiments, commands, overlay patches and workflows — was frozen by ADR 0024 and removed at plan step K8.2, after the Unix-form runtime passed the M3 acceptance (R2). Its plan stays as history in `@Docs/Implementation/P6.4-Plan.md` and its documents in `@Docs/Implementation/`. Never bring a Win32 surface back: .NET runs in its Unix form over the system layer.

## Validation

For native, boot, image or runner changes, run:

```powershell
dotnet build WitOS.slnx --configuration Release
dotnet run --project tools/WitOS.Dev --configuration Release -- test
```

Absolute deadlines may expire between a user clock read and kernel entry. Test deadline completion separately from mandatory idle-path coverage; do not require every successful sleep to park. Keep preemption and resource-accounting assertions independent and diagnostic.

Expected boot markers live in `tests/Expectations/*.json`; add a suite's new marker there, never as a list in `BootValidation`, and keep every expected marker emitted by a guest source. Contained user faults are accounted by the guest: a test accepts each expected fault through `wit_test_faulted`, and the host requires the closing `[TEST-SUMMARY] faults=N checked=N` to match the fault lines; never add a hand-counted fault total.

Guest boots run in QEMU virtual time (`-icount` with `sleep=off`, `BootScenarioRunner.InstructionClock`): QEMU's single-threaded TCG counts every processor's instructions in one clock, so the shift falls with the processors (2 on one, 1 on two, 0 on four or more, P2) and a 10 ms tick is 2.5 million instructions of each processor while all of them run, on every host. Keep tick budgets and timer expectations in guest instructions, never tuned to host speed; wall-clock boot limits only stop a hung QEMU.

A Linux host (T2.1a) builds and runs everything, with parity since T2.2: `setup` verifies the pinned LLVM Linux archive and builds QEMU from its pinned source release; the process runner starts a child through `setsid` as a process group and needs an init that reaps (`docker run --init`); host tests that test a Windows API carry `[Platform(Include = TestPlatforms.WINDOWS, Reason = ...)]`, and a native host harness is plain C17 built by `NativeHarness` (MSVC on Windows, the pinned clang against the system C library on Linux) with its memory calls behind `#if defined(_WIN32)`; local work runs in `build/linux/Dockerfile` on a volume copy of the tree, never in the Windows checkout's `.tools` or `artifacts`, and CI's Linux jobs are its gate: `linux-host` (a leg per ISA since D5.2, with that ISA's release kernel and runtime; the host tests and `format-check` in the x64 leg), `nuget-suites` (N2.2: a job per ISA and group of the NuGet libraries' suites on the install the `linux-host` leg uploaded), `side-by-side` (N3: .NET 8 built and installed beside that .NET 10, a job per ISA) and `linux-selftest` (`test` of both ISAs, the layer-2 scenarios among them, T2.2). Keep images independent of the host and the directory: the kernel links with `/pdbaltpath:%_PDB%`, and `fingerprint` compares builds.

Use `setup` once for the pinned local QEMU package, clang and the musl tarball. `libc` builds the pinned musl and boots the first libc program on x64 alone; the `test` suites of both ISAs include the scenario. The test tool must distinguish successful boot, panic, unexpected exit and timeout. Never infer a passing boot from an exit code or log line alone. Before running a program on a host, look whether it starts processes of itself, and run a host suite as its test runs it (`dotnet <dll>`). A boot that runs past its deadline leaves samples of the processor's registers in its monitor log before QEMU quits, and on x64 the frame at the top of the sampled kernel stack with the user stack it names (D5.2); with `WITOS_GUEST_DUMP=1` it also leaves the guest's memory as an ELF core beside the logs, which `guest-threads --core … --map … --serial …` reads (P3): every processor's registers at the dump's instant from the core's notes, the kernel lock, the dispatchers, each process's threads with their waits and contexts, a dynamic program's modules and frame chains named through `--symbols` directories (the runtime's `.dbg` files, OpenSSL's libraries, the services' `.dbg` files and `libc.so` linked under the modules' names), `--peek slot:address:words` and `--scan words` for a thread whose code keeps no frame records; ARM64 alone so far. A stall that comes one run in several is caught by replaying the runner's captured QEMU command many times at once with the data disk under `snapshot=on` and a memory dump on silence (P4 §2); a silence limit must exceed the longest stretch a suite runs without output (NUnitLite prints only the tests that write).

A VMware session (phase H, `@Docs/Implementation/H0-Hardware-Measurement.md`) runs the tool's image as a SATA disk the pinned `qemu-img` converts to a VMDK, in a machine written by hand (EFI with `efi.serialconsole.enabled`, the first serial port to a file, which is the log), started and stopped by `vmrun -T ws` without a window and without VMware Tools; a measurement instruments a scratch tree and reverts it, never a commit.

For changes of the runtime port (phase R), its patch set or its pin, run `runtime-witos` for both ISAs on a Linux host (the image of `build/linux/Dockerfile`, on a volume copy of the tree); its `runtime-acceptance` scenario is the guest proof of .NET, and CI's `linux-host` job runs it.

Keep generated images, binaries, firmware, downloads, logs and credentials out of Git. They belong in ignored `artifacts/` or `.tools/`. Record actual results and limitations in documentation; do not mark a future milestone complete based on M0 boot.
