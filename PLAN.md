## Что считаем запуском .NET

| Рубеж | Проверяемый результат | Статус |
| --- | --- | --- |
| Первый гостевой .NET, P4 | Обычный NativeAOT executable со стандартной CoreLib проходит настоящий bootstrap, входит в managed `Main`, выделяет объекты и выполняет реальный GC с сохранением корней | **Достигнут в bring-up профиле** |
| Полный M3, P5 | В одном гостевом runtime работают GC, finalization, managed exceptions и managed threads; проходят проверки жизненного цикла и отказов | **Достигнут в выбранном NativeAOT профиле** |
| Цель совместимости, P6 / M6 | Upstream CoreCLR/JIT запускает обычную portable managed-сборку, собранную на другой ОС, без перекомпиляции под WitOS | Не достигнут |

NativeAOT — средство раннего запуска и реализации системных компонентов. Он не заменяет CoreCLR/JIT как контракт приложений. Не создаём собственную CoreLib, особый язык C# или обязательный WitOS TFM. Сохраняем обычные SDK, TFM, NuGet и managed semantics; см. [контракт совместимости](@Docs/RFC-0015-DotNet-Runtime-Port-and-Compatibility-Contract.md).

## P1. Полная линковка и настоящий startup-драйвер

**Последний подтверждённый checkpoint:** полный guest executable связан без unresolved symbols и OS imports; настоящий handoff исполняет upstream bootstrap, managed `Main` и GC. Minimal/broad inventory — **0/6**; шесть broad-символов относятся к намеренно исключённым transport/TLS objects и разрешены в исполняемом образе. P1.8.g/h и весь P1 завершены; [поэлементный аудит](@Docs/Implementation/P1-Completion-Audit.md), [runtime/GC evidence](@Docs/Implementation/P1-Runtime-Rendezvous.md).

- [x] **P1.1** Получить воспроизводимый minimal standard-CoreLib workload и strict-link inventory с настоящими transport/TLS objects: [`NativeAotBoot`](experiments/NativeAotBoot/Program.cs), [readiness](@Docs/Implementation/NativeAot-Startup-Readiness.md).
- [x] **P1.2.** Для каждой группы зависимостей ниже проследить реальные call sites и составить таблицу: обязательная реализация / допустимое upstream отключение необязательной возможности / оставшийся блокер. Зафиксировать первоначальный профиль: x64, один CPU, static image, workstation GC; возможность non-concurrent GC подтвердить реальной конфигурацией и исполнением.
- [x] **P1.3.** Закрыть необходимые CRT/compiler primitives: math/formatting, `_fltused`, security cookie/check и выбранный CFG-профиль. Инициализировать защиты до защищённого кода. Никаких фиктивных cookie/check/dispatch-функций.
- [x] **P1.4** Определить источник случайности для фактически используемых runtime/security-путей. PRNG TLS constructor, часы и идентификатор потока не считать криптографической энтропией.
- [x] **P1.5.** Связать прямые CoreLib/native platform calls с реальными WitOS handles, memory, waits, identity и console services. Проверить значения, lifetime, ошибки, права и эквивалентность direct/import bindings.
- [x] **P1.6.** Реализовать нужные module/name/encoding/diagnostic paths. Для COM, Windows event log, dynamic library lookup и других необязательных Windows-механизмов принять явное решение по профилю. Не эмулировать всю Windows и не возвращать фиктивный успех.
- [x] **P1.7.** Закрыть выбранную GC OS policy: write-watch, large pages и debug break. Поддержать требуемое поведение либо доказать исключение опционального пути допустимыми upstream настройками; unsupported методы до этого остаются блокерами.

- [x] **P1.9** Guest entry thunk собран, связан и исполнен: validated handoff → image/environment → GS/TLS → readonly native initializer tables → настоящий upstream `wmain` → orderly process exit. ### P1.8. Завершённый чек-лист

Ниже — подзадачи одного P1.8, а не дополнительные независимые этапы. Runtime/GC acceptance выполняется совместно с P3; закрытие native-пробы не закрывает runtime integration.

- [x] **P1.8.a — kernel context foundation.** Kernel-owned capture, counted suspend/resume и validated set/restore; проверки прав, владельца, стеков, регистров и отсутствия частичной записи. Evidence: [capture](@Docs/Implementation/P1-Context-Capture.md), [suspension](@Docs/Implementation/P1-Thread-Suspension.md), [mutation](@Docs/Implementation/P1-Context-Mutation.md).
- [x] **P1.8.b — hosted unwind reference.** Pinned upstream algorithm сравнен с Windows на 14 сценариях; отдельно проверены 20 metadata cases, 8 read-boundary cases и 2593 записи полного reference image. Evidence: [reference](@Docs/Implementation/P1-Unwind-Reference.md), [metadata](@Docs/Implementation/P1-Unwind-Metadata.md).
- [x] **P1.8.c — checked unwinder (hosted).** Подключить bounded reads ко всем stack/code/metadata accesses алгоритма, ограничить объём работы и публиковать CONTEXT/handler outputs только после успеха. Приёмка: differential cases для адаптированного алгоритма, guard pages, повреждённые metadata и неизменные outputs при каждом отказе.
- [x] **P1.8.d — гостевой unwinder и loader contract.** Получать stack/image bounds и стабильный lifetime из kernel-owned state, связать настоящий `RtlVirtualUnwind`, согласовать поддержку loader с реальными consumers. Приёмка: guest walks по prolog/body/epilog, chained/frame/XMM cases и отрицательные тесты без выхода за диапазоны; parsing сам по себе не закрывает пункт.
- [x] **P1.8.e — exception dispatch и compiler handlers в выбранном native-профиле.** Реализовать нужные RaiseException/fail-fast/vectored/SEH paths, включая проверку специфичных GS/SEH payloads. Приёмка: реальная доставка контекста, handlers и unwind, contained fatal failures, исполнение actual production `/GS` context objects. Source-equivalent `/GS-` probes не заменяют эту проверку.
- [x] **P1.8.f — runtime attachment и shutdown.** Настоящие PalInitComAndFlsSlot/PalAttachThread, ThreadStore и RuntimeThreadShutdown исполнены в полном runtime: normal/detached workers, повторный attach, заполненный allocation context и реальный GC FixAllocContext, закрытие runtime handle, TLS cleanup, quota rollback/reuse и сохранность exit callbacks. 72 lifecycle на четырёх профилях × двух адресах; Release/source/audit/target/probe, 20 boot-сценариев и четыре native-профиля проходят. [Evidence](@Docs/Implementation/P1-Worker-Lifecycle.md). Межпоточные roots/rendezvous подтверждены следующим пунктом P1.8.g; прочие критерии P3 перечислены отдельно.
- [x] **P1.8.g — GC rendezvous/hijack.** Полный Thread::GcScanRoots удерживает kernel stack lease с парными foreign suspend/resume на весь обход. Actual compacting GC сохраняет main/worker stack и RAX/RBX roots; реальный upstream context redirection останавливает managed spin-loop. ## Проверки и правила обновления плана

Для native/boot/image/runner изменений обязательны:

```powershell
dotnet build WitOS.slnx --configuration Release
dotnet run --project tools/WitOS.Dev --configuration Release -- test
```

Для runtime/source-port изменений также выполняются `runtime-audit`, `runtime-probe`, `runtime-target` и `runtime-source` через тот же инструмент. `runtime-config` включает source-build/target/readiness и четыре native guest-прогона. Guest-managed acceptance выполняет `runtime-boot` (или `runtime-boot-run` для последнего hash-verified image); существующий `runtime-config` по-прежнему не доказывает managed execution. Точный состав проверок определяется [AGENTS.md](AGENTS.md).

1. Отмечать `[x]` только после выполнения условия и фактической проверки; для частично выполненного пункта оставлять `[ ]` и пояснять готовую часть.
2. После каждого завершённого участка обновлять здесь базовую версию, карту этапов и ближайший следующий пункт; добавлять ссылку на implementation doc с evidence.
3. После каждого изменения link boundary обновлять текущий unresolved snapshot; при закрытии P1 записать размеры actual guest image и уточнить оценку оставшейся работы. Старые измерения сохранять в исторических документах, не выдавать за текущие.
4. Новый обнаруженный блокер добавлять под нужный этап с зависимостью и критерием закрытия. Не перепрыгивать обязательную инфраструктуру ради количества закрытых символов.
5. Прогресс измерять прохождением рубежей P1–P6. Один commit, native probe или hosted test не закрывает весь рубеж.

Сейчас вне критического пути первого запуска: GUI/shell, GPU, networking, distributed services, широкая аппаратная поддержка, SMP и встраивание ядра во firmware/chip. Возвращаем их в план только по отдельной цели либо если конкретная runtime-зависимость этого требует.
