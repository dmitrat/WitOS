# D1.1 — The device manager discovers the devices

D1.1 is the first step of phase D. It applies [ADR 0025](ADR-0025-Devices-as-NativeAOT-Services.md): the device
manager is a NativeAOT program of the boot package, and the root task moves the device table to it. Both ISAs pass.

On ARM64 the virt board shows three devices: the Red Hat host bridge, the boot disk and the entropy device. This meets
points 1 and 2 of M4's definition of done (Implementation Strategy §45): the hardware appears as UHI records, and the
device manager discovers the virtual block device.

## The start of a service

- **Start message, version 4** (`witos/start.h`). After the log and the package, the message carries the optional
  capabilities its `Capabilities` field names, in this order: the process manager's endpoint, then the capability its
  creator grants (`WIT_START_GRANT`). The handles of a message leave no gaps, so the field says which ones are
  there. The libc keeps the grant in its process context, and `witos_take_grant` hands it out once. The initial
  directory now has 224 bytes, since the structure grew by 8.
- **Spawn request, version 3** (`witos/manager.h`). A request may carry a third handle, the grant of the new process,
  which the process manager moves into its start message. `witos_spawn_options` has a `grant`, which is moved on
  success and closed on failure.
- **Services before the first process.** `witos_manager_run_services` starts each service in turn. While it waits
  for the service's answer on its granted channel (a `WitServiceStatus`) or for the service's end, it serves spawn
  requests. Only then does it start `/bin/init`. A service runs until the root task ends.
- **The root task** (`src/RootTask`). When the package has `/system/DeviceManager`, the root task creates a channel
  and sends the device manager's start over it, with the device table in the one handle slot
  (`witos/device_manager.h`). It then grants the other end. It moves its own table handle, with the rights the kernel
  gave it, and so keeps no device authority. It moves rather than attenuates because `HANDLE_DUPLICATE` keeps
  `ACQUIRE` out of a memory object's rights. Without the program, the root task starts `/bin/init` as before.

## The capability API

**libwitos** (`witos/capabilities.h`, `capabilities.c`) offers what the device manager uses:
- the grant;
- closing and duplicating a handle;
- creating a channel, sending, and a receive that waits;
- mapping and unmapping a memory object.

A function returns zero or an `errno` value: `EPIPE` for a closed peer, `EAGAIN` for a full queue, `EMSGSIZE` for a
message that does not fit. No call number or status appears above layer 2. The device, interrupt and DMA functions
come with the steps that use them.

**`OutWit.OS`** (`src/OutWit.OS`) is the managed side:
- `Resources`: `KernelHandle` as a safe handle, `Grant`, `MemoryMapping`, `Rights` and `CapabilityException`;
- `Communication`: `Channel` and `ChannelMessage`. A sent handle moves, and the sender's safe handle gives it up
  without closing it;
- `Hardware`: `DeviceTable`, `DeviceDescriptor`, `DeviceRegion` and `DeviceLine`. The table is read through its
  memory object, and the bytes are validated before anything is built from them.

The functions are `LibraryImport`s of `libwitos`. NativeAOT binds them directly (`DirectPInvoke`), and the service
links `libwitos.a` from the sysroot.

## The device manager

`src/Services/DeviceManager` does three things.
- It takes its grant, receives the root task's start and reads the table.
- It translates each descriptor into a `DeviceRecord` (`Uhi/PciTranslator.cs`). The identity is the bus address with
  the vendor and device words. A virtio device, vendor `0x1AF4`, modern or transitional, is named by the contract
  its type serves: `BlockStorageController`, `EntropySource`, `NetworkQueueDevice` and so on. Every other function is
  named by its PCI class code: `HostBridge`, `SataController` and so on.
- It prints a discovery line for each device and a summary line that states the DMA isolation as it is. It answers
  `WitServiceStatus` zero, then serves its channel until the root task's end closes it.

A table it cannot read, or a start of another protocol, is answered with the error and ends it.

## Building and running

- **On the host**, `OutWit.OS`, the device manager and `tests/OutWit.OS.Tests` are part of `WitOS.slnx`. The tests
  cover the table's layout and refusals, the translation and the service messages. CI runs them on both hosts.
- **For witos**, `runtime-witos` publishes the device manager with the SDK's targets after the M3 acceptance. The
  generated project compiles the service's sources with `OutWit.OS`'s source folders and links `libwitos.a`.
  `RuntimeDevices.BuildAsync` then boots the `runtime-devices` scenario, whose package carries:
  - `/system/DeviceManager`;
  - `tests/User/devices_init.c` as `/bin/init`;
  - musl's dynamic linker and the shared C++ runtime.

  The scenario requires:
  - the discovery lines of the block and entropy devices;
  - the device manager's summary;
  - the root task's report that the device manager was ready before `/bin/init`;
  - `/bin/init`'s exit with zero.
- **`runtime-services`** repeats that step alone, with the tree and packages an earlier `runtime-witos` built. It
  saves rebuilding the runtime and rerunning its other scenarios while a service changes.

## Limits kept explicit

- The device manager acquires no device yet, and starts no driver. D1.2 adds that, together with the kernel change
  that lets a device handle cross a process boundary (ADR 0025, decision 3).
- The root task moves its own handle of the table, since `HANDLE_DUPLICATE` cannot keep `ACQUIRE`. The device
  manager therefore also holds `DUPLICATE`.
- The services' managed API is compiled into each service. It is not a package, and phase N publishes it.
