# D5.2 — System.IO over the namespace service

D5.2 is the second step of D5. An ordinary .NET program uses the files of the mounted volumes through System.IO, and a
private memory map of a volume's file is a copy. Nothing in .NET changes for it:

1. System.IO calls System.Native.
2. System.Native calls the libc.
3. The libc sends every path below a mount point to `/system/Namespace` (D5.1).

The step also fixed the kernel's dispatcher. It never let a process that kept a ready thread give the processor to
another process, and a .NET program was the first to wait for another process while one of its threads spun.

## The program (`tests/Runtime.Witos/Files`)

- **The build.** `/bin/files` is a NativeAOT program built by the SDK's targets, as the services are
  (`RuntimeWitos.PublishProgramAsync`). Its source is ordinary C#: it uses System.IO, and nothing of WitOS.
- **The start.** `/bin/init` (`tests/User/devices_init.c`) runs its POSIX checks, then starts `/bin/files` with
  `posix_spawn` and waits for it.
- **The areas.** Each area prints one line, and the last line counts them.

| Area | What it does |
| --- | --- |
| text | `WriteAllText`, `AppendAllText`, `ReadAllText`, `WriteAllLines`, `ReadAllLines`, and `FileInfo`'s length and write time against `DateTime.UtcNow` |
| stream | A `FileStream` written, seeked, overwritten, cut by `SetLength`, flushed to the disk and read back; then a `StreamWriter` appending and a `StreamReader` |
| directories | `CreateDirectory` with its parents, `EnumerateFiles` over a tree, `GetDirectories`, and a recursive `Directory.Delete` |
| moves | `File.Move`, `File.Move` with overwrite, `File.Delete` |
| current directory | `SetCurrentDirectory` to a volume's directory, a relative path, `GetFullPath` and `Environment.CurrentDirectory` |
| exceptions | `FileNotFoundException`, `DirectoryNotFoundException`, a write to the read-only `/boot`, and `FileMode.CreateNew` of an existing file |
| megabyte | A file of 1 MiB written in 64 KiB writes and read back whole |
| memory map | A copy-on-write `MemoryMappedFile` view: it reads the file's bytes and takes a write, and the file stays unchanged. A shared view is refused with `IOException` |
| fat | A file written, read and deleted on `/fat` |
| cleanup | The program's tree removed recursively |

- **The kept file.** The program leaves `/data/dotnet-kept.txt`. After the boot, the host's `debugfs` must read it
  byte for byte from the ext4 partition, which `e2fsck -fn` must find clean (`RuntimeExt4Volume`).

## Memory maps of a volume's file (`src/Substrate/libc/memory.c`, `files.c`)

- **A private mapping** (`MAP_PRIVATE`) is a copy, through the copy that already served unaligned package files and
  shared memory files:
  - The libc reserves and commits plain memory.
  - It reads the file's bytes into it through the namespace service and leaves the rest of the pages zero.
  - It sets the protection asked.
  - Writes stay the mapping's own. `mprotect` and `munmap` treat the copy as any plain mapping.
- **A shared mapping** (`MAP_SHARED`) is `ENODEV`. The service serves no file as memory; that needs a memory object
  of the file's pages, which is later work.
- **Refusals.** A descriptor opened for writing alone is `EACCES`, as on Linux. `PROT_EXEC` is `EACCES`, since plain
  memory never executes.
- **`msync`**, newly served, has nothing to write back:
  - a private mapping is the process's own memory;
  - a shared mapping of a shared memory file shows the file's own pages;
  - the package is read-only.

  So it checks the request as Linux does (the flags hold `MS_ASYNC` or `MS_SYNC` but not both, the address is
  page-aligned, a page the library did not map is `ENOMEM`) and succeeds. .NET's view calls it when it is disposed.
- **The checks.** `/bin/init` maps a file of each writable volume privately: it reads the bytes and the zeros past
  the end, writes to the copy, calls `msync` and `munmap`, and finds the file unchanged. A shared mapping is `ENODEV`.
  The .NET program's `memory map` area checks the same through `MemoryMappedFile`.

## The dispatcher (`src/Kernel/user.c`)

**The fault.** Before D5.2, `dispatch` began its search at the current component on every path, and in that component
at the thread after the one that ran last. The thread that had just run came back at the end of its own component's
search. So a component with a ready thread kept the processor at every tick and every `THREAD_YIELD`, and another
component ran only when every thread of the running one waited.

**Why it hung.** The .NET program hung at its first file call after its first `Console.WriteLine`, every time, at
whatever point in the areas that write came:

1. The console started System.Native's signal-handling thread.
2. That thread's first `read` of its pipe needs the libc's table lock for a moment.
3. The main thread held that lock across a call to the namespace service, which the libc makes under it (D5.1).
4. The signal-handling thread spun on the lock with `THREAD_YIELD`. Each yield chose it again, so the namespace service
   never ran to receive the request, and the main thread waited for its reply forever.

**The change.** A tick or a yield now rotates: the search begins at the next component and reaches the current one
last. A wait, an exit or a device line still begins at the current component.

- So a thread that keeps running, or that spins on a lock whose holder waits for another component, never keeps the
  processor from the others.
- What AGENTS.md always said, that the dispatcher round-robins the live components, now holds.
- Within a component, threads still take turns from the one that ran last.

## Finding the hang (`tools/WitOS.Dev/Host/QemuControl.cs`)

A guest that runs past its deadline now leaves samples of where the processor is in the monitor log, before QEMU quits.
Each sample records `info registers`. On x64, it also records:

- the kernel stack's page above the stack pointer, whose top holds the frame a system call or an interrupt saved;
- the user stack that frame names.

QEMU reads guest memory without changing it.

That is how the hang was found:

1. The samples showed the processor at CPL 0 in the HPET's register read, and never halted.
2. The stack pointer lay in the kernel stack of process slot 6, thread 2.
3. The frame at that stack's top held a user RIP in `libc.so`'s `__wit_lock`, called from `__wit_syscall`, with the
   lock word in RBX: `tables`, the table lock.
4. The thread's stack was nearly empty: a new thread's first call.

## Defects found on the way

- **The dispatcher kept the processor in one process.** See above.
- **No `msync`.** Disposing a `MemoryMappedFile` view calls `msync`, which the libc did not map, so .NET threw
  `IOException` ("Function not implemented").
- **FAT opens a file once for writing.** `OutWit.Common.Fat` takes one writer or many readers of a file, so an open
  that conflicts is `EBUSY`, which showed when `/bin/init` read a file while its descriptor for writing was still open.
  That limit stays FAT's, beside its refusal to remove an open file (D5.1).

## Results

`runtime-services` passes on both ISAs:

- **`/bin/init`** passes 54 of 54 POSIX checks on `/data` and `/fat`, the private and shared mappings among them.
- **The .NET program** prints `[FILES] System.IO over the namespace service under NativeAOT on X64: 10 areas passed,
  0 failed`, and the same on Arm64. It exits with 0, which `/bin/init` reports.
- **The host check.** After the boot, e2fsck finds the ext4 partition clean and debugfs reads both kept files.

The kernel's self-test suites (`test` on both ISAs) pass with the rotating dispatcher.

## Limits kept explicit

- **NativeAOT only.** CoreCLR (`dotnet`) loading a program or an assembly from a volume is D5.3. So is the libwitos
  loader reading an ELF through the service.
- **The memory map's copy is taken when the mapping is made.** It reads the whole range then, so its cost is the
  range's size, and later writes to the file do not reach it, nor its writes the file.
- **No shared mapping and no executable copy** of a volume's file (`ENODEV`, `EACCES`).
- **One namespace call at a time per process, under the table lock** (D5.1). A thread that needs the table lock while
  another waits for the service now yields to the service instead of starving it, but it still spins until the reply.
- **FAT takes one writer or many readers of a file** (`EBUSY` otherwise), and removes no open file.
- **The other limits of D5.1 stand:** one session per process, a rename that removes its target first, `flock` within
  one description, and no authority below the volume.
