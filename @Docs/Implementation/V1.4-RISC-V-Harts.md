# V1.4 — The other harts: SBI HSM starts them, the software interrupt carries the kernel's requests, `boot-smp2` on riscv64

Plan step V1.4, the last slice of V1 (the RISC-V kernel), 2026-10-17. V1.3
([V1.3-RISC-V-User-Mode.md](V1.3-RISC-V-User-Mode.md)) left seven operations of the port as stubs that panic by name:
the start of a secondary processor and the inter-processor interrupt in the architecture, a processor's interrupt
frames and the interrupt's send and completion in the board. This slice replaces them with K7.2's mechanism on RISC-V —
every hart of the device tree started at boot through the firmware's hart state machine, idling in S-mode and serving
the kernel's two requests, a fence and the invalidation of one page, through the supervisor software interrupt — so that
`boot-smp2` passes on the riscv64 virt board as it does on the two others and no stub is left in either directory. V1 is
complete: the loader (V1.1), the kernel foundation (V1.2), user mode (V1.3) and the harts (V1.4) run the common kernel,
the shared self-tests and the fixtures on the third ISA without a change to `src/Kernel`.

## 2. Starting a hart

OpenSBI starts the next stage on one hart and keeps the others stopped in its hart state machine until S-mode asks for
them. `wit_arch_secondary_prepare` records the boot hart's `satp` once (the kernel's Sv48 root, the same for every
hart), gives the hart a 64 KiB kernel stack of its own, lets the board map the hart's PLIC context (section 4) and
fences, since the entry reads the root and the stack top from memory. `wit_arch_secondary_start` is SBI HSM `hart_start`
(hart, address, opaque): the hart enters the address in S-mode with `a0` its identity and `a1` the opaque word, which
the kernel makes its own number of the processor, in the bare physical space with interrupts disabled. The kernel runs
identity mapped, so the entry's virtual address is its physical one, as on ARM64, where PSCI `CPU_ON` enters with the
MMU off.

The entry (`wit_rv64_secondary_entry`) disables the interrupt enables and clears `sip`, takes its stack from
`wit_rv64_secondary_stack_tops[a1]`, installs `stvec` and a zero `sscratch` (the kernel-mode side of V1.2's protocol:
a trap lands on the current stack), opens the floating-point unit (`sstatus.FS` initial, since the trap vector saves
`f0`–`f31`), installs the root with an `sfence.vma` — the next instruction is where it was — and calls
`wit_rv64_secondary_main(index, hart)`, which never returns. The main function requires the hart to be the one its
number names, marks itself started, lets the board mask its PLIC context, enables the software interrupt alone in
`sie` (no tick and no device line reaches a secondary hart until phase P), reports a zero features word and no cache
size, calls `wit_cpus_secondary_ready` and waits for interrupts with `sstatus.SIE` set.

## 3. The inter-processor interrupt

RISC-V has one software interrupt a hart — the supervisor software interrupt, SSIP — and no number to carry a kind, so
the board keeps the kind in memory: `wit_platform_ipi` writes `pending_ipi[hart]`, fences and asks the firmware for the
interrupt through SBI `send_ipi` (the IPI extension; a mask of one hart from the hart's base), which OpenSBI raises as the
target's SSIP. The target's trap vector takes the software interrupt on its own stack; the dispatcher asks the board to
claim it, the board sees SSIP in `sip` and answers the kind it kept (3, the inter-processor kind of the claim contract,
with the kind as the line), the dispatcher calls `wit_cpus_ipi_received` with it — a fence, or `sfence.vma` of the
address the request names — and `wit_platform_ipi_complete` clears SSIP in `sip`, the one pending bit S-mode clears
itself. The common kernel sends one request at a time and waits for its acknowledgement, so one word a hart suffices.

A running secondary knows its hart by the stack it runs on: S-mode reads no `mhartid`, and a secondary never leaves its
own stack before phase P, so `wit_rv64_secondary_hart` finds the stack the stack pointer lies in and
`wit_arch_processor_id` answers that hart before the boot hart's cached identity. The processor table keeps the device
tree's order; `processors.c` finds the boot hart in it by that identity, wherever OpenSBI's lottery put it.

## 4. The board

A hart's supervisor context is `2 × hart + 1` as the boot hart's (V1.2). `wit_platform_processor_prepare` maps the
context's enables page, which the first 32 contexts share and the boot hart mapped already, and its own threshold and
claim page — each only when `wit_virtual_view` says it is unmapped, since a device page is mapped once.
`wit_platform_processor_interrupts_enable` sets the context's threshold to 7, so that no priority passes: a secondary
hart's external interrupt stays disabled in `sie` as well, and its enables stay clear. `wit_platform_interrupt_claim`
checks SSIP before the PLIC's claim register, so the boot hart's device lines and a secondary's software interrupts go
through one function, as on ARM64 the GIC's acknowledge register serves both.

## 6. Findings

1. **One software interrupt, no number.** The GIC's SGI number and the APIC's vector carry the request's kind on the
   other boards; RISC-V's SSIP carries nothing, so the board keeps the kind in memory for the hart before the firmware
   call. The common kernel's one-request-at-a-time rule (K7.2) is what makes one word a hart enough.
2. **A secondary's identity is its stack.** S-mode reads no `mhartid`; a hart started by HSM learns its identity from
   `a0` once, and since it never leaves its own kernel stack before phase P, the stack pointer names the hart afterwards
   — the same place the boot hart's probe through HSM `hart_get_status` left off (V1.2).
3. **The PLIC's enables of 32 contexts share a page.** The boot hart's context mapped it already; a device page is mapped
   once, so the board asks `wit_virtual_view` before mapping, as the device tree and ECAM readers do.
4. **The board needs the kernel's kinds.** The first build failed on `WIT_IPI_FENCE` in the board's code: `witos/cpu.h`
   names the kinds, and the ARM64 board includes it for the same reason.
5. **Nothing in the common kernel moved.** `cpus.c`'s start, acknowledgement and bounded waits, `processors.c`'s search
   for the boot processor in the table and `smp_tests.c` ran on the third ISA unchanged, and the first two-processor
   boot of the port passed.

the C++ runtime, libwitos, the sysroot — and sets `KernelArchitecture.SystemLayer` for riscv64, so that the layer-2

device lines are phase P's, on the three ISAs alike.
