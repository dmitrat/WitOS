# C1.4 — the shell command and the console mark

Plan step C1.4 (phase C, RFC 0020 §34) is the developer's loop: one command of the tool boots WitOS with PowerShell on
the host's console, with a directory published on the host laid on the data volume, so that the system can be worked
with by hand; and the session's banner, the console mark of `@Docs/WitOS-Console-Logos.md`, rendered by the shell's
profile from files of the image. Measured on 2026-10-16 in the Linux container on both ISAs.

## 1. The shell command

`dotnet run --project tools/WitOS.Dev -- shell [--arch x64|arm64] [--publish <directory>] [--memory <MiB>]` builds the
package of the PowerShell scenario (the device services, the .NET install, `apps_init.c` with two lines: `cd /data` and
the interactive PowerShell) and a data disk of 1 GiB whose ext4 volume holds PowerShell with its native library under
`/pwsh`, the home `home/`, and, with `--publish`, every file of the directory under its name, so that
`dotnet /data/<name>/App.dll` runs what the host published. It boots the release kernel with 1 GiB (the `--memory`
default) and a terminal whose far side is the console the command runs on:

- **`TerminalRelay`** (`tools/WitOS.Dev/Host/TerminalRelay.cs`) is the terminal on the host's console, as `TerminalLink`
  is the terminal of a scripted scenario: a loopback listener QEMU's character device connects to; the guest's bytes go
  to the host's standard output as they are, so the host's terminal interprets them and answers the guest's queries
  itself (the cursor position report among them); what the person types is read key by key and sent as a terminal
  sends it — a printable character as its UTF-8, Enter as CR, Backspace as DEL, the cursor and editing keys as their
  escape sequences, Alt as ESC before the key, a control key as its control character, so Ctrl-C reaches the guest and
  not the tool (`Console.TreatControlCAsInput`). The guest's bytes are also kept in `artifacts/logs/<arch>-shell-<MiB>.terminal.log`.
- `BootRequest.InteractiveTerminal` asks the runner for the relay instead of a script; the boot's wall-clock limit is a
  day, and the session ends with PowerShell's `exit`, which ends `/bin/init`, the root task and the machine.
- `--disk <image>` keeps the data disk between sessions: it is made with the volume's files when missing and booted as
  it is when there, so what a session wrote stays for the next (a published directory is laid only when the disk is
  made). Without it the disk is made anew under the artifacts for every session.
- The install's `PATH` ends with `/dotnet`, so a session runs `dotnet App.dll` by name.
- The command needs a terminal to read keys from: in the Linux container, `docker exec -it`; the install it boots is the
  one `runtime-witos` built there. On a Windows host without that install the command stops at the install's files; an
  exported install (what CI's `linux-host` uploads) is a later step.

## 2. The console mark

The marks of `@Docs/WitOS-Console-Logos.md` — the emblem of 32 by 7, the wordmark of 42 by 6, the ASCII fallback of 33
by 4 — and the palette live in `build/console/logo` as plain text, byte-identical on every ISA, and the .NET install
carries them under `/etc/witos/logo`; a host test checks their sizes and characters and that the palette names every
role and every row of the emblem. Nothing of the system prints them: the kernel, the root task and the services stay as
they were, and the session renders.

**The renderer is the profile.** `build/console/profile.ps1` goes beside `pwsh.dll` on the volume as `$PSHOME/profile.ps1`,
which every interactive PowerShell session runs (the scenario's and the shell's PowerShell start with `-NoLogo`, so
PowerShell's own banner stays silent; the batch commands run with `-NoProfile`). It follows the guide's rules: nothing
when the output or the input is redirected or `WITOS_NO_LOGO` is set; the ASCII mark without colour when `TERM` is
`dumb` or the output encoding is not UTF-8; the one-line mark below 33 columns; the emblem alone below 70; the emblem
with the info panel from 70 (the terminal of N4.3 is 80 by 24, so the scenario shows the panel). The colour depth is
`NO_COLOR` and `TERM=dumb` → none, `COLORTERM` `truecolor`/`24bit` → 24-bit, `TERM` ending in `-256color` → 256 (what the
install's `TERM` gives), 16 otherwise; in colour every tier of the emblem is `█` and the palette's role of the row colours
it, with a reset at the end of every line; in monochrome the shading characters of the art stay.

**The panel reads the running system**, and a field that cannot be read is omitted: the title is the machine name (or
`witos`); `OS` is `RuntimeInformation.OSDescription`, `WitOS 0.1 ABI-1`; `Kernel` names the nano-kernel and
`RuntimeInformation.OSArchitecture`; `Runtime` lists the frameworks under `/dotnet/shared/Microsoft.NETCore.App`;
`Shell` is `$PSVersionTable.PSVersion`; `Volumes` are the mount points of `/etc/mtab` (C1.2a). Labels are padded to nine
columns in the layer-2 colour, values are truncated with `…` to the width, the emblem is never truncated.

**The scenario checks it.** The interactive session of `runtime-powershell` runs the profile and requires the emblem's
first row as the colour renderer draws it (`████          ████          ████`, which the transcript keeps between the
tiers' escape sequences) and `PowerShell 7.6.7` from the panel's `Shell` field, which appears nowhere else in the
session's output. The guide's questions, answered by the step: the art lives in the read-only package (there is no
writable `/etc` to override it with yet); the recovery console is the serial terminal of C2's time; the profile is the
renderer and `witfetch` is not needed yet; C2's console decides its own depth.

## 3. ReadyToRun, measured

The ordinary `powershell-7.6.7-linux-x64-fxdependent.tar.gz` carries ReadyToRun code compiled for linux-x64. Run on
witos-x64 in the C1.1 harness beside the same native library, its two batch commands took 144 and 196 s of guest time
against 141 and 208 s for the IL-only archive: no faster, so CoreCLR on witos takes none of that code (ReadyToRun
images name the OS they were compiled for) and compiles everything through the JIT either way. The pin stays the IL-only
archive, one for both ISAs; a start of two to five minutes under TCG is the price of the JIT in virtual time, not of
WitOS, and a real machine or a ReadyToRun compilation for `witos-<arch>` (which the SDK's crossgen could produce from the
witos runtime pack) are the ways to cut it.
