# D1. Перемежающийся сбой GC в управляемой приёмке

Дата: **2026-10-04**. Статус: **открыт**, причина не найдена; добавлена диагностика для следующего случая.

## Что произошло

После мержа Q2 в `main` полная матрица CI ([run 37172377878](https://github.com/dmitrat/WitOS/actions/runs/37172377878)) упала в `runtime-boot-run`. Профиль `runtime-boot-intel` (CPU Nehalem, 256 MiB), третье из четырёх исполнений управляемой нагрузки, база образа `0x8000100000`, фаза integration cycle (совместные GC, исключения, финализация и потоки с hijack чужих потоков), 98-й тик:

```
[NATIVE-FAIL-FAST] code=0xC0000005 address=0x0000008000143C92 rip=0x0000008000143C92
Runtime fatal code/parameters/rbx/r14/r15: 0xC0000005/0x0/0x0/0x0000010000A02460/0x0000008000024D90/0x2
```

По map-файлу образа из того же прогона RVA `0x43C92` — это `gc_heap::mark_object_simple+0xa2` (`gcwks.witos.cpp`). Параметры исключения `0/0` означают чтение по адресу 0. `rbx` указывает внутрь резервирования кучи GC (`0x10000040000 + 0x1400000`), `r14` — в стек главного потока.

Вероятная картина: сборщик при разметке получил ссылку на объект, у которого указатель на MethodTable равен нулю, то есть память объекта обнулена, а чтение полей MethodTable пришлось на адрес 0. Это вывод из одного отчёта, а не доказанная причина.

## Что известно

- Тот же код прошёл полную матрицу на PR #1 (несколько прогонов) и все локальные прогоны; прошлый упавший прогон `main` (30.09) был другим сбоем.
- 12 локальных прогонов `runtime-boot-run` (192 исполнения управляемой нагрузки) при `shift=2`, `shift=1` и в реальном времени сбой не повторили.
- Гипотеза для проверки: WitOS обнуляет страницы при `VirtualReset` сразу, а Windows при `MEM_RESET` обычно сохраняет их содержимое. Если сборщик где-то читает уже сброшенную память, на Windows это почти никогда не проявится, а здесь даст нулевой MethodTable. Адаптер передаёт ядру только выровненный по странице диапазон, и ядро обнуляет ровно его, так что выхода за диапазон нет.

## Диагностика для следующего случая

При неожиданном фатальном завершении управляемого исполнения харнесс `runtime-boot` печатает, пока память компонента ещё существует:

- `Runtime fatal code/address/parameters` — код, адрес и параметры исключения;
- `Runtime fatal thread/rip/rsp/stack` и `Runtime fatal image base/size/rip RVA`;
- `Runtime fatal registers` — все пятнадцать регистров общего назначения;
- `Runtime fatal memory <регистр>` — четыре слова по каждому регистру, указывающему в отображённую память компонента;
- `Runtime fatal stack RVAs` — до 32 слов со стека в пределах образа (адреса возврата и указатели на код);
- `Runtime memory journal` — операции памяти (reserve, commit, decommit, reset, protect, release с кодами 1–6) над страницами, на которые указывают регистры, и шестнадцать последних операций. Журнал на 256 операций ведёт ядро только в сборке `runtime-boot` (`WITOS_TEST_RUNTIME_BOOT`); в остальных сборках обёртки операций памяти возвращают статус без записи.

При провале профиля инструмент переводит RVA из отчёта в имена по `artifacts/runtime-readiness/guest-driver/WitOS.NativeAotBoot.map`, печатает их и сохраняет в `<профиль>.symbols.txt` рядом с журналом загрузки. Нативные функции получают точные имена; у управляемого кода в map нет собственных символов, поэтому такие кадры показываются как ближайший публичный символ с большим смещением.

Отчёт проверен на настоящем фатальном контексте: при временном вызове в исполнениях с намеренной недопустимой инструкцией символизация показала `wit_runtime_invalid_instruction`, `wit_runtime_native_fault`, `wit_native_tls_enter`, `wit_native_main` и `wit_native_start`.

## Следующие шаги

Когда сбой повторится, журнал покажет, сбрасывалась ли или выводилась ли из подтверждения страница объекта перед разметкой, а стек — откуда пришла ссылка (корень потока, хэндл или поле объекта). До этого D1 остаётся открытым в PLAN.md.
