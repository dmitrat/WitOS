# H2.1 — USB: an xHCI controller and a keyboard of the boot protocol

Plan step H2 (phase H, ADR 0029: the keyboard of every target is USB) gives WitOS a USB host stack. H2.1 is its first
slice: an xHCI controller driven from user space and the keyboards of the HID boot protocol on its root ports. The driver
serves their keys over the input protocol (`witos/input.h`), as the virtio keyboard's driver does, so the display service
and the terminal are unchanged. H2.2 adds hubs, keyboards that speak only their report descriptor, devices that arrive
after the start, and the recovery of a halted endpoint.

## 2. The controller

- **From the firmware.** Where the controller has USB Legacy Support (extended capability 1), the driver sets the OS Owned
  semaphore, waits up to a second for the BIOS to let go, and turns the SMIs off. It logs whether the firmware kept the
  controller.
- **Reset and start** (xHCI 1.2 §4.2). The driver waits for Controller Not Ready to clear, halts a running controller,
  then resets it. It enables 16 slots of MaxSlots and gives the controller:
  - the Device Context Base Address Array, whose entry 0 names the scratchpad pages when the controller asks for them
    (at most 16);
  - a command ring of a page;
  - one event ring segment of 256 TRBs and its segment table;
  - interrupter 0 enabled.

  It then sets Run/Stop with Interrupter Enable.
- **Register writes.** The driver writes a 64-bit register as two 32-bit writes, the low half first, because QEMU's xHCI
  acts on the high half's write (CRCR, ERSTBA, ERDP, DCBAAP). It reads CAPLENGTH and HCIVERSION as one dword, because
  QEMU answers a 16-bit read at offset 2 with zero.
- **The interrupt.** Interrupter 0 interrupts through an MSI-X message where the kernel serves messages and the function
  has the capability (`InterruptBinding.BindMessage`, `MsiX`; the PC since H1.2b), and through its INTx line otherwise.
  Serving it clears IMAN's Interrupt Pending and USBSTS's Event Interrupt, takes every event, writes ERDP back with Event
  Handler Busy, and unmasks the INTx line. A wait for a command or a control transfer also looks at the ring every
  10 ms, so a lost interrupt delays the driver instead of stopping it.
- **The ports** come from the Supported Protocol capabilities: each range of ports with its USB major and minor revision
  and its Protocol Slot Type. A port without power is powered where the controller switches power.
- **A device on a port.**
  - A USB 2 port is reset first: Port Reset, then the wait for Port Reset Change, then 10 ms of recovery. A USB 3 port
    enables itself.
  - Enable Slot names the port's slot type.
  - The Input Context gives the slot (speed, root port, one context) and the default control endpoint (8, 64 or 512 bytes
    by the port's speed).
  - Address Device follows.
  - The first eight bytes of the device descriptor give bMaxPacketSize0; when it differs, Evaluate Context updates the
    endpoint.
- **A control transfer** is a Setup Stage TRB with the packet as immediate data, a Data Stage TRB for its data and a
  Status Stage TRB with Interrupt On Completion, rung on the slot's doorbell for endpoint 1. Any stage's error ends the
  transfer with its completion code.
- **An interrupt IN endpoint.** Configure Endpoint adds the endpoint's context: its type, packet bytes, burst at high
  speed and interval exponent (full and low speed: the largest power of two of 125 µs units within bInterval frames,
  3–10; high speed and SuperSpeed: bInterval less one), and a transfer ring of its own. Each report is a Normal TRB with
  Interrupt On Completion and Interrupt on Short Packet. A Transfer Event's residual gives the bytes the device sent.

**QEMU's keyboard.** `usb-kbd` takes one queued key event per poll (`hid_keyboard_poll`), so a key's press and release,
which the runner sends in one `input-send-event`, arrive as two reports when the driver asks for the next report at
once. The runner types a key once the driver has logged the previous one's transitions. It counts the xHCI driver's
lines as it counts the virtio keyboard's.

**The gate.** `runtime-display` boots with the USB keyboard. The runner types the terminal probe's line, the check's line
and PowerShell's session on the screen through QMP into `usb-kbd`. The screendump at the last prompt equals the host's
frame pixel for pixel, and the services stop: the driver halts and resets the controller and answers the device manager.

| ISA | `runtime-display` | Key transitions logged |
| --- | --- | --- |
| x64 (container) | passed, 196 s | 160 |
| ARM64 (container) | passed, 255 s | 160 |
| riscv64 (container) | passed, 296 s | 160 |

**VMware.** The display image booted on VMware (`qemu-img` to a VMDK on the SATA controller, H0's machine). The driver
ran the controller, addressed every device and configured the keyboard. The display service took the driver's channel
and drew the 1024 by 768 GOP framebuffer as 128 by 48 cells. The boot then ended where the session needs `/data`, which
waits for H3's storage drivers. Typing on the guest is the H5 session's work.

## 4. What is not yet

- **Hubs** (H2.2): a device behind a hub needs the hub class, route strings and, at full and low speed behind a high-speed
  hub, its Transaction Translator.
- **Keyboards that speak their report descriptor alone** (H2.2): a HID keyboard without the boot subclass, or a combined
  device whose keyboard's reports carry an ID, needs the report descriptor parsed. The PocketTerm35's RP2040 is to be
  measured there.
- **Devices that arrive later** (H2.2): the driver logs a port's change after its start and takes no device.
- **A halted endpoint** (H2.2): a report that completes with an error ends that keyboard's reports, since a Reset Endpoint
  and a new dequeue pointer are not yet sent.
- **Several controllers.** Each controller has a driver, but the display takes one input channel: a virtio keyboard
  first, then the first xHCI driver.
- **USB storage** over `witos/block.h` waits for a need, as the plan says.
