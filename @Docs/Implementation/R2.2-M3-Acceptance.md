# R2.2 — the M3 acceptance of NativeAOT's Unix form

Plan step R2.2 repeats the M3 acceptance on the new substrate ([RFC 0015 v2 §9](../RFC-0015-DotNet-Runtime-Port-and-Compatibility-Contract.md)).
The acceptance covers GC, exceptions, finalization, threads and TLS, and waits. NativeAOT's Unix form runs the probes
in the guest on both ISAs, as `/bin/init` under the system layer's root task, against the witos CoreLib alone.

It needed one kernel step first. The first runs passed every probe but the waits, which failed with
`OutOfMemoryException`: the kernel ran four threads of a process, and the main thread, the finalizer and the thread
pool's threads filled them. K5.3 gives the system layer's processes sixteen
([K5.3-Process-Capacities.md](K5.3-Process-Capacities.md)). The acceptance then found a defect of the libc, fixed here:
a detached thread's stack stayed in the mapping table after the kernel had released it.

## What changed

### The probes

`tests/Runtime.Witos/Acceptance` carries the probes of the frozen line's acceptance, `experiments/NativeAotBoot`. That
program ran the same managed cases under the Windows reference and the frozen guest:

| Probe | What it checks |
| --- | --- |
| `FaultProbe` | Null reads, null writes and integer division by zero raise `NullReferenceException` and `DivideByZeroException` with live roots, collecting in each handler. |
| `ExceptionProbe` | Two-pass dispatch, in four rounds. A filter that throws counts as false; a finally releases a native page in the unwind pass; a rethrow keeps the exception's identity; a nested throw and catch run inside a finally. The steps are recorded in order, with six collections during dispatch. |
| `FinalizationProbe` | On the finalizer thread: three waves of finalizers that each release a native page and collect, a resurrection with re-registration, and suppression. The finalizer's thread identity is checked. |
| `ManagedThreadProbe` | Start and join, thread statics, a timed wait under a recursive lock, and a wait without the lock, which throws `SynchronizationLockException`. GC suspends a worker in a loop without calls (an activation) and a worker parked in `Monitor.Wait`, in four rounds. |
| `ThreadQuotaProbe` | A thread created and joined beside two parked ones, then a compacting collection. This is the frozen line's reference form; the guest form expected the kernel's refusal at four threads. |

`FaultProbe`, `ManagedThreadProbe` and `ThreadQuotaProbe` are unchanged except for their namespace. The other two
called kernel32 for a native page and for the thread's id. They now call the libc's `mmap`, `munmap` and `gettid` (the
`Libc` class), since a Unix-form program has no Win32 and WitOS emulates none.

The Unix form adds three probes:

- **`OutOfMemoryProbe`.** An allocation larger than the system layer's whole data arena throws
  `OutOfMemoryException` three times, then the process allocates and collects. The frozen line's `MemoryFailureProbe`
  relied on a 4 MiB hard limit its native driver set; a witos program runs with the GC's defaults.
- **`ThreadPoolProbe`.** Eight `Task.Run` results, a continuation and a `QueueUserWorkItem` on a thread pool thread.
- **`WaitProbe`.** `Monitor.Pulse` across threads, a `ManualResetEventSlim` and a `SemaphoreSlim` set by another
  thread, and a 50 ms `Thread.Sleep` that takes its time.

`Program.cs` runs the eight probes in four cycles, as `NativeAotBoot` ran its cycles. Each run prints a line, and a
final collection checks the program's static, local and array roots. The last line is
`[M3] NativeAOT on <isa>: 32 runs passed, 0 failed`, and `Main` returns 0 only then.

### Output through the libc

The class libraries above CoreLib (`System.Runtime`, `System.Console`) are not built for witos yet. The acceptance
therefore writes its lines with the libc's `write`, declared as `[DllImport("libc")]` and compiled with
`--directpinvoke:libc`, so the linker resolves it in the system layer's libc as it resolves `System.Native`.

### The build

`runtime-witos` compiles the acceptance's sources together with csc against the witos CoreLib (`-unsafe`,
`-nullable:enable`). ILC compiles it with the same publish arguments as the first program, plus the libc as a direct
P/Invoke, and the link is the same. The first program keeps its check that `Main` folds to the constant 0
(`RequireConstantMainAsync`).

The `runtime-acceptance` scenario boots the release kernel with the acceptance as `/bin/init`. It requires the last
line and the root task's `/bin/init exited with 0`. Like `runtime-program`, it is no suite scenario, since the program
comes from the runtime's build on a Linux host.

### A stale mapping after a detached thread's exit

With K5.3, x64 passed all 32 runs. ARM64 failed the finalization probe in cycles 2 to 4, the same way at every
virtual-time shift. Yet any change to the program made the failure vanish, even a method that ran only after the last
cycle, and so did any change to libc.so's `memory.c`. The failure therefore depended on addresses, not on timing:

- The kernel places a reservation in the lowest gap.
- The sizes of the program and of libc.so move every later one.

Tracing that moves no user address kept the failure:

- A dump of the probe's statics from libc.so's `exit_group` showed four finalizers run but two pages released.
- Kernel prints of the calls a thread makes, with the registers it resumes with, showed what `munmap` of one page did.
  It issued two partial `MEMORY_RELEASE` calls; the first released the page's reservation, and the second was refused
  with `NOT_RESERVED`. So `munmap` returned `EINVAL`, and the probe counted a failed release.

The cause was in the libc. musl ends a detached thread with `__unmapself` and its stack mapping, which the libc turns
into a `THREAD_EXIT` naming that reservation (S2). The kernel releases the reservation once the thread no longer runs,
but the libc's mapping table kept the entry. When the kernel later placed new reservations in that range, `munmap` met
the stale entry first: its partial release took the new reservation, and the real entry's release failed.

NativeAOT starts its threads detached, and the probes start and end many of them. Now `__unmapself` takes the mapping
out of the table under the table lock before the exit (`__wit_mapping_forget_locked`, `memory.c`, `syscall.c`).

`libc_hello.c` checks the fix on both ISAs: it maps a page with `MAP_FIXED_NOREPLACE` where a detached thread's stack
was, and `munmap` of that page must succeed. Without the fix the check fails on x64 too.

## Tests

- **Linux (the container).** `runtime-witos` and `runtime-witos --arch arm64` pass through R2.2:
  `NativeAOT on witos-<arch>: the M3 acceptance passed its 32 runs in the guest`.
- **The libc.** `libc` reports 122 checks on x64 and 120 on ARM64, none failed. Without the fix, the new check fails
  on x64.
- **Windows.** Both suites pass, and so do the host tests.

## Limits kept explicit

- **Output is the libc's `write`,** not `Console`; the class libraries for witos come with the SDK's targets (R2.3).
- **The thread quota probe runs in its reference form.** The kernel refuses a seventeenth thread, which `libc_hello.c`
  checks (K5.3), and the runtime turns that refusal into `OutOfMemoryException`, which the waits probe met before K5.3.
- **No stack overflow probe.** The frozen line's `StackOverflowProbe` ran only under its native worker fixture, and a
  stack overflow ends the process by design.
- **No hard limit.** The GC sizes for the machine; process-quota awareness is R3's `gcenv.unix` work (R2.1).
- **The frozen probes leave.** `experiments/NativeAotBoot` goes with the frozen line; the carried probes are their
  successors.
