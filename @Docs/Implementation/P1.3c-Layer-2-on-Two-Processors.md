# P1.3c — layer 2 on two processors

Plan step P1.3, last slice (phase P; P1.3a gave each processor its entry state and tick, P1.3b ran threads on every
processor in the kernel's self-tests): the layer-2 scenarios run on two processors as well as on one, on the three
ISAs. Made on 2026-10-18.

## 1. The scenarios

`KernelTestSuite` boots each layer-2 scenario twice (`RunOnOneAndTwoAsync`): as before, and again with two processors
under the name with the suffix `-smp2` — `libc`, `libc-test`, `cxx`, `spawn`, `process` and `sysroot`, on x64 (33
scenarios where there were 27) and on ARM64 and riscv64 (27 where there were 21). The release kernel, the root task and
every program are the same; only the processors differ. The threads of a process and the processes of a scenario run side by side there: musl's locks, futexes and
thread exits, the libc's pipes within and between processes, its signals and `posix_spawn`, the process manager and
the dynamic linker.

## 2. What two processors found

One test, not the system layer: `libc_hello.c`'s check that `pthread_kill` interrupts a worker's `sem_wait` with
`EINTR` sent the signal as soon as the worker had posted the semaphore that says it is about to park. On one processor
the worker parks before the main thread runs again; on two it may still be running, the handler runs with no wait to
interrupt, and the worker then parks for good while the main thread joins it — a deadlock the kernel's idle charge
then ended as the root task's budget. The same test races on Linux. The main thread now sends the signal until the
parked wait reports `EINTR`, one millisecond apart.

The way there: the deadlock looked like a lost futex wake. A temporary dump of every thread's state, wait handle and
saved stack pointer when a budget expires, a ring of the last `EVENT_SET` and `OBJECT_WAIT` calls with their deadlines,
and the libc's futex slots read from the process's memory at the symbol's address showed the worker parked on a word
of the main thread's stack — the test's `sem_t gates[2]` — and the main thread in `pthread_join`, with no wake lost.

## 3. What ran

In the Linux host's image, with the final code:

- `test --arch x64`: PASS, all 33 scenarios; on two processors `libc` 167 checks, `libc-test` all 386 tests, `cxx` 21
  checks, `spawn` 47, `process` 280 and `sysroot` 6, as on one.
- `test --arch arm64`: PASS, all 27; `libc` 165 checks, `libc-test` all 388 tests, `cxx` 21, `spawn` 47, `process` 280,
  `sysroot` 6 on two processors.
- `test --arch riscv64`: PASS, all 27; `libc` 167 checks, `libc-test` all 388 tests, `cxx` 21, `spawn` 47, `process`
  280, `sysroot` 6 on two processors.

Nothing of the system layer changed: the libc's locks, futexes, pipes, signals and process manager, written with
acquire and release where processes share memory, held on two processors under ARM64's and RISC-V's weaker ordering as
written.
