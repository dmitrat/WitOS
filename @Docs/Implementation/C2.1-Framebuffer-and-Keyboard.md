# C2.1 — The firmware's framebuffer and a virtio keyboard

Plan step C2.1 (RFC 0020 §24 and §28, RFC 0009 §26), 2026-10-16: the two devices a text console on a display needs,
brought to the device table and driven, before the display service of C2.2 draws text into one and takes keys from the
other. Nothing here is M9: no compositor, no GPU, no windows — a linear framebuffer the firmware set up, and a keyboard
whose events a driver reports.

## 1. The measurement: which device gives both boards a linear framebuffer

The plan asked which QEMU device gives a linear framebuffer to both boards, naming `ramfb` as the candidate. The loader
(`src/Boot.Uefi/display.c`) reads the firmware's graphics output protocol and prints what it finds; the release boots
of both ISAs measured, with the `release-display-256` boot added to the `release` command:

| Board | QEMU arguments | Firmware's framebuffer | Memory |
| --- | --- | --- | --- |
| q35 (x64) | default (`-vga std` implied) | 1280×800, stride 1280, BGRX at 0x80000000, 4,096,000 of the 16 MiB BAR; mode 0 of 30 | the VGA card's BAR 0 |
| q35 (x64) | `-vga none -device ramfb` | 800×600, stride 800, BGRX at 0x0E4CF000, 3,145,728 bytes; mode 1 of 3 | guest RAM, EFI type 0 (reserved) |
| virt (ARM64) | `-device ramfb` | 800×600, stride 800, BGRX at 0x4C7A0000, 3,145,728 bytes; mode 1 of 3 | guest RAM, EFI type 0 (reserved) |

`ramfb` is the one device both boards share: EDK II's `QemuRamfbDxe` drives it on OVMF and on ArmVirt alike, chooses
800×600 of its three modes, and allocates the framebuffer as reserved memory, which the loader never marks usable. QEMU
scans the display out of that memory after `ExitBootServices` without any further programming, so what the kernel's
owner writes shows. q35 must lose its default VGA card (`-vga none`), or OVMF shows the VGA's framebuffer instead. The
decision: `ramfb` on both boards (`KernelArchitecture.DisplayArguments`, `BootRequest.Display`); a board's own linear
framebuffer, as the VGA's BAR, goes the same way through the boot contract when a firmware offers it.

## 2. The boot contract v7 and the firmware bus

`WitBootInfo` grows by the framebuffer (184 bytes, `WIT_BOOT_VERSION` 7): the physical base and size in whole pages,
the width, the height and the stride in pixels, the format (`WIT_PIXEL_BGRX` 1 — blue, green, red, unused, as UEFI's
`PixelBlueGreenRedReserved8BitPerColor`; `WIT_PIXEL_RGBX` 2), zeros without one. The loader takes the current mode as
it is, never calls `SetMode`, refuses a bit-mask or Blt-only output, prints the mode, and while it converts the memory
map keeps any conventional region that holds a framebuffer page reserved, reporting the EFI type once (both boards:
type 0). The kernel validates the block whole in `validate_contract` (`Invalid framebuffer`) and reads no byte of it.

The platform publishes the framebuffer as a device: `WIT_DEVICE_BUS_FIRMWARE` (2), `Identity[0]` the kind
(`WIT_FIRMWARE_DEVICE_FRAMEBUFFER` 1), `Identity[1]` the width and the height (`width | height << 16`), `Identity[2]`
the stride, `Identity[3]` the format, region 0 the memory, no lines — the inline `wit_device_describe_framebuffer` of
`witos/device.h`, which both `wit_platform_devices` append after their bus's functions (the q35 and virt enumerations
were restructured so that a board without a bus still publishes it). The common kernel never calls it and reads none
of the words; the device manager's `FirmwareTranslator` turns it into the UHI record `FrameBuffer` of provider
`Firmware`, id `firmware/framebuffer`, and `OutWit.OS.Display.FramebufferGeometry` reads the words back.

## 3. ABI-1 1.3: `DEVICE_MEMORY`'s window

A memory object covers at most 64 pages, and `DEVICE_MEMORY` refused a region beyond 64 pages with `TOO_LARGE`; a
framebuffer of 3 MiB (768 pages) needs more. The call's third argument, which had to be zero, is now the window: the
region's page the object starts at, the object covering at most 64 pages from there, a window beyond the region
`INVALID_ARGUMENT`. A window of zero on a region within 64 pages is the call as it was; the device fixture's check that
window 1 on the one-page configuration region is refused stands. ABI-1 is 1.3 (`WIT_ABI_VERSION_MINOR`), additive.
libwitos adds `witos_device_memory_at`, `OutWit.OS` `Device.MemoryAt` and `Device.WINDOW_PAGES`.

## 4. The display probe and the host's judge

The device manager's `DisplayProbe` acquires the framebuffer, maps it window by window and draws
`OutWit.OS.Display.TestPattern` — a black frame of 16 pixels and four horizontal bands, red, green, blue, white — with
one aligned 32-bit store a pixel through `MmioRegion.Write32`: the mapping is device memory, where ARM64 forbids an
unaligned or vector store, so no `Span.Fill` or `memcpy` reaches it. It prints `[DEVICES] display probe: 800 by 600,
stride 800, BGRX, 1920000 bytes in 12 windows of 64 pages: test pattern drawn` and releases the device; the pattern
stays, since the framebuffer is memory nobody clears.

The runner (`BootRequest.Actions`, `BootAction`) watches the serial log and, once the probe's line appeared, takes
QEMU's `screendump` through QMP into `<boot>.screen.ppm` beside the logs (`QemuControl.ScreendumpAsync`; the QMP
session now serves a few commands while the guest runs and the quit at the end, one at a time). After the boot,
`Screenshot` reads the PPM and `RequireTestPattern` samples the frame's corners and the middle of each band against
the same `TestPattern` function for the screen's own size — the judge of C2.3's design, in place from the first slice,
and the PPM is the artifact a person looks at.

## 5. The keyboard

`virtio-keyboard-pci` on both boards (`BootRequest.Keyboard`): a virtio device of type 18, which the device manager
already named `InputDevice`; the driver table maps it to `/system/Drivers/VirtioInput`, a NativeAOT program beside the
block and console drivers, published by `runtime-witos` and `runtime-services` and shipped by `ServiceFiles`. The
driver takes the device as the console driver does, negotiates `VIRTIO_F_VERSION_1` alone, reads its configuration
through the select and subsel registers (virtio 1.x §5.8: the name, the device identifiers, the `EV_KEY` bits), sets
up the event queue with 64 buffers of one 8-byte event each and the status queue on pinned pages, binds the line to an
event, and reports every event: `[VIRTIO-INPUT] key 30 down`, `key 30 up`. The runner's second action presses and
releases `a` through QMP's `input-send-event` once the driver reported ready; QEMU routes the key to the virtio
keyboard, the newest keyboard handler of the console, and the scenario requires the two lines. The display's terminal
takes the keys from C2.2.

## 6. The scenario and the gates

`runtime-display` (`RuntimeDisplay`, after `runtime-terminal` in `runtime-witos`) boots the device services with the
display and the keyboard and `tests/User/display_init.c` as `/bin/init`, requires the loader's framebuffer lines, the
firmware bus's discovery line, the input driver's and the probe's lines, the key, init's line and the services'
stop, and then requires the pattern in the screendump. The `release` command's `release-display-256` boot proves the
loader's and the platform's part on both ISAs on every host, including CI's `boot`, `boot-arm64` and `linux-host`.

## 7. Results

- `release-display-256` passed on x64 and ARM64 on the Windows host (section 1's table), beside the two release boots
  without a display; the x64 and ARM64 self-test suites (`test`) passed with the device fixture's window check.
- The host tests: the firmware translator, the geometry's words and refusals, the pattern's frame, bands and byte
  orders, the driver table, the QMP session's sequencing (OutWit.OS.Tests 183, WitOS.Dev.Tests 96).

## 8. Findings

1. Both EDK II ports put `ramfb`'s framebuffer in reserved memory and pick 800×600; the loader's reservation of a
   conventional region holding a framebuffer never triggered, and stays as a guard.
2. On q35 the firmware's framebuffer is the VGA card's unless the card is removed: the device table then held both the
   PCI display controller and the firmware bus's framebuffer over the same BAR, which the kernel allows (it knows no
   overlap) and the plan avoids by `-vga none`.
3. The `DEVICE_MEMORY` window was the one kernel change the slice needed; the common kernel learned nothing of a
   display, and the firmware bus is a platform's description of the boot contract.
4. The required lines of a scenario must be plain words: the terminal the install names since C1.3 made NUnitLite
   colour its summary, which failed the libraries scenario on both ISAs in CI (fixed in C1.3's branch with the
   runners' no-colour options).
5. The probe draws the rows the geometry names (stride × height × 4 = 1,920,000 bytes, 8 windows), not the whole 3 MiB
   `ramfb` allocated for its largest mode; the device manager's display probe on the devices gate's x64 boots, which
   keep the default VGA, draws 1280×800 into the card's BAR through 16 windows — the same code over a PCI framebuffer.
6. QEMU's virtio keyboard reports bus 6 (virtual), vendor 0x0627, product 0x0001, 231 keys in its `EV_KEY` bits and an
   event queue of 64 entries; a key pressed through QMP reaches it rather than q35's PS/2 controller, since the newest
   keyboard handler of the console takes the event.
