# P1.3a — each processor's entry state and tick

Plan step P1.3 (phase P, `P1.0-SMP-Inventory.md` section 6) runs threads on every processor. It is split in two: P1.3a
gives each processor what an architecture needs before it can enter and leave user mode — its own SYSCALL entry on
x64, its own selected kernel stack and TLS base on ARM64 and riscv64 — and a tick of its own; P1.3b lets the
dispatcher run threads there. Threads still run on the boot processor alone (`wit_processors_scheduling()` stays 1).
Made on 2026-10-18.

## 1. Entry state per processor

- **x64**: SYSCALL switches no stack, and the GS base stays zero (no `swapgs`), so the entry cannot find a per-processor
  record. Each processor enters through a stub of its own instead (`user_entry.S`: `wit_x64_syscall_entry_0` to `_7`,
  generated by `.irp`, one per entry of `WIT_PROCESSOR_CAPACITY`, which `exceptions.c` asserts is 8). A stub reaches its
  processor's two words RIP-relative — the kernel stack of the thread it runs (`wit_x64_syscall_kernel_rsp[n]`, written
  beside that processor's `TSS.RSP0`) and the caller's RSP across the entry — and joins the common frame builder.
  `wit_x64_enable_syscall(n)` writes the processor's own LSTAR from `wit_x64_syscall_entries`; a secondary enables
  SYSCALL as it starts, after loading its task register.
- **ARM64**: `selected_top`, the kernel stack top an EL0 frame must resume at, is an array per processor
  (`frame.c`).
- **riscv64**: `selected_top` and `user_tls`, the TLS base a fresh frame takes when first resumed, are arrays per
  processor (`frame.c`). The hart record already held the kernel stack top the trap entry switches to (P1.1).

The root task's launch and return state (`host_rsp`/`host_cr3` on x64, `host_stack` on ARM64 and riscv64) stays
single: the root task runs from the boot processor's `wit_user_run`, and P1.3b keeps its return there.

## 2. A tick per processor

`wit_platform_timer_start`, `wit_platform_timer_stop` and `wit_platform_timer_acknowledge` act on the calling
processor:

- **q35**: the boot processor keeps the PIT through the PIC. A secondary's tick is its local APIC's timer
  (`witos/x64_local_timer.h`, implemented in the architecture's `secondary.c`, which owns the APIC): periodic, divided
  by 16, on the PIT's vector 0x20, so that one entry and one handler serve both, and acknowledged by the APIC's EOI
  where the boot processor's goes to the PIC. Its count for one tick is measured once, on the boot processor when
  secondary processors are online (`wit_platform_ipi_enable_boot`), against the monotonic clock over one tick — every
  APIC timer runs from the same bus clock.
- **virt (ARM64)**: each processor's own virtual timer, whose PPI 27 its own redistributor enables
  (`redistributor(index)`, the boot processor's at index 0).
- **virt (riscv64)**: each hart's own `stimecmp`, or the firmware's timer for it; only the boot hart opens its PLIC
  context, since device lines reach it alone.

Each architecture counts ticks per processor (`timer_ticks[WIT_PROCESSOR_CAPACITY]`), and `wit_arch_clock_ticks()`
reports the calling processor's; the boot processor's count, which the clock calibrations and the preemption
self-test read, is unchanged by a secondary's ticks. A secondary's timer runs only while asked; P1.3b starts it with a
run and stops it at the root's end.

## 3. The self-test

`Smp.Tick` (`tests/Kernel/smp_tests.c`, in `boot-smp2` on the three ISAs): the boot processor has the first secondary
start its timer by a RUN request, waits 100 ms of monotonic time, and has it stop the timer by another; the secondary
counted between 5 and 20 ticks on its own counter — 9 on each ISA, the first tick a period after the start — and the
boot processor's counter, whose timer is off during the self-tests, did not move.

## 4. What ran

In the Linux host's image, with the final code:

- `test --arch x64`: PASS, all 27 scenarios, `Smp.Tick` in `boot-smp2`; every system call of the user suites and the
  layer-2 scenarios entered through the boot processor's stub.
- `test --arch arm64`: PASS, all 21 scenarios; `test --arch riscv64`: PASS, all 21; `Smp.Tick` in `boot-smp2` on both.
- `release` on the three ISAs: `release-128`, `release-512` and `release-display-256` pass; the x64 release image still
  loads with 128 MiB.
