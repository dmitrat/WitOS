# C4.3 — the installer of base applications

Plan step C4.3 (phase C, ADR 0027 decisions 5 and 7, RFC 0010 §23–§24, §124–§132): an installer in the guest — WitOS's
first console tool on Arlecchino — installs and updates the data volume's base applications from a folder feed on any
volume, verified by SHA-256, keeps the versions side by side, switches the version in use and rolls back. Made on
2026-10-18.

## 1. The folder feed

A feed is a directory (`AppFeed`, `src/Apps/WitOS.Apps`) that holds, for each application's version:

```text
<feed>/<ApplicationId>/<version>.json   the entry: { "manifest": <the catalog entry>, "package": { "file", "sha256" } }
<feed>/<ApplicationId>/<version>.zip    the package: the version's files as the layer holds them, less the manifest
```

- **The manifest** is the version's catalog entry, as the layer writes it into `witos-app.json` (C4.1): the identity, the
  version, the framework, the source and its pin, the native part, the commands, the purpose.
- **The package** is a zip, extractable by standard tooling and offline-verifiable (RFC 0010 §21–§22): every entry a path
  within the version's directory, its entries in the order of their paths and all of one time, so that the same files
  make the same bytes.
- **A reading checks each entry whole** — the manifest, its identity and version against the directory and the file's
  name, a zip beside it, a SHA-256 of 64 lower-case digits — and an entry that fails is a problem the reading reports,
  not an exception, so that the rest of the feed stays usable.
- **What the SHA-256 gives** is integrity: a package of other bytes than its entry names is refused. Trust in whoever
  wrote the feed waits for signatures (RFC 0010 §44–§112, M8); the source the manifest pins is the provenance.

`apps --feed <directory>` (the host's tool) writes a feed of every application of `build/apps` for an architecture,
whose native parts it takes.

## 2. The layer's operations

`AppsDirectory` (`src/Apps/WitOS.Apps`) is the layer of C4.1 in a directory of the file system, shared by the installer
and the host's tool (`AppLauncher`, the launcher's writer, moved there from `AppsLayer`):

- **An installation** (RFC 0010 §124) hashes the package and compares it with the entry, extracts it into a hidden
  `.<version>.partial` directory beside the versions — each zip entry checked to stay inside, none of them a manifest, a
  mode the zip records applied — requires every command's assembly, writes the manifest last and renames the directory
  into place; then the version is made current. A failure removes the partial directory and leaves the layer as it was;
  a version the layer has is not written again.
- **Using an installed version** writes each command's launcher and then `current` through a new file renamed over the
  old, so that a reader sees the old or the new and never half of one. That is the update's last step and the rollback
  (RFC 0010 §126–§127, §130: an older version is never blocked).
- **No database:** the applications are the directories with at least one version that holds a manifest; hidden
  directories are never versions.

## 3. The installer

`witos-apps` (`src/Apps/Installer`) is an ordinary portable application on Arlecchino's package 2026.9.3, pinned exactly
with a lock file (ADR 0027 decision 7). The boot package carries it as part of the system (`InstallerPackage`): its
publish and the witos apphost under `/system/Installer`, from which it writes the layer's launchers, and its own
launcher `/usr/bin/witos-apps`, on `PATH`. `shell` sessions carry it too.

- **The screen** (`InstallerView`): the applications of the layer and the feed in a table — the versions installed, the
  one in use, the feed's version and what it means (`new`, `update`, `installed`, `older`) — with I to install or update
  the selected one, U to use another installed version through a picker that starts on the version in use, R to read
  again and F10 to quit. An installation runs off the frame thread under a notification that shows its steps
  (`Verifying`, `Extracting … n of m files`) and settles into what happened (`Installed <id> <version>`), which the
  status line repeats; a switch says `<id> uses <version>`.
- **The commands** for scripts: `witos-apps list [--feed <directory>]` prints a line for each application
  (`<id>: installed <versions>; in use <version>; feed <version> (<state>)`) and the feed's problems;
  `witos-apps install <id> [<version>] --feed <directory>` installs the feed's latest or named version and makes it
  current; `witos-apps use <id> <version>` switches; a failure is one line on standard error and exit code 1.
- **The options:** `--layer` (`/data/apps` by default), `--feed`, `--apphost` (the one beside the installer by default).

Its tests run on the host (`tests/WitOS.Apps.Tests`): the screen in Arlecchino's headless host (`ArlecchinoTestHost`),
driven by keys — the update beside the installed version, the rollback through the picker, F10 — and the commands, the
options, the feed's writing and reading with its refusals, the installation's refusals (other bytes, a zip entry that
leaves the directory, a missing assembly) and the order of versions.

## 4. The scenario

`runtime-installer` (`RuntimeInstaller`, after `runtime-commander` in `runtime-witos`, or alone) boots the display, the
keyboard and the mirror with the device services, the .NET install and the installer in the boot package:

- **The layer** holds Arlecchino.Commander's release v2026.9.1 (commit `09110d7`, 2026-09-11, whose submodule is
  Arlecchino's v2026.9.2, still in the library's repository), built from its source by `AppSourceBuild` and laid by the
  host's tool as C4.1 lays it — a real older version of the catalog's application.
- **The feed** on the data disk's FAT volume, `/fat/feed`, holds the catalog's 2026.9.19 (`RuntimeDataDisk.CreateAsync`
  takes files for the FAT volume): its 46 files in a package of 4,370,249 bytes, within the volume's 8 MiB.
- **`/bin/init`** runs in `/data`: `witos-apps --feed /fat/feed` (the screen), `witos-apps use Arlecchino.Commander
  2026.9.19`, `witos-apps list --feed /fat/feed` and `/data/apps/bin/arlc`.

The runner's actions (C2.3):

| After | Action |
| --- | --- |
| the terminal probe's prompt | `hello` and Enter |
| `2026.9.19 update`, the feed's cell | I: the update, verified and extracted beside 2026.9.1, made current |
| `Installed Arlecchino.Commander 2026.9.19` | U: the picker, which starts on the version in use |
| `Use which version of Arlecchino.Commander?` | Up, then Enter: the rollback |
| `Arlecchino.Commander uses 2026.9.1` | the screendump |
| at once | F10 |
| `type a command here`, the commander's command line | F10 |

The update goes back in use through the use command rather than the screen: the screen's renderer writes only the cells
that change, so a second switch's line after the first's (`… uses 2026.9.19` over `… uses 2026.9.1`) reaches the
transcript as the one digit that differs, and no trigger could wait for it. A trigger is a text the screen writes whole.

The scenario requires the services' lines, the installation and the rollback, each command's exit with 0, the use
command's `Arlecchino.Commander uses 2026.9.19`, the list's
`Arlecchino.Commander: installed 2026.9.1, 2026.9.19; in use 2026.9.19; feed 2026.9.19 (installed)`, the commander's exit
through its launcher, `4 commands, 0 failed`, the services' stop and the root task's report. Then the host requires the
screendump equal, pixel for pixel, to the frame it renders from the transcript, the rollback's line on it, and on the
data volume — unmounted by the guest and clean — `current` naming 2026.9.19, `/apps/bin/arlc` equal to the launcher of
2026.9.19 written from the apphost, every file of 2026.9.19 equal to the publish's, and 2026.9.1's `arlc.dll` kept.

## 5. What ran

In the Linux host's image, whose runtime trees of x64 and riscv64 it holds whole:

- `runtime-installer` on x64: PASS in 168 s — the screen's update and rollback (`witos-apps --feed` exited with 0 after
  174 s of guest time, 773 MiB free), `use` (21 s), `list` (23 s), the commander through its rewritten launcher (52 s);
  the screendump equal to the host's frame; the volume clean with the update's 46 files, its launcher and `current`,
  and the old version kept.
- `runtime-installer` on riscv64: PASS in 227 s, the same (244 s, 24 s, 28 s, 72 s).
- Host tests: `WitOS.Apps.Tests` (9: the feed and the layer's six, the screen in the headless host, the commands, the
  options), `AppsLayerTests` with the `apps` command's `--feed`, `format`.

ARM64 is CI's `linux-host` leg, which runs `runtime-installer` after `runtime-commander` with the rest of
`runtime-witos`, as do the other two legs.

The first try switched back to the update on the screen as well, and its trigger never came: the second switch's line
reached the transcript as the digit `9`, the one cell that differs from the first's (section 4).

## 6. Limits

- Sources are folder feeds; HTTPS sources (GitHub releases, nuget.org) wait for the network (M7), signatures and trust
  for M8.
- Removing an old version is by hand; the installer never deletes one.
- One layer, the one mounted at `/data`; `--layer` names another directory, not another volume's policy.
