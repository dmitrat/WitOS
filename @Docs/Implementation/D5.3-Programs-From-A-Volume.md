# D5.3 — Programs from a volume

D5.3 is the last step of D5. The boot package no longer has to carry every executable (M5 §50). Three kinds of program
now start from the ext4 volume:

- **A native program.** The root task's loader reads it through the namespace service.
- **A dynamic library.** The dynamic linker maps it from beside its program.
- **A .NET application.** `dotnet` runs it with its own library.

Before this step, a program was an ELF of the boot package, a library a file of the package, and an assembly a package
file `mmap` showed without a copy.

## The process manager reaches the namespace (`src/Substrate/libwitos/manager.c`, `src/Substrate/libc/namespace.c`)

The loader runs in the root task, inside the process manager, so the root task's own libc must reach the volumes:

- **The endpoint.** When the namespace service answers ready, the manager keeps its clients' endpoint for the
  processes it starts (D5.1). It now also gives that endpoint to its own libc (`__wit_process.Namespace`).
- **Connecting late.** A process without the endpoint no longer records a failed connection at its first path; it
  looks again at its next one. The root task opens package paths long before the service answers.
- **The channel quota.** The root task's live channels are now:
  - the manager's channel;
  - the device manager's channel;
  - the libc's session;
  - one start channel at a time.

  That is the kernel's limit of four.

## The loader (`src/Substrate/libwitos/spawn.c`)

- **Reading and checking.** A program on a volume is read through the libc's descriptors, as a package program is, and
  checked by the same rules before the process exists. Its interpreter may lie on a volume too.
- **Package programs** keep the package's own pages for their code.
- **A volume's code segment** is made of anonymous memory objects of at most 64 pages:
  1. The loader fills them through a writable view of its own.
  2. It publishes them for instruction fetch through a `READ|EXECUTE` view of its own, since `CODE_PUBLISH` needs every
     page mapped so.
  3. It maps them `READ|EXECUTE` into the process.
- **Other segments** are copies, as before.

## Memory maps of a volume's file (`src/Substrate/libc/memory.c`)

D5.2 made a private mapping a copy. D5.3 serves the two other mappings programs make of their files:

| Mapping | What the libc makes | Who maps so |
| --- | --- | --- |
| Private, not executable | A copy in plain memory (D5.2) | Data, copy-on-write views |
| Shared, not writable | A copy in plain memory, as a shared mapping of the package is a view of bytes nothing changes | CoreCLR's flat image layout: `CreateFileMapping(PAGE_READONLY)` and `MapViewOfFile(FILE_MAP_READ)`, which the PAL makes `mmap(PROT_READ, MAP_SHARED)` |
| Executable, private or shared but not writable | A shared memory file of the process's own (`shared.c`), filled through a view of the library's own, mapped as a shared mapping of that file is, and published for instruction fetch | musl's dynamic linker, for a library's code segment |
| Shared and writable | `ENODEV`: the service serves no file as memory | — |

**Replacing a range.** `MAP_FIXED` now replaces what lies in its range only once the descriptor is known good, as
Linux does. A copy that executes replaces the range only after its file is filled. Otherwise the file's chunk table, or
the view it is filled through, could take the range just freed.

## The scenario

**The volume.** The host lays `/programs` into the ext4 volume with `mkfs.ext4 -d`
(`RuntimeDevices.VOLUME_PROGRAMS`):

- `files/Files` is D5.2's System.IO check, a NativeAOT program, which the package no longer holds.
- `dynamic/dynamic` is the spawn scenario's dynamic program (`tests/User/dynamic_main.c`). Its library
  `libdynamic.so` and its plugin `libplugin.so` lie beside it, and it links with `RUNPATH $ORIGIN`. musl's dynamic
  linker takes `$ORIGIN` from `AT_EXECFN` (R7.1), so it maps the library from the volume and `dlopen` finds the plugin
  there. The program's `dladdr` check expects the library's path on the volume (`LIBRARY_PATH`).
- `app/App.dll` is a .NET application with its library `VolumeLibrary.dll`, its runtimeconfig and `greeting.txt`
  (`tests/Runtime.Witos/VolumeApp`). They are compiled against the reference pack as R5's application is, with no
  deps.json, so hostpolicy lists the directory for the application's assemblies.

**The package** carries R5's .NET install under `/dotnet` beside the services, so the boot disk grows to 128 MiB, and
the scenario boots with 512 MiB.

**`/bin/init`** (`tests/User/devices_init.c`) runs its POSIX checks, then starts and waits for:

- `/data/programs/files/Files`;
- `/data/programs/dynamic/dynamic 0`;
- `/dotnet/dotnet /data/programs/app/App.dll witos`. The application checks that its base directory and its library
  are on the volume, reads `greeting.txt` beside it, and prints a line with the library's answer.

**The checks.** The POSIX checks and the .NET program's `memory map` area now also require:

- that a read-only shared mapping shows the file's bytes;
- that a writable shared mapping is refused.

## Results

`runtime-services` passes on both ISAs:

- **`/bin/init`** passes 56 of 56 POSIX checks.
- **The System.IO check**, started from the volume, passes 10 of 10 areas.
- **The dynamic program**, started from the volume, passes its checks with its library and plugin mapped from the
  volume.
- **The .NET application** prints `[VOLUME-APP] App.dll and its library from /data/programs/app/ under CoreCLR on X64:
  Read from the ext4 volume, answered by VolumeLibrary`, and the same on Arm64.
- **Every program exits with 0.** After the boot, e2fsck finds the ext4 partition clean, and debugfs reads the files
  the guest wrote.

The kernel's self-test suites, whose layer-2 scenarios exercise `mmap` and the loader, pass on both ISAs (`test`):
libc-test passes 386 of 386 tests on x64 and 388 of 388 on ARM64.

## Defects found on the way

- **`MAP_FIXED` over a code copy failed with `EEXIST`.** musl's dynamic linker maps a library's whole span first, then
  each later segment with `MAP_FIXED`. `mmap` freed the range before the copy made its shared memory file. The kernel
  then placed the file's chunk table in the freed range, and the copy's own mapping met it. musl reported "Error
  loading shared library libdynamic.so: File exists".

## Limits kept explicit

- **A copy costs memory and time.** Every mapping of a volume's file is read whole through the service when it is
  made. A code copy takes chunks of 64 pages, as every shared memory file does.
- **A shared read-only mapping is a copy taken when it is made.** A later write to the file does not reach it.
- **One executable copy holds one of the process's 64 shared memory files** until it is unmapped.
- **The manager waits for the service.** It loads a program from a volume itself, so a slow volume holds every other
  request to it meanwhile.
- **`dotnet` itself comes from the package.** An install on a volume needs its runtime's libraries mapped as code
  copies and its framework read through the service. Nothing here refuses that, but no scenario checks it.
- **No authority below the volume** (§54–56): any process may start any program of a mounted volume.
