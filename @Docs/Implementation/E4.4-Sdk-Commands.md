# E4.4 — The SDK's commands in the guest

Plan step E4.4 (phase E, goal Ц6; the author's word of 2026-10-29). The E5 pre-check on VMware after E4.3 found that
the .NET SDK of the data volume's layer (C2.5) listed itself and ran none of its commands. `dotnet --list-sdks`
answered, and `dotnet --version` in `/data` ended with 150, "No frameworks were found". C2.5's gate had run the REPL,
which resolves the SDK through MSBuildLocator, and `--list-sdks` alone. The SDK's catalog entry says a session may build
with `dotnet`; this step makes that true and gates it.

Four causes stood in the way, each found by the guest after the one before was gone. The step changes no ABI-1 call,
no libc export (ABI-2) and no host's logic.

## 1. The framework beside the SDK

hostfxr runs an SDK found through `global.json`'s `sdk.paths` with the frameworks of the root it found the SDK in, not
the muxer's. `fx_muxer.cpp`'s `handle_cli` says so: "Use the root path from the resolved SDK to run the SDK dll". C2.5's
root, `/data/apps/DotNet.Sdk/10.0.300/`, held `sdk/` and the reference pack alone, so the SDK's `dotnet.dll` found no
`Microsoft.NETCore.App`.

The layer now lays the install's `Microsoft.NETCore.App` beside the SDK, under
`shared/Microsoft.NETCore.App/<version>/`: the files of `/dotnet/shared/...`, ReadyToRun where the install is (R9), with
their deps.json. The SDK asks for 10.0.8, and 10.0.12 serves it. That is 68 MB more on x64, on a disk of 1.5 GiB.
`RuntimeWitos.SharedFrameworkFilesAsync` gives the framework's files by their paths below a .NET root to the install
and to the layer alike. `AppsLayer` adds them to an archive's files wherever those hold `sdk/`, so a feed
(`apps --feed`, C4.3) carries them too.

## 2. The process's start time

The SDK's CLI asks `Process.GetCurrentProcess().StartTime` at every start, for its startup timing. On WitOS that was
`PlatformNotSupportedException`. Linux reads the time from `/proc/self/stat`, which WitOS never emulates, and the kernel
knows no process's start.

- **The loader.** It names the moment in the process's auxiliary vector. libwitos (`spawn.c`) writes
  `WIT_AT_START_TIME` (`witos/start.h`, 0x57490002) beside `WIT_AT_START` when it builds the first stack: the
  nanoseconds of `clock_gettime(CLOCK_MONOTONIC)`, the clock every process reads alike and the one .NET's `Stopwatch`
  reads on Unix.
- **System.Diagnostics.Process.** `Process.WitOS.cs` (its patch) reads the tag through musl's `getauxval`, which is
  already in ABI-2, with a `LibraryImport` of `libc`. For the current process it answers
  `(DateTime.UtcNow - Stopwatch.GetElapsedTime(started)).ToLocalTime()`, converted last as Linux's `BootTimeToDateTime`
  converts. Another process's start stays `PlatformNotSupportedException`, and so does a process started without the
  loader, whose vector has no tag.
- **The check.** The compatibility suite's `Platform.ProcessStartTime` requires a start before now and within a day,
  on the hosts and in the guest.

## 3. ASP.NET Core's reference pack

`dotnet build` then failed in restore with NU1301: no source answered (`api.nuget.org`, with no network in the
scenario). A console project with no package reference still asked for one: the restore's specification lists
`Microsoft.AspNetCore.App.Ref` 10.0.8 among its `downloadDependencies`. SDK 10's restore downloads ASP.NET Core's
reference pack wherever the root's `packs/` lacks it. A Windows install has it, so the same project restores there with
a dead source and no message. The layer now lays `packs/Microsoft.AspNetCore.App.Ref/10.0.8` from the SDK's own
archive, beside `Microsoft.NETCore.App.Ref`: 50 MB more.

## 4. The SDK's Linux apphosts

The build then failed in `CoreCompile`. Roslyn's `Csc` task started `Roslyn/bincore/csc` and met "Exec format error":
that file is the Linux apphost, a glibc ELF that no WitOS loader runs. Roslyn's `ManagedToolTask` uses the apphost
where the file exists and `dotnet exec csc.dll` otherwise (`UseAppHost`: `File.Exists(<tool directory>/csc)`).

The layer now leaves out the SDK's four Linux apphosts: `MSBuild`, and Roslyn's `csc`, `vbc` and `VBCSCompiler`.
`AppArchive`'s `leave` takes a file as well as a directory, which `AppsLayerTests` checks.

## 5. The gate

`runtime-csharprepl` (C2.5) runs, from `/data` and before the REPL:

1. `dotnet --version`.
2. `dotnet build` of `tests/Runtime.Witos/GuestBuild`, a console project laid on the volume as its source alone, with
   `UseAppHost=false` and no network.
3. `dotnet bin/Debug/net10.0/GuestBuild.dll`.

It requires each command's exit with 0 and the program's `[GUEST-BUILD] built in the guest, running on witos-<arch>`,
on x64 and ARM64. riscv64 has no SDK publication (C2.5). `runtime-witos` runs the scenario on each ISA after the
installer. The process, spawn and libc-test scenarios run again for the loader's new tag.

## 7. Limits kept explicit

- **Another process's start time** is `PlatformNotSupportedException`, as are its processor times. The tag is the
  process's own.
- **The SDK's workload manifests** (`sdk-manifests`) and templates are not laid. `dotnet build` says "An issue was
  encountered verifying workloads", and `dotnet new` has no templates.
- **The first run** of the SDK writes its sentinel and an ASP.NET Core development certificate under `HOME`
  (`/data/home`), as on Linux.
- **The compiler server.** Roslyn's task asks for shared compilation by default. Without its apphost, `VBCSCompiler`
  would start through `dotnet exec` and connect over a Unix domain socket (W4.1). Where no server answers, the task
  compiles in a process of its own. Which of the two compiled the gate's project is not recorded.
- **No apphost** is built for `witos-<arch>` in the guest: no feed there offers WitOS's host pack. A project sets
  `UseAppHost=false`, as C2.5 noted.
- **A package from NuGet** needs the network (phase W) and a source the guest reaches. The gate restores none.
