# R1.3 — ILC for witos

Plan step R1.3 completes R1. The NativeAOT compiler (ILC) learns the target `witos`. The host's JITs and ILC are built
from the pinned dotnet/runtime by the pinned clang and lld. A first program, compiled against the NativeAOT CoreLib
for witos (R1.2b), becomes an ELF object for each ISA. The program does not run yet: linking it with the NativeAOT
runtime and booting it in the guest is R2.

## What changed

**ILC's target.** Two files join the patch set, which grows to 17 files, CoreCLR's 3 of FreeBSD's 31 and Haiku's 18:

- `TargetDetails.cs` adds `TargetOS.WitOS` beside the other operating systems;
- `CommandLineHelpers.cs` parses `--targetos witos`.

Nothing else in the compiler changes, because ILC treats every target that is neither Windows nor Apple alike:

- objects are ELF (`ElfObjectWriter`), never COFF or Mach-O;
- x64 code uses the System V registers;
- the JIT is the Unix one (`clrjit_unix_x64_x64`, `clrjit_universal_arm64_x64`);
- startup is the Unix startup code.

Two optimizations stay with the targets upstream names, so witos takes FreeBSD's path:

- Inlined thread statics are Linux's and Windows'; witos reaches thread statics through the runtime's helper.
- On ARM64, Linux alone gets its unwind data reshaped into the form clang emits, for the compatibility of other
  unwinders with managed frames. witos keeps the per-instruction form FreeBSD gets. Whether a stack walk through
  managed frames needs the other form is a question for R2, whose acceptance throws exceptions and walks stacks.

**The host's compiler.** `runtime-witos` builds upstream's `clr.alljits+clr.tools` for the x64 Linux host, the only
host the pinned LLVM release serves:

- The build uses the pinned clang and lld (`CLR_CC`, `CLR_CXX`, the LLVM tools first on `PATH`), configured as an
  ordinary Linux build without a sysroot.
- The configure of a Linux host requires ICU's, Kerberos', LTTng's, OpenSSL's and zlib's development packages. The
  development image and CI's `linux-host` job install them. They serve the host build alone; nothing of them reaches
  WitOS.
- ILC is the published compiler under `linux.x64.Release/ilc-published`, beside its JITs.

**The program.** `tests/Runtime.Witos/Platform.cs` is a `Main` that returns 0 when the platform is WitOS and none of
Linux, FreeBSD and Windows:

1. The runtime's own SDK compiles it with `csc -nostdlib` against the witos `System.Private.CoreLib.dll` alone.
2. ILC compiles it with the NativeAOT class libraries of the `aotsdk` directory:
   `--targetos:witos --targetarch:<arch> --systemmodule:System.Private.CoreLib -O`.
3. `runtime-witos` checks the result:
   - The object is a relocatable ELF64 object, little-endian, for the architecture (machine 62 or 183).
   - Its `Platform_Program__Main` is the code the JIT folds the program to. CoreLib spells the platform as the
     constant `WITOS` (RFC 0015 §3), and `IsLinux()` and the others are constants of a witos build, so `Main` sets the
     return register to zero and calls nothing: `xorl %eax, %eax` on x64, `mov w0, wzr` on ARM64.

This is compile-time evidence: the witos CoreLib's identity reaches the compiled code. A Linux CoreLib would fold
`Main` to 1. The objects land in `artifacts/runtime-witos/ilc/<arch>`.

## Tests

- **Linux (the container).** `runtime-witos` and `runtime-witos --arch arm64` pass:
  - R1.1 and R1.2b as before;
  - the host build;
  - `ILC for witos-<arch>: tests/Runtime.Witos/Platform.cs is an ELF object whose Main returns the constant 0`.
- **CI's `linux-host` job** runs the same.
- **Host tests.** The patch set's pin test covers the two new patches. `format-check` checks the program.

## Limits kept explicit

- The object is not linked or run. R2 links it with the NativeAOT runtime through `Microsoft.NETCore.Native.Unix.targets`
  (the triple and lld with the sysroot) and runs it in the guest. The triple in the targets moves to R2, where the
  link is.
- The program needs CoreLib alone. The class libraries above CoreLib are not built for witos yet.
- ILC runs only on an x64 Linux host.
