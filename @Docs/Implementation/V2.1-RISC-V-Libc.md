# V2.1 — The libc on riscv64: musl for `riscv64-unknown-linux-musl` over ABI-1, the first libc program on the third ISA

Plan step V2.1, the first slice of V2 (layer 2 on riscv64), 2026-10-17. V1 ([V1.4-RISC-V-Harts.md](V1.4-RISC-V-Harts.md))
finished the kernel: the common kernel, the shared self-tests and the fixtures run on the third ISA. This slice brings
the first part of the system layer there — musl at the pinned release, built by the pinned clang for
`riscv64-unknown-linux-musl` after the same rules as the two other triples, with WitOS's system-call dispatch in place of
the `ecall` and WitOS's part of the library given its riscv64 branches — and proves it in the guest: the `libc`
scenario boots `tests/User/libc_hello.c` as the root task on riscv64 and passes its 165 checks at the first boot of the
port. The rest of layer 2 (libc-test and the shared library, the C++ runtime, libwitos and started programs, the
sysroot) and the runtime follow in V2's next slices.

Nothing of musl's C changed beyond the one patch every triple has: the riscv64 build takes the same 1,357 objects
musl's Makefile would (every generic file, the `src/*/riscv64/*` overrides — the fenv, setjmp, math, ldso and signal

signal entry left out, as the x86_64 and aarch64 builds leave theirs out: `__unmapself.s`, `clone.s`, `syscall_cp.s`,

assembly writes, as ARM64's writes TPIDR_EL0.

## 2. The library on the third ISA

- **The dispatch.** `arch/riscv64/syscall_arch.h`'s `__syscallN` become calls of `__wit_syscall` (the patch of S1.1 for
  the third triple); `VDSO_USEFUL` stays (section 6.1). musl's `bits/syscall.h.in` of riscv64 is the generic table —
  no `open`, `stat`, `dup2` or `pipe`, as aarch64's — and `syscall.c`'s `#if defined(SYS_…)` branches serve it as they
  serve aarch64's.
- **The startup.** `crt1.c`'s `_start` on riscv64 zeroes the frame pointer and the return address, aligns the stack and
  calls `_start_c` with the kernel's startup descriptor in `a0`, where the kernel put the first thread's argument
  (V1.3). It sets no global pointer: layer 2 on riscv64 is compiled without linker relaxation (section 6.4), so nothing
  addresses through `gp`, and a thread the kernel starts or a callback it enters needs none.
- **Threads.** `__wit_thread_entry` reads the launch block in `a0` as the ARM64 one does: the function, the argument
  and the thread pointer, which it installs in `tp` before the call — the kernel wrote it already from the request's
  TLS base at the thread's first resume (V1.3), so the trampoline's write is the library's own statement of it. The
  thread record of the running thread is found by `tp`, as by TPIDR_EL0 on ARM64; `__cp_cancel` tail-calls `__cancel`.
- **Signals.** The context profile is `FPREGS` and the stack pointer `X[1]` (x2); there is no red zone. A fault's
  cause (the vector and the error, which repeat `scause`, V1.3) classifies as Linux's riscv fault handler classifies:
  misaligned instruction, load and store addresses are `SIGBUS` with `BUS_ADRALN`; instruction, load and store access
  faults `SIGSEGV` with `SEGV_ACCERR`; an illegal instruction `SIGILL` with `ILL_ILLOPC`; a breakpoint `SIGTRAP` with
  `TRAP_BRKPT`; and the instruction, load and store page faults `SIGSEGV` with `SEGV_MAPERR` and the address in `stval`
  — the cause tells a missing page from a refused access no better than Linux's handler does without the tables, and
  the library reports the missing page, which is the fault the libc and the runtime watch for. The handler's
  `ucontext_t` is musl's riscv64 layout: `__gregs[0]` the program counter, `__gregs[1]`–`__gregs[31]` x1–x31, the D
  extension's 32 registers and `fcsr` in `__fpregs.__d`; it carries no fault address, which the `siginfo_t` gives. The
  trampolines are the ARM64 ones in RISC-V's registers: the fault callback enters `__wit_signal_deliver` with the token,
  the vector and the address in `a0`–`a2`; the handler's trampoline is entered through `EXCEPTION_CONTINUE` with the
  signal, the `siginfo_t`, the `ucontext_t`, the frame and the handler in `a0`–`a4` (the context's `X[9]`–`X[13]`), a
  zero return address so that a return from the trampoline faults, keeps the frame in `s1` across the handler and
  calls `__wit_sigreturn`; `__wit_sigreturn_switch` moves to the frame's stack and raises. riscv64 has no `SA_RESTORER`:
  musl's kernel restorer is never entered on any ISA, and the flag's mask is compiled where the flag exists.
- **`uname`** reports `riscv64` as the machine.

## 3. The builtins

clang emits calls to compiler-rt's binary128 soft-float helpers for `long double` on riscv64 as on aarch64 (musl's
printf, strtod and the long double mathematics), and the pinned subset compiles for the third triple unchanged, with one
file more and one less. `riscv/fp_mode.c` joins the pin (the rounding mode the helpers honour, read from `frm`, as
`aarch64/fp_mode.c` reads FPCR), and `compiler-rt.lock.json` names the directory a RISC-V file lives in (`riscv`, for
both widths) beside `x86_64` and `aarch64`. `clear_cache.c` leaves the riscv64 set: its Linux branch includes
`<linux/unistd.h>` and issues `riscv_flush_icache` with an inline `ecall`, which WitOS never does; `__clear_cache` on
riscv64 is `CODE_PUBLISH` (V0 §6) and comes with the runtime, which is what calls it (R2.1, R3.2b). 26 objects.

## 4. The first libc program

`libc_hello.c` names its ISA, raises `SIGILL` with `unimp` where x64 has `ud2` and ARM64 a zero word, and maps the
third page of the package's `/test/code.bin` executable (`li a0, 42; ret`, which `BootPackage` writes beside the x64
and ARM64 functions) and writes the same instruction into a shared mapping. The static link script gathers RISC-V's
small-data sections (`.srodata`, `.sdata`, `.sbss`) into their kinds, so that the ELF-to-flat conversion still sees three
segments. The scenario is the one of S1.1: musl over the dispatch as the root task — stdio to the log, malloc over
`mmap`, formatting, conversions, sorting, `setjmp`, errno, the clocks and entropy, thread-local storage, `atexit`, the
read-only package's files, threads with mutexes, condition variables, keys and semaphores, the thirty-two threads of a
process, duplicates and pipes, the signals with their contexts, mappings and their protections — 165 checks on riscv64
as on ARM64 (the two x64-only checks are the integer division fault).

## 5. The tool

`KernelArchitecture.Libc` says the libc builds for the ISA and the `libc` scenario runs on it (true for every ISA now),
beside `SystemLayer`, which gates the rest of layer 2's scenarios (false for riscv64 until V2 completes);
`KernelTestSuite.RunFoundationAsync` boots `libc` under the first and the other five under the second, so
`test --arch riscv64` holds 16 scenarios. `PltOptions` gives `-fno-plt` on x64 and ARM64 and nothing on riscv64, where
clang refuses the option as unused under `-Werror` (V1.3 found it for the fixtures; the musl build, the programs and the
runtimes take it from the one place now). riscv64's layer-2 options are `-mcmodel=medany -mno-relax`.

## 7. Findings

1. **`VDSO_USEFUL` stays on riscv64.** The x86_64 and aarch64 patches dropped musl's vDSO lines, since nothing else
   used them; on riscv64 `src/linux/cache.c`, musl's `__riscv_flush_icache`, asks `__vdsosym` for the vDSO's symbol
   whatever the macros say, and `vdso.c` defines `__vdsosym` only under `VDSO_USEFUL`. The first link failed on the
   symbol. The macro stays: `__vdsosym` finds no `AT_SYSINFO_EHDR` in WitOS's auxiliary vector and returns null, and the
   flush takes `SYS_riscv_flush_icache` through the dispatch, which answers `ENOSYS` until the runtime slice maps it to
   `CODE_PUBLISH`.
2. **`clear_cache.c` is Linux's on riscv64.** Its riscv branch, taken because the triple defines `__linux__`, includes
   a kernel header the sysroot has not and issues the system call with an inline `ecall`; it leaves riscv64's builtins,
   and `__clear_cache` comes with the runtime as `CODE_PUBLISH`.
3. **No `-fno-plt`, no `SA_RESTORER`.** clang refuses the PLT option for RISC-V, now from one place (`PltOptions`), and
   musl's riscv64 `bits/signal.h` names no restorer flag, so the mask that drops it is compiled where the flag exists.
4. **Linker relaxation and the global pointer.** With relaxation lld may turn an absolute access into a `gp`-relative one
   wherever `__global_pointer$` is defined, which musl's `rcrt1`/`Scrt1` start code references; `gp` would then have to
   hold that value in every thread the kernel starts and every callback it enters. Layer 2 on riscv64 is compiled with
   `-mno-relax` instead, as the kernel is: no object carries `R_RISCV_RELAX`, so nothing addresses through `gp`.
5. **The first boot passed.** With the kernel's user mode of V1.3 and the dispatch's Linux convention, musl ran its 165
   checks on riscv64 the first time it booted there; the slice's work was the build, the branches and the two findings
   above, not the kernel.
