# K5.3 — the system layer's process capacities

Plan step K5.3 gives the system layer's processes (the root task and the processes it creates) the thread, handle and
event capacities a .NET program needs. The frozen line's components keep theirs. R2.2's acceptance program stopped at
the kernel's four threads of a process. Its main thread, the finalizer, the thread pool's workers and its gate thread
filled them, so the waits probe's own threads failed with `OutOfMemoryException`.

No call changes; ABI-1 stays at v69. As with the reservation table of S5.4 and the object quota of S6.1, the change is a
quota of the system layer's profile beside the frozen line's.

## What changed

**Three capacities (`limits.h`).**

| Capacity | Constant | Value |
| --- | --- | --- |
| Threads of a process | `WIT_PROCESS_THREAD_CAPACITY` | 16 |
| Handles | `WIT_PROCESS_HANDLE_CAPACITY` | 64 |
| Events | `WIT_PROCESS_EVENT_CAPACITY` | 32 |

These are the largest tables, so every process record's arrays are sized by them. That covers the threads, the handle
table and its thread references, the event table and its memory-pressure slots, and the frozen file table, which is
indexed by handle slot. Each profile sets its limits:

- A system layer process gets all three: `wit_user_create_flat` for the root task, `wit_user_create_empty` for
  `PROCESS_CREATE`.
- A component of the ordinary or full runtime profile keeps four threads (`ThreadLimit` is `WIT_USER_THREAD_CAPACITY`),
  16 or 32 handles and 4 or 16 events, as before.

**Handle and event budget.** The numbers follow from what a thread costs in the system layer:

- Every thread holds a handle for its identity in its own table.
- The libc keeps the reference handle of every thread it created, which `pthread_kill` needs (S3).
- Sixteen threads therefore take 31 handles before the startup handles, the futex events and a program's own.
- The libc's futex slots hold an event each.

**The thread limit (`ThreadLimit`).** The process record now carries a thread limit beside `ObjectLimit`. A version 2
or version 3 `THREAD_CREATE` looks for a free slot below the target's `ThreadLimit` and answers `NO_MEMORY` when there is
none. The kernel's loops over a process's threads cover the whole array.

**Version 1 stays at four.** A version 1 thread places its stack and TLS in the window of its index (`user_layout.h`),
and only four windows exist. It therefore keeps looking among the first `WIT_USER_THREAD_CAPACITY` slots in every
process. For the same reason, the frozen PE TLS of a loaded library (`user_library_tls.c`) refuses a thread beyond the
fourth instead of writing outside the windows.

**Kernel stacks.** Each registry slot has a static kernel stack for every thread it may run (K5.2c). The arrays
`wit_x64_user_kernel_stacks` and `wit_a64_user_kernel_stacks` grow from 8 × 4 to 8 × 16 regions of 72 KiB (64 KiB and
two guard pages), from 2.25 MiB to 9 MiB of kernel image on each ISA. Their guard pages, 264 on x64 and 262 on ARM64,
are unmapped as before.

**The libc's futex slots (`futex.c`).** The slots grow from 8 to 16, as many as the kernel's threads of a process,
since a thread waits on one word at a time. With the exit word's event, that is 17 events, within the 32.

## Tests

- `tests/User/libc_hello.c`, the root task of the `libc` scenario of both suites, runs fifteen threads beside the main
  one. They park on one semaphore together, each in a futex slot of its own, and a seventeenth `pthread_create` fails
  with `EAGAIN`, the kernel's `NO_MEMORY`. The checks rise to 121 on x64 and 119 on ARM64.
- libc-test gets back the four tests that waited for this quota (S2, S1.3, S7.1). Each runs in a process the root
  task's manager created, so they cover the created process's profile:
  - `functional/sem_init`: three waiters at once, beside the main thread;
  - `functional/tls_init`: five threads at once;
  - `regression/pthread_cond-smasher`: ten threads;
  - `regression/tls_get_new-dtv`: ten threads across a `dlopen` with TLS. It runs dynamically alone, as libc-test builds
    it, with its library `regression/tls_get_new-dtv_dso`.

  The selection is now 95 tests and 186 runs beside the math suite. The scenario passes all 382 runs on x64 and all
  384 on ARM64.
- The frozen line's fixtures keep their four-thread expectations: `user_thread_tests.c` still fills four version 1
  threads.

## Limits kept explicit

- The capacities are prototype bounds, not an ABI promise. A process cannot ask for more, and the quotas are not
  hierarchical (the open question of K5.2).
- Kernel stacks stay static per slot and thread: 9 MiB on each ISA whether processes run or not, until a kernel stack
  is allocated with its thread.
- `pthread_create-oom` stays out: it needs `setrlimit(RLIMIT_DATA)`, which the libc answers with `ENOSYS`.
- The frozen line's components, their TLS windows and version 1 threads keep four threads until K8 removes them.
