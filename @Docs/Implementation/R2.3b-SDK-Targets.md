# R2.3b — programs built by the SDK's targets

Plan step R2.3 brings what a program is built with to witos. Its second slice, R2.3b, builds the M3 acceptance as a
.NET program is built: `dotnet publish` with `PublishAot` and the runtime identifier `witos-<arch>`, by the SDK's
NativeAOT targets. Until now `runtime-witos` called csc, ILC and the link itself.

## What changed

### The packages

A NativeAOT publish for a runtime identifier takes three packages:

| Package | What it holds |
| --- | --- |
| `Microsoft.DotNet.ILCompiler` | The targets (`Microsoft.NETCore.Native*.targets`) |
| `runtime.<host>.Microsoft.DotNet.ILCompiler` | ILC for the host |
| `Microsoft.NETCore.App.Runtime.NativeAOT.<target>` | The target's runtime: the NativeAOT class libraries, the runtime's static libraries and the native shims |

`runtime-witos` packs all three from the witos tree as upstream packs them, into the tree's package feed
(`artifacts/packages/Release/Shipping`):

- **The runtime pack.** For each ISA it builds `Microsoft.NETCore.App.Runtime.NativeAOT.sfxproj` with `-os witos`
  after the shared framework (R2.3a).
- **The ILCompiler packages.** Once, for the Linux host, it builds `Microsoft.DotNet.ILCompiler.pkgproj` twice: as the
  targets package, and with `PackageTargetRuntime=linux-x64` as the host's ILC. That ILC is the one R1.3 builds, which
  knows `--targetos:witos`. The package project resolves the host's own libraries, so the host's native libraries and
  shared framework are built first (`libs.native+libs.sfx -os linux`).

The packages carry the tree's version, `10.0.7-dev` at the pin, and keep it from build to build.

`packs.product -os witos` as a whole does not build. It also packs ILC to run on witos itself, which the SDK refuses
(NETSDK1203), and with `UseNativeAotForComponents=false` it wants an application host for witos (NETSDK1084).
Neither is needed to build for witos from a Linux host, so `runtime-witos` builds the three projects by
`--projects` alone.

### The link (one upstream patch)

`Microsoft.NETCore.Native.Unix.targets` gains a witos branch beside FreeBSD's
(`patches/runtime/src.coreclr.nativeaot.BuildIntegration.Microsoft.NETCore.Native.Unix.targets.patch`):

- lld is the linker, and the triple is `<arch>-unknown-linux-musl`.
- System.Net.Security.Native and System.Security.Cryptography.Native.OpenSsl are not linked, since witos builds no
  GSSAPI and no OpenSSL shim (R1.2b).
- The program links libc++, since the runtime is built against it (R1.2b). Its ABI library has the
  `__cxa_thread_atexit` that the runtime's `thread_local` destructors call; without it the link failed on that symbol.

The patch set grows to 18 files. CoreCLR's part is 4, against FreeBSD's 31 and Haiku's 18.

### WitOS's part of a project

`build/runtime/witos.targets` is what a program's project imports to build for witos. Given the packages' version,
the patched runtime identifier graph, the sysroot, the pinned clang and the sysroot's link options, it does four
things:

- adds `witos-x64` and `witos-arm64` to the SDK's known ILCompiler and NativeAOT runtime packs, at that version;
- points `RuntimeIdentifierGraphPath` at the graph that knows witos, since the SDK's own graph does not (NETSDK1083);
- sets `SysRoot` and `CppCompilerAndLinker`;
- passes the sysroot's link options as `LinkerArg` items.

The link options are `Sysroot.LinkOptions`, now split out of `Sysroot.DriverOptions`: the sysroot's clang resource
directory, compiler-rt, libunwind, the 4 KiB page size and separate loadable segments that the system layer's loader
needs (S5.3), and the architecture's options. The targets add the target, the sysroot and the linker themselves.

### The acceptance's project

`runtime-witos` generates a project for the acceptance under `artifacts/runtime-witos/publish/<arch>/Acceptance`:

- **SDK and build properties.** A `global.json` names the witos tree's SDK, since the repository pins another, and
  empty `Directory.Build.*` files keep the repository's build properties away.
- **Packages.** A `nuget.config` points at the tree's feed and nuget.org.
- **The project.** It compiles `tests/Runtime.Witos/Acceptance/*.cs` with `PublishAot`, `InvariantGlobalization`,
  `DirectPInvoke` for the libc and the import of `witos.targets`.

The packages keep their version from build to build, so their copies in the project's NuGet cache
(`artifacts/runtime-witos/nuget`) are dropped before each publish. The published executable boots as before, in the
`runtime-acceptance` scenario.

The first program (`Platform.cs`) is still compiled directly, since its check reads the object ILC writes.

## Tests

- **The exploration.** A console program published this way printed its platform line in the guest, and the
  acceptance follows it.
- **The container.** `runtime-witos` on both ISAs packs the three packages, publishes the acceptance and runs it:
  `dotnet publish -r witos-<arch>` and `[M3] NativeAOT on <isa>: 32 runs passed, 0 failed`.

## Limits kept explicit

- **The packages are local.** They live in the witos tree's feed under the tree's version; nothing is published to a
  feed others use.
- **The project gives WitOS's part.** The paths to the sysroot and the toolchain come from properties that
  `runtime-witos` writes; an SDK that knows witos by itself is a later step.
- **ILC runs on the Linux host alone.** Building on witos itself waits for CoreCLR (R3) and the hosts (R5).
