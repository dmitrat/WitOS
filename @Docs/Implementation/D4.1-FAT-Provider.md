# D4.1 — The filesystem contract and the FAT provider

D4.1 is the first half of D4. It lays down the contract every filesystem of WitOS serves (storage document §20) and
gives it its first provider: FAT12, FAT16, FAT32 and exFAT through `OutWit.Common.Fat`. That library is the
independent portable OutWit library the storage document names (§14–16), reached unchanged through an adapter.

In the guest, the device manager mounts two volumes through the virtio driver's block channel of D3.2:

- the boot disk's FAT16 volume, read-only, which it reads and checks;
- the data disk's FAT partition, which it writes, mounts again and reads back.

The tool formats that partition on the host with the same provider. After the boot, it reads the guest's files back
and checks the volume.

D4.2, the managed ext4 provider (§17–18), comes next.

## The contract (`OutWit.OS.FileSystems`)

- **`IFileSystem`** is a mounted volume. A path is absolute within the volume, its components separated by '/'.
  - `GetEntryAsync` returns null when nothing is there.
  - `EnumerateAsync` lists a directory without "." and "..".
  - `OpenAsync` takes a `FileMode` and a `FileAccess`, as `FileStream` does, except `Append`.
  - `CreateDirectoryAsync` creates the missing parents too.
  - `DeleteAsync` deletes a file or an empty directory.
  - `RenameAsync` moves an entry into an existing directory where nothing is at the destination.
  - `FlushAsync`: whatever completed before is durable when it completes.
  - `CheckAsync` checks the structures and changes nothing (§72–73).
  - `Volume` describes the volume: format, label, bytes, allocation unit, read-only.
- **`IFileHandle`** is an open file whose bytes are addressed by offset, with no shared position (§8, §53). This is
  what a namespace service needs to serve `pread` and `pwrite`.
  - A read returns fewer bytes than asked only at the end of the file.
  - A write past the end grows the file, and the gap reads as zeros.
  - `SetLengthAsync` cuts or grows the file.
- **`FileSystemEntry`** carries an entry's path, name, kind, length, attributes and times. Its attributes are the ones
  more than one format records: read-only, hidden, system, archive.
- **`FileSystemException`** is an `IOException` whose `FileSystemError` names what went wrong, the same for every
  provider. The namespace service of D5 maps each error to one errno value (`NotFound` to `ENOENT`, `NotEmpty` to
  `ENOTEMPTY`, `ReadOnly` to `EROFS`, and so on).

## The FAT provider (`OutWit.OS.FileSystems.Fat`)

- **The device.** `FatBlockDevice` is the library's block device over an `IBlockStorage`.
  - A sector is a logical block, which must be a power of two between 512 and 4096 bytes with no larger alignment.
    Otherwise the provider refuses the resource as `Unsupported`.
  - The device's end leaves the resource open: the resource stays its owner's.
- **Mounting and formatting.** `FatFileSystem` provides:
  - `MountAsync`, read-only when the resource is;
  - `FormatAsync`, in the format the library chooses for the size (§59);
  - `DetectAsync`, which reports whether a volume is there (§58: detection is not authority).
- **Operations.** Each operation maps to one of `FatVolume`'s. `FatErrors` translates the library's failures:
  - a `FatException` by its kind;
  - a write to a read-only device as `ReadOnly`;
  - an invalid name, or a path above the root, as `InvalidName`.
- **Handles.** `FatFileHandle` positions the library's stream for each request.
- **One caller at a time.** The library serves one caller at a time, so the provider serializes every operation and
  every handle's requests behind one lock. §52 allows a serialized prototype; it does not define the final semantics.
- **Times are UTC.** FAT records local times without a zone. WitOS's FAT volumes record UTC, on the host as in the
  guest (`UtcClock`), so a time reads the same wherever the volume is mounted.
- **The package.** `OutWit.Common.Fat` 1.0.0 comes from nuget.org: `PackageReference` in `OutWit.OS.csproj`, pinned by
  version and by the test projects' lock files. Nothing of it is copied in (§15).
  - Its dependency `OutWit.Common` 1.4.0 comes with it.
  - WitOS's own code references neither library outside `FileSystems/Fat`.
- **The guest build.** A service compiles the provider's folders only when it needs them. `RuntimeDevices` then adds
  OutWit.OS's package references, read from its project, so the version has one place. The device manager compiles
  them; the driver does not.

## The scenario

- **The data disk.** `RuntimeDataDisk` writes the data disk anew for every boot: 16 MiB with two partitions.
  - "WitOS test" is the raw partition of D3.2, 1 MiB.
  - "WitOS FAT" is formatted on the host by the FAT provider, labelled `WITOS DATA`, and holds `/hello.txt`.
- **The device manager's filesystem probe** (`FileSystemProbe`):
  - **The boot disk.** It has no GUID partition table and holds a FAT volume. The probe mounts it read-only through
    the block channel, lists its root and reads the first bytes of the loader under `/EFI/BOOT` (`MZ`). It then checks
    the volume, which also checks the tool's own boot image writer.
  - **The FAT partition.** The probe mounts the partition and reads the host's file. It creates `/guest`, writes a
    file of 100,000 bytes over several clusters and a note, and flushes. It checks the volume, unmounts it, mounts it
    again and reads both files back.
- **The host check.** After the boot, `RuntimeDataDisk.CheckAsync` requires the test partition's pattern. It then
  mounts the FAT partition from the image with the same provider and requires the guest's files and the host's file.
  The volume's check must be clean.

## Tests

- **`tests/OutWit.OS.Tests`**: `FatFileSystemTests` runs on three backends, the substitution test of §71: memory, a
  partition of a disk, and the block protocol over a driver in the test's own process, whose transfers are smaller than
  the library's requests. It covers:
  - the volume a format describes;
  - files that survive a second mount, with UTC times and a clean check;
  - reads and writes at offsets, a gap that reads as zeros, a read past the end, a cut;
  - directories, long names, rename and delete;
  - each failure with its error;
  - a read-only resource mounted read-only, which refuses changes;
  - a resource without a volume, refused.
- **`tests/WitOS.Dev.Tests`**: the data disk carries both partitions and a clean FAT volume with the host's file, and
  the check after the boot requires the probes' writes.

## Results

`runtime-services` passes on both ISAs, and the tool's check after each boot finds the guest's files on a clean volume
(3 files, 1 directory). Both ISAs print the same lines; only the loader's name and size differ.

- **The boot disk.**
  - It is a FAT16 volume of 33,554,432 bytes in units of 2048, read-only.
  - `/` holds `EFI`, `WITOS.PAK` and `WITROOT.BIN`.
  - The loader is `BOOTX64.EFI` (161,280 bytes) or `BOOTAA64.EFI` (160,256 bytes). Each starts with `MZ`.
  - The check is clean: 3 files, 2 directories.
- **The FAT partition.** The library formatted it as FAT16 of 13,631,488 bytes in units of 1024.
  - The probe reads the host's `/hello.txt`.
  - It writes `/guest/written.bin` (100,000 bytes) and `/guest/note.txt` (85 bytes), and the check is clean.
  - After a second mount, it reads both back.
- **The device manager's size.** With the FAT library compiled in, the device manager grows from 1.8 MB to 3.3 MB on
  x64. The publish reports no trimming warning.

## Limits kept explicit

- **One caller at a time** in the provider, as in the library: no parallel operations (§52).
- **No append mode** on a handle. A caller that appends writes at the file's length, as a namespace service serving
  `O_APPEND` will.
- **No ownership, permissions or links.** FAT records none, and the contract has none yet. Those come with ext4 and
  the namespace's authority (§54–56).
- **The probe lives in the device manager.** Volumes are mounted there until the namespace service of D5 holds the
  block channels and mounts them (§21: a filesystem is a service).
- **No exFAT in the guest yet.** The provider serves exFAT as the library does, but the scenario's volumes are FAT16
  and whatever the library chooses for the FAT partition's size.
