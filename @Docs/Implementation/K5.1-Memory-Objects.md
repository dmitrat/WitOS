# K5.1 — Memory objects (ABI v57)

Plan step K5.1 brings the memory objects of [RFC 0011 v3 §7.2](../RFC-0011-Kernel-Architecture-and-ABI.md) into the
kernel ahead of K3, because a device's memory (K3) is a memory object and the root task's package (K4) is one too:
`MEMORY_OBJECT_CREATE` (18), `MEMORY_OBJECT_MAP` (19) and `CODE_PUBLISH` (20), the handle kind `MEMORY_OBJECT`, the
rights `MAP` (8192) and `EXECUTE` (16384), the protection `EXECUTE` (4) and the pseudo-handle `WIT_PROCESS_SELF`. The
call-by-call reference is [ABI-Reference.md](ABI-Reference.md). The rest of the original K5 — processes, the one
thread form, stacks with guard pages, the `SYSCALL` transport — is K5.2 in the plan.

## What changed

> Since K5.2b ([K5.2b-Kernel-Memory-Objects.md](K5.2b-Kernel-Memory-Objects.md)) the table is the kernel's, an object
> owns its pages and the creator is charged for them; the component's table, `wit_user_space_allocate_pages` and
> `wit_user_space_free_pages` described below are gone. The calls, the mapping and the reference rules are unchanged.

**An object is pages without an address.** `MEMORY_OBJECT_CREATE(size, 0, 0)` takes `size / 4096` pages from the
component's owned-page quota at once, zeroed, and records them in the component's object table
(`WIT_MEMORY_OBJECT_CAPACITY` 8 objects, `WIT_MEMORY_OBJECT_PAGES` 64 pages each; beyond that `TOO_LARGE`, beyond
the quota `NO_MEMORY` with nothing taken). The handle carries every object right: `MAP`, `WRITE`, `EXECUTE`, `QUERY`,
`DUPLICATE` and `TRANSFER`. Anonymous objects are the one kind; device memory arrives with K3 as another kind of the
same table.

**A mapping is a reservation over the object's pages.** `MEMORY_OBJECT_MAP(WitMemoryMapRequest, 56, 0)` validates
the whole request before it reserves anything: the version, the size, the flags, a protection among `NONE`, `READ`,
`READ|WRITE` and `READ|EXECUTE` (never `WRITE` with `EXECUTE`), the target (`WIT_PROCESS_SELF` only until K5.2; any
other is `UNSUPPORTED`), the handle's `MAP` right and its `WRITE` or `EXECUTE` right for the protection asked
(`DENIED`), the page alignment of the window and the address, and the window's place within the object
(`TOO_LARGE`). Address 0 lets the kernel choose a place in the dynamic data arena; a fixed address must be a free
page-aligned address of either dynamic arena (`BUSY` when it overlaps a reservation, `BAD_ADDRESS` outside the
arenas). The pages are entered as alias entries of a new reservation that remembers the object and the rights of
the handle that mapped it; two views of the same pages see the same bytes.

**The ordinary memory calls know the mapping.** `MEMORY_PROTECT` changes a mapping's protection within the rights it
was made with, `READ|EXECUTE` included; `MEMORY_COMMIT`, `MEMORY_DECOMMIT` and `MEMORY_RESET` on a mapping are
`DENIED`, because the pages are the object's and not the reservation's; `MEMORY_RELEASE` at a mapping's base unmaps
it and drops the object's reference. A plain reservation goes its old way through the same calls.

**The object lives by references.** Every handle and every mapping is one reference; the object ends, and its pages
return to the quota, with the last of them. Closing the last handle while a mapping lives changes nothing the mapping
sees; a message in a channel holds a reference for the handle it carries until the message is delivered or dropped.
`HANDLE_DUPLICATE` of an object needs `DUPLICATE` and grants the same or fewer rights; a handle moves through a
channel with `TRANSFER` like an event or an endpoint.

**Code is published, not written in place.** `CODE_PUBLISH(base, size, 0)` makes code written through a writable
mapping visible to instruction fetch through an executable mapping of the same pages: every page of the range must
be mapped `READ|EXECUTE` (a writable page is `DENIED`, an unmapped one `NOT_COMMITTED`); the architecture cleans the
data cache to the point of unification and invalidates the instruction cache (`wit_arch_publish_code_page`,
`wit_arch_publish_code`), which TCG does not check but hardware requires. The frozen Windows-form line keeps
`CODE_MEMORY` (218) and its near-code arena until K8; nothing new uses it.

## Kernel

- `memory_object.h`: `WitMemoryMapRequest` (56 bytes), the object record and table, `WIT_MEMORY_OBJECT_ANONYMOUS`.
- `user_memory_object.c`: creation, mapping, the release of a mapping or a plain reservation (`wit_user_memory_unmap`,
  the `MEMORY_RELEASE` handler's path), the object's close, duplication, and the reference a dropped message held.
- `user_space.c`: pages without an address (`wit_user_space_allocate_pages`, `wit_user_space_free_pages`, tagged
  like the table pages), the mapping as a reservation with alias entries (`wit_user_space_map_object`) and the
  records `MappedObjects` and `MappedRights` per reservation; the guards of commit, decommit and reset and the
  rights check of protect; `WIT_CODE_EXECUTE` shares the value of `WIT_MEMORY_EXECUTE`.
- `user_calls.c`: the three handlers; `user.c`: the object's close in `HANDLE_CLOSE` and the table's reset with the
  component; `user_reference.c`: `HANDLE_DUPLICATE` of an object; `user_channel.c`: the object as a movable kind and
  the reference a dropped message releases.

## Fixtures

`tests/User.X64/memory_objects.asm` and `tests/User.A64/memory_objects.asm`, driven by the common
`tests/Kernel/user_memory_object_tests.c` in four modes: `User.MemoryObjectViews` (validation of creation and of the
request, a chosen and a fixed address, two views sharing pages, protect within the rights, an attenuated duplicate
refused `READ|WRITE` and commit, `BUSY` on an occupied fixed address, the object outliving its handle and ending
with its last mapping, the object quota), `User.MemoryObjectCode` (a writable view receives the instructions, an
executable view at a fixed address of the code arena runs them after `CODE_PUBLISH`, publication through the writable
view is `DENIED`, a view protected to `READ|EXECUTE` runs them too), `User.MemoryObjectTransfer` (an object moved
through a channel: the sender's handle is gone, its view stays, the receiver's view reads) and
`User.MemoryObjectLimits` (`TOO_LARGE` beyond 64 pages, `NO_MEMORY` beyond the page quota with nothing taken, the
reservation quota bounding the mappings). After every mode the kernel checks that no handle, object, mapping record
or alias survived and that the component owns exactly the pages it owned before, and that the allocator is whole.

## Limits kept explicit

- The target of a mapping is the caller's own process. Mapping into another process, the first use of which is the
  creator's placing of a child's image, arrives with processes (K5.2).
- Objects are eagerly backed; there is no lazy commit, no sharing between components beyond a transferred handle
  and no device or package kind. K3 adds device memory (uncached, never executable); K4 adds the read-only package.
- `CODE_PUBLISH` is single-processor like `wit_user_code_publish`: SMP instruction-cache maintenance across CPUs is
  K7.
- The quotas (8 objects, 64 pages per object) are those of the test profile, not of a product; K5.2 derives quotas
  from real limits.
