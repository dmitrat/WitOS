# S7.1 — libc-test, a process for every test

Plan step S7.1 opens the substrate's acceptance (phase S, S7). musl's libc-test now runs as libc-test's own runner
runs it: every test is a program of its own, built statically and dynamically, and runs in a process of its own. With
processes (S6) and dynamic linking (S5) in place, the one-program driver of S1.3 gives way, and the tests that waited
for a fresh process or for `dlopen` join the selection. ABI-1 stays at v68; nothing of libc-test is patched.

## What changed

**Programs (`LibcTestSuite.BuildProgramsAsync`).** Every test `tests/User/libc-test.json` selects is compiled
unchanged with libc-test's options and its own `main`. It is linked twice, as libc-test's Makefile links it: as a
static program (`-static.exe`, a started program of S5.2) and as a dynamic program against `libc.so` (`.exe`, S5.3).

- The `dynamicOnly` tests (`dlopen`, `tls_align_dlopen`, `tls_init_dlopen`) open a shared library, so they are built
  dynamically alone.
- The `libraries` are libc-test's shared libraries (`dlopen_dso`, `tls_align_dso`, `tls_init_dso`), built beside
  their tests with their names as sonames.
- `linkLibraries` names the libraries a test needs at its start: `tls_align` links `tls_align_dso` dynamically, and
  its static form links the library's object, as libc-test does.
- `exportDynamic` gives `dlopen` libc-test's `-rdynamic`.

The package keeps libc-test's layout under `/libc-test` (`/libc-test/src/functional/argv.exe`, …), with `libc.so` as
the interpreter at `/lib/ld-musl-<arch>.so.1`.

**The runner (`tests/User/libc_test_runner.c`).** The scenario boots the system layer's root task, and its
`/bin/init` is the runner. It starts every run with `posix_spawn`, by its package path, from the directory
`/libc-test`, as libc-test's `runtest` runs a test from libc-test's root. Two kinds of path depend on that: `t_pathrel`
finds a test's library beside the test, and `tls_init_dlopen` opens `src/functional/tls_init_dso.so` relative to the
root. `LD_LIBRARY_PATH` names the directories of the libraries a test needs at its start. A run passes when it exits
with zero, which is the `t_status` its `main` returns; the runner prints one line per run and the summary the scenario
requires, and exits with zero only when every run passed. A fault or a signal is reported per run and no longer ends
the whole suite. The S1.3 driver (`tests/User/libc_test_driver.c`) is gone.

## The selection

91 tests make 179 runs: 88 tests in both forms and the three dynamic-only tests. New since S3:

- `functional/pthread_mutex`: it leaves a deadlocked thread on a returned stack frame by design, which only a process
  of its own survives;
- `functional/tls_align`, `functional/dlopen`, `functional/tls_align_dlopen`, `functional/tls_init_dlopen`: dynamic
  loading and TLS modules.

Still excluded, with the reasons of S1.3 and S2 otherwise:

- `functional/tls_init` and `regression/tls_get_new-dtv`: five and ten threads at once, beyond the kernel's four threads
  of a process (back with K5.3's sixteen, [K5.3-Process-Capacities.md](K5.3-Process-Capacities.md));
- `functional/spawn`, `popen` and `vfork`: they need pipes or `fork`, and `posix_spawn`'s file actions take no
  descriptor but the standard ones (S6.2).

## Tests

The `libc-test` scenario of both suites requires `[LIBC-TEST] musl 1.2.5 on <isa>: all ` and passes all 179 runs on
x64 and on ARM64.

## Limits kept explicit

- There is no timeout and no resource limit per test, which libc-test's `runtest` sets: a test that hangs stops the
  boot.
- The math suite (`src/math`) is S7.2; the API checks (`src/api`) are not selected.
- Every run is a process of the eight the kernel has: the root task, the runner and the test take three.
