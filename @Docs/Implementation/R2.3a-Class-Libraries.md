# R2.3a — the class libraries and the Console

Plan step R2.3 brings what a program is built with to witos: the class libraries above CoreLib, then the SDK's
targets. Its first slice, R2.3a, builds upstream's shared framework for witos and moves the M3 acceptance onto it. The
acceptance now compiles against the reference pack, as an SDK build compiles a program, and prints through
`System.Console`. The Console needs two things of the system layer's libc that it did not have: duplicates of
descriptors and pipes.

## What changed

### The shared framework

`runtime-witos` builds `libs.sfx -os witos` after NativeAOT's native part. No patch was needed: upstream's build
already takes the libraries' Unix flavors (`net10.0-unix`) for witos, where an assembly has no platform flavor of its
own, and trims the `witos-<arch>` shared framework. The results are the runtime pack's `lib/net10.0` and the reference
pack `microsoft.netcore.app.ref`.

`CompileProgramAsync` now takes a program's references and the libraries ILC sees:

- **The first program** keeps the witos CoreLib alone (R1.3) and its constant-`Main` check.
- **The acceptance** compiles against the reference pack. ILC takes the shared framework's libraries beside the
  NativeAOT ones, as a publish's `IlcReference` items do.

### The acceptance's output

The acceptance's lines go through `Console.WriteLine`. A first line names the platform as the class libraries see it,
for example `[M3] WitOS 0.1 ABI-1, witos-x64, 1 processor(s)`. The libc stays a direct P/Invoke only for the probes'
native pages and the thread's id (`Libc.cs`).

### What the Console needed of the libc

A first run printed nothing: `Unhandled exception. System.IO.IOException: Invalid argument`. The libc's trace of
failing calls, in the container's copy, showed the causes one by one.

**Duplicates.** The Console opens standard output as `SafeFileHandle(dup(1))`, and the libc had no `dup`. It now has
`dup`, `dup2`, `dup3`, `F_DUPFD` and `F_DUPFD_CLOEXEC` (`files.c`):

- **Shared open file descriptions.** Descriptors point to open file descriptions that their duplicates share, as on
  Linux. A description holds one position and the status flags; `F_SETFL` changes `O_NONBLOCK`. Each descriptor keeps
  its own `FD_CLOEXEC`, which `F_SETFD` now stores.
- **Duplicates of standard streams.** A duplicate of a standard stream is a stream descriptor that writes to the log,
  as 1 and 2 do. It answers `TIOCGWINSZ` and `fstat` as a character device.
- **Descriptors 0–2 are slots of the same table.** A slot is its standard stream until it is closed. A closed slot is
  free for the lowest descriptor an `open` or a `dup` takes, which libc-test's `rewind-clear-error` relies on.
- **`dup2` onto a standard slot.** It may put a file, a pipe or another stream there; libc-test's `fgetwc-buffering`
  reads standard input from a pipe. Within the process that descriptor then stands for the standard stream. A child
  started with `posix_spawn` still gets the log for each standard stream the caller has open as the log, and nothing
  for the others: a pipe never crosses a process.

**Pipes.** Before its first write, the Console calls System.Native's `InitializeTerminalAndSignalHandling`, which
creates a pipe for its signal handling thread. `pipe` and `pipe2` were `ENOSYS`, and the Console threw
`Win32Exception (38)`. Pipes now exist within a process (`pipe.c`):

- **The buffer.** A pipe is a 16 KiB ring buffer of anonymous memory with its own lock, and there are 16 pipes in a
  process.
- **Parking.** A reader that finds the pipe empty, or a writer that finds it full, parks on a futex word that every
  change bumps.
- **Transfers outside the table lock.** `__wit_syscall` holds the table lock only to find a pipe and take a reference,
  and again to drop it. A blocked read therefore never holds the lock a writer needs, and a close that races a blocked
  transfer cannot free the buffer under it.
- **Linux's semantics.**
  - A read of an empty pipe whose writers are all closed is the end of the file.
  - A write without a reader raises `SIGPIPE` and fails with `EPIPE`.
  - Writes of at most `PIPE_BUF` (4096) bytes are atomic, and so is a `writev` of at most that much in all, which
    musl's stdio uses to flush.
  - An end opened or set with `O_NONBLOCK` answers `EAGAIN`.
  - `FIONREAD` reports the bytes held, `fstat` says `S_IFIFO`, and `lseek` and `pread` are `ESPIPE`.

With both, the Console works unchanged, and the platform line reads `WitOS 0.1 ABI-1, witos-x64`.

## Tests

- `tests/User/libc_hello.c`, the `libc` scenario of both suites, checks:
  - **duplicates:** a duplicate of standard output that reaches the log; `F_DUPFD_CLOEXEC` from 20; a file's
    duplicate that shares its position and outlives the original; `dup2` reopening a closed standard error; `dup`
    taking the closed standard input; a pipe standing for standard input until `dup2` gives the stream back;
  - **pipes:** bytes in order; a FIFO with `FIONREAD` and no position; a `writev` in one write; a reader parked for a writer thread that sends
    40000 bytes, more than the buffer holds, and then reaching the end of the file; `EAGAIN` on an empty pipe and on a
    full one with `O_NONBLOCK`; `EPIPE` once no reader is left.

  The checks rise to 137 on x64 and 135 on ARM64.
- libc-test gets back `regression/rewind-clear-error` and `regression/fgetwc-buffering`. That makes 386 runs on x64
  and 388 on ARM64, all passing.
- **The container.** `runtime-witos` on both ISAs builds the shared framework and runs the acceptance through the
  Console. It prints the platform line and `[M3] NativeAOT on <isa>: 32 runs passed, 0 failed`.

## Limits kept explicit

- `poll`, `ppoll` and `select` see no descriptor yet (`ENOSYS`). The Console's reading of keys needs them, and so do
  the libraries' asynchronous pipes; writing does not.
- Pipes stay within a process: `posix_spawn`'s file actions and the start message carry no pipe, so `Process` with
  redirected streams waits for R4.
- 16 pipes of 16 KiB in a process, and 64 descriptors.
- The SDK's targets (`dotnet publish -r witos-<arch>`) are R2.3b; the programs are still compiled by `csc` and ILC
  directly.
