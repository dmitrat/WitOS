# N4.2 — Processes: `Process.Start` over the process manager

The second slice of the application environment (RFC 0015 §8: "`posix_spawn` over the process manager"; §9's gate
N4). `System.Diagnostics.Process` starts a program, gives it its standard streams as pipes, learns when it ended and
reads its exit code, as on Linux, without `fork`, without `exec` of the own image and without a signal to another
process. The step has two parts: the system layer (N4.2a) and the runtime's patch with the checks (N4.2b).

## What .NET needs

System.Native's `SystemNative_ForkAndExecProcess` (`pal_process.c`) is the one entry: it makes a pipe for each
redirected stream, forks, in the child binds the pipes' ends to 0, 1 and 2, changes the directory and `execve`s, and
gives the parent the child's id and its ends of the pipes; an `exec` that fails reports its errno through a
close-on-exec pipe. `Process` then learns the end of a child from `SIGCHLD`: the PAL's signal thread calls
`ProcessWaitState.CheckChildren`, which asks `waitid(P_ALL, WEXITED | WNOHANG | WNOWAIT)` which child ended and reaps
it with `waitpid(pid, WNOHANG)`; `WaitForExit` waits on an event that path sets, and a process that is not a child is
polled with `kill(pid, 0)`. `Process.Kill` is `kill(pid, SIGKILL)`.

WitOS has every piece but three: the libc's `posix_spawn` starts a program through the process manager (S6.1) with
the caller's directory and standard streams (S6.2), but a pipe as a stream was `ENOSYS`, since a pipe lived within
one process (R2.3a); nothing raised `SIGCHLD`; `waitid` and `kill` of another process were absent.

## Decisions

**Pipes between processes.** A pipe stays what it is, a ring buffer of the process, until a `posix_spawn` file action
binds one of its ends to a standard descriptor of the child. Then the libc shares it: the ring moves into a memory
object, and each end gets one endpoint of a channel for wakeups. A process that holds an end maps the object and holds
that end's endpoint; after each change (bytes written or read, an end closed in this process) it sends an empty
message on its endpoint, so that the other end's waiters look again, and a waiter drains its endpoint's queue, looks
at the ring, and waits on the endpoint (`OBJECT_WAIT`) when there is nothing to do. The kernel's channel gives the rest
for free: a message is lost only when four are queued, and then the waiter looks anyway; the end of the file and
`EPIPE` are the kernel's `PEER_CLOSED`, which a reader sees once every handle of the write end's endpoint in every
process is closed and a writer once the read end's is, so a parent that forgets to close its copy of the child's end
keeps the pipe open exactly as on Linux. The ring is written by one process at a time per end (head and tail are the
reader's and the writer's words, with acquire and release), which is what a parent and a child do.

Why not channels alone: a message carries 256 bytes and an endpoint queues four, so a stream of bytes through
messages would wait for room on every kilobyte, and "a wait for queue room" is not a mechanism the kernel offers. Why
not every pipe shared from the start: a shared pipe costs a channel and a memory object, and CoreCLR and the PAL make
pipes freely (the signal thread's, the thread pool's), so a channel for each would spend the process's quota on
nothing that crosses a process.

**The quota.** A process created at most four live channels (K2), enough for the system layer's own protocols. Three
streams of one child are three channels, so the quota becomes a profile's: a fixture keeps 4
(`WIT_USER_CHANNEL_CAPACITY`), a system layer process gets 16 (`WIT_PROCESS_CHANNEL_CAPACITY`), as threads, handles
and events went by profile at K5.3, and the kernel's table grows from 32 to 128 channels (`WIT_CHANNEL_TABLE_CAPACITY`),
about 400 KiB of kernel memory. ABI-1 stays 1.2: a quota is not a call.

**How the child gets its ends.** The start message (version 6) counts the streams; they follow on the granted channel
as `WitStreamMessage`s, each moving the pipe's memory object and the end's endpoint for one standard descriptor. The
grant slot of the spawn request (D1.1) carries the channel's end; the libc's `posix_spawn` makes the channel, queues
the streams on the child's end, closes its own end and asks the manager; the child's `start.c` receives them before
`main` and installs each as a pipe end at its descriptor, then closes the grant, so a process with streams has no
grant. A service is started by the process manager's own paths with its grant and without streams; the two never
meet. A message holds four handles, and the log, the package, the manager and the grant fill them, so the namespace's
endpoint, which every process of the system layer takes (D5.1), follows in a second message on the start endpoint
when the first has no room (`WIT_START_NAMESPACE_NEXT`): the creator sends both before it starts the thread, and the
libc receives both before it closes the endpoint.

**Which descriptors the child gets.** `posix_spawn` reads the caller's standard descriptors as the child would see them
after the file actions: the log stream itself stays the log, a pipe end there (the caller's own standard input or
output redirected by its parent) is given to the child as on Linux, and anything else there (a file, a duplicate of
another stream) stays the caller's, as S6.2 left it; a `dup2` of a pipe end onto 0–2 binds it, a `dup2` of a standard
descriptor already bound to a pipe binds the same end (`2>&1`), a `dup2` of a file is `ENOSYS`, and a `dup2` of a
descriptor an earlier action closed is `EBADF`.

**`SIGCHLD`.** The libc raises it. A reaper thread of the libc, started by the first `posix_spawn`, waits on the
children's process handles (three at a time with the event a new child sets; more are polled at 50 ms, as `wait4`
polls) and, when one ends, marks it and raises `SIGCHLD` to itself, so a handler runs on that thread: the PAL's writes
a byte to its pipe, and its signal thread does the rest. The child stays waitable: `waitid` with `WNOWAIT` reports it,
`waitpid` reaps it and closes the handle.

**`kill`.** A child's id with `SIGKILL` is `PROCESS_KILL` of its handle (the child ends as if by `SIGKILL`); with 0 it
is the existence check; with any other signal it is `EPERM`, since the kernel delivers an activation only within a
process (RFC 0011 §7.5) and the libc claims no signal to another process. `Process.Kill` is `SIGKILL`.

**The runtime.** `SystemNative_ForkAndExecProcess` gets a `TARGET_WITOS` branch beside the others (RFC 0015 §4, the
third preference): the pipes with `pipe2`, `posix_spawn` with `adddup2` of the child's ends onto 0–2 and
`addchdir_np` of the directory, the errno of a failed start returned at once; credentials are `ENOTSUP`. Nothing else
of `Process` changes.

## Limits kept explicit

- A pipe is shared when a `posix_spawn` file action gives one of its ends to a child, never otherwise; a file as a
  standard stream stays `ENOSYS`.
- A shared pipe's end is read, or written, by one process at a time; two processes reading the same end interleave.
- `poll` on any descriptor looks again every 10 ms while a shared pipe lives, since a change in another process bumps
  no word of this one; an idle `poll` on a pipe no other process holds parks as before.
- `SIGCHLD` is raised on the libc's reaper thread; `SA_NOCLDWAIT` and `SA_NOCLDSTOP` have no meaning.
- No signal reaches another process but `SIGKILL` of a child; no process groups, no sessions, no `fork`, no `exec`.
