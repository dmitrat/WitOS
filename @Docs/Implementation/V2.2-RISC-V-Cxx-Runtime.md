# V2.2 — The C++ runtime on riscv64: LLVM's libunwind, libc++abi and libc++ for the third triple, the Itanium trace on the third ISA

Plan step V2.2, the second slice of V2 (layer 2 on riscv64), 2026-10-17. V2.1 ([V2.1-RISC-V-Libc.md](V2.1-RISC-V-Libc.md))
built musl for `riscv64-unknown-linux-musl` and ran the first libc program on the third ISA. This slice builds the C++
runtime above it — LLVM's libunwind, libc++abi and libc++ at the toolchain's release, compiled unchanged after the
runtimes' CMake rules as for the two other triples — and proves it in the guest: the `cxx` scenario boots S4's
`cxx_exceptions.cpp` with `cxx_main.cpp` as the root task on riscv64, and its 21 checks pass at the first boot, the
Itanium trace of the exception scenarios equal to the one a native Linux build prints (`tests/User/cxx_itanium_trace.h`).
What the slice found was one thing: the sanitized Linux headers the runtimes' build includes keep RISC-V's `asm`
headers in a directory of their own. libc-test and the shared libraries move to V2.3 with libwitos: libc-test runs
every test in a process of its own through `posix_spawn`, which is the process manager's, and the shared library is
proven by the `spawn` scenario.

## 2. The headers

libc++'s atomic waits include `<linux/futex.h>`, which the runtimes' build takes from sabotage-linux's sanitized
headers (S4); every architecture's `asm` headers live in a directory of that tree, which `setup` extracts for the
ISAs the tool builds. The tree names the RISC-V directory `riscv`, one for both widths, where x64's is `x86` and
ARM64's `arm64`; `HEADER_ARCHITECTURES` lists the three, `KernelHeaderIncludes` maps an ISA to its directory, and a tree
extracted before riscv64 joined — a developer's `.tools`, CI's cache — is extracted again when any of the three is
missing, so the pin and its hash stay what they were.

## 3. The scenario

`cxx_main.cpp` names riscv64 as its ISA; the rest is S4's: the Itanium exception scenarios of `cxx_exceptions.cpp`
(throws across frames, nested and rethrown exceptions, destructors and copies on the way, `std::exception_ptr`, the
trace of every step), libc++'s containers, strings, streams and algorithms. The root task links statically with
`libc++.a`, `libc++abi.a` and `libunwind.a` after the program and before `libc.a` and the builtins (`MuslLibc.LinkAsync`
with the runtime's archives), and the flat image is the one static.ld lays out (V2.1's small-data sections included).

`KernelArchitecture.CxxRuntime` says the runtime builds for the ISA and the `cxx` scenario runs on it (true for every ISA
now), between `Libc` and `SystemLayer`; `test --arch riscv64` holds 17 scenarios.

## 5. Findings

1. **One directory for RISC-V's headers.** The sanitized tree keeps `riscv/include/asm` for both widths (its `riscv64`
   entry is not a tree of its own), so the tool's name for an ISA's directory is a table, not the ISA's name, and the
   extraction that chose `x86` and `arm64` by hand now takes the table and repairs a tree that lacks a member.
2. **The runtime needed nothing of its own.** Unwinding through the kernel's user mode, `tp`-relative TLS, the
   trampolines and the atomics (`A` extension) of the pinned LLVM runtimes ran on riscv64 as compiled for the triple;
   the Itanium trace matched Linux's at the first boot, as it did on ARM64 (S4).
