# C4.1 — the layer of base applications

Plan step C4.1 (phase C, ADR 0027 decisions 1–6, RFC 0010 §3–§9, §28, §124–§127): the base applications become a layer
of directories on the data volume, made from a catalog of pinned upstream publications, with launchers on `PATH`, a
new version installed beside the old and a rollback; PowerShell moves onto it. Made on 2026-10-18.

## 1. The catalog

`build/apps/<ApplicationId>.json` (`AppCatalog`) names a base application: its identity (the file's name), the version,
the shared framework, the source, an optional native part, the commands and a purpose. A source is one of three kinds,
checked whole when the catalog is read:

| Kind | What it pins | First user |
| --- | --- | --- |
| `archive` | a release archive's https URL, its file and the SHA-256 of its bytes | PowerShell (C4.1) |
| `tool` | a .NET tool package of nuget.org and the SHA-256 of the package | CSharpRepl (C2.5) |
| `source` | a repository, a commit and the project the stock SDK publishes without a RID | the file manager (C4.2) |

Never a Linux RID's binary. PowerShell's entry moved here from `src/Substrate/powershell.lock.json`, the same pin with
its native part (PowerShell-Native's commit, `libpsl-native.so`) and the command `pwsh` of `pwsh.dll`;
`PowerShell.ReadPinAsync` reads it. The `tool` and `source` kinds are checked now and laid by their first users' steps.

## 2. The layer

`AppsLayer` writes the layer through a store — a directory of the host (`DirectoryLayerStore`), from which a new data
disk's ext4 volume is made, or the ext4 volume of an existing disk through the host's debugfs (`Ext4LayerStore`):

```text
/data/apps/<ApplicationId>/<version>/    the files as the source publishes them, the native part, witos-app.json
/data/apps/<ApplicationId>/current       the version in use (a file: no links until D7)
/data/apps/bin/<command>                 the launcher, executable
```

- **The manifest** `witos-app.json` is the catalog entry the version was installed from. A version is installed when its
  manifest is there, which is written last.
- **A launcher** is upstream's witos `apphost` (built by `host.native` since R5) written for the version's assembly as
  the SDK writes a .NET tool's shim: the path `../<id>/<version>/<assembly>`, relative to the launcher, in place of the
  apphost's placeholder (the SHA-256 of "foobar"), ended by the buffer's zeros. The apphost finds its own path through
  `AT_EXECFN` (R3.2a) and the install through `/etc/dotnet/install_location` (R5), so `/data/apps/bin/pwsh` starts
  PowerShell on the shared framework as `dotnet pwsh.dll` did.
- **An installation** writes a version the layer lacks, then makes it the one in use: `current` and the launchers. A
  version the layer has is not written again. **Using another installed version** rewrites `current` and the launchers,
  which is the rollback; the old version's files stay until something removes them.
- **No installation database:** the layer is its directories; what is installed is what holds a manifest.
- **Modes:** the ext4 volume keeps a file executable when its source is (`RuntimeExt4Volume`), so a launcher is 0755,
  which .NET's `Process.Start` and PowerShell's command discovery look for on `PATH`.

The `apps` command (`AppsDisk`) makes a data disk with the layer of every application of the catalog when the disk is
missing; on an existing disk it brings the layer up to the catalog — a new version beside the old, its launchers
written — and `--use <id>=<version>` switches an application to an installed version. The disk's ext4 partition is
copied out, repaired by e2fsck (which replays a journal a session left), changed through debugfs as one script, repaired
again and required clean, and copied back; the rest of the disk stays as it is. Like the volume's making, it needs
e2fsprogs on a Linux host.

```text
dotnet run --project tools/WitOS.Dev -- apps --arch x64 --disk data.img
dotnet run --project tools/WitOS.Dev -- apps --arch x64 --disk data.img --use PowerShell=7.6.7
```

## 3. The environment

`/etc/environment` (the install's, which the root task gives every process) puts the launchers on `PATH` after the
package's directories and before `/dotnet` — `PATH=/bin:/usr/bin:/data/apps/bin:/dotnet` — and sets
`SHELL=/data/apps/bin/pwsh`, the shell applications run commands through (ADR 0027 decision 6). WitOS provides no
`/bin/sh`; `Compatibility-Differences.md` records it.

## 4. The scenarios

`runtime-powershell`, `runtime-display` and `shell` boot with a data volume made by `AppsDisk.VolumeFilesAsync` — the
layer and the home directory — and start PowerShell as `/data/apps/bin/pwsh -NoLogo`. `runtime-powershell` also prints
`$env:SHELL` and `Test-Path /bin/sh` and requires `shell=/data/apps/bin/pwsh` and `sh=False`. CI's install artifact
carries the apphost, so a session can be prepared from it (C2.4).

## 5. What ran

In the Linux host's image, on riscv64, whose runtime tree that image holds whole since V2.4:

- `runtime-powershell`: PASS — PowerShell 7.6.7 started three times through its launcher
  (`[APPS-INIT] /data/apps/bin/pwsh -NoLogo exited with 0`), the version table, the pipeline, the files, `SHELL` and
  the absent `/bin/sh`, then the interactive session under PSReadLine with the console mark.
- `runtime-display`: PASS — the same launcher on the screen, the screendump equal to the host's frame in colour (5 colours
  beside white and black).
- `apps`: a disk made with the layer (`PowerShell 7.6.7, in use; commands /data/apps/bin/pwsh`); the same disk brought
  up to the catalog (`PowerShell 7.6.7 was there`); `--use PowerShell=7.6.7`; `--use PowerShell=7.0.0` refused (`The
  layer has no PowerShell 7.0.0.`).
- Host tests (`AppsLayerTests`, 6): the catalog's PowerShell entry and its checks, the launcher's bytes, a version
  installed beside the old and the rollback in a directory and on an ext4 volume through debugfs (the disk's other
  partitions unchanged), the command's options. On Windows the ext4 one is skipped, as every e2fsprogs test is.

x64 and ARM64 are CI's `linux-host` legs, which run `runtime-powershell` and `runtime-display` with the rest of
`runtime-witos`.

## 6. Limits

- The `tool` and `source` kinds are checked but not laid until C2.5 and C4.2 bring their first applications.
- Removing an old version is by hand (a volume's directory); the layer never deletes one itself.
- Updating a disk needs a Linux host's e2fsprogs; the installer in the guest (C4.3) lifts that.
- One volume holds the layer, the one mounted at `/data`.
