# H1.1 — The PC platform

Plan step H1.1 (phase H, [ADR 0028](ADR-0028-First-Release-Target.md)), 2026-10-23: the x64 kernel's board layer
becomes the PC's, so that one kernel boots on QEMU's q35, QEMU's `pc` machine and VMware Workstation, and the image the
gates judge is the one VMware boots. The step adds no ABI: what [H0](H0-Hardware-Measurement.md) §5 proposes for ABI-1
1.5 (the MSI binding, the power call, a device table beyond a page and without bridges) and for the port mechanism
was decided by [ADR 0029](ADR-0029-PC-Interrupts-Power-and-Device-Table.md) on 2026-10-23 and is H1.2; the port
mechanism left release 1, since the keyboard is USB on every target.

## 1. What changed

`src/Kernel.Platform.Q35` is now `src/Kernel.Platform.Pc` (layer `kernel-platform-pc`). Four things tied it to q35,
and each now follows what the board reports:

| What | Before | Now |
| --- | --- | --- |
| The monotonic clock | the HPET at q35's fixed 0xFED00000, a period dividing 10^15, Intel's vendor id | the HPET the ACPI HPET table names (system memory, 1 KiB aligned), any period the specification allows (at most 100 ns), any vendor; the frequency is 10^15 / period rounded to the nearest hertz |
| The ECAM window | the q35 host bridge's PCIEXBAR register | the ACPI MCFG's entry for segment 0, published as the configuration region of each function on a bus the entry covers |
| INTx routing | ICH9's PIRQ E–H routed wherever device 31 is an Intel function | only where device 31 is ICH9's LPC bridge (8086:2918); every other board keeps the firmware's lines |
| Lines | an Interrupt Line below 16 was a line | 0, the timer's line on every PC, is no line either |

Two more changes make an overcrowded board visible and keep its screen:

- The framebuffer's descriptor (C2.1) keeps its slot: the bus's functions fill the table less one slot when the boot
  contract carries a framebuffer. VMware's machine of H0 has 46 functions; the table of 16 descriptors holds 15 of
  them and the screen, where the screen was dropped before.
- A line reports the count: `PCI: <found> functions, <described> described, ECAM <base>`.

The ACPI reader (`acpi.c`) finds a table by its signature for the three users (the MADT, the HPET table, the MCFG),
verifying each table's length and checksum before its body is read, and interprets no AML.

## 2. The frequency

VMware's HPET counts with a period of 69,841,279 fs: 14,318,179.94 Hz. The monotonic domain reports an integral
frequency, so the platform reports 14,318,180 Hz, 0.004 ppm above the counter's rate: a second in seven years, far
below the tolerance of a crystal. QEMU's period of 10 ns divides 10^15, and its frequency stays exactly 100 MHz, which
the self-test suite requires. The clock's line now names the period and the block's address:

```
HPET frequency: 14318180 (period 69841279 fs at 0x00000000FED00000)
```

A board without an HPET table panics with `No HPET in the ACPI tables` (the self-test suite's `no-hpet` boot, q35 with
`hpet=off`, requires that line); a table whose block is not in system memory or misaligned, or a block without a
64-bit counter or three comparators, `Unsupported HPET`.

## 3. The gate

The `release` command boots `release-pc-256` on x64 beside its q35 boots: QEMU's `pc` machine (i440FX with PIIX3, the
HPET, no MCFG), two processors, the boot disk on PIIX's IDE channel (QEMU writes a snapshot, since an IDE disk cannot
be read-only), the default VGA card's GOP as the framebuffer, and no virtio device at all. The firmware's entropy comes
from RDRAND (`-cpu qemu64,+rdrand`): measured, OVMF on `pc` with neither a virtio entropy source nor RDRAND leaves the
loader without `EFI_RNG_PROTOCOL` (`[PANIC] UEFI RNG unavailable`), while with RDRAND it boots. The boot requires the
release suite's markers, `[BOOT] Framebuffer: `, `Processors present/online: 2/2` and
`PCI: 5 functions, 5 described, ECAM 0x` (the host bridge, PIIX3's ISA, IDE and ACPI functions, the VGA card).

The self-test kernel stays on q35: its device and interrupt fixtures know the board's virtio block function by its
ECAM configuration space (`tests/User/Fixtures/devices.c`), which an i440FX board does not have. A trial of the
self-test kernel on `pc` passed every suite before the device fixture, which stopped at that check (code 10).

## 4. VMware

The same kernel, unchanged, on the machine of H0 (four processors, 1024 MiB, the four PCIe root ports, SATA, NVMe,
e1000e, vmxnet3, xHCI, the SVGA adapter, the HPET), with the `libc` image converted by `qemu-img` to a VMDK:

| What | Measured |
| --- | --- |
| Clock | `HPET frequency: 14318180 (period 69841279 fs at 0x00000000FED00000)`; the clock's tests pass |
| Processors | `Processors present/online: 4/4` |
| PCI | `PCI INTx: no ICH9 LPC bridge, the firmware's lines kept`; `PCI: 46 functions, 15 described, ECAM 0x00000000E0000000`; no function has a line (VMware's registers read 0xFF) |
| Screen | the SVGA adapter's GOP, 1024×768, described after the 15 functions |
| Root task | `musl 1.2.5 on x86_64: 177 checks passed, 0 failed`, `[ROOT] exit code 0` |
| End | QEMU's exit port does nothing, and the kernel halts with the machine up, as in H0: the soft-off waits for H1.2's power call |

## 5. What remains of H1

H1.2, by [ADR 0029](ADR-0029-PC-Interrupts-Power-and-Device-Table.md): the binding of a device's MSI or MSI-X message to
an event (VMware routes no INTx, and q35's virtio functions gain more than four lines), the power off and the reset at
the root task's end (soft-off through PM1a_CNT with `_S5`'s static package, reset through the FADT's RESET_REG), and a
device table of 64 descriptors that describes no bridges. The keyboard is USB on every target (H2); the PS/2 keyboard
and port access wait for a PC beyond VMware.
