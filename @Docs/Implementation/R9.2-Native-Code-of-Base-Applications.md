# R9.2 — Native code of base applications, compiled at installation

Plan step R9.2. The author's decision of 2026-10-27, after the discussion in
[R9-ReadyToRun-Framework.md](R9-ReadyToRun-Framework.md) §6: no precompiled code is distributed. The layer takes upstream's
publications as they are, IL and portable across ISAs (ADR 0027 unchanged), while the framework stays ReadyToRun in the
system image, which is built for each ISA anyway, as upstream's runtime pack is. The model is .NET Framework's NGEN, which
CoreCLR does not have: what the JIT writes lives in a process's memory and carries its addresses, and the portable form of
compiled code is ReadyToRun, so the cache of compiled code is ReadyToRun images made on the machine. On 2026-10-28 the
author decided to finish the step before phase E, since it serves the speed of starting applications.

## 1. What was measured

On VMware (x64, two virtual processors, 2026-10-28), the tree's crossgen2 in the guest — its IL under the install's JIT,
with the witos builds of `libjitinterface_x64.so` and `libclrjit_unix_x64_x64.so`, 4.8 MB — compiled PowerShell's 59
top-level assemblies one process each in 224 s: System.Management.Automation in 28 s, Microsoft.CodeAnalysis.CSharp in
30 s, the small ones in about 2 s each, which is crossgen2's own start under the JIT. All 59 images were byte for byte the
images the host's crossgen2 writes with the same references, in 15 s. A trial session with those images reached the
prompt 5.2 s after the services were ready instead of 6.5 s, and a child `pwsh -Command exit` took 1.3–1.8 s instead of
2.0–2.4 s, its JIT compiling 266 methods instead of 4,902. The measurement found S8.3: the namespace service died under the
load of the assemblies' mappings ([S8.3-Collector-Decommits-in-Place.md](S8.3-Collector-Decommits-in-Place.md)).

## 2. The native directory

`WitOS.Apps.NativeCode` is the contract the host's tool and the guest's installer share.

- **Where.** `<layer>/<id>/<version>/native-<arch>/`, for a version with commands; a version without one, such as the .NET
  SDK, is reached by others and has nothing to launch.
- **What.** A copy of the version's files in which every assembly crossgen2 compiles is replaced by its ReadyToRun image
  for the architecture. A ReadyToRun image keeps its IL, so the directory stands alone: the apphost's application base, the
  runtimeconfig, the deps file and PowerShell's `$PSHOME` with its modules all lie in it.
- **Derived.** The directory is written in a hidden `.native-<arch>.partial` beside it, the marker `witos-native.json`
  last (the architecture, the assemblies compiled, those kept as IL), and renamed into place over any earlier one. A
  directory without the marker holds no native code; it may be removed and made anew at will.
- **Launchers.** `AppsDirectory.Use` and the host's `AppsLayer.UseAsync` write a launcher for `native-<arch>/<assembly>`
  while the marker is there and for the version's own assembly otherwise; another architecture's directory is not taken.

What crossgen2 compiles:

- An assembly with IL code that is no ReadyToRun image already (the .NET SDK's are), no reference assembly
  (`ReferenceAssemblyAttribute`: PowerShell's `ref/`), no satellite of resources and no facade without methods, outside
  `runtimes/<rid>/` of systems other than `unix` and `witos`, the parents of `witos-<arch>` in the RID graph.
- Each directory's assemblies are one compilation, since the names of crossgen2's inputs must differ (PSReadLine carries
  `Polyfiller.dll` twice). The references are the directory's own assemblies, then the frameworks', then the rest of the
  version's, the first of a name winning, as crossgen2 takes references.
- One crossgen2 process compiles a directory: `--targetos:witos --targetarch:<arch> -O --single-file-compilation
  --out-near-input`, through a response file of one token a line. A compilation that fails is run again input by input,
  and an input that fails alone keeps its IL and is named in the marker.

## 3. The host

`NativeCodeBuild` compiles on the Linux host with the tree's crossgen2 (`crossgen2-published` of R9's host build) against
the install's ReadyToRun framework, so that every layer the tool writes — a new disk (`AppsDisk`, the layer scenarios,
`shell --pc`) and an existing one (`apps --disk`) — carries the native code of each version with commands, its marker last.
A compilation is kept under `.tools/apps-native/<arch>/` by the hash of what it reads: crossgen2, the module of
`WitOS.Apps` (the rules), the framework's files and the version's files. riscv64 keeps its layer IL until R9.3, since its
framework is IL ([R9-ReadyToRun-Framework.md](R9-ReadyToRun-Framework.md)).

The same builder compiles the system's own managed parts in the boot package: the installer under `/system/Installer`
and the guest's crossgen2.

## 4. The guest

- **crossgen2.** `/system/Crossgen2` holds the tree's crossgen2 — its assemblies, compiled to ReadyToRun for the
  architecture — with the JIT interface and the JIT the witos build of the runtime makes for the architecture
  (`libjitinterface_<arch>.so`, `libclrjit_unix_x64_x64.so` or `libclrjit_universal_arm64_arm64.so`) and its launcher,
  the witos apphost. The boot package carries it with the installer, on the architectures whose layer has native code.
- **witos-apps compile <application> [<version>].** Compiles an installed version, the one in use when none is named,
  against the framework the installer itself runs on, the install's `Microsoft.NETCore.App`, and writes the launchers
  again when the version is in use. `install` compiles the version it installed where the system has crossgen2, so that
  the native code exists at installation, not at the first start.

## 6. Limits kept explicit

- The installer's screen installs without compiling; its command line compiles. A background job after an installation,
  the decision's last word, follows the measurement of the compilation's time on a machine (VMware, then the Pi): under
  TCG it is a quarter of an hour for Commander's 11 MB, which says nothing of a real processor.
- An application is compiled against `Microsoft.NETCore.App` alone; none of the base applications runs on another
  framework (ASP.NET Core's would be one).
- A file of a volume is copied into the process that maps it privately (D5.2), and a ReadyToRun image is some 2.5 times
  its IL; mapping a volume's file without a copy, as the namespace service's chunks serve shared mappings (R4.2), stays a
  step of its own.
- riscv64 stays IL (R9.3).
