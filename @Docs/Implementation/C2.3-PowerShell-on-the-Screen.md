# C2.3 — PowerShell on the screen: C1's session typed on the keyboard, one answerer of the terminal's queries, a scroll that stores the pixels that changed

Plan step C2.3, the last slice of C2 (the screen and the keyboard, RFC 0020 §28, RFC 0009 §26), 2026-10-17. C2.2
([C2.2-Display-Service.md](C2.2-Display-Service.md)) made the display a console of the terminal and judged a small
program's lines on the screen pixel for pixel. This slice puts upstream PowerShell there: the `runtime-display` scenario
boots the device services, the .NET install and PowerShell on the data volume with the board's framebuffer, a virtio
keyboard and the mirroring virtio console, the runner types C1.3's interactive session on the keyboard through QMP —
`$PSVersionTable`, `1 + 2`, `Get-Date`, `Get-ChildItem /data` at PSReadLine's prompt — and the screendump at the last
prompt must equal the frame the host renders from the mirror's transcript, on both ISAs. It also answers the two
questions C2.2 left: the runner's side of the mirror no longer answers the terminal's queries while the display is the
main console, and the renderer stores only the pixels that changed, which makes a scroll cost the text that moved rather
than every cell. The same image without a display runs PowerShell on the serial console (`runtime-powershell`, C1.3), so
C2 is complete.

## 2. PowerShell on the screen

The scenario's package is C1.3's package of applications — the device services, the .NET install, `apps_init` as
`/bin/init` with the commands of `/etc/apps`, the environment with `__PWSH_LOGIN_CHECKED=1` — plus
`tests/User/display_check.c` as `/bin/display-check`; the data volume carries PowerShell under `/data/pwsh` and the home
directory, as `runtime-powershell` lays it out (1 GiB disk, 1024 MiB of guest memory). The commands are three:

```
cd /data
/bin/display-check
/dotnet/dotnet /data/pwsh/pwsh.dll -NoLogo
```

The check is C2.2's `display_init` as a command: the standard streams are a terminal of the display's grid (100 by 37), a
line typed on the keyboard comes back, four checks. Then PowerShell starts on the same terminal, whose main console is
the display: the profile draws the console mark (C1.4), PSReadLine queries the cursor position, the display answers,
and the prompt `PS /data>` appears on the screen and, mirrored, in the virtio console's transcript, where the runner
reads it. The runner then types each command of the session, one after each prompt, through QMU's `input-send-event`
on the virtio keyboard — the keys travel the keyboard driver's input protocol to the display service, through the US
layout to the terminal service's discipline, and from there to PSReadLine — and at the prompt after the last command it
takes the screendump and types `exit`. PowerShell's exit with 0 and `apps_init`'s `2 commands, 0 failed` end the boot,
and the services stop in C2.2's order.

The judge is C2.2's: the screendump must equal, pixel for pixel, the frame the host renders from the mirror's transcript
(from the terminal probe's prompt on) with the same emulator, renderer and font. PowerShell's output exercises what the
check's lines did not — PSStyle's colours (SGR, parsed and ignored on both sides), PSReadLine's cursor movements and
line redraws, the emblem's block characters, and the scroll, since the session's output fills more than 37 rows. The
required lines add C1.3's facts seen on the screen: `PSVersion` and `WitOS` in the version table, the emblem's row and
`PowerShell <version>` in the mark's panel, the prompt, `Directory: /data` of the listing, and the exits.

## 3. Typing on the keyboard

`KeyTyping` turns a text into the QKeyCode names QEMU's keyboard takes: a lower-case letter or a digit is its own key,
an upper-case letter or a shifted character (`$`, `+`, `?`, `"`, …) a chord `shift+<key>`, the punctuation by its US key
(`minus`, `slash`, `spc`, …), CR and LF the Enter key, which the guest's layout gives a program as CR — what PSReadLine
reads raw. `QemuControl.SendKeyAsync` sends one key a QMP command, since the keyboard driver holds 64 one-event buffers
and the guest refills them only between commands: a chord's keys go down in order and up in reverse, so `shift+4` is
shift down, 4 down, 4 up, shift up, and the layout in the display service makes `$` of it. A line of fifteen characters
is fifteen commands; PSReadLine echoes each key, and the display paints each echo before the write returns.

The actions of a request now follow each other (`ActionSequence`): an action is due once its line appeared in the
serial log or the transcript *after the previous action's line*, as the terminal script's inputs are typed (C1.2), so
that the prompt PowerShell shows again after every command fires one action a time; an action with an empty line
follows the previous one at once (the `exit` after the screendump). C2.2's two actions on one line, which fired
together, are the one case this changes.

## 4. One answerer

PSReadLine and .NET's `Console` ask the terminal where the cursor is (`ESC [ 6 n`) and wait for the report. In C1.2 the
runner's `TerminalLink` answered from its emulator, since the serial console had no screen of its own; in C2.2 the
display answers too, from the screen it draws — and with two consoles both answered, two reports reached PSReadLine,
and the second was read as keystrokes. The rule now: the display answers, the mirror is silent. `TerminalLink` takes
`answersQueries`, false when `BootRequest.DisplayIsMainConsole` (a display and a keyboard: the device manager's policy
for the main console), and still paints its screen for the transcript's sake. The terminal service stays out of it: a
line discipline has no screen and answers nothing, as C1.2 decided.

## 5. The scroll

C2.2's renderer redrew every cell whose character changed since the last frame, 128 pixels a cell in 32-bit stores
through device memory, and a scroll changes almost every cell of a text-filled screen. The plan's remedy was to move the
framebuffer's rows instead of redrawing cells. Measured against the device, that is no gain: a row moved in device memory
is a load and a store a pixel, two accesses, for every pixel of the 36 rows that move — 460,800 pixels, 921,600
accesses a line scrolled — where a redraw is one store a pixel of the cells that changed, and under an emulator a load
from the framebuffer costs what a store costs. The renderer instead keeps a word for every pixel of the framebuffer
(1.9 MB in the service's memory) and, of a drawn cell, stores only the pixels that differ from what the framebuffer
shows: a glyph replaced by another glyph differs in the pixels the two glyphs do not share, a glyph replaced by a blank in
its lit pixels. A scroll then costs the text that moved, not the cells, and no row is read back. The screen counts the
lines it scrolled, the renderer the cells drawn, the pixels stored and the pixels a row move would have stored, and the
display service reports all of them when it stops, so the comparison is measured in the guest, not reasoned
(section 6). A blank cell is the background whatever glyph a font gives a space, since `Clear` leaves every cell blank
without drawing one; the renderer clears the framebuffer itself when nothing did yet. The frame is the same as before:
the host's render and the display's agree pixel for pixel, as the judge requires, and `FrameRendererTests` requires a
frame drawn in steps across scrolls to equal one drawn at once.

The screendump waits for a quiet guest: a program that showed its prompt may still be writing its last sequences, and
the display paints each write before the mirror receives it, so the runner waits until the serial log and the transcript
stopped growing for a second (at most fifteen) before it dumps the screen and keeps the transcript of that moment.

## 7. Findings

1. **The display never completed a held READ after a write.** The display answered the cursor position query into its
   input queue since C2.2, but completed the terminal's outstanding READ only when a key arrived; PowerShell wrote its
   query, waited for the report, and the first x64 run timed out after an hour with the console mark drawn and no
   prompt. The fix is one call after each write (`DisplayConsole.Completed`). C2.2's check wrote no query, so the path
   had no exercise before a program that asks where the cursor is ran on the screen; the mirror's silence (section 4)
   made it visible, since the runner's emulator had answered for the display until now.
2. **C2.2 broke `runtime-terminal`'s required lines.** The terminal service names its consoles since C2.2 ("80 by 24 by
   default, 1 console", "1 console released"), the scenario required N4.3's wording, and the C2.2 gate ran
   `runtime-services` and `runtime-display` and not `runtime-terminal`, so CI's `linux-host` failed the scenario on both
   ISAs for #138 while every check of `terminal_init` passed. Fixed on the C2.2 branch (16eef5e) and the stack rebased;
   the lesson: a slice that changes a service's line reruns every scenario that requires it.
3. **The row move is a loss, measured.** For the x64 session the renderer stored 658,850 pixels in all, where moving the
   framebuffer's rows for its 21 scrolled lines alone would have stored 9,676,800 (and loaded as many); the pixel
   shadow costs 1.9 MB of the service's memory and nothing else.
4. **A blank cell is the background.** The tests' sample font names `?` its default character and has no space, so a
   cell that went blank drew a `?` where `Clear` had left the background, and a frame drawn in steps differed from one
   drawn at once; the renderer treats a space as the background whatever the font gives.
5. **Actions one at a time, and a quiet screen.** C2.2's two actions on one line fired together; a prompt the program
   shows after every command needs each action to follow the previous one's line, and a screendump needs the screen the
   transcript describes, so the runner waits for a second of silence before it dumps.
6. **One key a QMP command, each after the guest took the last.** The keyboard driver holds 64 one-event buffers and
   gives them back only when it runs; a line sent as one `input-send-event` could overflow them, so each key is its own
   command, and a chord's keys go down in order and up in reverse. One key a command was not enough either: QEMU's
   virtio-input drops a whole report when the event queue has no room, and on a CI host whose guest was busy redrawing
   PowerShell's prediction for each key the Return of `Get-ChildItem /data` was lost, so the boot waited an hour for a
   prompt that never came (#144's x64 leg, the same commit passing on ARM64). The runner now types a key only once the
   driver reported the previous key's transitions in the log (`[VIRTIO-INPUT] key`, which it writes after it gave the
   buffers back), so at most one key's four events are ever in flight, and a key the guest does not report within a
   minute ends the boot at once with the key named.

## 8. What follows

C2 is complete: PowerShell runs on the screen with the keyboard on both ISAs, and the same image without a display runs it
on the serial console (`runtime-powershell`). C3, the native WitOS module and its providers over `OutWit.OS`, is the
horizon the plan details after M8. The display keeps C2.2's bounds — the US layout until M9's input model, colours parsed
and ignored, 100 by 37 cells of one font — and a sixth bound virtio device still needs shared lines or MSI-X (phase P).
