# S8.2 — Base relocations of ReadyToRun code without a writable and executable window

Plan step S8.2, found while closing C2.5 on ARM64 (2026-10-20): with the arm64 SDK laid in the layer, CSharpRepl died
at its first evaluation with `FileLoadException: Could not load file or assembly 'NuGet.Versioning, Version=7.6.0.0'
… The access code is invalid` (`ERROR_INVALID_ACCESS`, the PAL's name for `EACCES` from `mprotect`), where x64 ran.

## 1. What was measured

- The SDK's assemblies are ReadyToRun images of their RID: `NuGet.Versioning.dll` of the linux-x64 archive has the
  PE machine 0xFD1D (AMD64 under the Linux mark 0x7B79) and the arm64 archive's 0xD11D (ARM64 under it), neither
  IL-only, both with `SectionAlignment` and `FileAlignment` 0x200 and `ImageBase` 0x180000000. The witos CoreCLR
  accepts both as native images, since the musl triple defines `__linux__` and `pedecoder.h` takes the Linux mark
  from it.
- The arm64 image carries 12 base relocations of type `DIR64` in `.text` and 313 in `.data`; the x64 image carries
  329, all in `.data`. The image never loads at its preferred base on WitOS, so CoreCLR applies the relocations
  (`PEImageLayout::ApplyBaseRelocations`), and for a section that is not writable it opens a window: `PAGE_READWRITE`,
  except that on `TARGET_UNIX` an executable section takes `PAGE_EXECUTE_READWRITE` ("On SELinux, we cannot change
  protection that doesn't have execute access rights to one that has it"), Apple's ARM64 apart, which toggles
  `PAL_JitWriteProtect` instead.
- WitOS's libc answers `mprotect` with `PROT_WRITE | PROT_EXEC` `EACCES` (`protection_of`: writable and executable at
  once is never granted), so the x64 image, whose code needs no relocation, loads, and the arm64 image fails.

## 2. The change

- `patches/runtime/release-10.0/src.coreclr.vm.peimagelayout.cpp.patch` (RFC 0015 §4's third choice, a
  `TARGET_WITOS` branch beside Apple's): on witos the section stays writable alone while the relocations are written,
  and the restore that follows gives it the section's protection again.
- The libc publishes an object mapping that `mprotect` makes executable (`__wit_mprotect`, `CODE_PUBLISH` of the
  range): its pages may have been written through the writable window, and instruction fetch sees them only after
  the kernel's cache maintenance on ARM64 and riscv64. A mapping of a shared memory file's chunk (CoreCLR's double
  mapping, D5.3's executable copies of a volume's code) carries both rights, so the kernel allows the flip; plain
  memory still never executes, and writable and executable at once stays refused.
- `tests/User/libc_hello.c` flips a shared memory file's page between writable and executable: code that returns 42
  written through the writable mapping runs once the mapping is executable, new code that returns 43 runs after the
  mapping was writable and executable again, `PROT_WRITE | PROT_EXEC` is refused, and plain memory refuses
  `PROT_EXEC` — on the three ISAs through the `libc` scenario of `test`.
- `runtime-csharprepl` runs on ARM64 again.

## 3. What ran

S8.2 closed on 2026-10-20.

- **Host.** `RuntimeWitosTests` and `UpstreamPatchesTests` (14) pass with the new patch in the set and the pin;
  `WitOS.Dev.Tests` whole; the format check.
- **Guest.** The `libc` scenario with the flip passes on x64 on the Windows host and, through `test`, on x64, ARM64
  and riscv64 in the container (one and two processors). Every scenario of `runtime-witos --arch arm64` passes with
  CoreCLR rebuilt under the patch (26 scenarios, 6,219 s); among them `runtime-csharprepl` passes on ARM64, the REPL
  exiting with 0 after 2,746 s of the guest's time, which closes C2.5 on x64 and ARM64 (riscv64 has no SDK
  publication). CI's `linux-host` legs rebuild CoreCLR with the patch on the three ISAs.
