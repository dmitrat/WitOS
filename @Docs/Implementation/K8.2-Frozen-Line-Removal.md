# K8.2 — the Windows-form line removed

[ADR 0024](ADR-0024-Three-Layers-and-Unix-Form-Runtime.md) froze the runtime line of P6.4: upstream .NET in its
Windows form behind a Win32 facade over WitOS's PAL. That line had passed the M3 acceptance first. It stayed in the tree
as the kernel's running workload until the Unix form passed M3 again (plan step R2, [R2.2](R2.2-M3-Acceptance.md)), and
it then had to be removed. K8.2 removes it.

The kernel policy the line needed is a separate matter. That policy is the PE loader, the DLL lifecycle, files over the
boot package and the kernel-held environment. It stays until K8.4, with `src/Runtime.Native` (its user side) and the
fixtures and host harnesses that test it.

## What was removed

536 files, about 67,000 lines.

**Code.**
- `src/Runtime.Cxx`, `src/Runtime.Crt`, `src/Runtime.NativeAot`, `src/Runtime.Pal.Win32` and `src/Runtime.CoreClr`: the
  guest C++ runtime and STL, the UCRT subset, the NativeAOT adapters, the Win32 binding surface and the CoreCLR host.
- `experiments/`: NativeAotBoot, NativeAotProbe, NativeAotTarget, CoreClr, CoreClrHost and CoreClrProbe.
- `tests/Runtime.NativeAot`.

**Guest tests.**
- The x64 fixtures that existed only for this runtime: the PAL, GC, runtime, CRT, STL, C++ library, host and CoreCLR
  fixtures, 120 files of `tests/User.X64`. `build/fixtures` and its PAL fixture compiler went with them.
- Sixteen x64 self-tests:
  - the GC adapter, PAL threads, services, errors, waits, memory pressure, modules, environment and background workers;
  - dynamic C++ TLS and native process exit;
  - the runtime configuration, unwind and boot tests;
  - the code memory and file/storage tests of the CoreCLR scenarios.
- 90 of the 202 markers of `x64-users.json`, and the `coreclr-memory`, `coreclr-storage` and `runtime-config`
  expectations.
- The self-test kernel's memory journal and budget report, which only `runtime-boot` read.
- The protocol's GC and native-heap constants.

**Commands.** Every `coreclr-*` command, and every `runtime-*` command except `runtime-witos`: `runtime-audit`, `-probe`,
`-target`, `-port`, `-source`, `-boot`, `-boot-run`, `-readiness`, `-unwind`, `-exception`, `-gp`, `-failfast`, `-seh`,
`-gc-policy`, `-encoding` and `-config`.

**Tool code.** `CoreClr/`, `Pe/`, `NativeAot/` and the image builders of the removed fixtures. The boot package lost its
.NET assemblies and native library fixtures, which only the CoreCLR scenarios carried, and the boot suites and
expectations of those scenarios went too.

**Host tests.**
- 31 host tests: the CRT, C++ and STL differentials against Windows, the PE corpus, fuzz and coverage lanes, the CoreCLR
  import and experiment tests, and the runtime boot protocol.
- Their test categories `Pe`, `PeCoverage` and `PeFuzz`.

**Patches and CI.**
- The frozen NativeAOT overlay: 15 patches of `patches/runtime`. The witos patch set's 18 stay.
- `patches/openlibm`.
- The workflows `nativeaot.yml` and `coreclr-host.yml`, and the STL cache and fixture artifacts of `kernel.yml`.

## What moved

- **Upstream patching** (`UpstreamPatches`, `UpstreamPatch`, `UpstreamPatchHunk`) moves to `tools/WitOS.Dev/Upstream`,
  with its tests. musl's and the runtime's patch sets use it. Its tests now pin only those two sets.
- **The Git wrapper** of the runtime checkout becomes `Host/Git.cs`, which libc-test's checkout uses.
- **`cxx_exceptions.cpp`** moves to `tests/User`. The `cxx` scenarios, `/bin/cxx` and CI's `itanium-reference` job
  compile it unchanged.
- **The CPU cache discovery self-test** is now called from `kernel_tests.c`, between the bootstrap and compiler TLS
  tests. The GC test used to call it.
- **`VirtualGapPropertyCasesTest`** is now an ordinary Windows test. It tests a mechanism of the common kernel, and it
  no longer waits for the runtime-source image that its category once required.

## The coverage only the frozen line gave

Some ABI-1 mechanisms that stay had no guest test outside the PAL fixtures:
- the memory-pressure event;
- `THREAD_SUSPEND`;
- a suspended thread's context read and replaced;
- the semantics of a wait on several objects;
- `MEMORY_RESET`.

Layer 2 has no other consumer of them yet. The root task now checks them on both ISAs in `tests/User/root_mechanisms.c`,
on threads of the one form whose stacks are the task's own reservations and which name those reservations for the kernel
to release at their exit. It logs `[ROOT] waits, suspension, activation, pressure and reset`, which `boot-128` of both
suites requires.

**Waits.**
- The request and every handle are checked before anything is consumed: a foreign handle beside a signaled event
  leaves the event signaled.
- A count of zero, a count above four and a deadline beyond the monotonic maximum are refused.
- The first ready object wins and alone is consumed: an auto-reset event is consumed, a manual one stays set.
- A deadline ends the wait, never before it.
- A parked worker wakes with the index of the event set, which it consumed.
- A close ends a parked wait with `CLOSED`.
- A thread's exit wins a wait beside unset events.

**Suspension.**
- A thread created suspended has not run. Its context is its entry at the top of its empty stack.
- Suspension counts up and down.
- A running thread's context is read, never replaced.
- A suspended thread does not run while its creator sleeps.
- Its context reads as suspended and ready, on its own stack.
- A stack pointer above its stack is refused and changes nothing.
- A context that sends it to another function, with an argument, at the top of its empty stack is applied, and the
  thread resumes there.

**An activation of a thread that has not run.** The fault callback (`ms_abi` on x64, the kernel's convention) receives
the activation vector and the marker, and the thread ends there.

**Memory pressure.**
- The event is wait-only, so `EVENT_SET` is denied, and it is unset at first.
- Committing the headroom down to below the low mark sets it. The headroom is the smaller of physical memory and the
  page quota.
- Releasing the memory clears it again. The pressure settles at the end of each call.

**`MEMORY_RESET`.**
- A range with a page that is not committed is refused whole, and its contents stay.
- The committed pages read zero and stay committed and writable, with the same owned and committed bytes.

The root task's sources share their declarations with hidden visibility (`tests/User/root.h`). The build passes
`-fno-plt`, so a call between two objects would otherwise go through a GOT, which the flat image refuses as an unaligned
segment.

## A kernel fault the checks found

A thread of the one form starts with its stack pointer exactly at the top of its stack. `validate_return` accepts that
state, since the stack is empty. Three other paths did not:

- **`owned_context`**, which reads a thread's saved frame for `THREAD_CONTEXT_GET` and `SET`, treated a stack pointer at
  the top as a lost frame and panicked. Any process could stop the kernel this way. The trigger was reading the context
  of a thread that had not run, or of one whose leaf loop never touches its stack, which ARM64 makes common. The ARM64
  root task hit the panic the first time the checks ran.
- **The context validation** of `THREAD_CONTEXT_SET` and `EXCEPTION_CONTINUE` refused such a stack pointer.
- **The fault and activation delivery** refused it, which ended the component instead of entering the callback.

All three now follow `validate_return`: the stack pointer may equal the top of the thread's stack or alternate stack.
The page that validation probes is the one a push writes, and the callback frame goes below the stack pointer either
way. The root task's checks cover all three paths.

## Tests

- `format-check` passes.
- Host tests: the suite runs 67 tests where it ran 98; the rest went with the removed line.
- `test`: all 27 x64 scenarios pass, and the user suite requires 112 markers.
- `test --arch arm64`: all 21 foundation scenarios pass.
- `runtime-witos` in the Linux container passes the M3 acceptance on both ISAs, because the kernel's delivery changed
  under the libc's signals.

## Limits kept explicit

- **Policy coverage lost early.** The guest tests of the file namespace, the DLL lifecycle and code memory went with the
  CoreCLR scenarios, although that policy leaves only at K8.4. The host harnesses of its parsers remain. The PE fuzz and
  coverage lanes are gone.
- **Physical pressure.** The pressure checks reach the low mark through the page quota, which is the smaller headroom
  in every scenario. The physical-memory path of the same computation has no guest test.
- **Handle reuse after a close.** A wait snapshot that meets a reused handle generation is no longer tested in the guest.
  A close while parked is.
- **No guest consumer for some calls.** `MONOTONIC_QUERY` and `CPU_CACHE_SIZE` have none left, and are candidates for
  K8.4.
- **The write barrier.** `PROCESS_WRITE_BARRIER` runs under musl's `membarrier` and the GC, but no test asserts it.
- **Thread capacity.** The self-test kernel keeps four threads of a process until K8.4.
