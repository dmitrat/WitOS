# Compatibility differences

This list covers how a .NET program on WitOS behaves differently from the same program on Linux. RFC 0015 §8
requires every absent or unsupported area to fail explicitly and to appear here. Each row names the behaviour, how a
program observes it, and the step that verified it. Rows change only together with a check that verifies the new
behaviour.

| Area | On WitOS | How a program sees it | Verified by |
| --- | --- | --- | --- |
| Files | The boot package is the root of the file system, read-only. The namespace service mounts the disks' volumes below it: ext4 at `/data`, FAT at `/fat` and the boot disk's FAT at `/boot`, read-only; and `/tmp`, a volume in the service's memory of 64 MiB whatever disks there are, whose files last the boot (N4.1). There are no symbolic links in the package, and the libc follows none on a volume. | Reads, `File.Exists`, directory enumeration, `FileStream` seeking and relative paths behave as on Linux. On `/data`, `/fat` and `/tmp`, files and directories are created, written, copied, cut, moved, replaced and deleted as on Linux. A write, a create or a `mkdir` in the package or on `/boot` throws `IOException` or `UnauthorizedAccessException` (`EROFS`, or `EEXIST` for an existing name). On `/fat`, a file open for writing cannot be opened again, nor an open file deleted (`EBUSY`, `IOException`). `Path.GetTempPath()` is `/tmp/` unless `TMPDIR` says otherwise. | R4.1, `libc_hello.c`, D5.1, D5.2, N4.1, `devices_init.c`, `Files.cs`, the N1 suite |
| Memory-mapped files | A private mapping of a volume's file is a copy taken when it is made, and an executable one a copy that executes. A shared mapping shows the namespace service's pages of the file, the same in every process; the service writes them back at `msync` and when the last handle that mapped the file writable closes. A shared mapping past the page that holds the file's end is `ENXIO`. | `MemoryMappedFile` views of every access work as on Linux; a `ReadWrite` view's writes reach the file at `Flush` or when it is disposed. CoreCLR loads assemblies, and the dynamic linker libraries, from a volume. | D5.2, D5.3, R4.2, `devices_init.c`, `Files.cs`, the runtime-devices scenario |
| File modes and times | A volume's files show the modes and times their volume records; `chmod`, `fchmod`, `fchmodat`, `utimensat` and `futimens` set what the volume's format keeps (N4.1): ext4 and `/tmp` keep the bits and the times to the nanosecond; FAT keeps read-only alone, so a mode without a write bit sets the attribute (0444, 0555), one with the owner's clears it (0644, 0755), and any other mode, and any time set by hand, is `EPERM`, as Linux's vfat answers for a mode its masks cannot represent. The package is `EROFS`. There is no `umask`, no `chown`. | `File.SetUnixFileMode`, `File.GetUnixFileMode`, `File.SetAttributes(ReadOnly)`, `File.SetLastWriteTimeUtc` and `File.Copy`, which copies the source's mode and times, work on `/data` and `/tmp` as on Linux; on `/fat`, a mode other than read-only or not and a time set by hand throw `UnauthorizedAccessException`, while `File.Copy` completes, since System.Native tolerates `EPERM` for a copy's metadata, as on a FAT volume under Linux. | N4.1, `devices_init.c`, the N1 suite, N2.2 (Roslyn's analyzer loading tests) |
| File locks | `flock` locks are those of the process's own open file descriptions. | `FileShare` behaves as on Linux within the process. No other process sees the locks. | R4.1, `libc_hello.c` |
| Shared memory | `shm_open` and `memfd_create` files live within the process, on memory objects. `/dev/shm` is the one directory in which a process creates files, and each process has its own. | CoreCLR's double mapping works. Files of `/dev/shm` are read, written, appended to and mapped as on Linux's tmpfs; a private mapping is a copy taken when it is made. `/dev/shm` holds no subdirectories (`mkdir` is `ENOSYS`), and its files are 0600 until `chmod` changes them (N4.1). Another process does not see them. | R3.2b, R7.2a, N4.1, `libc_hello.c`, the PAL suite |
| Time | UTC from the board's real-time clock. The .NET install carries tzdata's TZif files under `/usr/share/zoneinfo` with `zone.tab` (N4.1). There is no `/etc/localtime`, so the local zone is UTC unless `TZ` names one. | `DateTime.UtcNow` is right; `TimeZoneInfo.FindSystemTimeZoneById`, conversions and `GetSystemTimeZones` work with IANA ids as on Linux; `TimeZoneInfo.Local` is UTC. | R4.1, N4.1, the N1 suite |
| Globalization | ICU 78.3 with its full release data, in `/usr/lib` of the .NET install. | Cultures, culture-aware formatting, comparison and casing, normalization and IDN work as on Linux. A package without the install (NativeAOT programs, `corerun`) runs in invariant mode by its own configuration. | R4.3, N1 |
| Cryptography | System.Native's random bytes, plus the managed SHA-1/256/384/512, HMAC, HKDF, PBKDF2 and SP 800-108 implementations the browser also uses. | `RandomNumberGenerator` and the hashes work. `RSA`, `ECDsa`, `AES`, X.509 and every other algorithm throw `PlatformNotSupportedException`. | R4.1 |
| Console | Output goes to the kernel log. Standard input ends at once and is not a terminal. | `Console.WriteLine` works. `Console.ReadLine` returns null, and `Console.IsInputRedirected` is true. | R4.1 |
| Processes | There is no `Process.Start`. | `Process.Start` throws `PlatformNotSupportedException`. `Environment.ProcessId` works. | R4.1, N1 |
| File change notifications | The namespace service sends no change notifications. | `FileSystemWatcher` throws `PlatformNotSupportedException`. | N1 |
| Named synchronization objects | .NET keeps named mutexes and semaphores as files under the fixed `/tmp/.dotnet`, which is on the `/tmp` volume since N4.1, locked with `flock` and mapped shared; `flock` is the process's own. | A named `Mutex` is created, taken and released within a process as on Linux. Two processes that open the same name do not exclude each other, since the lock is the process's. | N1, N4.1 |
| Signals | Terminal and job-control signals install but are never raised, since there is no terminal service yet. | `PosixSignalRegistration.Create` and `Console.CancelKeyPress` succeed, and their handlers never run. | R4.1 |
| Platform identity | `OSPlatform.Create("WITOS")`, `PlatformID.Unix`, and the RIDs `witos-x64` and `witos-arm64`. | `RuntimeInformation.IsOSPlatform(OSPlatform.Create("WITOS"))` is true, and `OperatingSystem.IsWindows`, `IsLinux`, `IsMacOS` and `IsFreeBSD` are all false: an application that infers Windows from "not Linux and not macOS" misbehaves. Under `corerun`, the RID arrives as a property. | R2.3a, R3.3, R4.1, N1 |
| Processors | One processor schedules threads until phase P. | `Environment.ProcessorCount` is 1. | R2.2, R4.1 |
| Thread priority | Every thread runs at one priority, which is `SCHED_OTHER` at 0. | Setting `Thread.Priority` succeeds and has no effect on scheduling. A native call that asks for a real-time policy gets `ENOSYS`. | R7.1, `process_init.c` |
| Executable memory | Plain memory never executes. Code comes from the package or from the double mapping of a shared memory file. | The JIT works. A native library that maps anonymous memory executable (`mmap` with `PROT_EXEC`, `VirtualAlloc` with `PAGE_EXECUTE*` under the PAL) gets an error. | R3.2b, R7.1 |
| Threads and resources | A process may run 32 threads and hold 2048 handles, 64 events, 1024 memory objects, 1024 descriptors and 1024 shared memory files (`shm_open`'s, `memfd_create`'s and every volume file mapped shared, N4.1), and own 1 GiB of memory; the kernel holds 4096 memory objects in all, and a file of a volume mapped shared takes one for every 256 KiB. The root task tells the GC the smaller of that and the memory free when the system started (`DOTNET_GCTotalPhysicalMemory`), as a container's limit would, and the GC keeps its heap to 75% of it; `GC.RefreshMemoryLimit` does nothing, as the GC does under that knob on Linux. Thread stacks are 1.5 MiB and the main thread's 2 MiB (Linux gives 8 MiB), committed when the thread starts. A process may run an hour of processor time; past it, it ends as if by `SIGXCPU`. | Beyond a quota, thread creation fails with `OutOfMemoryException` and `open` with `EMFILE`. An allocation past the GC's heap throws `OutOfMemoryException`. A stack overflow on a thread ends the thread without the "Stack overflow" report. | R6, N2.2 |
| Hosts | `dotnet`, `hostfxr` and `hostpolicy` are upstream's, unpatched, in the shared-framework layout under `/dotnet`. The framework's deps.json is written by WitOS's tool, since upstream's CoreCLR runtime pack needs crossgen. | `dotnet App.dll` works as on Linux. The SDK's commands are not installed. | R5 |
| Code | Every method is JIT-compiled. No ReadyToRun code exists for `witos`. | Startup is slower than on Linux, and the behaviour is the same. | R3.2 |
| Networking | Absent until the network milestone. | Not exercised yet. | — |
| Diagnostics | No `createdump`, no EventPipe transport and no diagnostic IPC. | The runtime's diagnostic server fails to open its socket and runs without it. | R3.2a (trace) |
