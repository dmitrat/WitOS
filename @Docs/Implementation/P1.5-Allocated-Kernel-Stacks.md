# P1.5 — the kernel stacks out of the image

Plan step P1.5 (phase P, `P1.0-SMP-Inventory.md` section 7): a user thread's kernel stack lies in a window of the
kernel half with guard pages and takes its pages from the allocator, the static stacks per registry slot leave the
kernel image, and the registry grows from twelve slots (eight in the self-test kernel) to thirty-two. Made on
2026-10-19.

## 1. What the image held

The x64 release image measured 37.1 MiB of `.bss` with twelve slots; the thread stacks, `[12][32]` regions of 64 KiB
with their two guard pages, were 28.3 MiB of it, the pool of process records 4.35 MiB (363 KiB a record) and the memory
object table 2.3 MiB. The firmware loads the whole image into one allocation, which is why sixteen slots (52.5 MiB)
failed to load with 128 MiB (N4.3) and the self-test kernel kept eight.

## 2. The stack window

`witos/kernel_stacks.h`: the window starts at `0xFFFFA00040000000`, inside top-level entry 320 on the three ISAs, a
gigabyte above the package window and the root task image, which the same entry holds. Every user root shares that
entry's subtree: x64 copies PML4[320] by value at a root's creation, riscv64 copies root entries 256–511, and ARM64's
TTBR1, which holds the kernel half, is never switched. A stack of a slot and a thread index sits at
`window + (slot × 32 + index) × 72 KiB + 4 KiB`: 64 KiB with a guard page below and above, which is never mapped. Each
architecture makes the window's tables at boot, before any user root exists (`wit_virtual_initialize`), so that a mapping
at run time writes a leaf alone (`wit_arch_kernel_window_set`, `wit_arch_kernel_window_clear`: read and write, never
executable, supervisor alone; global on ARM64 and riscv64 as every kernel page is, x64 has no global pages) and never
allocates or panics. The boot checks that every guard of the window is unmapped. `stack_low(slot, thread)` in each
architecture's `frame.c` computes the address from the window instead of the static array, and the arrays and their
guard entries are gone.

## 3. A stack's life

- **Backing**: a thread's creation takes its stack's 16 pages from the allocator (`wit_kernel_stack_ensure`), the first
  thread of a component at its preparation, `THREAD_CREATE` as the last resource it checks before granting anything,
  refused with `NO_MEMORY` when the allocator has none left. A stack released but not yet collected is kept for the
  slot's next thread at that index.
- **Release**: a reaped thread releases its stack, a torn-down slot every stack of the slot
  (`wit_kernel_stack_release`, `_release_slot`) — never freed there, since the processor that reaps an exiting thread,
  or abandons the thread of a component another processor ended (P1.3b), still runs on that thread's stack.
- **Collection**: `wit_kernel_stacks_collect` returns the pages of every released stack no processor runs on. Each
  processor names the stack it runs on (`wit_kernel_stack_running`: the dispatcher's pick, the root task's launch, and
  none in the idle loop and on the host's stack); the name changes only under the kernel lock, which a processor gives
  up once it runs on the next frame's stack (P1.3b), so a collection under the lock sees where every processor runs.
  Every processor drops the translations of a collected page before it goes back, since the thread may have run on any
  of them (`wit_cpus_invalidate_all`). Collections run at every kernel entry, in the idle loop, after a run on the host's
  stack and after `wit_user_destroy`, so a component's stacks are back when a self-test counts the free pages.

The record pool stays a static array, sized by the registry: thirty-two records are 11.6 MiB, which the image takes
easily once the stacks are gone, while allocating records would need multi-page allocations or window mappings with
shootdowns for nothing yet. The two static scratch arrays the inventory named (a commit's rollback bitmap and a map's)
stay too: memory calls run one at a time under the kernel lock, so one array each serves every processor; a finer lock
would revisit them.

## 4. The registry

`WIT_PROCESS_CAPACITY` is 32 in both kernels. A slot costs the image its record, and its stacks cost physical memory
only while its threads exist. The kernel-wide channel table (128) and the per-process limits are unchanged.

## 5. The hang sampler

WitOS.Dev's sampler of a boot that ran past its deadline (D5.2) read the kernel stack at its stack pointer with QEMU's
`xp`, which reads physical memory and found the identity-mapped static stacks; it reads through the processor's
translation (`x`) now, which reaches the window.

## 6. The acceptance

- `process_init.c` starts twenty children that sleep three seconds, beside the root task and init: every one is still
  running once the last started (`waitpid` with `WNOHANG` answers 0 for each), and each is reaped with its code — more
  processes at once than the twelve slots before; `process` and `process-smp2` run it on one and two processors.
- The thread suite's rollback test counts the stack's 16 pages a successful `THREAD_CREATE` now takes; every other
  free-page count of the self-tests holds as before, since a component's stacks are back after its destroy.

## 7. What ran

In the Linux host's image, with the final code:

- The images' `.bss` with thirty-two slots: x64 release 15.3 MiB (37.1 MiB with twelve), ARM64 release 15.4 MiB,
  riscv64 release 15.1 MiB; the self-test kernels 23.1 MiB (x64), 22.0 MiB (ARM64) and 21.5 MiB (riscv64), where the
  x64 self-test kernel had eight slots before. `boot-128` and `release-128` load on the three ISAs.
- `test --arch x64`: PASS, all 34 scenarios; `test --arch arm64`: PASS, all 28; `test --arch riscv64`: PASS, all 28 —
  every user suite with its threads' stacks in the window, `boot-smp2` and `boot-smp4` among them; `process` and
  `process-smp2` with twenty children at once (281 and 282 checks on x64, 282 on ARM64 and riscv64 on two processors).
- `release` on the three ISAs: `release-128`, `release-512` and `release-display-256` pass.
- `runtime-terminal --arch x64`: PASS (the device manager, the drivers and the terminal service); `runtime-portable-app
  --arch x64`: PASS, 12 of 12 checks under CoreCLR's threads.

The first run failed the thread suite's rollback test, which counted no page for a successful `THREAD_CREATE`.

## 8. Left for later

- The process records and the memory object table stay static (11.6 MiB and 2.3 MiB of the x64 image).
- RISC-V implementations without Svvptc may cache an invalid leaf; a stack's first mapping is not shot down, since no
  processor touched its unmapped addresses, which QEMU and Svvptc hardware honour.
