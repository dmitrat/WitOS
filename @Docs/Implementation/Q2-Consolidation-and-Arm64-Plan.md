# Q2 — консолидация и слоение, A — ARM64-ядро, продолжение P6

Дата: **2026-10-02**. База: user ABI v48 / boot ABI v4, upstream .NET 10.0.8, HEAD `4979af0`. Источник: аудит кода после P6.4 (static DLL TLS). Этот документ фиксирует согласованный план работ; отслеживание выполнения ведётся в [PLAN.md](../../PLAN.md).

## Вывод аудита, который определяет план

По оси корректности код сильный: валидация до мутации, откат при сбое, поколенческие хэндлы, сериализация с IF=0, hash-verified upstream, строгая линковка, VM-приёмка с классификацией исхода. По оси сопровождаемости и универсальности код слабый:

- политика ядра (потоки, ожидания, объекты, APC, references, stack leases, DLL-загрузчик, исключения) лежит в `src/Kernel.Arch.X64/user_*.c`, хотя к ISA не относится; общее ядро `src/Kernel` содержит 2,5 тыс. строк против 11,2 тыс. в арх-каталоге;
- в арх-каталоге смешаны ISA-код, устройства платы q35, ~30 файлов self-test и ~20 MASM-переходников пользовательского Win32-слоя;
- две системы сборки нативного кода: рукописный список исходников в `tools/WitOS.Dev/DevTool.cs` и CMake-оверлей `runtime-overlay.cmake`; правки upstream существуют как строковые операции в C#, а не как файлы патчей;
- поздние файлы написаны в сжатом стиле (несколько операторов в строке, строки по 200+ символов), функции-диспетчеры по 100+ строк; человек не может ревьюить это при текущем темпе;
- версии расходятся: заголовок v48, PLAN v47, README v37 / boot v3, баннер `0.0.44` в `kernel.c`;
- тесты вшиты в образ ядра, релизной сборки нет; протокол гость-хост это ручные списки строк и счётчиков в C#.

Общее ядро не содержит x64-зависимостей. Политика опирается на 24 функции `wit_x64_*` и десяток обращений к полям регистров кадра прерывания. Поверхность арх-интерфейса маленькая и перечислимая; это делает слоение и ARM64 реалистичными.

## Согласованные решения

| Вопрос | Решение |
| --- | --- |
| Порядок | Q2.0–Q2.5 как ядро фазы, затем Q2.6, Q2.7, Q2.10 как предусловия ARM; A0 стартует после них, не дожидаясь конца Q2; затем P6 |
| Компилятор ARM64 | MSVC ARM64 cross tools (`Hostx64\arm64\cl.exe`, `armasm64.exe`, `link.exe /machine:arm64`), компонент Build Tools `VC.Tools.ARM64`; паритет с upstream win-arm64 codegen и unwind |
| Каталоги | `src/Kernel.Arch.A64`, `src/Kernel.Platform.Q35`, `src/Kernel.Platform.QemuVirt`, `src/Runtime.Pal.Win32`; нынешний `src/System.Native` переименовывается в `src/Runtime.Native`, имя `System.Native` резервируется под upstream-порт `SystemNative_*` |
| Стиль | `.clang-format` и `dotnet format`: лимит строки 120, скобки как в ранних файлах ядра, один оператор в строке; проверка формата в CI |

| ABI в Q2 | Не меняется. Единственное исключение: справочник и классы стабильности, без изменения номеров и структур |

## Фаза A: ARM64-ядро

Цель фазы: вторая ISA как доказательство слоения. Общая политика должна исполняться на ARM64 без изменений в `src/Kernel`. ARM идёт до заморозки ABI в P6.5, чтобы замораживать ABI, проверенный на двух архитектурах.

Среда: QEMU из pinned-пакета уже содержит `qemu-system-aarch64.exe`, `edk2-aarch64-code.fd` и `edk2-arm-vars.fd`. Машина `virt` с `gic-version=3`, TCG, EDK2, тот же FAT-образ с `EFI/BOOT/BOOTAA64.EFI`. Код завершения для тестов передаётся через ARM semihosting `SYS_EXIT`; это QEMU-специфичный механизм и живёт в `Kernel.Platform.QemuVirt`.

Технические решения:

- Уровень исполнения EL1 без EL2; процессоры `cortex-a72` для базового профиля и `max` для расширенного, по аналогии с `Nehalem` и `max` на x64.
- Два корня таблиц: TTBR1 для ядра, TTBR0 для компонента; гранула 4 КиБ, 48-битный адрес. Это естественное разделение, которое на x64 эмулируется supervisor-only слотами PML4.
- Syscall через SVC: номер в x8, аргументы в x0..x2, статус в x0, результат в x1. Регистровая часть ABI описывается в справочнике Q2.2 отдельно для каждой ISA; номера вызовов, структуры и статусы общие.
- TLS: TPIDR_EL0 для сырого TLS, x18 для compiler TLS, так как Windows ARM64 держит TEB в x18 и указатель TLS по смещению 0x58, как на x64. Раскладка страницы compiler TLS остаётся общей.
- Время от generic timer: CNTPCT_EL0 и CNTFRQ_EL0 как монотонный домен, CNTV_TVAL как дедлайн-таймер. Второй домен в духе PIT не нужен.
- Состояние FP: NEON Q0–Q31, FPCR, FPSR. SVE и SME запрещены профилем, как AVX на x64.
- Консоль PL011, прерывания GICv3, диск virtio-blk-pci, энтропия virtio-rng через EFI_RNG_PROTOCOL.
- `Boot.Uefi` параметризуется: машина PE `0xAA64`, граница 4 ГиБ для образа и пакета становится параметром платформы.

| Срез | Что делаем | Критерий приёмки |
| --- | --- | --- |
| A0 | Обнаружение MSVC ARM64, `build --arch arm64`, параметризованный `Boot.Uefi`, `BOOTAA64.EFI` грузится на `virt`, печатает контракт загрузки, выходит через semihosting. | Сценарии boot-128/512, invalid-boot-info, overlapping-map, timeout на `virt`; четыре исхода различаются |
| A1 | MMU с TTBR0/TTBR1, принадлежащие ядру таблицы, guard-страницы стеков, таблица векторов и диагностика исключений, GICv3 и IRQ таймера, контексты ядра с вытеснением, физические страницы из общего аллокатора, монотонные часы. | Матрица, эквивалентная x64 M1: BRK, undefined, data abort, guard-страницы, таймер, часы без IRQ |
| A2 | EL0-компоненты через общую политику: SVC-вход, TLS, разреженная память, потоки, события, PE-загрузка. Фикстуры получают общие C-исходники и ARM64-входы. | `UserFixture`, `ThreadFixture`, `WaitFixture`, `PeFixture` проходят на `virt` без правок в `src/Kernel` |
| A3 | Позже, внутри P6: ARM64-вариант валидатора unwind-метаданных и Win32-адаптеров. Первая по-настоящему архитектурная часть runtime. | Отдельный план после A2 |

CI: тот же runner `windows-2025` исполняет `qemu-system-aarch64` под TCG; второй job в `kernel.yml`. Реальное железо с UEFI-прошивкой это отдельный шаг после A2.

## Продолжение P6

После A2 возвращаемся к P6 в порядке PLAN.md с поправками:

- P6.4 продолжается как есть: host, startup, binding `runtimeconfig.json` и `deps.json`.
- P6.5 получает подэтап заморозки ABI: биты возможностей, правило «только добавление», двусторонние тесты совместимости (старый гость с новым ядром и наоборот), syscall-заглушка, которую поставляет ядро. Заморозка опирается на справочник Q2.2 и на проверку двумя ISA из A2.
- R1, параллельный исследовательский срез: инвентаризация libc-поверхности, которую требуют upstream `System.Native` и `pal.unix`, против Win32-поверхности текущей CoreLib, на существующем инструменте строгой линковки. Результат определяет, какая часть Win32-слоя остаётся в runtime PAL навсегда, и становится основой дорожной карты TargetOS witos.

## Таргет платформы и приложения

Вопрос, который возникает регулярно: требует ли «TargetOS witos / RID witos-x64» особой компиляции приложений. Нет. Это два разных уровня.

| Уровень | Кто собирает | Что означает witos |
| --- | --- | --- |
| Приложение | Разработчик на Windows, Linux, macOS | Ничего. Проект `Microsoft.NET.Sdk`, TFM `net10.0`, `dotnet build`, перенос `App.dll`, `App.deps.json`, `App.runtimeconfig.json`. RID не задаётся, WitOS не упоминается. Это контракт [манифеста](../WitOS-Developer-Experience-Manifesto.md) и RFC-0015 |
| Платформа | Мы, из upstream `dotnet/runtime` | TargetOS это имя ОС, под которую собираются CoreCLR, JIT, CoreLib, `System.Native`, host и shared framework. Оно даёт честные `OperatingSystem.*`, `RuntimeInformation`, разделители путей, `System.Native` и hosting PAL. Это тот «большой слой .NET», который живёт на устройстве и обновляется часто |

RID `witos-x64` появляется в потоке приложения только в трёх необязательных случаях: self-contained publish, NativeAOT и NuGet-пакеты с нативными ассетами под `runtimes/<rid>/native`. Все три перечислены как граница в разделе 12 манифеста. Чисто managed пакеты используют `lib/<tfm>` и RID не требуют.

Факт из pinned-исходников, который нужно учитывать при TargetOS: `ReadyToRunInfo::ComputeReadyToRunInfo` в `src/coreclr/vm/readytoruninfo.cpp` строго отвергает R2R-образ с чужим machine/OS override (`COR_E_BADIMAGEFORMAT`), а не откатывается на JIT. Обычный `dotnet build` даёт IL без R2R, поэтому манифестный поток не затронут. Решение о собственном `IMAGE_FILE_MACHINE_NATIVE_OS_OVERRIDE` для witos, против переиспользования значения Windows, принимается на этапе TargetOS; по умолчанию собственное значение, чтобы платформенная принадлежность образов оставалась явной.

## Правила выполнения

1. Один срез, один или несколько коммитов, матрица зелёная до перехода к следующему; PLAN.md обновляется после каждого среза.
2. Переформатирование и переносы файлов не смешиваются с изменениями логики в одном коммите.
3. Квоты, адреса и имена устройств не переезжают в общее ядро; при обнаружении такой зависимости срез фиксирует её в карте слоёв и выносит за интерфейс.
4. Утверждения о локальности или публикации изменений в PLAN.md не считаются ограничением плана.

Новые команды инструмента:

Манифест растёт в Q2.3; в CI шаг стоит в `kernel.yml`.
- `fingerprint [--compare <file>] [scenario...]` собирает сценарии `boot`, `coreclr-memory`, `coreclr-storage` с фиксированным build id в `artifacts/fingerprint/` и хэширует каждую секцию каждого нативного PE, включая подготовленный runtime-образ. Debug-каталог, его данные и метка времени экспорта маскируются.

Проверки инструментов: два независимых прогона совпали по 54 образам и 233 секциям; изменение одной строки в `src/Kernel/events.c` изменило `.text`, `.data` и `.pdata` образа ядра; `format-check` отверг нарушение в C# и неотформатированный `memory.c`. Эталон отпечатков: `artifacts/q2-baseline/fingerprint-q2.0.json`. Q2.1 меняет баннер ядра, поэтому эталоном для переформатирования Q2.3 станет отпечаток после Q2.1.

Выбранный стиль проверен на копии всех 357 нативных файлов: ошибок нет, все строки кода в пределах 120 символов, один комментарий длиннее предела правится вручную. Объём вырастет примерно с 29 до 52 тысяч строк из-за обязательных фигурных скобок и одного оператора в строке.
