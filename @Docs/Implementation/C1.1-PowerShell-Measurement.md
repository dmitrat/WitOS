# C1.1 — PowerShell on WitOS: the measurement

Plan step C1.1 measures what upstream PowerShell 7 needs to run on WitOS before anything is built for it: the package,
its native library, where it lives in the image, and what breaks at each startup stage. Everything was measured on
2026-10-16 in the Linux container on the tree of `main` (6082519) with the runtime an earlier `runtime-witos` built
(10.0.12), on x64; the trial harness is described at the end. The result is the list of facts in §3 and the work
C1.2–C1.4 inherit in §4. No PowerShell binary was patched and none will be: PowerShell is an application (RFC 0020 §59).

## 1. The package

PowerShell 7.6.7 (2026-10-13) ships a framework-dependent archive that is IL alone,
`powershell-7.6.7-linux-x64-musl-noopt-fxdependent.tar.gz` (SHA-256
`034931e34232df4854c7769299ba60618abbbef1c6b5d1f6378f38160ffc22f7`, 23.6 MB, 475 files, 69 MB extracted): `pwsh.dll`
with `runtimeconfig.json` for `net10.0` (`Microsoft.NETCore.App` 10.0.0, `rollForwardOnNoCandidateFx`), the engine, the
built-in modules under `Modules/` and the native library `libpsl-native.so` for the RIDs linux-x64, linux-arm64,
linux-arm and linux-musl-x64 under `runtimes/`. The managed part is one for every ISA, which is what WitOS needs: the
"noopt" variant has no ReadyToRun code, the ordinary `linux-x64-fxdependent` has it for linux-x64 (whether CoreCLR on
witos accepts those images or falls back to the JIT is C1.3's measurement; it decides the startup time below).

**The native library is rebuilt, not reused.** The package's `linux-musl-x64/libpsl-native.so` needs `libstdc++.so.6`
and `libgcc_s.so.1`, which the sysroot does not have (ABI-2 is libc++), and hostpolicy would not select it anyway: the
witos RIDs import `witos` and `unix-<arch>`, never `linux-musl-<arch>`. Its source is the PowerShell-Native repository,
package version 700.0.2 (tag `v700.0.1` is the nearest; 29 C++11 files under `src/libpsl-native/src`, two configure
results: `HAVE_SYS_SYSCTL_H 0`, `HAVE_SYSCONF 1`). The pinned clang builds it unchanged for both triples against the
sysroot (`--target=<triple> --sysroot=… -resource-dir=<sysroot>/usr/lib/clang/20 -stdlib=libc++ -fuse-ld=lld
--rtlib=compiler-rt --unwindlib=libunwind -std=c++11 -O2 -Wall -Werror -fPIC -shared -Wl,-soname,libpsl-native.so
-Wl,--no-undefined`): 29 KB on x64, 32 KB on ARM64, needing `libc++.so.1`, `libc++abi.so.1`, `libunwind.so.1` and
`libc.so`, all in the package's `/lib`. Placed beside `pwsh.dll`, CoreCLR loads it by the P/Invoke name from the
assembly's directory (`NativeLibrary.Load("libpsl-native", SMA assembly)` and by path both succeed in the guest;
`NATIVE_DLL_SEARCH_DIRECTORIES` is the framework's directory alone).

**It does not fit the boot package.** `WIT_PACKAGE_MAX_BYTES` is 128 MiB; PowerShell beside the .NET install exceeds it
("Assembly package byte quota exceeded"). PowerShell therefore lives on the data volume, `/data/pwsh`, and runs as
`dotnet /data/pwsh/pwsh.dll`, which is also where applications belong (M8's application directory); the quota stays.

## 2. What the guest showed, stage by stage

Each run is one boot of the device services, the .NET install and the terminal with `/etc/apps` commands; PowerShell
starts in 139–242 s of guest time per process (IL-only package, every method through the JIT under TCG).

1. **`EntryPointNotFoundException: sysctl in libc`** from `ManagedPSEntry.AttemptExecPwshLogin`
   (`src/powershell/Program.cs`). The login-shell check reads `/proc/self/cmdline` when `Platform.IsLinux` and
   otherwise takes the macOS path, `sysctl(KERN_PROCARGS2)`, so every Unix that is not Linux crashes at the first line
   of `Main`. This answers RFC 0020 §58 #1 for the first shim. The trial sets `__PWSH_LOGIN_CHECKED=1`, the variable
   the re-exec sets, which skips the check; the fix is upstream's, a `Platform.IsMacOS` guard with a plain return
   otherwise.
2. **`IOException: Read-only file system: /.cache/powershell`** from `Platform..cctor` →
   `SelectProductNameForDirectory`: PowerShell creates `$HOME/.cache/powershell`, `.config/powershell` and
   `.local/share/powershell/Modules` at startup, and the install's `/etc/environment` says `HOME=/`, the read-only
   package. With `HOME=/data/home` (the first `HOME` line wins; appending a second changes nothing) PowerShell starts.
3. **`$PSVersionTable` prints on WitOS:** `PSVersion 7.6.7`, `PSEdition Core`, `OS WitOS 0.1 ABI-1`, `Platform Unix`,
   exit 0 — RFC 0020 §57.2's first line, 139 s after the start.
4. **Every file cmdlet and every module name fail:** `Measure-Object`, `Get-Date`, `Set-Content`, `Get-ChildItem`
   "not recognized"; `Import-Module Microsoft.PowerShell.Utility` "no valid module file was found", while
   `Import-Module /data/pwsh/Modules/Microsoft.PowerShell.Utility/Microsoft.PowerShell.Utility.psd1` loads all 120
   cmdlets; `Test-Path /data/pwsh/Modules` is `False`, `Get-ChildItem /data` says "Cannot find path '/ata'",
   `Set-Content /data/pwsh.txt` writes to '/a/pwsh.txt', `Get-Content` looks for '/:/ata/pwsh.txt'. The root cause is
   one: **`DriveInfo.GetDrives()` and `Environment.GetLogicalDrives()` return nothing on WitOS.** System.Native's
   `pal_mount.c`, built for witos with `HAVE_MNTINFO 0` and `HAVE_SYS_MNTENT_H 0`, enumerates mount points with
   `setmntent("/proc/mounts")`, which does not exist, so PowerShell's `FileSystemProvider.InitializeDefaultDrives`
   creates no `/` drive (its Unix root drive comes from `DriveInfo` with `VolumeSeparatedByColon = false`), and the
   session auto-mounts a drive for the current path instead (`SessionStateDriveAPIs`), with the default colon
   semantics of a Windows drive — hence `/:` paths and names shortened by the drive's length. Module discovery by name
   resolves `Modules/<name>/<name>.psd1` through the provider (`GetResolvedPath`) and fails with it; an import by full
   path takes another route and works. `New-PSDrive -Name /` is refused ("/" is not a valid drive name), so there is no
   workaround inside PowerShell.
5. **What works once the modules are imported by path:** `1..10 | Where-Object { $_ % 2 -eq 0 } | Measure-Object`
   (count 5, §57.4), `Get-Date` with the time zone, `Get-Process -Id $PID` (pid 1, `dotnet`), `Import-Module
   PSReadLine` (2.4.5) — the engine, the pipeline, formatting, the module loader and the native library are fine.
6. **An interactive `pwsh` printed no prompt** within the remaining wall time of its boot. Not yet diagnosed; the
   hypothesis is .NET's cursor-position query (`ESC[6n`), which `Console.CursorLeft` sends and waits for and the
   terminal service of N4.3 does not answer — the item C1.2 planned for PSReadLine.

Also measured: `Platform.IsLinux` is used at 10 sites, `IsMacOS` at 6 and `IsWindows` at 39 in 7.6.7; beside the login
check, the relevant ones are the native asset folder (`linux-<arch>/.so` or `osx/.dylib`; WitOS gets an empty folder
and extension, with no visible effect so far), `$IsLinux`/`$IsMacOS`/`$IsWindows` all `$false`, syslog escaping,
`UnblockFile` (Linux xattr), the named-pipe path length and `ComputerUnix` (macOS uptime).

## 3. Facts for the record

| Fact | Consequence |
| --- | --- |
| The IL-only fxdependent package runs on WitOS as it is | the application contract holds; no pwsh file changes |
| `libpsl-native` must be built from the pinned PowerShell-Native source for both triples | a substrate build step, like ICU (R4.3) |
| 128 MiB package quota | PowerShell on a volume, `dotnet /data/pwsh/pwsh.dll` |
| `HOME` must be writable | the process environment names a home on a volume |
| `DriveInfo.GetDrives()` empty | a platform difference to fix: the mount points are known to the libc (`WIT_NAMESPACE_MOUNTS`) but not to System.Native |
| the login check's macOS path | upstream fix; the environment variable until then |
| 139–242 s per start under TCG | ReadyToRun's acceptance is C1.3's measurement |

## 4. What C1.2–C1.4 inherit

1. **Mount points for .NET.** `DriveInfo.GetDrives()` and `Environment.GetLogicalDrives()` answer with the namespace's
   mount points. Default: the libc serves a synthetic read-only `/etc/mtab` in `mntent` form from the mount table it
   already keeps (`/` as the package, then each point the service names: `/data`, `/fat`, `/boot`, `/tmp`), and
   `pal_mount.c` gets a `TARGET_WITOS` branch that opens `/etc/mtab` where Linux opens `/proc/mounts` — a patch in the
   10.0 and 8.0 sets, in RFC 0015 §4's third position (no configure check or knob covers it). `statfs` stays `ENOSYS`
   until an application needs sizes, so `DriveType` is `Unknown` and PowerShell creates exactly the `/` drive. The N1
   suite gains a `Files.LogicalDrives` check, and `Compatibility-Differences.md` records the row.
2. **A writable home.** The process environment's `HOME` names a directory on a writable volume: `/data/home` when the
   data volume is mounted, created by the namespace service with the mount; `/tmp/home` otherwise.
3. **The terminal under PSReadLine.** The service answers the cursor-position report and the rest of the VT subset
   System.Console and PSReadLine need, measured against the interactive session that printed nothing.
4. **Upstream.** Two proposals to PowerShell/PowerShell: the login check's macOS path guarded by `Platform.IsMacOS`,
   and the Unix root drive created even when `DriveInfo` reports nothing (robustness; WitOS fixes its side regardless).
5. **The real step's build.** The pinned archive by SHA-256 and the PowerShell-Native source at its tag, both through
   `setup`; `libpsl-native` built by the substrate for both ISAs; terminfo from a pinned ncurses; `TERM` and `HOME` in
   `/etc/environment`; the `runtime-powershell` scenario with the package on the data volume.

## 5. The trial harness

A command of the tool kept in the container only, `trial-pwsh` (`tools/WitOS.Dev/Commands/CommandTrialPwsh.cs`,
uncommitted): it packages the device services, the install and `apps_init.c` with the commands of a file as
`/etc/apps`, replaces `HOME`, adds `TERM=xterm-256color`, `__PWSH_LOGIN_CHECKED=1` and the container's compiled
`xterm-256color` terminfo, lays the extracted PowerShell and `home/.keep` on a 1 GiB data disk and boots the
`runtime-libraries` scenario's kernel with 1024 MiB, with or without the terminal; the guest's lines land in
`artifacts/logs/x64-runtime-libraries-1024.{serial,terminal}.log`. The diagnostic command lines are in
`/work/c1/diag-*.txt`; the built libraries in `/work/c1/libpsl-native-{x64,arm64}/`.
