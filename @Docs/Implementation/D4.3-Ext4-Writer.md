# D4.3 — The managed ext4 provider writes through the journal

D4.3 completes D4. The ext4 provider of D4.2 now writes as well as reads. Every change is one transaction through the
volume's jbd2 journal, so a power failure at any point leaves a volume that is clean once its journal is replayed, and
the change is in it whole or not at all (storage document §45–50).

The tests judge the writer by e2fsprogs (§73):

- e2fsck finds every written volume clean;
- debugfs reads what the provider wrote;
- e2fsck replays the provider's journal;
- the provider replays e2fsprogs' journal, revoke records included.

In the guest, the device manager writes the data disk's ext4 partition through the virtio driver's block channel, and
the host's e2fsck and debugfs judge it after the boot.

## Mounting

- **Writable mounts.** A resource that accepts writes mounts writable when the volume has `extents` and every
  read-only compatible feature it uses is one the provider writes: `sparse_super`, `large_file`, `huge_file`,
  `gdt_csum`, `dir_nlink`, `extra_isize` and `metadata_csum`.
- **Read-only mounts.** Everything else mounts read-only, as in D4.2: ext2 and ext3 with block maps, and volumes with
  quota, `bigalloc` or the read-only mark.
- **The journal at mount.** A writable mount first replays a journal that needs recovery, then reads the volume again.
  The superblock carries `needs_recovery` while the volume is mounted, and a clean unmount clears it.
- **A journal on a read-only mount.** A read-only mount refuses a journal that needs recovery, since it cannot write
  the replay.

## The journal (`Ext4Journal`)

Every jbd2 field is big-endian. The journal lives in the journal inode's blocks.

- **Recovery** replays whatever another implementation left, as the kernel does.
  - It scans the log from `s_start` and keeps the transactions whose commit block is present and sound.
  - It gathers the revoke records.
  - It puts each logged block in place unless a revoke in the same transaction or a later one names it.
  - It checks descriptor tails, commit blocks and data tags. Checksum v2 tags are compared on their 16 bits and v3
    tags in full, and a logged block that fails its checksum is skipped, as the kernel skips it.
  - It also handles escaped blocks, 64-bit tags and a log that wraps around.
- **A commit** writes one transaction at the start of the log with `CSUM_V3`:
  1. The descriptor blocks: tags carrying the target block and a CRC-32C of the logged copy, the UUID after the first
     tag, and the tail's checksum over the whole block. A copy that begins with the journal's magic is escaped.
  2. The commit block, carrying its own checksum.
  3. The journal's superblock, now pointing at the transaction; then a flush.
  4. The checkpoint: the blocks written in place; then a flush.
  5. The journal's superblock again, emptied.

  Before the log, a flush makes the file's data durable first, which is the journal's ordered mode. The log never
  holds more than one transaction, so no revoke record is ever written: a freed block cannot be reused while an older
  transaction still sits in the log.

## The writer

- **`Ext4Transaction`** holds each metadata block a change touches. The block is copied once and changed in the copy,
  and the volume's reads see the copy while the change runs. A file's data never enter the transaction: they go
  straight to their blocks before the commit.
- **`Ext4Allocator`** takes blocks and inodes from the groups' bitmaps and gives them back.
  - Each bitmap is checked by its descriptor's checksum when it is first read, and sealed again at the commit.
  - It keeps the groups' and the superblock's free counts, the directory counts and `itable_unused`.
  - A group whose block bitmap was never written (`BLOCK_UNINIT`) is passed over.
  - A group whose inode bitmap was never written (`INODE_UNINIT`) gets an empty bitmap, its bits past the group's
    inodes set.
- **`Ext4InodeRecord`** writes a record's fields in the transaction's copy of its inode table block and seals its
  checksum. A new record starts empty: extents, the extra size the superblock asks, all four times with nanoseconds and
  epoch bits, and a fresh generation.
- **`Ext4ExtentWriter`** writes an inode's tree anew from its runs.
  - Runs that continue each other merge, up to 32,768 blocks per extent (32,767 when uninitialized).
  - Up to four extents fit in `i_block`. Beyond that, up to four leaves sit below an index.
  - Leaves reuse the tree's old blocks first, and old blocks left over are freed.
  - Each leaf's tail carries its checksum.
- **`Ext4DirectoryWriter`** changes directory entries.
  - An entry is inserted wherever another entry has room past its name, or in a new block added at the directory's
    end.
  - An entry is removed by joining it to the entry before it.
  - Every block it touches gets its tail checksum again.
  - Inserting into an htree would need hash order, so the directory first becomes linear: its root and index blocks
    become empty leaves and the index flag goes. Removing an entry keeps the index, which stays true.
- **`Ext4Writer`** runs each change as one transaction and commits it. A change that fails leaves the volume as it
  was: nothing reached its blocks before the commit, and the descriptors and the superblock the mount holds in memory
  are restored from snapshots. The changes:
  - **Create** a file (mode 0644) or a directory (mode 0755, with its first block), in the parent's group.
  - **Write.** The blocks a file lacks come from near its other blocks. A fresh block is zeros with the data in it, a
    partly written block is read, changed and written back, and contiguous blocks go in one write. The part of an
    uninitialized extent the write touches becomes initialized.
  - **Cut or grow.** Blocks past a cut are freed and the rest of the cut block is zeroed. A growth is a hole.
  - **Remove** a file or an empty directory. With the last link, the inode and its blocks are freed and `dtime` is set.
  - **Rename.** A directory moved to another parent gets its ".." changed, and both parents' link counts follow.
  - **Times.** Each change updates ctime and mtime on the inodes it touches.
- **`Ext4FileSystem`** serializes every operation of a writable mount behind one lock; read-only mounts stay
  lock-free. A writable handle (`Ext4WritableHandle`) reads the inode as it is now for each request. Every change is
  durable when it completes.

## Tests

`tests/OutWit.OS.Tests`: 176 tests, all of which pass on Linux. On Windows, which has no e2fsprogs, 38 are skipped.

- **The writer** runs on four variants: ext4 with 4 KiB blocks, with 1 KiB blocks (several groups), without
  `metadata_csum`, and with 128-byte inodes. On each, starting from the reference tree of D4.2, it:
  1. creates nested directories;
  2. writes a 1.1 MB file in three writes around a hole;
  3. writes a note;
  4. cuts a file inside a block;
  5. writes across mkfs's sparse file and its holes;
  6. removes a file;
  7. moves a file and a directory to another parent;
  8. adds 60 entries to the htree and removes 40.

  After the unmount, `e2fsck -fn` must report the volume clean, and `debugfs dump` must read back every written file
  byte for byte. The provider then reads the tree again and checks it.

  The writer also refuses what it must: a non-empty directory, a move into itself, a name that exists, and any change
  on a read-only resource. The unmount must clear `needs_recovery`.
- **Power failure.**
  - A mount, a directory and a file are cut after each one of their writes in turn, every cut point tried. Each time
    the provider replays the journal at its next mount, `e2fsck -fn` reports the volume clean, and the file is either
    whole or absent.
  - A cut that leaves the last transaction in the log is replayed by `e2fsck -fy` itself, and the volume is then clean.
- **Foreign journal.** debugfs writes three transactions with `CSUM_V3` (two blocks, one block, then a revoke of the
  first transaction's second block). The provider's replay puts the blocks in place and leaves the revoked block as it
  was, and e2fsck then reports the volume clean.

## The scenario

- **The device manager's `Ext4Probe`** now mounts the data disk's ext4 partition writable through the block channel.
  1. It reads the tree as in D4.2.
  2. It writes: `/guest/logs` with a 200,000-byte file written around a hole, `/guest/note.txt`, 50 entries added to
     the htree `/many`; it removes `/docs/readme.txt` and moves `/link` to `/guest/link`. Each of these is one
     transaction through the journal.
  3. It mounts the partition again, reads the changes back and checks the volume.
- **The host check.** After the boot, the tool runs `e2fsck -fn` on the partition, which must report it clean, and
  uses `debugfs dump` to read the guest's files and compare them with what the guest wrote.

## Results

`runtime-services` passes on both ISAs with the same lines. After each boot, the host's `e2fsck -fn` finds the
partition clean and `debugfs` reads the guest's file and note byte for byte.

- **Before the changes.** The probe reads the tree as in D4.2, now on a writable mount, and the check is clean: 403
  files, 4 directories.
- **The changes.** It writes `/guest/logs/written.bin` (200,000 bytes around a hole) and `/guest/note.txt`, adds 50
  entries to `/many`, removes `/docs/readme.txt` and moves `/link` to `/guest/link`, all through the journal.
- **After a second mount.**
  - `/guest` holds `link`, `logs` and `note.txt`.
  - `/many` holds 450 entries.
  - Every byte reads back as written.
  - The check is clean: 454 files, 6 directories.

## Limits kept explicit

- **One transaction in the log at a time**, checkpointed before the next: four flushes per change and no grouping of
  changes. The kernel batches; correctness comes first here (§51).
- **Extent trees** of at most one index level: four leaves, 1360 extents with 4 KiB blocks. A file that needs more is
  refused as `TooLarge`.
- **No block maps are written.** ext2 and ext3 stay read-only. Block-mapped files on an ext4 volume are refused as
  `Unsupported` for writes.
- **No htree insertion.** An htree a change inserts into becomes linear, which is correct but slower for very large
  directories. `e2fsck -D` can index it again.
- **No block allocation in `BLOCK_UNINIT` groups**, no extended attributes, ACLs, quotas or symlink creation, and no
  fast commits (a journal with `FAST_COMMIT` is refused).
- **One operation at a time** on a writable mount (§52).
