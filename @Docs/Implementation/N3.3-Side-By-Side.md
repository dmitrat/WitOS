# N3.3 — Two .NET versions side by side, and ABI-2 1.0

N3.2 built .NET 8 for witos and ran an application on it. N3.3 completes N3 (RFC 0015 §7). One install holds both
frameworks, and the host picks between them as on every platform: by an application's `runtimeconfig.json` and its
`rollForward`. ABI-2 is declared 1.0, as RFC 0011 §10.2 sets for N3, the first image with two runtimes.

## The selection, in the guest

The `runtime-side-by-side` scenario boots the device services and `runtime-witos`'s .NET 10 install with .NET 8's
framework beside it. `tests/User/apps_init.c` runs the commands of `/etc/apps`, as for N1 and N2.

The application `tests/Runtime.Witos/SideBySide` (one project with the target frameworks `net8.0` and `net10.0`) is
built twice by the stock SDK, from a copy apart from the repository's build properties, as the applications of N1 and
N2 are:

- `/app/net8`: for `net8.0`, against 8.0's reference pack;
- `/app/net10`: for `net10.0`, against 10.0's.

The SDK records the target framework in each assembly, so the application can say what it was built for. The stock
SDK is the one every host has: CI's `side-by-side` job runs on the install the `linux-host` leg uploads and builds no
.NET 10 tree of its own, so the tree's compiler and reference pack are not there. It runs ten checks and prints the framework the host gave it. Its argument is the major version the
host must pick, which its first check requires.

| Command | Framework picked | Why |
| --- | --- | --- |
| `dotnet --list-runtimes` | — | It lists `Microsoft.NETCore.App 8.0.31` and `10.0.12`. |
| `dotnet /app/net8/App.dll 8` | 8.0.31 | The runtimeconfig asks for 8.0.0 with the default `Minor` roll forward. |
| `dotnet /app/net10/App.dll 10` | 10.0.12 | The runtimeconfig asks for 10.0.0. |
| `dotnet /app/net8-latest/App.dll 10` | 10.0.12 | The .NET 8 build with `"rollForward": "LatestMajor"` in its runtimeconfig. |
| `dotnet exec --roll-forward LatestMajor /app/net8/App.dll 10` | 10.0.12 | dotnet's own option does the same. |

The muxer and `hostfxr` are 10.0's. Each framework's own `hostpolicy` starts its own CoreCLR. Every run passed its ten
checks on both ISAs: the framework, the platform, tasks, threads, exceptions, a finalizer, a file, culture data, JSON
and a compiled regular expression. The scenario requires the list's two lines, each run's line naming the framework the
host picked, and every command's exit with 0.

## A defect the scenario found

The first run failed `/app/net8/App.dll`: "The application to execute does not exist". The cause was in the libc's
reader of the boot package.

A directory of the package is a prefix of names before a `/`. The libc looked for the first entry sorting after the
name and took the directory as present when that entry continued the name with a `/`. But `app/net8-latest/App.dll`
sorts between `app/net8` and `app/net8/App.dll`, since `-` is below `/`. So `/app/net8` did not exist to musl's
`realpath`, which reads every directory of a path, and `hostfxr` refused the application.

The libc now looks for the name with its `/` (`files.c`, `lookup`). The children of a directory follow one another from
there, whatever sorts between the name and them.

## ABI-2 1.0

ABI-2 is what a runtime built for witos links (RFC 0011 §9.1):

- `libc.so`, which is also the dynamic linker;
- LLVM's C++ runtime: `libc++.so.1`, `libc++abi.so.1` and `libunwind.so.1`.

At N3 it is frozen as executable rules, not as prose:

- **`build/abi2.json`** records version 1.0, the four libraries by the names a runtime links them, and the names
  `libc.so` exports on each ISA: 1647 on x64 and 1644 on ARM64.
  - **Left out:** the system layer's private `__wit_` names. Its own libwitos reaches them, and no runtime does.
  - **`ElfExports` reads the exports** from the dynamic symbol table: defined global and weak symbols of default or
    protected visibility.
- **Every sysroot build checks the record** (`SystemLayerAbi`, on both hosts):
  - each library must be there;
  - `libc.so` must export exactly the recorded names;
  - a name that disappears breaks the runtimes built against 1.0;
  - a new name is an addition, which the record takes with a new minor version, as ABI-1's rule has it.
- **A host test checks the record:** sorted, no repeats, no private names, and the C library's interface present.

LLVM's C++ runtime is ABI-2 by its sonames; its own ABI is LLVM's, and the pin of S4 fixes it.

Both runtimes link the same libraries: .NET 10 since R3, .NET 8 since N3.2. So RFC 0011 §10.2.4 holds in the image: a
runtime built against 1.x runs on every later 1.y system layer.

## Limits kept explicit

- **libwitos is not part of ABI-2 1.0.** It is still a static library (`libwitos.a`), linked into the root task and
  the NativeAOT services, and no runtime links it. RFC 0011 §10.2.2 has `libwitos.so.1` carry its major in its soname
  and `WITOS_1.x` symbol versions. That applies when libwitos ships as a shared library to a consumer outside the
  system layer; until then it is an open question of the plan.
- **No version query.** ABI-2's version is the record's; a process does not query it. musl's rule needs none: a symbol
  is there or the loader reports it missing.
- **No other combinations.** No preview frameworks, no `DOTNET_ROLL_FORWARD` from the environment, no framework
  resolution failure. The scenario covers the selections RFC 0015 §7 names.
