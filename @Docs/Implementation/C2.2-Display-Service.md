# C2.2 — The display service: a terminal on the framebuffer with the keyboard's keys

Plan step C2.2, 2026-10-17. C2.1 ([C2.1-Framebuffer-and-Keyboard.md](C2.1-Framebuffer-and-Keyboard.md)) put the
firmware's framebuffer into the boot contract and the device table, reached it through `DEVICE_MEMORY`'s windows and
drew a test pattern, and gave the virtio keyboard a driver that logged its keys. This slice makes the screen a console:
the NativeAOT service `/system/Display` draws a terminal emulator's cells into the framebuffer with a bitmap font, takes
the keys from the keyboard driver over an input protocol and serves the serial protocol to the terminal service exactly
as the virtio console driver does, so that the terminal service drives the display as one of its consoles — the main
one, whose size the terminal takes, while the virtio console mirrors it and stays the recovery console RFC 0020 §28 asks
for. A process whose standard streams are the terminal now writes on the screen and reads the keyboard, and the host
judges the screen by rendering the frame it expects with the same emulator, renderer and font and comparing it with
QEMU's screendump pixel for pixel.

## 2. The design

**The display is a console driver.** RFC 0009 §26 maps `System.Console` onto an available text terminal — a serial
console, a graphical terminal, a remote one — and RFC 0020 §31 lets a session have mirrored endpoints. The display
service therefore speaks the protocol the terminal service already drives, the serial protocol of `witos/serial.h`: a
`WRITE` paints its bytes through the emulator and the renderer before it is answered, so that what a program wrote is on
the screen when its write returns; a `READ` gives the bytes the keys produced and the emulator's answers to the queries
it serves (the cursor position report .NET's Console and PSReadLine wait for, which C1.2 found must come from the far
side of the line), held until there are any unless `NONBLOCK`; `SIZE` is the grid, 100 by 37 cells of 8 by 16 pixels on
the 800 by 600 framebuffer of both boards. The terminal service's `ConsoleLink`, the line discipline, the sessions and
the libc's `terminal.c` are unchanged: the display is one more console.

**Two consoles, one terminal.** The device manager's DEVICE message to the terminal service carries one or two
consoles: the display's console first when the display service is ready, then the virtio console. The hub keeps a list
of links: every write and every echo goes to each link in turn, the main one first, and input from any link enters the
one discipline; the size is the first link's that reports one. Which console is the main one is the device manager's
policy — the display when there is one, the serial console otherwise — and the process manager gives every process the
same terminal endpoint as before, so no process knows how many consoles show it. The serial console stays the recovery
console (RFC 0020 §28): a board without a display is unchanged, and a board with one still shows everything on the
serial line, which is also what the host judges by.

**The keyboard reaches the display, not the terminal.** The virtio input driver offers an input channel with its ready
answer (`witos/input.h`: a window attached, one `READ` outstanding, answered with evdev's events, eight bytes each, held
until a key comes; the driver queues up to 256 events for a slow client and drops the oldest beyond). The display
service holds that channel: its `KeyboardLink` keeps a `READ` outstanding beside the console channel and the device
manager's, translates each key through the US layout — the characters under Shift and Caps Lock, the control characters
under Ctrl, an ESC prefix under Alt, xterm's sequences for the arrows, Home, End, Insert, Delete, the pages and the
function keys — and queues the bytes for the console's `READ`. The layout is the US one until the input model of M9; the
driver keeps logging every key, which the scenario's judge still requires.

**The font is a pin.** Spleen 2.1.0 (Frederic Cambus, BSD 2-Clause) is pinned by the SHA-256 of its release tarball in
`src/Substrate/spleen.lock.json`, fetched and extracted by `setup`, which requires the 8 by 16 BDF and the LICENSE in
the tarball and the SPDX line in the BDF; the boot package carries both under `/system/fonts`, the display service reads
the BDF at its start (`BitmapFont.ParseBdf`: every glyph placed into the font's cell by its own box and the ascent, the
default character for what the font lacks), and the host reads the same file to render the frame it expects. The BDF
reader serves monospaced fonts of up to 32 by 64 pixels; Spleen's 969 glyphs cover Latin, Latin-1, Latin Extended-A,
the box-drawing and block elements and Braille.

**Rendering.** `FrameRenderer` draws white on black into an `IFrameSink` — the framebuffer's windows in the service
(`FramebufferSink`: all eight 64-page windows mapped for the service's life, one aligned 32-bit store a pixel, since
device memory forbids wider or unaligned stores on ARM64) and a byte array on the host (`MemoryFrame`) — redrawing only
the cells whose character changed and the cells the cursor left and entered, the cursor an inverted cell. The emulator
is `TerminalScreen` of C1.2, moved from the tool into `OutWit.OS.Display` and shared: the runner's `TerminalLink` and the
display service run the same code, which is what makes the frame judge possible.

**The judge.** The display scenario boots with the display, the keyboard and a virtio console with an empty script, so
that the virtio console mirrors the display and its transcript is exactly the byte stream the display drew. The runner
types on the keyboard through QMP (`input-send-event`, several keys an action) what the terminal probe and
`display_init.c` ask for — the actions now trigger on the terminal's transcript as well as the serial log — takes the
screendump once init printed its last line, keeps the transcript of that moment beside it, and presses Enter so that init
ends. The host then feeds the transcript — from the terminal probe's prompt on, since the firmware writes its own console
output to the virtio console before the terminal exists and the display never saw it — to a `TerminalScreen` of the
screen's grid, renders it with the pinned font into a `MemoryFrame` of the screendump's size and requires the screendump
to equal it pixel for pixel
(`Screenshot.RequireFrame`): the plan's C2.3 judge, brought forward because the renderer and the emulator were on the
host already. The test pattern of C2.1 is still drawn by the device manager's probe before the display service takes the
framebuffer, as the measurement of the `DEVICE_MEMORY` path; the service clears it when it starts.

## 3. The protocols

`witos/input.h` (version 1): `ATTACH` with the window (one page) in the handle slot; `READ` with the bytes the events may
fill and their offset in the window, `NONBLOCK` for an answer at once; the reply's `Length` the bytes written; a
`WitInputEvent` is `Type` (0 synchronization, 1 key), `Code` (the evdev key code) and `Value` (1 down, 0 up, 2 repeat).
Errors are the serial protocol's: `EINVAL`, `EOPNOTSUPP`, `EPROTO`, `EBUSY` for a second `READ` while one waits.

`witos/display.h` (version 1): `WIT_DISPLAY_START` carries the framebuffer's descriptor as `WitDriverStart` does, the
framebuffer device in the first handle slot (the device manager's last reference, so that the service becomes its holder,
ABI-1 1.2) and the keyboard driver's input channel in the second when the board has a keyboard; the service answers with
a `WitServiceStatus` whose one handle is the end of its console channel. `WIT_DISPLAY_PATH` is `/system/Display`,
`WIT_DISPLAY_FONT` the BDF's path in the package.

`witos/terminal.h`: `WIT_TERMINAL_DEVICE` carries one or two consoles, the main one first. Nothing of the three is an
application API; applications see `System.Console` through the libc.

## 4. The device manager

After the namespace service and the display probe, the device manager starts the display service when the table holds a
framebuffer and an `InputDevice` driver is ready — a console needs input, so q35's VGA card in the scenarios that boot
without a display leaves the terminal on the serial console and the framebuffer for a later display service, which the
device manager says (`display service /system/Display not started on firmware/framebuffer: no keyboard`): it acquires the
device, takes the input driver's channel, starts
`/system/Display` through the process manager with the grant of a channel and moves the device, its descriptor and the
keyboard's channel to it (`DisplayActivation`), and keeps the console channel the ready answer brings. Then it starts the
terminal service with the consoles it has — the display's, the virtio console's, or both — and probes the terminal as
before. The stop order is the terminal service (which holds the consoles' channels), the display service (which holds
the keyboard's), the namespace service, then the drivers; each answers before the next stops.

## 5. The scenario

`runtime-display` (`RuntimeDisplay`, after `runtime-terminal` in `runtime-witos`): the device services with the display,
the keyboard and the mirroring virtio console; the runner types `hello` and Enter on the keyboard once the terminal
probe reported, and the probe echoes the line to the terminal and the log; `/bin/init` (`display_init.c`) checks that
its streams are a terminal of 100 by 37, asks for a line, which the runner types on the keyboard (`screen` and Enter),
prints it back and reports its four checks; the runner takes the screendump, keeps the transcript and presses Enter. The
scenario requires the display service's ready line (the geometry, the windows, the grid, the font's glyphs, the
keyboard), the terminal service's two consoles, the probe's echo, the keyboard driver's first key, init's echo and final
line, the stops in their order and the root task's zero — and the screendump equal to the frame the host rendered.

## 6. Results

In the container (the image of `build/linux/Dockerfile`, QEMU 11.1.0 under TCG), on the services `runtime-services`
published for each ISA:

- `runtime-services`: the five boots of the devices scenario passed on x64 and ARM64 as before; the device manager says
  `display service /system/Display not started on firmware/framebuffer: no keyboard` on x64, where q35's VGA card gives
  the firmware a framebuffer, and the terminal stays on the serial console.
- `runtime-display`: **PASS on x64 and ARM64**. The keyboard driver on slot 6 (`pci/00:06.0/1af4:1052`, line 5 on q35,
  shared with the entropy source), the console driver on `pci/00:04.0/1af4:1003`; the display service:
  `800 by 600 BGRX in 8 windows, 100 by 37 cells of 8 by 16 (969 glyphs of spleen-8x16.bdf), the keyboard's keys: serving
  the serial protocol`; the terminal service: `100 by 37, 2 consoles, canonical with echo`, `on firmware/framebuffer,
  mirrored on pci/00:04.0/1af4:1003`; the probe `100 by 37, canonical with echo` and `echo: hello` after the keys
  `h e l l o ret` typed through QMP (`[VIRTIO-INPUT] key 35 down` first); `/bin/init` on the display's terminal:
  `[DISPLAY-INIT] started`, `type a line`, `echo: screen`, `display on x86_64: 4 checks passed` (and `aarch64`); the
  stops in order (`terminal service: 1 sessions stopped, 2 consoles released`, `display service ... stopped after 205
  bytes, the framebuffer released`, 207 on ARM64), `/bin/init exited with 0`. The host rendered the frame from the
  transcript's 205 (207) bytes from the probe's prompt on — eight lines — and the screendump of each ISA **equalled it in
  all 480,000 pixels**. The screendumps show the eight lines of white text on black in the top left of the screen with
  the cursor's inverted cell below them.
- Host: 199 tests of `OutWit.OS.Tests` (the BDF reader, the layout, the renderer, the codecs, the display start) and 96 of
  `WitOS.Dev.Tests`; `format-check` clean; the C# projects of the display service and the input driver build on Windows.

Two guest runs preceded the pass: the first with every scenario timing out because the console driver's line was taken
(§7), the second with the frame judge failing in 11,312 pixels because the virtio console's transcript began with the
firmware's own console output (`BdsDxe: loading Boot0001 ...`), which the display never received; the judge now starts
at the terminal's first bytes, the probe's prompt.

## 7. Findings

- **Five virtio devices on four INTx lines.** Both boards route a slot's INTA by the slot's number modulo four (q35's
  PIRQ E–H to lines 10, 11, 5, 6; virt's interrupt map to four SPIs), and the kernel binds a line once (RFC 0011 §7.7: a
  binding is one per line kernel-wide). With the boot disk (slot 1), the keyboard (2), the entropy source (3), the data
  disk (4) and the console (5), the console landed on the boot disk's line: `PCI INTx: 0:1.0 ... line 11`, `0:5.0 ...
  line 11`, and the console driver's binding was refused with `EBUSY` on both ISAs — the terminal came up with the
  display alone, nothing reached the transcript, and the scenario waited for input that never came. The runner now
  puts the keyboard on slot 6, whose line is the entropy source's, which nothing binds once the firmware reset the
  device, so the four devices drivers hold have four lines. A sixth bound device needs shared level lines (a line
  fanned out to every binding, unmasked when all acknowledged) or MSI-X — a question for phase P, recorded here.
- **The display needs a keyboard to be a console.** q35's VGA card gives every scenario a firmware framebuffer; a display
  service there would have made `/bin/init`'s terminal the screen and taken its lines out of the serial log of every
  scenario the host judges. The device manager starts the display service only beside a ready `InputDevice` driver.
- **The screen worked at the first guest boot.** Before the console's line was fixed, the keys typed through QMP already
  reached the terminal through the display service — `[DEVICES] terminal probe: echo: hello` on both ISAs — and the
  display service reported the font's 969 glyphs and 100 by 37 cells; what failed was the mirror, not the display.
- **A gate that kills itself.** `pkill -f pattern` inside `docker exec bash -c` matched its own command line and killed
  the shell (exit 137); the patterns are written `qemu-syste[m]` since.

## 8. What C2.3 inherits

PowerShell on the screen: `runtime-display` with pwsh and the keyboard on both ISAs, C1 on the screen. Two questions
this slice leaves open: a scroll redraws almost every cell (37 rows of 100 cells, 128 pixels each, through device
memory), which pwsh's output will make frequent, so the renderer may need to move rows instead of redrawing them; and
with two consoles the runner's `TerminalLink` and the display both answer the cursor position query, which C1.2 found
breaks input when two answer — the runner's side should stop answering while a display is the main console. The layout
stays US until M9's input model; colours (SGR) are parsed and ignored, as on the serial console.
