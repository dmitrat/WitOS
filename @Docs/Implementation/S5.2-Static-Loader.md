# S5.2 — the static ELF loader in the root task (ABI v68)

Plan step S5.2 starts a program of the boot package in a new process
([RFC 0011 v3 §7.8, §9.3](../RFC-0011-Kernel-Architecture-and-ABI.md)). The kernel reads no image: it gives the
creator an empty address space with one channel endpoint (`PROCESS_CREATE`), mappings into it (`MEMORY_OBJECT_MAP`
naming the process) and a first thread in it (`THREAD_CREATE` version 3), all present since K5.2c. What was missing
lies in layer 2: a program format another process can start, its startup, the loader, and a way to give the new
process the root task's output. This step adds those and the first message of the process manager's protocol of S6.

## What changed

**The kernel (ABI v68).** The kernel log becomes a capability that moves. `HANDLE_DUPLICATE` accepts a console handle
and attenuates it like the clock's (`WRITE`, `DUPLICATE`, `TRANSFER`; no record behind the handle), `CHANNEL_SEND`
moves it with `TRANSFER`, and the root task's log handle carries all three rights. RFC 0011 §7.1 calls `DEBUG_WRITE`
the root task's output before any service exists; the processes the root task starts are part of that output until
the console service of phase D. Nothing else in the kernel changes.

**The program format.** A started program is a static position-independent executable: ELF `ET_DYN` with
`PT_DYNAMIC`, no `PT_INTERP`, linked by lld with `-static -pie --no-dynamic-linker -z text -z max-page-size=4096
-z norelro --eh-frame-hdr` (`MuslLibc.LinkStartedProgramAsync`). A static program at a fixed address cannot be
loaded by another process, because a creator maps only into the target's dynamic arenas, and position independence is
what `ld.so` needs in S5.3 anyway. The build refuses a program with a relocation that is not relative, a needed library
or text relocations (`StartedProgram.Validate`): musl's `dlstart.c` applies relative relocations and nothing else.
The scenario's program has 9 relative relocations on x64 and 120 on ARM64.

**The startup (`src/Substrate/libc/rcrt1.c`, `start.c`).** `rcrt1.o` is musl's `ldso/dlstart.c`, included unchanged
the way musl's own `crt/rcrt1.c` includes it and compiled with musl's options for its startup files (`-DCRT -fPIC`).
`_start` takes the stack the creator built, the first stage finds the base through `PT_DYNAMIC` and applies the
relocations, and the second stage calls `__wit_start_program` before `__libc_start_main`. That function reads
`WIT_AT_START` from the auxiliary vector, receives the start message on that endpoint (waiting if it is not there
yet), fills the library's process context, closes the endpoint and sets up the main thread's record and the fault
callback, as crt1 does for the root task. A start without the vector entry or with a malformed message ends the
process with 127. The library's process context (`witos/libc_context.h`) replaces the startup descriptor pointer the
libc used before: the log, the package and its size are all the library reads, and the root task's crt1 fills them
from the kernel's descriptor.

**The start protocol (`src/Sysroot/include/witos/start.h`).** The auxiliary vector carries `WIT_AT_START`
(`0x57490001`, beyond musl's `AUX_CNT`, so musl's own startup ignores it), the child-local handle of the endpoint
`PROCESS_CREATE` installed. The start message is a `WitStartMessage` (version, size, the package's size) with two
handles: the log (`WRITE|TRANSFER`) and the package (`MAP|EXECUTE|QUERY|TRANSFER`). The creator sends it before it
starts the thread and closes its own end at once; the started program closes the other end once the message arrived,
so the channel is not charged to the creator while the program runs. Arguments and the environment are on the stack,
as Linux puts them; S6 moves the rest of the process's initial state into this protocol.

**The loader (`src/Substrate/libwitos/spawn.c`, `witos/spawn.h`).** libwitos is WitOS's library of layer 2 beside the
libc, built into `libwitos.a` (`LibWitos`). `witos_spawn(&process, path, argv, envp)` opens the file through the libc,
learns its bytes in the package (`__wit_file_map_source`), and checks the whole ELF before anything is created: a
64-bit little-endian `ET_DYN` of the ISA; loadable segments readable, never writable and executable at once, ascending
on distinct pages within 64 MiB, congruent to their file offsets modulo the page, inside the file, zero-filled only
where writable; a dynamic section, no interpreter, no executable stack; the entry in an executable segment; the
program headers inside a loaded segment. Then it creates a channel and the process and lays the program at the start
of the process's code arena, where the kernel places no reservation of its own:

- a segment that is not writable is a mapping of the package's own pages, `READ` or `READ|EXECUTE`, in windows of at
  most 64 pages; executable windows are first mapped into the loader, published with `CODE_PUBLISH` (the cache
  maintenance acts on the pages, so every mapping of them sees it) and released;
- a writable segment is anonymous objects of at most 64 pages, filled through a view of the loader's own with the
  file's bytes and zero elsewhere, mapped `READ|WRITE` into the process; the loader closes its handle and the
  process's mapping keeps the object;
- the first stack is one object of 64 pages at the top of the code arena, with nothing mapped below it. On it the
  loader builds what a Linux kernel builds: argc, argv, envp and the auxiliary vector (`AT_PHDR`, `AT_PHENT`,
  `AT_PHNUM`, `AT_PAGESZ`, `AT_ENTRY`, `AT_RANDOM` with 16 bytes from `RANDOM`, the user and group ids, `AT_SECURE`,
  `AT_HWCAP`, `WIT_AT_START`), with the strings above. There is no `AT_BASE`: `dlstart.c` would take it for the
  base of an interpreter.

Finally the loader sends the start message and creates the thread at the entry, closing the thread handle; the
process runs with its own threads, signals, files and heap. A failure after `PROCESS_CREATE` closes the process
handle, and a process without a thread ends with its last handle and takes its mappings along. `witos_wait` waits on
the process handle and reads `PROCESS_QUERY`.

## Tests

- The root task fixture (`tests/User/root.c`, every suite's root task): a duplicate of the log with `WRITE|TRANSFER`
  moves over a channel, is gone from the sender's table, and writes `[ROOT] log delegated` from where it arrived; a
  duplicate without `TRANSFER` is refused by the send, and one without `DUPLICATE` has no duplicates.
- The `spawn` scenario of both suites: `tests/User/spawn_main.c` runs as the root task over the libc and libwitos
  (31 checks) and starts `/bin/child` (`tests/User/spawn_child.c`, 18 checks of its own). A missing file is `ENOENT`,
  a text file and `/dev/zero` are `ENOEXEC`, and 80 KiB of arguments are `E2BIG`, all before any process exists. A
  program with three arguments and an environment checks its relocated pointers, its auxiliary vector, the
  environment, a package file, thread-local storage in a second thread, a MiB of heap and a raised signal, and exits
  with 7. Two programs run at once at the same addresses and exit with 9 and 7. An aborted program exits with 134,
  and a program waiting in `pause` is ended by `PROCESS_KILL` with 99. Afterwards the kernel's free memory and the
  root task's reservation count equal what they were before the first start. The suite requires the child's first
  line and the root's last.

## Limits kept explicit

- Only static programs start: a program with `PT_INTERP` is `ENOEXEC` until `ld.so` (S5.3).
- Memory objects of a started program's writable segments and stack are charged to the creator while it lives, as
  every object is; each start holds two of the creator's eight live objects (more for a writable segment beyond 64
  pages), so a root task runs at most four started programs at once. The process's own allocations are its own.
- The first stack is fixed at 64 pages; it does not grow. Arguments and environment take at most a quarter of it.
- The program lies at a fixed base, the start of the code arena; there is no address randomization.
- A started program's process has the full profile's 32 reservations, as the root task has; the image and the stack
  take four of them, and a program whose mappings, allocations or threads need more fails with `ENOMEM`.
- The log is the only output and the package the only file system a started program receives; there is no current
  directory but `/`, no inherited descriptors and no `posix_spawn` until the process manager (S6).
