# D6.3 — A failing disk, and what it says

D6.3 is the last step of D6. It meets M5 §52's fifth condition: storage failure produces meaningful diagnostics.

A device that fails a read now produces these diagnostics:

- **The driver** logs the device and the failed request.
- **The namespace service** logs the file and the operation the failure hit.
- **The program** gets `EIO` from `read`.
- **The system** goes on: the same session reads the rest of the volume, and the boot ends with its services stopped
  and the volume clean.

## What each layer says

| Layer | What it does with a failed read |
| --- | --- |
| The virtio queue (`VirtioBlockQueue`) | Names the request and the device's status: `the device failed a read at sector S: status 1 (VIRTIO_BLK_S_IOERR)`. A write and a flush are named the same way, and status 2 is `VIRTIO_BLK_S_UNSUPP` |
| The driver (`BlockServer`) | Logs `[VIRTIO-BLOCK] driver of <device>: <that>; the client gets EIO` and answers the block protocol's request with `EIO`, as before |
| The block layer (`ChannelBlockStorage`) | Throws `IOException`: `The driver answered READ of N bytes at O with errno 5.` |
| The filesystem provider | Lets the device's failure through unchanged. It is no filesystem error, so it maps to no `FileSystemError` |
| The namespace service (`NamespaceSession`) | Catches the `IOException`, logs `[NAMESPACE] a read of /data/big.bin (N bytes at O) failed below the volume: <the block layer's message>` and answers `EIO`. Before this step the session caught nothing of the kind, and the connection logged a request number |
| The libc and the program | `read` returns -1 with `errno` `EIO` |

## The scenario's fifth boot

**The failing disk** (`BootRequest.DataDiskReadErrors`). The runner puts QEMU's `blkdebug` between the raw format and
the data disk's image:

- an `inject-error` rule per sector, for `read_aio` events and reads;
- the drive given `rerror=report` and `werror=report`, so virtio-blk reports `VIRTIO_BLK_S_IOERR` to the guest instead
  of stopping the board.

Every read that covers such a sector fails with `EIO`; every other request passes.

**The failing sector.** `RuntimeDataDisk.Ext4SectorAsync` finds the disk's sector of `/big.bin`'s first data block:
`debugfs -R "bmap /big.bin 0"` on the ext4 partition, then the partition's start plus the block times eight. It maps
the file's first logical block. `blocks` would list the extent tree's blocks too, and those are metadata that the ext4
probe's check reads. The DM's
probes and the services read no data of `/big.bin`, only metadata, so the first read of that sector in the boot is
`/bin/init`'s.

**What `/bin/init` does** (`FAIL_BOOT`, after the files the cut left):
1. It opens `/data/big.bin` and reads its first bytes.
2. It requires `EIO`.
3. It requires `/data/hello.txt` to still read.
4. It goes on with everything else: the POSIX checks, the programs from the volume, the stop.

**The required lines** follow the failure through the stack:
- the driver's line with `VIRTIO_BLK_S_IOERR`;
- the namespace service's line naming `/data/big.bin`, with the block layer's `errno 5`;
- `/bin/init`'s line: `EIO (Input/output error); /data/hello.txt still reads`.

After the boot, the host checks the disk as after every stopped boot, reading the image directly, without blkdebug.

## Tests

`tests/OutWit.OS.Tests`: a namespace session over a FAT volume whose disk starts failing reads. The read gets `EIO`,
never an exception, and once the disk answers again the same handle reads the file.

## Results

`runtime-services` passes on both ISAs, five boots each. On both, `/big.bin`'s first block lies at sector 29280 of
the data disk, and the fifth boot prints:

```
[VIRTIO-BLOCK] driver of pci/00:04.0/1af4:1001: the device failed a read at sector 29280: status 1 (VIRTIO_BLK_S_IOERR); the client gets EIO
[NAMESPACE] a read of /data/big.bin (16 bytes at 0) failed below the volume: The driver answered READ of 512 bytes at 14991360 with errno 5.
[DEVICES-INIT] a read of /data/big.bin on the failing sector: EIO (Input/output error); /data/hello.txt still reads
```

The device is `pci/00:03.0` on ARM64. Then the boot runs everything else: 60 POSIX checks, the System.IO check's 10
areas, the programs from the volume. Its services stop and its volume is clean.

In the same runs, the cut boot of D6.2 fell inside a journal transaction on x64, and the fourth boot replayed 1
transaction.

M5 §52 is met:

| Condition | Where it is met |
| --- | --- |
| A virtio storage device is usable | D2, D3.2 |
| Files survive reboot | D6.1, and through a cut, D6.2 |
| Directories can be enumerated | D4, D5.1, D5.2 |
| An executable can be loaded from storage | D5.3 |
| Storage failure produces meaningful diagnostics | D6.3 |

## Limits kept explicit

- **A read of chosen sectors fails.** A device that fails writes is reported the same way: the block protocol's `EIO`,
  then the provider's failed change. A change that fails part-way leaves what the journal's order leaves (D4.3), but no
  guest scenario fails a write.
- **No retry, and no health state.** A failed request fails once, upward. Nothing remembers that a device failed or
  takes a disk out of service.
- **The log is the console.** The lines go to the kernel log as every service's output does. There is no structured
  event or diagnostic channel yet.
