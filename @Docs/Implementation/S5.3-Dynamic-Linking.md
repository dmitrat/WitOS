# S5.3 — dynamic linking: musl's libc.so and ld.so

Plan step S5.3 runs dynamic programs ([RFC 0011 v3 §9.1, §9.3](../RFC-0011-Kernel-Architecture-and-ABI.md)): musl
built as `libc.so`, which is also its dynamic linker, programs with `PT_INTERP`, their `DT_NEEDED` libraries from
the boot package, `dlopen` and `dlsym`, and TLS modules. Layer 2 does all of it with the calls S5.1 and S5.2 already
use; the kernel does not change and ABI-1 stays at v68. The shared C++ runtime and the acceptance of phase S follow in
S5.4.

## What changed

**libc.so (`MuslLibc.BuildSharedAsync`).** As musl's Makefile does, every source of `libc.a` is compiled again with
`-fPIC`, `ldso/dlstart.c` and `ldso/dynlink.c` join them, and the objects are linked with `-shared -e _dlstart` and
the linker options musl's configure finds (`--dynamic-list=dynamic.list`, `--hash-style=both`, `--no-undefined`,
`--exclude-libs=ALL`, `--gc-sections`, `--sort-section=alignment`). WitOS's part of the library joins with `-fPIC`,
without the startup objects of static programs. `Scrt1.o` is musl's `crt/Scrt1.c`. The file sits in the boot package
at musl's `LDSO_PATHNAME`, `/lib/ld-musl-<arch>.so.1`; a program's `DT_NEEDED` "libc.so" is the linker itself, as
musl resolves it. Linking the whole library needs the complex multiplication builtins of compiler-rt (`__mulsc3`,
`__muldc3`, `__mulxc3` on x64, `__multc3`), which the pin now carries beside the binary128 helpers; an entry may name
the architectures compiler-rt's CMake builds it for.

**The start hook (`patches/musl/dynlink.c.patch`).** The dynamic linker opens libraries and may write a diagnostic
before the program's own startup runs, so the start message has to arrive first. The patch calls
`__wit_start_program` in `__dls3`, right after the auxiliary vector is decoded and before anything is opened, as
`rcrt1.c` does for a static program before `__libc_start_main`. The patch is the only change to musl's dynamic
linker, applied through `UpstreamPatches` to the pinned bytes of `ldso/dynlink.c`.

**No TLS in libc.so.** musl's dynamic linker gives no TLS module to itself, so `libc.so` may have no thread-local
variable; the first attempt faulted in `__syscall_cp_asm` at a `__tls_get_addr` that returned zero. The library's
three thread-local words (the signal hold count, the signal that arrived while held, the cancellation point in
flight) moved into the thread records `thread.c` keeps, as a `WitThreadLocal` found by the thread pointer without a
system call: the FS base's first word on x64, TPIDR_EL0 on ARM64. The record of a thread the library created carries
the pointer it was created with; every other pointer is the main thread's, whose pointer musl moves during startup.
Before musl installs the main thread's pointer there is no state: x64 learns that from WitOS's own
`__set_thread_area`, ARM64 from a zero TPIDR_EL0. The constructor that used to set a readiness flag is gone. The main
thread's id is 1 from the start, since the dynamic linker reads it through `set_tid_address` before the start
message completes the record.

**membarrier.** `dlopen` of a TLS module installs its TLS for the threads that exist and then issues
`membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED)`. The libc serves the private expedited barrier with
`PROCESS_WRITE_BARRIER`, which fences every online processor; registration needs nothing, and the other commands are
`EINVAL`. musl's fallback over signals is not used.

**The loader (`witos_spawn`).** A program's `PT_INTERP` names an absolute path of the package. The loader checks the
interpreter as it checks a static program (and refuses an interpreter of an interpreter), requires `PT_PHDR` of a
dynamic program, since musl's linker finds the program's base by it, maps the program at the start of the code arena
and the interpreter 64 MiB above it, adds `AT_BASE` (the interpreter's base) to the auxiliary vector and starts the
thread at the interpreter's entry. A missing interpreter is `ENOEXEC`. The dynamic linker run as a command,
`/lib/ld-musl-<arch>.so.1 /bin/dynamic`, is a static image for the loader, and the linker maps the program itself.

**Images another component maps.** A shared library and a dynamic program link with
`-z separate-loadable-segments`: every loadable segment starts a page of the file. A file with code is then at least
a page long, so the package writer places it at a page boundary, and `mmap` of its executable segment shows the
package's pages without a copy and without data beside the code. The first libraries of the scenario were smaller than
a page, unaligned in the package, and their executable segments were refused with `EACCES`.

## Tests

The `spawn` scenario of both suites adds a dynamic program, `tests/User/dynamic_main.c` (22 checks), with its
library `lib/libdynamic.so` (`tests/User/dynamic_library.c`) and the library it opens, `lib/libplugin.so`
(`tests/User/dynamic_plugin.c`). The program checks:

- the library's constructor ran, its function is bound, and its data is written by the program and seen by the
  library;
- the library's TLS in the main thread and in a second thread;
- `dladdr` names `/lib/libdynamic.so`, `dl_iterate_phdr` finds the library and the linker, and `dlsym(RTLD_DEFAULT)`
  finds the library's function;
- `dlopen` of a missing library fails with `dlerror` set;
- `dlopen("libplugin.so")` finds the plugin on the default path, and `dlsym` finds its data and its function and
  refuses a missing symbol;
- the plugin's TLS is reached from the main thread, from a thread that started before the module was loaded and from
  one started after it, each with its own copy;
- a second `dlopen` returns the same handle, and a raised signal reaches its handler.

The root task starts it twice. Once the loader maps the program and the linker, and the program exits with 5. Once
the linker runs as a command, loads the program itself, and the program exits with 6. The root task makes 39 checks;
the kernel's free memory is the same before and after. The program reports the kernel reservations its process
holds: 21 of 32.

## Limits kept explicit

- The C++ runtime is still static only; `libc++.so`, `libc++abi.so` and `libunwind.so` and the acceptance of phase S
  (a dynamic program with threads, a C++ exception and a signal) are S5.4.
- A dynamic process holds 21 of its 32 reservations with two small libraries: every mapping, every split of the
  library span and every thread stack takes one. Larger programs need a larger reservation table, which S5.4 has to
  measure and provide.
- `dlclose` is musl's: libraries stay loaded. There is no lazy binding, as in musl.
- Library search is musl's default path, `/lib:/usr/local/lib:/usr/lib`, and `LD_LIBRARY_PATH`; there is no
  `/etc/ld-musl-<arch>.path` in the package.
- Private file mappings are copies (S5.1): a library's read-only segments and its first span cost committed pages.
- Programs sit at fixed bases in the code arena; libraries go where the kernel places reservations. There is no
  address randomization.
