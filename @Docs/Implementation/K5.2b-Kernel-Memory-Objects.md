# K5.2b — Memory objects in the kernel's table (ABI v60)

Plan step K5.2b prepares the processes of [RFC 0011 v3 §7.8](../RFC-0011-Kernel-Architecture-and-ABI.md) without
changing ABI-1: the memory objects of §7.2, which K5.1 kept in a table per component, move into one table of the
kernel. A handle that crosses a channel between two processes and a mapping into another process (K5.2c) must name
the same object by the same number, and an object's pages must outlive the component that created it when another
process still refers to them; neither is possible while the object and its pages belong to one component's records.
The call-by-call reference is [ABI-Reference.md](ABI-Reference.md); the processes themselves, `PROCESS_CREATE`,
`THREAD_CREATE` into another process and `MEMORY_OBJECT_MAP` with a process as the target are K5.2c.

## What changed

**One table.** `WitMemoryObjectTable` is a kernel-wide record of `WIT_MEMORY_OBJECT_TABLE_CAPACITY` (64) objects in
`user_memory_object.c`; an object's number is its index plus one, the same in every process, in every handle, every
mapping record (`MappedObjects`), every pin and every capability in flight. `WitUserProcess` no longer carries a
table. A component's quota is `WIT_MEMORY_OBJECT_CAPACITY` (8) *live objects it created*: `MEMORY_OBJECT_CREATE`,
the adoption of a device region or the device table (K3.1) and of the boot package (K4) all count against it, and
the ninth is `NO_MEMORY` as before.

**An object owns its pages.** An anonymous object's pages come from the kernel's page allocator, zeroed, and go back
to it with the object's last reference; they are no longer entries of the creator's `OwnedPages`. The creator is
charged for them instead: `WitUserSpace.ChargedPages` counts the pages of the live objects the component created
and is bounded, together with `OwnedCount`, by `PageLimit`, so a page a memory object holds is a page the component
cannot commit, exactly as before. `MEMORY_QUERY`'s `OwnedBytes` and the memory-pressure derivation count both. The
charge is taken all or nothing before any page is allocated and rolled back with a failed allocation; the object's
end takes it off; the component's teardown orphans the objects it created and still live (`Creator` becomes zero),
which then live on uncharged with the references other holders have.

**A component's references end with it.** At its exit (`wit_user_finish`), before the handle table is wiped: the
channels drop every queued message (`wit_user_channels_drop`), so that capabilities in flight — memory objects,
devices, interrupts, pins, events, endpoints — return to their objects while the records that count them still
exist; then the interrupt bindings, the pins (each releasing its object's reference) and the devices are reset, and
every memory object handle releases its reference (`wit_user_memory_objects_release_handles`). At its teardown
(`wit_user_destroy`), the same order runs for a component torn down without an exit, and then every mapping releases
its reference (`wit_user_memory_objects_release_mappings`) and the charges are orphaned, before the address space is
destroyed. An object referenced only by the mappings of an exited component therefore lives until the teardown, and
a test can see it there.

**A dropped message leaves the queue before its capabilities are released.** `drop_queue` copies a message's
capabilities, dequeues it, then releases them. A release may close another endpoint whose queue drops within and may
come back to the endpoint being dropped; with the message already out of the queue the recursion sees a consistent
queue. The drop of a whole component runs in two passes: every live end's queue first, with every end still live so
that a capability to an end of the component finds its record, then every end its handles kept is closed.

## Kernel

- `memory_object.h`: the object record gains `Creator` and `Allocator`; the table has 64 entries and is the kernel's;
  `wit_memory_objects_live`, `wit_memory_objects_charged`. `limits.h`: `WIT_MEMORY_OBJECT_TABLE_CAPACITY`.
- `user_memory_object.c`: the static table; `reserve_entry` (the creator's quota, a free entry), `publish`,
  `release_object` (pages to the allocator, the charge off the creator); `wit_user_memory_object_release`, `_kind`,
  `_retain` and `_pages` take the object number alone; `wit_user_memory_objects_release_handles`,
  `wit_user_memory_objects_release_mappings`, `wit_memory_objects_orphan`.
- `user_space.c`: `ChargedPages` in `allocate`'s bound, `wit_user_space_charge`, `wit_user_space_uncharge`,
  `wit_user_space_take_mapped_objects`; `wit_user_space_allocate_pages` and `wit_user_space_free_pages` are gone.
  `user_pressure.c`: the quota headroom counts the charge.
- `user.c`: the exit and teardown orders above; a fresh component asserts that nothing is charged to its record.
  `user_channel.c`: `drop_queue`, `wit_user_channels_drop`. `user_dma.c`: `wit_user_pins_reset` releases the objects
  of live pins. `user_device.c`, `root_task.c`: the new signatures.

## Fixtures

`tests/User.X64/memory_objects.asm` and `tests/User.A64/memory_objects.asm` gain the mode `User.MemoryObjectExit`,
driven by `tests/Kernel/user_memory_object_tests.c`: the fixture creates an object, maps it, duplicates its handle
and sends the duplicate through a channel it leaves open, creates a second object and exits with everything live.
The kernel checks after the exit that no handle or channel survived, that one message was dropped, that exactly one
object lives — the mapped one, charged to the component with one page and one alias entry — and after the teardown
that no object lives, nothing is charged and the allocator holds every page it held before. The four modes of K5.1
now check the kernel's table (`wit_memory_objects_live() == 0`) and the charge (`ChargedPages == 0`) in place of the
component's table; the device and interrupt scenarios do the same.

## Limits kept explicit

- The target of a mapping is still the caller's own process, and a channel still joins two handles of one
  component: the first cross-process holder of an object is K5.2c.
- A component's charge ends with its teardown, not with the last reference to what it created: an object a torn-down
  component created lives on charged to nobody, bounded by the kernel's table and the physical pages. Attributing a
  surviving object to its holders is an open question for K5.2c's quotas.
- The mappings of an exited component keep their objects until the teardown; K5.2c tears a process down when it
  ends, so the gap is a test's observation, not a lifetime user space can rely on.
