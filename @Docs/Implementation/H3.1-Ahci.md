# H3.1 — PC storage: an AHCI driver

Plan step H3 gives the PC its disks, as VMware and real machines present them: SATA disks on an AHCI controller and NVMe
disks. A driver serves each over the block protocol (`witos/block.h`), so the namespace service and everything above it
are unchanged. H3 is cut into three slices:

- H3.1, this document: the AHCI driver, and the block protocol's server shared by the block drivers.
- H3.2: the NVMe driver.
- H3.3: the PC's image, one GPT disk with an EFI system partition and an ext4 data partition.

## 1. The pieces

| Where | What |

## 2. The controller

- **From the firmware.** Where CAP2 names BIOS/OS Handoff, the driver sets the OS Owned semaphore. It waits 25 ms for the
  BIOS to let go, or two seconds while the BIOS reports itself busy, and logs whether the firmware kept the controller.
- **Reset** (§10.4.3). The driver sets AHCI Enable, then HBA Reset, and waits for the reset to end. It then sets AHCI
  Enable again, clears the controller's interrupt status and enables its interrupt.
- **The links.** Every implemented port is spun up where CAP names staggered spin-up. The driver gives the links 20 ms,
  then waits until no port sees a device it has no communication with (PxSSTS's DET of 1), at most a second. An empty
  port (DET 0) is passed at once, so a controller without disks costs no wait.
- **A port with a link** (DET 3, interface active):
  1. it is stopped;
  2. its command list (1 KiB) and received FIS area (256 bytes) are given;
  3. its errors and interrupt status are cleared;
  4. FIS reception is turned on, and the device's first D2H FIS is awaited, its busy and data request bits clear;
  5. its signature tells what the device is.

  An ATA disk (0x00000101) gets its interrupts enabled and its command list started. An ATAPI device or another
  signature is stopped and left.
- **The interrupt.** An MSI message where the kernel serves messages and the function has the capability
  (`InterruptBinding.BindMessage`, `Msi`; the PC), the INTx line otherwise. Serving it takes the controller's status,
  clears every port's status it names and keeps what the port reported, clears the controller's status, and unmasks the
  INTx line. A command's wait also looks at the port every 10 ms, so a lost interrupt delays the command instead of
  stopping it.

## 3. The disk

- **IDENTIFY DEVICE** at the start gives the model, serial number and firmware (strings whose words hold their characters
  byte-swapped), the 48-bit capacity, the logical sector (words 117–118 where word 106 says it is longer than 256 words)
  and the physical one, and the write cache, supported and enabled. A disk without 48-bit addresses is refused.
- **A command** goes through command slot 0, one at a time:
  1. the Register Host to Device FIS is written;
  2. one PRDT entry per physical segment, up to 128 (more than the 64-page window's pages, so that a transfer is the
     window);
  3. the command header with the FIS's length, the direction and the entries;
  4. PxCI's bit is set, and the driver waits for it to clear.

  A transfer is READ DMA EXT or WRITE DMA EXT of whole sectors, at most 65536 of them; a flush is FLUSH CACHE EXT (FLUSH
  CACHE on a disk without it). A durable write is the write and then the flush, as with virtio-blk.
- **A failure** — a task file error, a host bus or interface error, the task file's error bit, or no completion in 10 s
  — stops the port, clears its errors and status, resets its link (COMRESET) where the device stays busy, and starts it
  again (§6.2.2.1). Only then is the failure reported, with the task file's status and error and SError. The block server
  answers `EIO` and logs it.

## 4. Measured

**QEMU's ICH9 SATA controller** (8086:2922): AHCI 1.0, 6 ports (implemented 0x3f), 32 command slots, 64-bit addresses,
no BIOS/OS Handoff. Its disk `ide-hd` signs as an ATA disk at 1.5 Gb/s and identifies itself as "QEMU HARDDISK",
firmware 2.5+, with 48-bit addresses, FLUSH CACHE EXT and a write cache enabled. q35 always has this controller at
00:1f.2, so every x64 boot of the services now starts the AHCI driver for it. Without a disk the driver answers `ENODEV`
and the device manager counts it among the drivers that are not ready.

**The gate.** `runtime-devices` boots its data disk a sixth time with the disk on AHCI:

- on x64, on q35's own controller with an MSI message;
- on ARM64 and riscv64, on an `ich9-ahci` through its INTx line.

The device manager's probe reads the partition table through the AHCI driver, writes the test partition durably and
reads it back, writes the FAT partition and the ext4 partition through its journal. The namespace service mounts `/data`
from it; `/bin/init` counts the sixth boot, finds what the fifth left and runs its checks and programs. The host then
requires the boot count and a clean volume, as after every boot.

## 5. What is not yet

- **Several disks of a controller.** The driver serves the first ATA disk and logs the others it started; the block
  protocol's one channel per driver serves one disk.
- **ATAPI devices** (a CD-ROM) are left.
- **Native Command Queuing.** One command at a time through slot 0; NCQ's 32 slots wait for a need.
- **Hot plug and link power management**: a port's connect change is cleared, not served.
- **VMware's controller** (15ad:07e0) is the H5 session's to measure; CAP2's BIOS/OS Handoff is served for it and for
  real machines, and QEMU has none.
