# E4.5 — Working on VMware

Plan step E4.5 (phase E, goal Ц6). On 2026-11-03 the author asked for real work on VMware after E4.4. The pre-check
used the PC's one disk with E4.4 in the H5 machine, headless (`vmrun -T ws … nogui`, the screen through VMware's VNC
server on 127.0.0.1). At the session's pwsh prompt it wrote a console project, built it with the layer's SDK, ran it,
then ran it again from Arlecchino.Commander's command line. Two things stood in the way. A share of the Windows host,
mounted in the machine (§4), showed two defects more, the step's own disk a fifth, and a USB drive in the machine two
more: the machine's clock and the error of a path below a drive that is not there (§5). This step removes all seven.

## 1. What the work found

| Run | Machine | Result |
| --- | --- | --- |
| `dotnet --version` | 1 GiB, 2 processors | `10.0.300` in 2 s, code 0 |
| `dotnet build` of a console project | 1 GiB | failed after 19 s: Roslyn's `Csc` task reported "Out of memory" |
| the same build | 2 GiB | succeeded in 22 s, then in 15 s on the machine of §3 |
| the program it built | 2 GiB | printed its line and returned 7 |
| `mkdir`, `ls`, `mv`, `clear` at the prompt | either | "The term 'mkdir' is not recognized as a name of a cmdlet …" |

- **Memory.** One GiB leaves 805 MiB usable, and a build runs pwsh, MSBuild and the compiler at once. The machine needs
  2 GiB (1829 MiB usable), as the QEMU gates give their SDK scenario 1024 MiB with one processor.
- **The shell's commands.** pwsh on Unix leaves `ls`, `cp`, `mv`, `rm`, `rmdir`, `cat`, `sort`, `sleep`, `tee` and
  `clear` to the system's coreutils and defines no `mkdir`. WitOS has no coreutils and no `/bin/sh` (ADR 0027). So the
  commands a person types first were missing, at the prompt and on Commander's command line alike.
- **A log line, not a failure.** Each build logs `[LIBC] mprotect refused (plain memory never executes): …, protection
  0x5` once, and builds anyway: one of the build's processes asks for executable plain memory and then takes another
  way.

## 2. The shell's commands

The session's profile (`build/console/profile.ps1`, `$PSHOME/profile.ps1`) names the cmdlets as Windows' PowerShell
does: `ls` Get-ChildItem, `cp` Copy-Item, `mv` Move-Item, `rm` and `rmdir` Remove-Item, `cat` Get-Content, `sort`
Sort-Object, `sleep` Start-Sleep, `tee` Tee-Object, `clear` Clear-Host, and the function `mkdir`, which is New-Item
of a directory. pwsh on Unix clears the screen by running the `clear` program, so `Clear-Host` itself, which `cls`
and `clear` name, failed too; the profile defines it as `[Console]::Clear()`, which writes the sequence the install's
terminfo gives. The names are set before the profile's early return, so a session with redirected streams and every
command Commander runs through `SHELL` get them too. `ps` and `kill` stay out, since another process's list and its
termination are `PlatformNotSupportedException` on WitOS.

`runtime-powershell` types, at the interactive prompt:

```
clear; $cleared = $?; mkdir /data/unix/inner | Out-Null; Set-Content /data/unix/inner/t.txt unix; cp … c.txt; mv … m.txt;
'aliases=' + (cat /data/unix/m.txt) + ':' + ((ls /data/unix -Name | sort) -join ',') + ":cleared=$cleared"; rm -r /data/unix
```

It requires `aliases=unix:inner,m.txt:cleared=True`, the last part `$?` after `clear`.

## 3. The machine

`shell --pc --prepare <directory>` writes `WitOS-pc-x64.vmx` beside the image and its descriptor on x64
(`RuntimeDataDisk.WriteVmxAsync`). It is the machine H5's sessions measured:

- EFI firmware without Secure Boot, with its serial console;
- the HPET the kernel's clock takes (H1.1);
- the real-time clock in UTC (`rtc.diffFromUTC = "0"`, §5);
- the disk on SATA;
- the e1000e adapter on NAT (H4);
- the first serial port to `serial.log` beside the machine, which is the kernel's log;
- no virtual USB keyboard, whose presence costs the first second of a boot's keys (H5 §2.2);
- a USB drive, `WitOS-usb.vhd`, on the xHCI controller's port 6 (§5);
- 2 GiB and two processors.

It has no remote display, since VMware's VNC server has no password. A person opens the machine in VMware Workstation.
`RuntimeDataDiskTests` checks the text.

A machine of exactly that text, with VNC added for the headless check, booted to the prompt with 1829 MiB and 2 of 2
processors. At the prompt:

- the project built in 15 s;
- `dotnet bin/Debug/net10.0/hello3.dll` printed "Hello from WitOS 0.1 ABI-1, built on this machine" and returned 7;
- Commander ran the same command from `/data/hello3` with the terminal given to the program;
- the session's `exit` powered the machine off with `/bin/init`'s status 0.

## 4. The Windows host's share

The author made a share on the Windows 11 Pro host, which is not in a domain. A folder `C:\WitOS-Share`, a local
account `witos` that owns nothing else, the share `\\DESKTOP-OFFICE\WitOS` with access for that account alone, and an
inbound rule for TCP 445 from VMware's NAT network `192.168.119.0/24` on the VMnet8 adapter alone. The scripts that
make and remove them lie outside the repository. A program published on the host with the stock SDK and no RID was
put in the share. On the machine of §3:

```
witos-volumes mount //192.168.119.1/WitOS --user witos --domain DESKTOP-OFFICE --as Windows
```

- The service mounted it at the first try against Windows: `SMB3 volume "WitOS" of 1999298883584 bytes, writable,
  from //192.168.119.1/WitOS (SMB 3.1.1 at 192.168.119.1:445 as DESKTOP-OFFICE\witos)`.
- `witos-volumes` listed it as `smb3`, 1.8 TiB, 192.0 GiB free, `rw`.
- The program ran from the share and from a copy on `/data` made by `Copy-Item`.
- The files it and pwsh wrote appeared in `C:\WitOS-Share` with their text.
- Commander's drive picker (Ctrl-F1) offered the share as `Windows`. F5 copied its `Hello` folder to `/data`, from
  where dotnet ran it: goal Ц6's path, on VMware.
- Existence checks of a missing file and directory of the share answered false, and of a present file true.
- The share unmounted.

Two defects showed, and this step fixes both:

- **`readlink` of a missing path of a share** answered `EINVAL`, "not a link", where it must answer `ENOENT`.
  `SmbFileSystem.ReadLinkAsync` refused every path as no link, and musl's `realpath` tells a missing path from a present
  one by `readlink`. So `realpath` of a missing file of a share succeeded. .NET's host, which reaches
  `runtimeconfig.dev.json` through `realpath`, then printed "Failed to map file. open(…Hello.runtimeconfig.dev.json)
  failed with error 2" before every run of a program from a share. It now looks the entry up first, as FAT and the
  memory volume do. `SmbFileSystemTests` requires `NotFound` of a missing path against Samba.
- **A share mounted when the machine stopped** logged `stopping /media/Windows: CapabilityException: CHANNEL_SEND failed
  with errno 32`. The device manager stopped the network service before the namespace service, which had mounted
  the share through it. It now stops the namespace service first, and the share closes and logs off while the network
  is there.

The step's own disk, in the machine of §3 with the share mounted, confirmed both fixes. A program run from the share
printed no "Failed to map file" line. A stop with the share still mounted logged `namespace service: 1 sessions
stopped, 5 volumes unmounted` before the network service stopped, and `/bin/init` ended with 0. The profile's commands
worked there, but `clear` did not: on Unix Clear-Host itself runs the `clear` program, and the profile now defines it
(§2).

## 5. A USB drive, and the machine's clock

VMware attaches a disk image to its xHCI controller as a USB drive, so E3's path can be checked without a device of
the host. The keys are not in VMware's documentation. A Broadcom forum report gives them for the EHCI controller, and
they work for xHCI too:

```
usb_xhci:6.present = "TRUE"
usb_xhci:6.deviceType = "disk"
usb_xhci:6.fileName = "usb.vmdk"
usb_xhci:6.readonly = "FALSE"
```

The image was 256 MiB with an MBR and a FAT32 partition labelled `WITUSB`, holding the host's `hello.txt`. The
descriptor `usb.vmdk` names it as its one flat extent. On the machine of §3, headless:

- **The drive.** VMware put "VMware Virtual Storage 1.00" (0e0f:0005) on port 7, a USB 2.0 port. It reports itself as
  USB 3.0 with a port speed of 0, which no protocol defines. The xHCI driver configured it: `a drive, interface 0, bulk
  endpoints 81 and 02 of 1024 bytes, 1 logical unit`, `268435456 bytes in blocks of 512, removable, writable`.
- **The volume.** The namespace service mounted the partition at `/media/WITUSB`.
- **At the pwsh prompt.** pwsh listed `/media`, printed the host's file, wrote `guest.txt` and copied
  `/etc/environment` there.
- **On the host.** After the machine stopped, mtools read both files from the image, and `fsck.vfat -n` found the
  volume clean.

A drive passed through from the host is not measured; it meets the same controller and the same driver.

**The machine's drive.** `shell --pc --prepare` gives the machine of §3 such a drive. `WitOS-usb.vhd` is 1008 MiB
with an MBR and a FAT32 partition labelled `WITUSB` from block 2048, as Windows formats a USB drive, holding a
`readme.txt` that says how to use it (`RuntimeDataDisk.WriteUsbDriveAsync`). The disk is followed by the footer of a
fixed VHD, so the one file is two things:

- Windows opens it as a disk, through Mount in Explorer's menu of the file, to put files on the drive or take them;
- VMware attaches it through `WitOS-usb.vmdk`, whose flat extent is the disk without the footer.

1008 MiB is 2048 cylinders of 16 heads and 63 sectors. The footer's geometry, as the VHD specification computes it,
covers the disk exactly, so a reader that sizes a VHD by its geometry and one that reads its size agree. A drive
already in the directory is the person's and stays as it is. The footer is the tool's own; the pinned `qemu-img`
opens the file as a VHD (`-f vpc`, which checks the footer's checksum) of exactly the disk's bytes.
`RuntimeDataDiskTests` checks the footer, the table, the volume, the descriptor's extent and the machine's keys.

On VMware, the tool's machine with VNC added:

- the drive was "VMware Virtual Storage 1.00" of 1056964608 bytes, the footer left out;
- the namespace service mounted `/media/WITUSB`;
- pwsh read the readme and wrote a file, a directory and a copy of `/etc/environment`;
- after the stop, mtools read them with the guest's UTC times, and `fsck.vfat -n` found the volume clean.

While the machine runs, VMware holds the file open and keeps `WitOS-usb.vmdk.lck` beside it. Its handle shares reading
and writing, so the file does not lock other programs out. Windows' Mount of the file was not measured, since it needs
an administrator. The readme and the tool's message say to open the drive in Windows only while the machine is off, and
to eject it before the machine starts.

**The xHCI interrupts.** H5 left open why no interrupt transfer of VMware's xHCI had ever reached the driver. A scratch
build of the driver counted its interrupter's wakes and asked the two interrupt endpoints of VMware's absolute mouse
(0e0f:0003), which the driver otherwise leaves.

- MSI-X interrupts arrive. The root ports' changes at the start woke the driver's loop, and so did the drive's
  transfers.
- The mouse sent no report while VNC moved the pointer and clicked. Whether VMware gives VNC's pointer to that mouse is
  not known.

So the open question narrows to the interrupt IN endpoints of a device that has something to report.

**The clock.** The files the guest wrote on the drive carried 14:48 where UTC was 12:48. The kernel reads the CMOS
real-time clock as UTC (H1.1), as Linux does by default. VMware runs the clock of a new machine of guest type
`other-64` in the host's local time, UTC+2 on this host.

| Machine | Guest's `[DateTime]::UtcNow` | Host's UTC |
| --- | --- | --- |
| new, without `rtc.diffFromUTC` | 15:01:56 | 13:01:57 |
| new, with `rtc.diffFromUTC = "0"` | 13:04:04 | 13:04:05 |

VMware keeps the offset in the machine's `nvram`. Once a boot with the key set the clock to UTC, the same machine kept
UTC without it. `WriteVmxAsync` writes the key, and `RuntimeDataDiskTests` requires it.

**A path below a drive that is not there.** On a machine without the drive, `Set-Content /media/WITUSB/t2.txt` failed
with "Read-only file system". `/media` refused every change with `EROFS`, a path below a name that is no mounted alias
too. Linux answers a path through a missing directory with `ENOENT` before it looks at the file system's mode, and
.NET then reports "Could not find a part of the path". `MediaDirectory` now answers that way:

- `ENOENT` for any path below a name, for an open of a missing name without creation, and for a change of a missing
  name's mode or times;
- `EROFS` for a name created, removed or renamed in `/media` itself.

`VolumeCatalogTests` checks each answer.

## 6. Limits kept explicit

- **A command's code in Commander is pwsh's.** Commander runs a command through `SHELL`, which is pwsh, and
  `pwsh -Command` exits with 1 when the last native program exits with anything but 0. A program that returns 7
  shows `[exit 1]`; one that returns 0 shows `[exit 0]` (E4.3). A shell that passes the code on, as bash does, is not
  in the system.
- **The panels' free space** is that of `/`, the boot package (E4.2 §5).
- **Files from Windows** reach the machine through the host's share (§4) or a USB drive (§5). A physical drive
  passed through from the host is not measured; VMware's virtual one is, and the machine carries one. Its file serves
  Windows or the machine, one at a time, and nothing enforces the turn.
- **A PC whose firmware keeps local time**, as Windows sets it, would give the guest the same offset as §5. The kernel
  takes the real-time clock as UTC, and H7.4's saved time and network time are where a board's time gets corrected.
