# R3.2a — What CoreCLR's PAL needs from the system layer

R3.2 runs a managed `Main` under CoreCLR through the JIT. Its first slice starts upstream's `corerun` in the guest and
gives the system layer what CoreCLR's PAL needed to get through `coreclr_initialize` up to executable memory. The
executable memory itself is R3.2b.

## The probe

The `runtime-corerun` scenario boots the system layer's root task with `tests/User/corerun_init.c` as `/bin/init`.
That program starts `/coreclr/corerun -c /coreclr /coreclr/CoreRun.dll` with `posix_spawn`, waits for it and reports
how it ended. The package holds the following under `/coreclr`:

- upstream's `corerun`;
- `libcoreclr.so` and `libclrjit.so`;
- CoreCLR's CoreLib from `IL/`, since no crossgen runs for `witos`;
- the framework's libraries the program needs, with `libSystem.Native.so`;
- `tests/Runtime.Witos/CoreRun/CoreRun.cs`, which the SDK's C# compiler builds against the reference pack.

`corerun`'s TPA list is every assembly of its directory.

Every assembly for `witos` is IL alone. CoreLib and the framework carry no ReadyToRun code, so the JIT will compile
every method, and no PE section is ever executed.

The scenario requires `[CORERUN] managed Main through the JIT on <ISA>`. That line is not reached yet; R3.2b and R3.2c
get there.

## The method

Two container-only instruments drove the slice:

- **A trace in the libc's `__wit_syscall`** logged every failing system call with its number, its first three
  arguments, its result and, for path calls, the path.
- **The kernel's fault line** gave the faulting address.

Each round fixed the first failure that mattered. These failures stay and are harmless, since the PAL continues past
them:

- `brk` (`ENOMEM`);
- `readlink` of a package path (`EINVAL`, as for a file that is no link);
- `getsid`, `statfs` of `/sys/fs/cgroup` and `/proc/self/mountinfo` (no cgroups);
- `getrlimit(RLIMIT_NOFILE)` (the PAL keeps its descriptor limit).

## What the system layer gained

| Failure | Cause | Now |
| --- | --- | --- |
| `corerun` faulted at address 0 | .NET's `minipal_getexepath` reads `/proc/self/exe`, then falls back to `getauxval(AT_EXECFN)`. Both failed, and `corerun` built a `std::string` from the null result. | libwitos puts the program's path, as the caller named it, at the top of the first stack and names it with `AT_EXECFN`, as a Linux kernel does. `process_init.c` checks that `/bin/init` sees its own path and that `realpath` resolves it. |
| `coreclr_initialize` returned `0x8007054F` (`ERROR_INTERNAL_ERROR`) | Every thread the PAL starts resets its affinity to the process's mask, and `sched_setaffinity` was `ENOSYS`. | `sched_setaffinity` accepts a mask that holds every processor threads run on, which changes nothing. A mask holding none is `EINVAL`, as on Linux. A mask holding some of them alone is `ENOSYS` until threads run on several processors (phase P). |
| The PAL's synchronization thread spun on `poll` | It waits on its own pipe with `poll`, which saw no descriptor. | `poll` and `ppoll` (see below). |
| `sigaltstack` failed with `EFAULT` | The PAL makes the bottom page of each thread's alternate stack `PROT_NONE` as a guard. The kernel accepts only a committed writable range, so it refused the whole stack. | The libc gives the kernel the writable part above the refused pages, page by page while at least `WIT_EXCEPTION_STACK_MINIMUM` is left, and keeps the whole range for its own handlers. `libc_hello.c` checks a guarded stack. |

### `poll` and `ppoll`

Pipes are the only descriptors that wait, so the design is small:

- **Readiness, under the table lock.** Each descriptor reports its readiness:
  - a pipe's read end is readable with bytes in the pipe, and hung up (`POLLHUP`) once no writer is left;
  - its write end is writable while `PIPE_BUF` bytes fit, and in error (`POLLERR`) once no reader is left;
  - a file, a directory, a device or a standard stream is ready for whatever was asked, as a regular file is on
    Linux;
  - a closed descriptor reports `POLLNVAL`.
- **The park.** When nothing is ready and the timeout allows, the caller parks on one futex word. Every change of any
  pipe bumps that word. The caller reads it before it reads the readiness, so a change in between wakes the park at
  once.
- **How the wait ends.** A monotonic deadline from the timeout ends the wait with 0. A signal handler ends it with
  `EINTR`. A cancellation point about to park does not park.
- `ppoll` with a signal mask is `ENOSYS`, and `select` remains `ENOSYS`.

`libc_hello.c` checks the readiness of both ends and of a stream, a timeout that passes in full, a poller that parks
until another thread writes, a hung-up read end and a closed descriptor.

### The x64 fault line

A contained user fault on x64 now names `rip=` before `cs=`, as ARM64's line names `elr=`. `BootValidation` checks
the new form.

## Where `coreclr_initialize` stops

CoreCLR's double mapper, used when W^X is on (the default), stops here:

1. Since `witos` is neither Linux nor FreeBSD, the mapper takes POSIX's `shm_open("/shm-dotnet-<pid>")`. In the libc
   that is a create in `/dev/shm`, which the read-only package refuses with `EROFS`.
2. Without the double mapping, CoreCLR turns W^X off and asks for a read-write-execute page.
3. WitOS never grants `WRITE|EXECUTE` (RFC 0011 §7.2), so `mprotect` refuses with `EACCES`.
4. CoreCLR then writes to the page and faults.

This happens on both ISAs.

R3.2b gives the libc POSIX shared memory over memory objects, so the double mapper gets its RX and RW views of the same
pages. It also enables EL0 cache maintenance by VA on ARM64, which CoreCLR's `__clear_cache` performs itself.

## Limits kept explicit

- `sched_setaffinity` changes nothing while one processor schedules threads.
- `ppoll`'s signal mask and `select` are not implemented.
- A stream polls ready although its reads end the input.
- The probe scenario does not pass yet, and `runtime-witos` does not boot it.
