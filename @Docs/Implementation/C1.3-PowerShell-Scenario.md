# C1.2b and C1.3 — PowerShell on WitOS: the terminal under PSReadLine and the scenario

Plan steps C1.2b and C1.3 (phase C, RFC 0020) turn the measurement of C1.1 and the platform work of C1.2a into a gate:
upstream PowerShell 7, pinned and unchanged, runs on WitOS from the data volume, non-interactively and interactively
under PSReadLine on the terminal, as the `runtime-powershell` scenario of `runtime-witos` on both ISAs. This is RFC 0020
§56's T2 and §57.2–57.5 by fact; what the step leaves out is at the end.

## 1. The terminal under PSReadLine (C1.2b)

**What the interactive session needed.** The C1.1 trial's interactive `pwsh` printed nothing. Its first bytes to the
terminal were `ESC[?1h ESC= ESC[6n`: .NET's Console asks the terminal for the cursor position (DSR 6) before PSReadLine
draws anything, and waits for the report (`ESC[row;colR`). Nothing on the runner's side answered, and the N4.3 terminal
service does not either, rightly: it owns the line discipline, not a screen, and the far side of the serial link is
whatever terminal is there — a desktop terminal answers for itself, and in C2 the display service will, since it has
the screen. Two answerers would garble the input.

**The runner's emulator.** `TerminalScreen` (`tools/WitOS.Dev/Host/TerminalScreen.cs`) is a small VT100/xterm
emulator the runner's `TerminalLink` feeds every chunk the guest writes: a grid of cells and a cursor; printable text,
CR, LF, BS, TAB; the CSI sequences CUU/CUD/CUF/CUB, CNL/CPL, CHA, CUP/HVP, ED, EL, SU/SD, VPA, SCP/RCP and SGR (ignored);
the private modes (ignored); ESC 7/8, ESC M, ESC c, the charset designations and OSC strings (ignored); deferred wrap at
the last column; UTF-8 decoded across chunks. It answers DSR 6 with the cursor position report and DSR 5 with OK, and the
link sends the answers before anything the script types. Seven host tests cover the painting, the moves, the erases,
the scrolling and the reports, including a sequence and a character split between chunks. The link exposes the screen,
so a later scenario can judge what a program drew rather than the byte stream (RFC 0020 §58 #12's answer begins here:
the subset above is what System.Console and PSReadLine used in this session).

**Enter is a carriage return.** With the report answered, PSReadLine drew `PS /data>` and echoed the typed command with
syntax colors, but did not run it: the runner typed `\n`, which PSReadLine, reading the terminal raw, does not bind,
while a canonical read of N4.3's tests accepts it as the end of a line. The Enter key of a terminal is CR, and the
scenario's script types `\r`.

## 2. The pins

- **PowerShell 7.6.7** (`src/Substrate/powershell.lock.json`): `powershell-7.6.7-linux-x64-musl-noopt-fxdependent.tar.gz`
  by its SHA-256 at the release's URL — the framework-dependent archive that is IL alone, so one archive serves both ISAs
  (the ordinary `linux-x64-fxdependent` carries ReadyToRun code for linux-x64). `setup` downloads and extracts it under
  `.tools/powershell-7.6.7`. The archive runs as `dotnet /data/pwsh/pwsh.dll` on the .NET install (its runtimeconfig
  names `Microsoft.NETCore.App` 10.0.0 with roll-forward; 10.0.12 serves it). Nothing in it is changed.
- **PowerShell-Native** at commit `0e619cee3591727a7beb1554b8e300fb790395d2` (tag `v700.0.1`, the nearest to the
  package version 700.0.2 the archive's deps file names), checked out by `setup` under `.tools/powershell-native/<commit>`
  as libc-test is. `Substrate.PowerShell.BuildNativeAsync` compiles its 29 C++11 sources unchanged with the pinned clang
  against the sysroot (`Sysroot.DriverOptions`, `-std=c++11 -O2 -Wall -Werror -fPIC -shared -Wl,-soname,libpsl-native.so
  -Wl,--no-undefined`, a `pal_config.h` with `HAVE_SYS_SYSCTL_H 0` and `HAVE_SYSCONF 1`, which is what musl answers)
  into `artifacts/<arch>/powershell/libpsl-native.so`: 29 KB on x64, 32 KB on ARM64, needing libc++, libc++abi,
  libunwind and the libc. It goes beside `pwsh.dll` on the volume, where CoreCLR finds a P/Invoke's library in the
  calling assembly's directory. The archive's own `runtimes/linux-musl-x64/native/libpsl-native.so` needs libstdc++,
  which the sysroot does not have, and the witos RIDs (`witos`, `unix-<arch>`) would not select it anyway.
- **ncurses 6.5** (`src/Substrate/ncurses.lock.json`): the release tarball by its SHA-256 through GNU's mirror
  redirector (ftp.gnu.org itself refuses repeated requests; whatever mirror answers, the bytes are the hash's), of which
  `setup` extracts `misc/terminfo.src`. `Substrate.Terminfo` compiles the entries `xterm-256color`, `xterm` and `vt100`
  with the Linux host's `tic -x` (as a distribution's ncurses-base compiles them; tzdata's `zic` is the precedent) into
  `artifacts/terminfo`, and the .NET install carries them under `/usr/share/terminfo/{x,v}/`, where System.Console on
  Unix reads the `TERM` entry's capabilities; the install's `/etc/environment` names `TERM=xterm-256color`, the terminal
  the runner's emulator and a desktop terminal are. ftp.gnu.org answers a request without a user agent with 403, so the
  tool's downloads name it.

## 3. The scenario

`runtime-powershell` (`tools/WitOS.Dev/Runtime/RuntimePowerShell.cs`), after `runtime-terminal` in `runtime-witos` and
alone as the command of the same name, boots the device services, the install and the terminal with 1 GiB and a data
disk of 1 GiB whose ext4 volume holds the archive's files and the ISA's `libpsl-native.so` under `/pwsh` and the home's
`home/.keep`; `apps_init.c` runs three commands from `/data`:

1. `dotnet /data/pwsh/pwsh.dll -NoLogo -NoProfile -NonInteractive -Command $PSVersionTable` — the version table, whose
   `OS` is `WitOS 0.1 ABI-1` and `Platform` is `Unix` (§57.2).
2. The same with `'even=' + (1..10 | Where-Object { $_ % 2 -eq 0 } | Measure-Object).Count; Set-Content /data/pwsh.txt
   written-by-pwsh; Get-Content /data/pwsh.txt; 'date=' + (Get-Date).ToString('yyyy-MM-dd'); Get-ChildItem /data` — the
   pipeline (§57.4) and the date as plain words (`even=5`, `date=2026-10-16`: on a terminal PowerShell colors its
   formatted output and formats a date by what came before it, so a required line never spans a label and its value),
   files on the volume through the FileSystem provider, and the listing as a table.
3. `dotnet /data/pwsh/pwsh.dll -NoLogo -NoProfile` — the interactive session, into which the runner types, after each
   `PS /data>`, `$PSVersionTable`, `1 + 2`, `Get-Date`, `Get-ChildItem /data` and `exit`, each with `\r`.

The scenario's `/etc/environment` adds `__PWSH_LOGIN_CHECKED=1`, the variable PowerShell's own re-exec sets, which skips
its login-shell check: that check reads `/proc/self/cmdline` on Linux and calls `sysctl` on every other Unix, which is
one of the two upstream proposals of C1.1 (§5). The required lines, in the serial log or the transcript: `PSVersion`,
`WitOS`, `Platform`, `even=5`, `written-by-pwsh`, `date=20`, `Directory: /data`, `PS /data>`,
`pwsh.dll exited with 0` and `3 commands, 0 failed`.

## 4. What the guest showed

The trials of C1.1's harness with the platform of C1.2a and the emulator, before the scenario existed, on both ISAs
(2026-10-16): the version table; `Count : 5`; `hello` written and read back; `Get-Date`; `Get-ChildItem /data` as a
table of `UnixMode User Group LastWriteTime Size Name` with `home`, `pwsh` and `pwsh.txt` among the entries; then the
interactive session — the prompt, PSReadLine's incremental redraws of each typed command with colors, `1 + 2` → `3`, the
date, the listing, `exit` with code 0. Each `pwsh` start took 117–225 s of guest time on x64 and 171–327 s on ARM64 under
TCG: the archive is IL alone, so every method of the engine goes through the JIT; whether CoreCLR on witos accepts the
`linux-x64` ReadyToRun images of the ordinary archive, which would cut this, is a measurement for C1.4 (the images carry
the OS in their machine field).

The scenario's own runs are recorded in the plan's journal entry for C1.3.

## 5. Left out, and the upstream proposals

- `Get-Process` without arguments, `Get-Process -Name` and anything else that enumerates processes fail explicitly: there
  is no `/proc` (Compatibility-Differences: Processes); `Get-Process -Id $PID` works.
- Remoting (RFC 0020 §19), jobs (§18) beyond thread jobs, script signing (§43), the native WitOS module and providers
  (§11–12) are later steps; the serial console stays the headless mode (§8, §28).
- Two proposals to PowerShell/PowerShell, which WitOS does not wait for: the login-shell check's `sysctl` path guarded
  by `Platform.IsMacOS` with a plain return elsewhere; the FileSystem provider's root drive created on Unix when
  `DriveInfo.GetDrives()` reports nothing (WitOS reports its mount points since C1.2a regardless).
