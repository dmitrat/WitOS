# H7.1 — One ARM64 platform by the device tree

On 2026-10-25 the author decided that the Raspberry Pis get no kernel of their own. One ARM64 kernel image serves every
board a device tree describes: QEMU's `virt`, the Raspberry Pi 4 and, as the goal, the Pi 5. The plan had a
`Kernel.Platform.Bcm2711` beside `Kernel.Platform.QemuVirt`. Instead, the ARM64 platform takes from the tree what the PC's
platform takes from ACPI (H1.1: one x64 kernel for q35, QEMU's `pc` and VMware). This is how a phone's, a tablet's or an
embedded board's kernel is usually built, and the H6 entry already hands the kernel the tree a board's bootloader gives.

H7.1 is the first slice:

- the platform becomes `src/Kernel.Platform.Arm` (the layer `kernel-platform-arm`), with a reader of the tree that every
  part of it shares;
- the interrupt controller, the timer's interrupt and the real-time clock come from the tree;
- a GICv2 is driven beside the GICv3: the GIC-400 of both Pis is one.

The console and the start of secondary processors follow in H7.2, with the Pi 4 on QEMU's `raspi4b`.

## 1. The pieces

| Where | What |
| --- | --- |

| WitOS.Dev | `BootRequest.Gic2` boots `virt,gic-version=2`. `release --arch arm64` and `test --arch arm64` gain boots on it (§5). |

## 2. The reader

`wit_arm_tree_open` checks the header (version 17 or later, the blocks within the total, each at most 256 KiB). It maps
the structure and strings blocks once, never the firmware's padding. `wit_arm_tree_next` returns the walk item by item:
a node's beginning, a property or a node's end, each with its depth (the root node is depth 1).

The walk keeps each open node's `#address-cells`, `#size-cells` and `ranges`. With them, `wit_arm_tree_reg` translates a
`reg` into the processor's address space:

- A child of the root addresses the processor's space directly.
- A deeper node's address passes through the `ranges` of each bus above it.
- Empty `ranges` are the identity, and a bus without `ranges` translates nothing.

`virt` puts its devices at the root. The Pi 4's tree puts the GIC-400 and the PL011 under `/soc`, whose `ranges` map the
VideoCore's bus addresses (0x7e000000, 0x40000000) to the processor's (0xfe000000, 0xff800000). The tree's own cell
counts default as the binding says (2 and 1). An interrupt controller's `#address-cells` for an interrupt map stays 0
when absent, as Linux reads it.

## 3. The board's facts

`wit_arm_board` walks the tree once. A node's kind is decided at its end, since its `compatible` may follow its `reg`.

| Fact | From |
| --- | --- |
| The GIC | The first node compatible with `arm,gic-v3` (reg: the distributor, then the redistributors), or with `arm,gic-400`, `arm,cortex-a15-gic` or `arm,cortex-a7-gic` (reg: the distributor, then the CPU interface). QEMU's `virt` names `arm,cortex-a15-gic` for its GICv2, and the Pi 4 `arm,gic-400`. Without a GIC the kernel panics: "No GIC in the device tree". |
| The tick's interrupt | The third entry (the EL1 virtual timer) of `arm,armv8-timer`'s `interrupts`: PPI 11 on `virt`, INTID 27, which is also the default without a timer node. |
| The real-time clock | The first `arm,pl031`: `virt` has one, the Pi none. |

The platform prints what it found once paging is active:

```
Interrupt controller: GICv3, distributor 0x0000000008000000, redistributors 0x00000000080A0000, timer interrupt 27
Interrupt controller: GICv2, distributor 0x0000000008000000, CPU interface 0x0000000008010000, timer interrupt 27
```

## 4. The GICv2

A GICv2 is reached by memory alone:

- the distributor's first page, whose registers of the private interrupts (the first enable word, the first eight
  priority and target words) are banked per processor;
- the CPU interface's first page: `GICC_CTLR`, `GICC_PMR`, `GICC_BPR`, `GICC_IAR`, `GICC_EOIR`.

| | GICv3 (as before) | GICv2 |
| --- | --- | --- |
| Forwarding | `GICD_CTLR` ARE and group 1, waiting for RWP | `GICD_CTLR` bit 0 |
| CPU interface | `ICC_SRE_EL1`, `ICC_PMR_EL1`, `ICC_IGRPEN1_EL1` | `GICC_PMR` 0xFF, `GICC_BPR` 0, `GICC_CTLR` bit 0 |
| The tick and the SGIs | The processor's redistributor, woken first | The distributor's banked first word, enabled by the processor itself |
| A device line | Group 1, routed by `GICD_IROUTER` to the boot processor's affinity | Routed by its `GICD_ITARGETSR` byte to the boot processor's CPU interface |
| The doorbell | `ICC_SGI1R_EL1` by affinity | `GICD_SGIR` with the target's CPU interface in the target list |
| Acknowledgement | `ICC_IAR1_EL1` / `ICC_EOIR1_EL1` | `GICC_IAR` / `GICC_EOIR`; an SGI's acknowledgement names its sender in bits 12:10, which the end of the interrupt must name again, so each processor keeps the last one it took |

A GICv2 target list names CPU interfaces, not affinities. Each processor reads its own interface from the banked
`GICD_ITARGETSR0` once it enables its interrupts (the boot processor at the mapping), and a doorbell finds the target's
interface by its hardware identity. A GIC of one interface reads zero there and fixes its targets, so no doorbell is sent
in it.

The groups stay as the firmware left them, and only bit 0 of `GICD_CTLR` and `GICC_CTLR` is set:

- Without the security extensions (QEMU), every interrupt stays in group 0. Group 0 is signalled as IRQ while
  `GICC_CTLR.FIQEn` is clear.
- With them, a Pi's firmware puts every interrupt in group 1. A non-secure access sees group 1 alone, and its bit 0 is
  group 1's enable.

## 6. What is not yet

- **The console from the tree.** The console is still the PL011 at `virt`'s 0x09000000. H7.2 takes it from `/chosen`'s
  `stdout-path`. The boot layers must hand the tree to the platform before their first line. On the UEFI path the tree is
  known only once the configuration tables are read.
- **Secondary processors by the tree's `enable-method`.** They still start by PSCI over `hvc`, whatever `/psci`'s method
  says. The Pi 4's firmware parks them in a spin table. This is H7.2.
- **Several processors at EL2.** As in H6, the EL2 boots run on one processor. `virt,virtualization=on` names PSCI by
  `smc`, which the kernel does not use yet.
- **The PCI bridge below a bus.** The ECAM bridge is still looked for among the root's children, where `virt` has it.
