# P1.1 — per-processor state

Plan step P1.1 (phase P, `P1.0-SMP-Inventory.md` section 6): each processor knows its number from a register of its
own, the dispatcher keeps its state per processor, and a processor idles on a stack of its own instead of the waiting
thread's. Threads still run on the boot processor alone (`wit_processors_scheduling()` stays 1); what changes is where
the state lives, so that P1.2 and P1.3 can let more processors in. Made on 2026-10-18.

## 1. The processor's number

`wit_arch_processor_set_index(index)` and `wit_arch_processor_index()` (`witos/arch.h`) give each processor its number
in the kernel's table, read without a lock or a memory location processors share:

- **x64**: a task state per processor (`exceptions.c`): the boot processor's at selector 0x18, as before, and each
  other's two GDT entries apiece from entry 7, after the user selectors SYSRET requires at 0x2B and 0x33. A secondary
  loads its own task register as it starts, and `str` names the processor. `TSS.RSP0` is written in the running
  processor's task state. The GS base stays zero.
- **ARM64**: TPIDR_EL1, which EL0 cannot reach, written once at the start (`processor_registers.S`).
- **RISC-V**: a record per hart (`processor.c`: the kernel stack top of the thread the hart runs, the thread's sp across
  a trap, the number) that `tp` points to in S-mode. The trap entry swaps `tp` with `sscratch` as Linux does
  (`entry.S`): while U-mode runs `sscratch` holds the record, so a trap from U-mode lands on the kernel stack top the
  record names and keeps the thread's sp in it; a trap from S-mode swaps a zero and takes the kernel's `tp` back. The
  frame keeps the interrupted `tp` in X[4] and the interrupted sp in X[2], as before, and a frame that returns to U-mode
  writes its kernel stack top into the record and the record into `sscratch`. Before, `sscratch` held the stack top
  itself, and no per-hart register was left for the kernel.

The boot processor records 0 in `wit_processors_initialize` (RISC-V already in `wit_arch_initialize`), and a secondary
its number first thing in its main function; `wit_cpus_secondary_ready` and every request a secondary serves require
the number to name the processor's hardware identity, and `wit_processors_current()` is that number.

## 2. The dispatcher per processor

`user.c` keeps a record per processor — the component it runs, or the one that went idle on it, the thread it runs,
whether it idles, and how the dispatch that sent it idle looked for a thread — where it kept the globals `current_user`
and `user_idle`. A processor that enters the kernel from its thread (`enter()`: a call, a tick, a device line, a fault)
makes its component's `CurrentThread` the thread it runs, so that the calls, which name their caller through
`CurrentThread`, keep doing so when two processors run threads of one component (P1.3); with one scheduling processor
the two never differ.

## 3. Idle on the processor's own stack

The dispatcher halted on the kernel stack of the thread that went to wait, and a tick there knew the idle path by that
stack. With a second processor that thread's frame could be resumed elsewhere while this one halted on its stack. Now a
dispatch that finds no ready thread leaves for the processor's idle stack (`wit_arch_idle_stack`) through
`wit_arch_run_on_stack` and runs the idle path there: it halts, and after a tick or a device line looks
for a ready thread again as the dispatch that sent it there looked; a ready thread's frame resumes from there with
`wit_arch_resume_frame`, which abandons the idle stack. `wit_arch_frame_is_idle` judges an interrupted idle frame by
that stack — the frame and its stack pointer within it, the idle path's resume address, the kernel's mode, the user TLS
reset.

The idle stacks cost the kernel image nothing: each architecture's table of secondary start stacks
(`stacks[WIT_PROCESSOR_CAPACITY]` in `secondary.c`, 64 KiB each) always held an entry 0 no start used, which is now
the boot processor's idle stack, and a secondary's idle stack is its own start stack, which it abandons once it
dispatches (P1.3). A first version kept eight idle stacks of its own in `user.c`; the x64 release image grew by
512 KiB to some 35.9 MiB of memory, and the firmware no longer found room to load it with 128 MiB (`release-128`:
`Out of Resources`), so the image stays at its size of K7 and the static arrays per slot remain P1.5's question.

## 4. What ran

In the Linux host's image, with the final code:

- `test --arch x64`: PASS, all 27 scenarios — `boot-128` and `boot-512` with the user suites, `boot-smp2` with
  `Smp.Online`, `Smp.Ipi` and `Smp.Identity` on two processors, `boot-intel`, the layer-2 scenarios (`libc`,
  `libc-test`, `cxx`, `spawn`, `process`, `sysroot`) and the fault and refusal scenarios.
- `test --arch arm64`: PASS, all 21 scenarios; `test --arch riscv64`: PASS, all 21.
- `release` on the three ISAs: `release-128`, `release-512` and `release-display-256` pass.
- `runtime-terminal --arch x64`: PASS (the services idle and wake on the dispatcher's new path).

The first riscv64 run panicked in the self-test's kernel workers (`Scheduler.Preemption`: a load page fault at
`0x10`): their frames carried a zero `tp`, which the S-mode code now reads; a worker's frame carries the hart's record
like every S-mode frame. CI's `linux-host` legs run every runtime scenario on the three ISAs.

## 5. Left for the next slices

- The kernel lock and requests from any processor to any (P1.2), with the x64 vector of a device line or a request
  passed on the stack instead of `wit_x64_device_vector` and `wit_x64_ipi_vector`.
- The x64 SYSCALL entry's stack and scratch (`wit_x64_syscall_kernel_rsp`, `syscall_user_rsp`) and the other
  architectures' selected stack tops stay single until P1.3 lets a second processor run threads.
