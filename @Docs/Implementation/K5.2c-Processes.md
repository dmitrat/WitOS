# K5.2c — Processes (ABI v61)

Plan step K5.2c brings the processes of [RFC 0011 v3 §7.8](../RFC-0011-Kernel-Architecture-and-ABI.md) into the
kernel: `PROCESS_CREATE` (90), `PROCESS_KILL` (91), `PROCESS_QUERY` (92), the handle kind `PROCESS` with the rights
`KILL` (262144) and `MANAGE` (524288), `MEMORY_OBJECT_MAP` into another process (§7.2) and `THREAD_CREATE` version 3
into another process (§7.3). A process is an empty address space with one capability, the channel endpoint its
creator chose; the creator places the image and the first stack with mappings, starts the first thread, and sends
everything else over the channel. The kernel reads no image format, no name and no path. The call-by-call reference
is [ABI-Reference.md](ABI-Reference.md).

The step has two commits: the channels move into one table of the kernel first, as the memory objects did in K5.2b;
then the processes arrive.

## What changed

**Channels in the kernel's table.** `WitChannelTable` is kernel-wide (`WIT_CHANNEL_TABLE_CAPACITY` 32), an endpoint
has one number in every process, a channel is charged to its creator's quota of four live channels while the creator
lives, and a change of an end re-evaluates the parked waits of every live component. A capability of a kind whose
record belongs to one process — an event, a device, an interrupt binding, a pin — carries the Id of the process it
left (`WitChannelCapability.Origin`) and is received by that process alone (`CHANNEL_RECEIVE` by another returns
`UNSUPPORTED`, the message stays queued); endpoints, memory objects, process handles and thread handles cross
processes. A component's end voids the capabilities of its own kinds still in flight, releases every endpoint handle
it held and collects the ends only cycles of queues keep.

**The registry and the pool.** The two component slots become a registry of `WIT_PROCESS_CAPACITY` (8) slots with a
kernel stack per thread of every slot on both ISAs (`wit_x64_user_kernel_stacks`, `wit_a64_user_kernel_stacks`; the
stack guards grow with them). The components the host creates (tests, the root task) stay caller-owned records;
`PROCESS_CREATE` takes records from a pool of eight in `user_process.c`. A record lives while the process runs or any
handle refers to it: an ended process is torn down at once, leaves the registry and keeps its state and exit code for
`PROCESS_QUERY` until the last handle goes.

**`PROCESS_CREATE(WitProcessCreateRequest, 32, output)`.** The request names a live channel endpoint handle of the
caller with `TRANSFER`, a page quota (zero for the default `WIT_RUNTIME_PAGE_CAPACITY`, at most that) and zero flags.
Everything is validated — the request, the 8-byte output, the endpoint, a free handle slot, a free pool record, a free
registry slot and the child's root table — before anything changes; then the endpoint moves into the child's table
with its rights (the child-local value goes to the output), the child gets the full profile's quotas (32 handles, 16
events, 32 reservations) with the page quota asked and the creator's tick budget, no thread, and the caller gets the
process handle with `WAIT`, `QUERY`, `KILL`, `MANAGE`, `DUPLICATE` and `TRANSFER`. The child is part of the schedule
from now on.

**`MEMORY_OBJECT_MAP` with a process as the target.** `Target` is `WIT_PROCESS_SELF` or a process handle with
`MANAGE`; the mapping is then a reservation of the target's address space at an address of the target's arenas,
with the same validation as before. A target that ended is `CLOSED`.

**`THREAD_CREATE` version 3 (56 bytes).** `WitThreadCreateRequest3` is the version 2 form plus `Process`:
`WIT_PROCESS_SELF` or a process handle with `MANAGE`. The stack pointer must lie in a committed writable reservation of
the target (a mapping the creator made into it), the entry must be executable there; the thread handle and its record
go to the caller's table, the thread's identity to the target's. A thread handle held by another process serves
`OBJECT_WAIT` and `THREAD_QUERY`; the context, suspension and activation calls on it are `UNSUPPORTED`.

**`PROCESS_KILL(handle with KILL, code, 0)`** ends every thread of the process and the process with the code;
`WIT_PROCESS_SELF`, or a handle to the caller's own process, ends the caller like `PROCESS_EXIT`. **`PROCESS_QUERY
(handle with QUERY, WitProcessInfo, 40)`** copies the state (`LIVE`, `EXITED`, `FAULTED`), the live threads, the exit
code and the pages charged. A process handle is ready for `OBJECT_WAIT` once the process ended.

**Scheduling across processes.** `dispatch` round-robins over the live components of the registry from the current
one and over each component's threads from the one that ran last; another component's thread means its address
space (`wit_arch_space_switch`: CR3 on x64, TTBR0 with `TLBI VMALLE1` on ARM64), its kernel stack and its TLS. Deadlines
and memory pressure are expired for every live component on one clock read. A device line reaches its binding's
owner, whichever component runs. Ticks are charged to the running component alone.

**Ending.** The last thread's exit ends its component with its code. A created process that ends — by exit, a fault,
its budget or a kill — is settled (threads over, references released: channels, bindings, pins, devices, memory
objects, process handles, then the table), torn down at once with its address space left for the kernel's root, taken
off the registry, and its handles' waiters wake; if it was the running one, the dispatcher resumes another thread's
frame directly (`wit_arch_resume_frame`) and the dead kernel stack is abandoned. A thread the end cuts short reports
the component's code to the handles that observe it. The root's end — the component `wit_user_run` launched — ends
every created process still alive and returns to the host; nothing of the pool survives a run. A process without a
thread whose last handle goes ends too: nothing could ever start a thread in it.

## Kernel

- `user_abi.h`: v61, the `PROCESSES` feature, the calls 90–92, the rights `KILL` and `MANAGE`; `handles.h`:
  `PROCESS` 15; `process.h`: the request and the info; `thread_reference.h`: version 3; `limits.h`:
  `WIT_CHANNEL_TABLE_CAPACITY`, `WIT_PROCESS_CAPACITY`.
- `channels.c`, `user_channel.c`: the kernel's table, the creator's charge, `Origin`, the void, release and collect
  of a component's end, the process capability.
- `user_process.c`: the pool, the three calls, the handle's lifecycle, `Holders`, `wit_user_process_target`.
- `user.c`: the registry of eight, `root_user`, `release_references`/`settle`/`teardown`/`retire`,
  `wit_user_finish` for a created process, `wit_user_end`, `end_children`, `wit_user_create_empty`, the dispatcher,
  `expire_waits` over every component, the last thread's exit, the interrupt and tick paths.
- `user_thread.c`: `create_in` (version 2 and 3); `user_memory_object.c`: the target; `user_objects.c`: the waitable
  process handle; `user_reference.c`: exits reach every component, `live_target` by the identity's owner;
  `user_interrupt.c`: delivery to the binding's owner.
- `arch.h`: `wit_arch_space_switch`, `wit_arch_resume_frame`. x64: `page_table.c`, `user_entry.asm`, `stacks.c`,
  `x64.h`. ARM64: `entry.asm` (`wit_a64_switch_translation`), `frame.c`, `bringup.c`, `a64.h`.

## Fixtures

`tests/User.X64/processes.asm` (over `SYSCALL`) and `tests/User.A64/processes.asm`, driven by
`tests/Kernel/user_process_tests.c` (`User.ProcessLifecycle`): `QUERY` reports the family; a channel; a memory object
refused as the endpoint (`WRONG_TYPE`); the child created with one end, which leaves the creator's table; the child
queried live without threads; the child's program written through a writable view, published through the fixture's
own executable view and mapped executable into the child at a fixed code address (a duplicate without `MANAGE` is
`DENIED`); a stack object mapped writable into the child; a version 3 thread refused with a stack pointer outside the
child (`BAD_ADDRESS`) and started at the stack's top with the child-local endpoint handle as its argument; the child
sends eight bytes and exits with 42; the creator waits for the process handle and the thread handle, queries the
exit, receives the message, is refused a thread into the ended process (`CLOSED`); a second child killed before it
has a thread reports its code and wakes its waiter, and a second kill is `CLOSED`. The kernel checks that no pooled
record, object, channel, handle, mapping or page survives.

The frozen line's native thread fixture now treats version 4 as the foreign request version.

## Limits kept explicit

- Eight registry slots and eight pooled records with static kernel stacks per slot and thread: "N bounded by memory"
  is a constant here, and kernel stacks from pages are deferred.
- A child's quotas are the full profile's, bounded by the page quota asked; hierarchical accounting against the
  creator (§12) stays open: an object or channel a torn-down process created lives on uncharged.
- Events, devices, interrupt bindings and pins stay with the process that holds their records: they do not cross
  processes through a channel yet. A thread handle in another process is for waiting and querying only.
- `CODE_MEMORY` of the frozen line is untouched: its one consumer leaves at K8 with the rest of the Windows-form
  user space, and `MEMORY_OBJECT_MAP` into a process is the replacement.
- A process whose last handle goes while it has no thread ends; a process with threads lives on without handles.
