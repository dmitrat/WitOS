# E4.3 — Process ids of their own

Plan step E4.3 (phase E, goal Ц6). The check of E4.2 on VMware and in QEMU found that Arlecchino.Commander shows a
command's exit code as `[exit -1]`. Since N4.2, `getpid` has answered 1 in every process, and a parent has numbered its
children itself from 2. .NET's System.Native takes a process whose id is 1 for init. `pal_signal.c` computes
`reapAll = g_pid == 1 || IsSigIgn(…)`, and on every SIGCHLD it reaps every child with `waitpid(-1)`. Commander's own
`waitpid` for the shell it started therefore answered `ECHILD`. Any .NET program that starts children with
`posix_spawn` rather than `Process` meets the same. The runtime's default diagnostic port also had one name for every
process (W4.1).

The fix gives each process an id of its own, which the process manager hands out. ABI-1 does not change; the kernel
knows no process ids.

## 1. The protocol

- **The process manager (`witos/manager.h`, version 6).**
  - The manager numbers every process it starts from 2: services, the first process and every process a request
    starts. The root task is 1. An id is never given twice in a boot.
  - A spawn request names the requester's id in `WitManagerRequest`'s `ParentId`, which was `Reserved`.
  - The reply carries the new process's id: `WitManagerReply` grows to 24 bytes, with `ProcessId` and `Reserved`.
  - Services and the first process have the root task as their parent.
- **The start message (`witos/start.h`, version 7).** It carries `ProcessId` and `ParentId`: 40 bytes, so the initial
  directory now holds 216 bytes. A creator that starts a program without the manager, such as the spawn scenario's root
  task, gives none (zero).
- **libwitos.** `witos_spawn_options` gains `process_id` and `parent_id`, which `witos_spawn_ex` writes into the start
  message. The manager's client, `witos_manager_spawn`, through which the device manager starts its drivers, names the
  caller's id in its requests.

## 2. The libc

- `WitProcessContext` keeps `ProcessId`, where `Reserved` was, and `ParentId`. `start.c` fills them from the start
  message: an id of zero becomes 1, and the parent stays zero. The root task's `crt1` sets 1.
- `getpid` answers `ProcessId` and `getppid` answers `ParentId`. `prlimit` of the own id and `SO_PEERCRED` use the own
  id; the peer's id is not carried over a connection.
- `posix_spawn` answers the id the manager's reply carries, which `waitpid`, `waitid` and `kill` take. The library's own
  counter of child ids is gone. A reply with no id above 1 is a broken protocol (`EIO`).
- Thread ids stay the library's own, and the main thread's stays 1. musl's dynamic linker reads the main thread's id
  (`set_tid_address`) before the start message comes (S5.3), so it cannot be the process's id. On Linux the main
  thread's id is the process's; here it is not, which nothing measured depends on.

## 3. Managed code

`OutWit.OS.Communication.ServiceStatus.VERSION` and the `WitServiceStop` it heads are version 6 with the header. Every
service publishes anew with the libc.

## 4. The gates

- **`process` scenario** (`tests/User/process_init.c`, `process_child.c`). `/bin/init`'s id is above 1 and its parent
  is 1. A child started with `ids <parent>` checks that its parent is the id it was given and that its own id differs.
  It exits with its id's low bits, which must equal those of the id `posix_spawn` answered.
- **`runtime-file-manager`** (E4.2). It requires `[exit 0]` in Commander's output view (Ctrl+O) after the program ran,
  then leaves the view with Esc and quits with F10 once the panels are back. The `[exit -1]` that showed the defect is
  gone.
- **Other runs.** The `spawn` scenario's root task starts its programs without the manager, so they are 1, as before.
  `libc-test` starts every test with `posix_spawn` under the manager. `test` runs the layer-2 scenarios on one processor
  and on two; the gate ran `process`, `spawn` and `libc-test` by their own commands. `release` boots the release
  kernel. `runtime-services` covers the device manager starting drivers through the manager's client.
  `runtime-terminal` covers a pseudo-terminal's child and grandchild. `runtime-compatibility` (x64) covers the
  diagnostic IPC and the process checks.

## 6. Limits kept explicit

- The kernel knows no process ids; the process manager's are the system layer's, numbered per boot from 2.
- A program started without the process manager has the id 1.
- The main thread's id is 1, not the process's.
- `SO_PEERCRED` names the caller's own id, not the peer's.
- No signal but `SIGKILL` reaches another process, as before (N4.2).
