# H3.3 — PC storage: the PC's one disk

H3.1 and H3.2 served the PC's SATA and NVMe disks. H3.3 makes the disk a PC boots from. In QEMU's scenarios, WitOS has
had two disks: a read-only FAT boot disk on virtio-blk, which the firmware boots, and a writable data disk with a GUID
partition table. A PC — VMware's machine, a real one — has one disk on its SATA or NVMe controller. That disk holds the
EFI system partition the firmware boots from, beside the partitions the system writes.

## 1. The pieces

| Where | What |
| --- | --- |
| `OutWit.OS.Storage.GptPartition.EFI_SYSTEM` | The EFI system partition's type GUID (UEFI 2.10 §5.3.3). |
| The namespace service (`VolumeMounter`) | A GUID disk's EFI system partition whose volume is FAT mounts at `/boot`, read-only whatever the disk, since the firmware boots from it — as the boot disk's whole-disk FAT volume did. The data partitions mount as before: "WitOS ext4" at `/data`, "WitOS FAT" at `/fat`. |
| The device manager (`StorageProbe`) | The probe reads an EFI system partition's FAT volume as it reads a boot disk's: its root, the loader, a clean check. |
| `RuntimeDataDisk.CreateAsync(bootImage:)` | The PC's one disk: the data disk's partitions, then the boot disk's FAT volume, unchanged, as the EFI system partition "EFI System" after the ext4 partition. GPT does not ask the system partition to come first, so the data partitions keep their places and every check of the data disk applies to the one disk. |
| `RuntimeDataDisk.WriteVmdkAsync` | A VMDK descriptor beside the raw image: a monolithic flat disk whose one extent is the raw image as it is (`RW <sectors> FLAT "<image>" 0`), which VMware attaches to a SATA or NVMe controller with no conversion and no `qemu-img`. The QEMU WitOS builds on Linux has no tools. |
| `BootRequest.BootDiskController` | The boot disk on a read-only virtio-blk device, as every scenario has it. For the PC's one disk, which the guest writes, it hangs writable on an AHCI controller's first port (q35's own, an `ich9-ahci` where the virtio boot disk would be elsewhere) or as an `nvme` namespace there, booted first. |
| `runtime-devices` | After its seven boots of the data disk, the scenario boots the PC's one disk (§3). |
| `shell --pc` | The session's one disk — PowerShell's package as the system partition, the layer of base applications on the ext4 partition — booted from NVMe. With `--prepare <directory>` it is written as `WitOS-pc-<arch>.img` with its descriptor `WitOS-pc-<arch>.vmdk` for a VMware machine with EFI firmware: the image H5 boots. |

## 2. The firmware

Measured by booting a boot disk as the only disk of a board, on each controller:

| Board | NVMe | AHCI |
| --- | --- | --- |
| x64, q35 (OVMF) | boots | boots (its ICH9 controller) |
| ARM64, `virt` (ArmVirtQemu) | boots | finds no boot device and starts the UEFI shell: the firmware has no SATA driver |
| riscv64, `virt` | boots | boots |

The WitOS AHCI driver serves an `ich9-ahci` on ARM64 all the same (H3.1's gate). ARM64 machines boot from NVMe or a
controller their firmware drives. The Raspberry Pi 5 reaches NVMe through its PCIe connector.

## 3. The gate

`runtime-devices` writes the PC's one disk anew: the data disk's partitions and programs, and the scenario's boot disk
as its EFI system partition. It boots that disk with no other disk beside it:

- first from NVMe, on the three ISAs;
- then from AHCI, on x64 and riscv64.

The second boot finds what the first left. In each boot:

- the firmware boots the loader from the system partition;
- the disk's driver serves the whole disk;
- the device manager's probe reads the partition table of four partitions and the system partition's volume, and
  writes the test, FAT and ext4 partitions;
- the namespace service mounts `/boot` from the system partition, read-only, beside `/data` and `/fat`;
- `/bin/init` runs its checks and programs, refused a write on `/boot` as on the boot disk;
- the services stop.

After each boot the host judges the disk as it judges the data disk.

The scenario's disk is 160 MiB: the data disk's 32 MiB, then the 128 MiB system partition from block 63488. The
partition holds the scenario's boot disk, with `/EFI/BOOT/BOOTX64.EFI` (or the ISA's name), the root task and the package.

| ISA | The PC's one disk from NVMe | from AHCI |
| --- | --- | --- |
| x64 (container) | passed: QEMU's NVMe controller on MSI-X | passed: q35's ICH9 controller on MSI, the disk on port 0, QEMU's CD-ROM on port 2 left |
| ARM64 (container) | passed: QEMU's NVMe controller on its INTx line | — (the firmware has no SATA driver) |
| riscv64 (container) | | |

## 4. What is not yet

- **VMware.** The prepared disk boots in the H5 session, on VMware's SATA (15ad:07e0) and NVMe (15ad:07f0) controllers.
- **A system partition the system writes.** `/boot` is read-only. A system update writes the package anew, ADR 0027's
  whole-system update, which has no in-place form yet.
- **The disk's size.** The prepared disk is written from one array of the host's memory, so it stays below 2 GiB. A
  disk grown to the machine's would need its ext4 partition resized.
