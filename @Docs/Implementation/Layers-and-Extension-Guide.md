# Слои WitOS и как их расширять

Документ описывает раскладку кода, правила зависимостей между слоями и два сценария расширения: новый системный вызов и новая платформа. Целевое состояние достигается срезами Q2.4–Q2.10 [плана консолидации](Q2-Consolidation-and-Arm64-Plan.md); до их завершения в таблице отмечено, где код лежит сейчас.

## Слои

| Слой | Каталог (цель) | Где сейчас | Что содержит | Может зависеть от |
| --- | --- | --- | --- | --- |
| Загрузчик UEFI | `src/Boot.Uefi` | там же | Вход `efi_main`, карта памяти, образ ядра, энтропия, загрузочный пакет, `ExitBootServices` | `witos/boot.h`, `platform.h`; `arch.h` для передачи управления ядру |
| Общее ядро | `src/Kernel` | там же с Q2.5; слои `kernel-boot` (вход ядра, аллокатор страниц, консоль) с A0, `kernel-foundation` (загрузочный пакет и хранилище, ChaCha20) с A1.2, остальное в `kernel-common` | Физические страницы, хэндлы, события, PE-валидатор, пакет, случайность, процессы, потоки, ожидания, APC, references, stack leases, DLL, исключения как политика | только `src/Kernel/include` и `witos/arch.h` |
| Архитектура | `src/Kernel.Arch.X64`, затем `src/Kernel.Arch.A64` | x64: только код ядра, с T3.1 — C под clang и ассемблер GNU (`.S`), а пользовательский `chkstk.asm` замороженной линии переехал в `src/Runtime.Native/X64`; A64: идентичность и вход с A0, векторы исключений с A1.1, таблицы страниц ядра и guard-страницы с A1.2 | Векторы, вход и выход из пользовательского режима, сохранение контекста, таблицы страниц, профиль FPU, CPUID и кэш, барьеры | общее ядро через `arch.h` |
| Платформа | `src/Kernel.Platform.Q35`, `src/Kernel.Platform.QemuVirt` | `src/Kernel.Platform.Q35` с Q2.6; `src/Kernel.Platform.QemuVirt` с A0: PL011, выход через Arm semihosting, generic counter как монотонные часы с A1.2 | Консоль, контроллер прерываний, таймер тиков, монотонные часы, тестовый выход | `platform.h` |
| Self-test и фикстуры ядра | `tests/Kernel`, `tests/Kernel.X64`, `tests/Kernel.A64` | общие тесты (аллокатор страниц, `self_test.h`) в `tests/Kernel` со слоем `kernel-selftest-shared` с A1.1; x64 с Q2.7; ARM64 с A1.1; белые ящики под `WITOS_SELFTEST` рядом со своими модулями | `*_tests.c`, `self_test.asm`; собираются только с `WITOS_SELFTEST` | все слои ядра |
| Гостевые фикстуры | `tests/User.X64`, `tests/Runtime.NativeAot` | там же; ассемблерные `*_fixture.asm` переехали из арх-каталога в Q2.8 | Пользовательские процессы и runtime-пробы, которые встраиваются в тестовые образы | пользовательские слои |
| Пользовательский native-слой | `src/Runtime.Native` | там же с Q2.8 (прежде `src/System.Native`); `X64/native_start.asm`: вход процесса, syscall, блокировки, fail-fast | Обёртки syscall, bootstrap, TLS-цикл, пути, файлы, DLL lifecycle | только `user_abi.h` и его заголовки |
| Win32-форма PAL | `src/Runtime.Pal.Win32` | с Q2.8 Win32-привязки `X64/native_*.asm`; реализации `native_*.witos.cpp` пока в `src/Runtime.NativeAot` поверх PAL NativeAOT, перенос вместе с отвязкой от upstream `Pal.h` в P6.4 | Реализации Win32-имён, которые ждёт runtime, собранный под Windows ABI | `Runtime.Native` |
| Адаптеры runtime | `src/Runtime.NativeAot`, `src/Runtime.CoreClr` | там же; ISA-код в подкаталогах `X64` | GC OS interface, PAL NativeAOT, minipal, CoreCLR VMToOS, hosting PAL | `Runtime.Native`, `Runtime.Pal.Win32` |
| Upstream .NET | вне репозитория, pinned; правки в `patches/` | `.tools/upstream` | `dotnet/runtime` с hash-проверкой и оверлеем | адаптеры runtime |
| Инструменты | `tools/WitOS.Dev`, манифесты `build/` | `tools/WitOS.Dev` | Сборка, QEMU, приёмка, evidence | — |

Правила:

1. Общее ядро не включает заголовки архитектуры и платформы и не упоминает регистры, адреса устройств или квоты конкретной платы.
2. Архитектурный слой не принимает решений политики: он исполняет то, что попросило общее ядро, и сообщает о событиях процессора.
3. Пользовательские слои видят ядро только через `user_abi.h`. Никакой код в `src/Runtime.*` не включает внутренние заголовки ядра.
4. Тестовый код не попадает в релизный образ ядра.

## Интерфейс архитектуры

[`witos/arch.h`](../../src/Kernel/include/witos/arch.h) объявляет всё, что политике нужно от процессора; с Q2.4 политика вызывает только эти функции. Поток задаётся номером слота компонента и индексом потока; его кадр регистров `WitArchFrame` для общего ядра непрозрачен и лежит на стеке ядра этого потока, пока поток вне пользовательского режима.

| Группа | Операции |
| --- | --- |
| Переключение | запустить поток, выйти в ядро, выбрать стек ядра потока или загрузочный стек, установить и сбросить TLS потока, проверить активное адресное пространство ядра и флаг прерываний, idle с ожиданием прерывания |
| Кадр потока | создать начальный кадр, проверить принадлежность кадра стеку потока, происхождение из пользовательского режима, пригодность для возврата и idle-кадр, прочитать PC и SP, подготовить флаги возврата, слоты статуса и результата syscall, кадр callback исключения, диагностический вывод |
| Контекст | профиль сохранения (FXSAVE64 для x64), метаданные профиля, снимок кадра в `WitThreadContext`, проверка регистров и состояния FPU, PC и SP контекста, применение контекста к кадру, описание CPU-профиля |
| Исключения | какие векторы доставляются в callback, класс аппаратного сбоя для счётчиков, архитектурные поля записи исключения, состояние сбоя для диагностики |
| Адресные пространства | кодирование листовой записи (READ, WRITE, EXECUTE и программные OWNED, ALIAS), обход с созданием таблиц, чистка пустых таблиц, сброс TLB, трансляция адреса с проверкой прав, ядерные ветви нового пространства, проверка активного пространства, публикация кода |
| Запуск | идентичность архитектуры (`wit_arch_identity`: значение для контракта загрузки, PE-машина, имена), вход ядра из загрузчика, таблицы дескрипторов, запрет прерываний, остановка процессора, отображение страницы устройства |
| Время | тики планировщика, которые считает вход прерывания таймера; сам таймер и монотонные часы даёт плата через `platform.h` |
| Процессор | размер кэша, барьер записи процесса |

Типы, которые общее ядро встраивает, не читая их полей, архитектура объявляет в своём каталоге `include`: для x64 это [`src/Kernel.Arch.X64/include/witos/arch_types.h`](../../src/Kernel.Arch.X64/include/witos/arch_types.h) с `WitArchFaultState`. Этот каталог единственный архитектурный путь включения общего ядра. Регистровое соглашение syscall (номер в RAX, аргументы в RCX, RDX, R8) раскодирует точка входа архитектуры, а политика получает уже готовые номер и аргументы.

Хостовые тесты `KernelLayeringTests` проверяют, что файлы политики не называют `wit_x64_*`, регистры, селекторы и инструкции процессора, а файлы `src/Kernel` не включают архитектурные заголовки.

## Как добавить системный вызов

1. Выбрать класс по [справочнику ABI](ABI-Reference.md). Вызов класса experimental не должен становиться зависимостью core-кода.
2. Взять следующий свободный номер из справочника и добавить `WIT_CALL_*` в `user_abi.h`.
3. Если вызов принимает структуру, описать её в отдельном заголовке `witos/<имя>.h` с полями `Version` и `Size` первыми, нулевыми `Reserved` и `WIT_STATIC_ASSERT` на размер.
4. Реализовать политику в общем ядре: копирование запроса, полная валидация, затем мутация; при ошибке откат и неизменный пользовательский буфер.
5. Добавить обработчик и строку `[WIT_CALL_...] = обработчик` в таблицу `src/Kernel/user_calls.c` и поднять `CALL_COUNT`, если номер новый последний; хостовый тест `CallTableCoversEveryCallTest` требует ровно одну строку на каждый вызов. Обработчик пишет статус и значение через `WitUserCall` и возвращает 0, чтобы вызов завершился общим путём `wit_user_syscall` (истечение ожиданий, приостановка, диспетчеризация, TLS), или кадр, который надо возобновить как есть. Регистровое соглашение остаётся в архитектурном слое: точки входа `wit_x64_user_syscall` и `wit_a64_user_trap` только раскодируют регистры.
6. Добавить обёртку в `Runtime.Native`, если вызов нужен пользовательскому коду.
7. Добавить гостевую фикстуру в `tests/User.X64` с положительными и отрицательными случаями и маркером `[TEST-PASS]`, ожидание маркера в манифесте сценария.
8. Увеличить `WIT_ABI_VERSION`, обновить справочник, `PLAN.md` и документ среза. Хостовый тест сверяет справочник с заголовком.

## Квоты

Квоты ядра (объекты компонента, страницы и резервирования, бюджет тиков, байты одного вызова, пределы загрузчика PE) определяются только в `src/Kernel/include/witos/limits.h`, пользовательские — только в `src/Runtime.Native/native_limits.h`. Новая квота добавляется туда с комментарием о том, что она ограничивает; заголовок, которому она нужна, подключает файл квот. Константы формата (массивы ABI-структур, адреса раскладки) остаются рядом со своими структурами.

## Как изменить upstream-исходник

Pinned-исходники не правятся ни в рабочем дереве upstream, ни заменами строк в инструменте. Правка — это файл `patches/<репозиторий>/<выход>.patch`, где репозиторий `runtime` или `openlibm`, а выход — имя файла, который получает сборка.

1. Взять pinned-файл из кэша загрузки (`.tools/runtime-audit/runtime/<commit>/<путь>` или `.tools/math-audit/<revision>/<путь>`), скопировать и изменить копию.
2. Получить diff: `git diff --no-index -U3 <оригинал> <копия>` и заменить его заголовки на `--- a/<путь>` и `+++ b/<путь>`, где путь — путь в upstream-репозитории.
3. Перед diff записать четыре строки `Source: <путь>`, `Output: <выход>`, `Before: <sha256 пина>`, `After: <sha256>` и абзац о том, зачем нужна правка. `After` можно взять из сообщения об ошибке первого применения.
4. В инструменте вызвать `UpstreamPatches.Apply(root, репозиторий, путь, выход, текст)` и записать результат в `artifacts`; в отчёт добавить `UpstreamPatches.Describe`.
5. Хостовые тесты требуют, чтобы база патча была пином, чтобы инструмент применял каждый патч и чтобы патч воспроизводил свой выход. При смене пина каждый патч отказывает, пока его не переделают на новой базе.

## Как добавить платформу

Платформа это пара «архитектура плюс плата». ARM64 на QEMU `virt` — первый пример (фаза A).

1. **Тулчейн.** Компилятор, ассемблер и линковщик, дающие PE/COFF для целевой машины; обнаружение в `Toolchain`. Для x64 с T3.1 это закреплённые clang и `lld-link` (триплет ядра `x86_64-unknown-windows`), для ARM64 до T3.2 — MSVC ARM64 cross tools.
2. **Загрузчик.** `Boot.Uefi` общий: архитектуру для контракта загрузки и машину собственного PE он берёт у `wit_arch_identity()`, имя `BOOT*.EFI` задаёт инструмент. Предел образа и пакета в 4 ГиБ пока общий: на `virt` с RAM до 3 ГиБ он выполняется.
3. **Архитектура.** Каталог `src/Kernel.Arch.<isa>` реализует `arch.h` и `virtual.h`. Путь ядра требует идентичность, группу запуска, векторы исключений, таблицы страниц ядра и счётчик тиков; контексты, вход и выход из пользовательского режима и FPU-профиль добавляются вместе со слоем `kernel-common`, который их вызывает. ARM64 прошёл это за три шага: A0 грузился в профиле «только загрузка» (`WITOS_BOOT_ONLY`: ядро останавливалось после аллокатора), A1.1 добавил векторы, A1.2 таблицы страниц и часы и убрал профиль, A1.3 таймер и вытеснение потоков ядра, A2.1 пользовательский режим с `kernel-common` (кадры потоков на стеках ядра, вход и выход, таблицы компонентов, публикация кода по страницам и помощники компилятора `memcpy`, `memset`, `__chkstk`, которые MSVC вызывает на ARM64); для третьей архитектуры его можно вернуть из истории (`e2ded71`).
4. **Плата.** Каталог `src/Kernel.Platform.<board>` реализует `platform.h`: вывод байта консоли (форматирует общий `console.c`), устройства, нужные до отображения по требованию (`wit_platform_boot_devices`: архитектура отображает их как device-память вместе с таблицами ядра), прерывания, таймер, часы, тестовый выход. Если все прерывания приходят в один вектор (GIC), плата реализует `wit_platform_interrupt_claim`: подтверждает прерывание и сообщает, таймер ли это. Тестовый выход отдаёт хосту тот же код, что `isa-debug-exit` на q35: `(code << 1) | 1`, поэтому runner одинаково различает исходы на всех платах.
5. **Манифест сборки.** `build/kernel-<isa>.json` называет общие каталоги include, слои в порядке линковки (`boot-uefi`, `kernel-boot`, `kernel-foundation`, `kernel-common`, слой архитектуры, слой платы), self-test слои (общий `kernel-selftest-shared` и свой) и необязательные `defines`. Каждый слой это `build/layers/<слой>.json` со своими исходниками; новая архитектура добавляет `kernel-arch-<isa>.json`, `kernel-platform-<board>.json` и `kernel-selftest-<isa>.json`, а общие слои переиспользует. Пока архитектура не умеет пользовательский режим, цель не линкует `kernel-common`; хостовый тест это фиксирует для ARM64 до A2. Цель со статусом `template` драйвер не собирает.
6. **Сценарии.** `KernelArchitecture` в инструменте описывает MSVC-инструменты, имя EFI, PE-машину, машину QEMU, процессор, прошивку и тестовый выход. `build --arch <isa>` и `test --arch <isa>` выбирают её; набор `Foundation` проверяет баннер, строку сборки архитектуры, маркеры фундамента в порядке x64, частоту счётчика, вытеснение потоков ядра, пользовательские наборы и Hello; ожидаемые маркеры лежат в `tests/Expectations/<isa>-*.json`, а сдержанные сбои сверяются с итоговой строкой гостя `[TEST-SUMMARY]`, а тот же runner различает успех, panic, исключение и таймаут.
7. **Проверка слоения.** Общее ядро собирается без изменений; любое ISA-ветвление в `src/Kernel` считается дефектом слоения.
8. **CI.** Отдельный job с той же матрицей сценариев; для ARM64 это `boot-arm64` в `kernel.yml`.
