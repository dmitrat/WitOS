# Слои WitOS и как их расширять

Документ описывает раскладку кода, правила зависимостей между слоями и два сценария расширения: новый системный вызов и новая платформа. Целевое состояние достигается срезами Q2.4–Q2.10 [плана консолидации](Q2-Consolidation-and-Arm64-Plan.md); до их завершения в таблице отмечено, где код лежит сейчас.

## Слои

| Слой | Каталог (цель) | Где сейчас | Что содержит | Может зависеть от |
| --- | --- | --- | --- | --- |
| Загрузчик UEFI | `src/Boot.Uefi` | там же | Вход `efi_main`, карта памяти, образ ядра, энтропия, загрузочный пакет, `ExitBootServices` | `witos/boot.h`, `platform.h` |
| Общее ядро | `src/Kernel` | частично; политика в `src/Kernel.Arch.X64/user_*.c` | Физические страницы, хэндлы, события, PE-валидатор, пакет, случайность, процессы, потоки, ожидания, APC, references, stack leases, DLL, исключения как политика | только `src/Kernel/include` и `witos/arch.h` |
| Архитектура | `src/Kernel.Arch.X64`, затем `src/Kernel.Arch.A64` | там же, вперемешку | Векторы, вход и выход из пользовательского режима, сохранение контекста, таблицы страниц, профиль FPU, CPUID и кэш, барьеры | общее ядро через `arch.h` |
| Платформа | `src/Kernel.Platform.Q35`, `src/Kernel.Platform.QemuVirt` | в `src/Kernel.Arch.X64` | Консоль, контроллер прерываний, таймер тиков, монотонные часы, тестовый выход | `platform.h` |
| Self-test и фикстуры ядра | `tests/Kernel.X64` | в `src/Kernel.Arch.X64` | `*_tests.c`, `*_fixture.asm`; собираются только с `WITOS_SELFTEST` | все слои ядра |
| Пользовательский native-слой | `src/Runtime.Native` | `src/System.Native` | Обёртки syscall, bootstrap, TLS-цикл, пути, файлы, DLL lifecycle | только `user_abi.h` и его заголовки |
| Win32-форма PAL | `src/Runtime.Pal.Win32` | `src/Runtime.NativeAot` и `native_*.asm` в `src/Kernel.Arch.X64` | Реализации Win32-имён, которые ждёт runtime, собранный под Windows ABI | `Runtime.Native` |
| Адаптеры runtime | `src/Runtime.NativeAot`, `src/Runtime.CoreClr` | там же | GC OS interface, PAL NativeAOT, minipal, CoreCLR VMToOS, hosting PAL | `Runtime.Native`, `Runtime.Pal.Win32` |
| Upstream .NET | вне репозитория, pinned | `.tools/upstream` | `dotnet/runtime` с hash-проверкой и оверлеем | адаптеры runtime |
| Инструменты | `tools/WitOS.Dev`, манифесты `build/` | `tools/WitOS.Dev` | Сборка, QEMU, приёмка, evidence | — |

Правила:

1. Общее ядро не включает заголовки архитектуры и платформы и не упоминает регистры, адреса устройств или квоты конкретной платы.
2. Архитектурный слой не принимает решений политики: он исполняет то, что попросило общее ядро, и сообщает о событиях процессора.
3. Пользовательские слои видят ядро только через `user_abi.h`. Никакой код в `src/Runtime.*` не включает внутренние заголовки ядра.
4. Тестовый код не попадает в релизный образ ядра.

## Интерфейс архитектуры

Целевой `witos/arch.h` (Q2.4) объявляет то, что политике нужно от процессора. Набор выведен из 24 функций `wit_x64_*`, которые политика вызывает сейчас.

| Группа | Операции |
| --- | --- |
| Кадр потока | создать начальный кадр (entry, argument, stack), записать статус и результат syscall, прочитать PC и SP, проверить, что кадр пользовательский, подготовить кадр callback исключения |
| Контекст | снимок в `WitThreadContext`, проверка и применение входного контекста, маска допустимых флагов, профиль FPU |
| Переключение | запустить поток, выйти в ядро, idle с ожиданием прерывания, установить стек ядра и TLS потока |
| Время | монотонный счётчик и частота, тики планировщика, запуск и остановка таймера |
| Процессор | размер кэша, барьер записи процесса, описание вектора исключения |

## Как добавить системный вызов

1. Выбрать класс по [справочнику ABI](ABI-Reference.md). Вызов класса experimental не должен становиться зависимостью core-кода.
2. Взять следующий свободный номер из справочника и добавить `WIT_CALL_*` в `user_abi.h`.
3. Если вызов принимает структуру, описать её в отдельном заголовке `witos/<имя>.h` с полями `Version` и `Size` первыми, нулевыми `Reserved` и `WIT_STATIC_ASSERT` на размер.
4. Реализовать политику в общем ядре: копирование запроса, полная валидация, затем мутация; при ошибке откат и неизменный пользовательский буфер.
5. Добавить строку в таблицу диспетчера (после Q2.9) или `case` в `wit_x64_user_syscall` (до Q2.9). Регистровое соглашение остаётся в архитектурном слое.
6. Добавить обёртку в `Runtime.Native`, если вызов нужен пользовательскому коду.
7. Добавить гостевую фикстуру в `tests/User.X64` с положительными и отрицательными случаями и маркером `[TEST-PASS]`, ожидание маркера в манифесте сценария.
8. Увеличить `WIT_ABI_VERSION`, обновить справочник, `PLAN.md` и документ среза. Хостовый тест сверяет справочник с заголовком.

## Как добавить платформу

Платформа это пара «архитектура плюс плата». ARM64 на QEMU `virt` — первый пример (фаза A).

1. **Тулчейн.** Компилятор, ассемблер и линковщик, дающие PE/COFF для целевой машины; обнаружение в `Toolchain`. Для ARM64 это MSVC ARM64 cross tools.
2. **Загрузчик.** `Boot.Uefi` уже не зависит от архитектуры, кроме машины PE, предельного физического адреса и имени `BOOT*.EFI`; они передаются параметрами сборки.
3. **Архитектура.** Каталог `src/Kernel.Arch.<isa>` реализует `arch.h`: векторы, вход и выход из пользовательского режима, контекст, таблицы страниц, FPU-профиль.
4. **Плата.** Каталог `src/Kernel.Platform.<board>` реализует `platform.h`: консоль, прерывания, таймер, часы, тестовый выход.
5. **Манифест сборки.** `build/kernel-<isa>.json` перечисляет исходники общего ядра, архитектуры, платы и, для тестовой сборки, self-test.
6. **Сценарии.** Описание машины QEMU (модель, процессоры, прошивка, устройства) и ожидаемых исходов в манифесте сценариев; тот же runner различает успех, panic, исключение и таймаут.
7. **Проверка слоения.** Общее ядро собирается без изменений; любое ISA-ветвление в `src/Kernel` считается дефектом слоения.
8. **CI.** Отдельный job с той же матрицей сценариев.
