# E2.1 — The SMB 3 client

Plan step E2.1 (phase E, goal Ц6; the author's decision of 2026-10-28: a network share is the most convenient way in,
and WitOS writes its own client): a managed client of SMB 3 in `OutWit.OS.FileSystems.Smb` that mounts a share of a
Windows or Samba server as an `IFileSystem`, judged on the host against Samba. E2.2 mounts it in the guest as a volume
of the catalog (ADR 0032, `ORIGIN_NETWORK`, below `/media`).

## 1. Why a client of its own

- **Windows 11 24H2 Pro** requires SMB signing on every connection, both ways, and refuses guest access by default; a
  client must log on with NTLMv2 and sign every message.
- **SMBLibrary** is LGPL-3.0; WitOS's services are NativeAOT programs linked statically, where the LGPL's relinking
  clause does not fit. Other managed clients are Windows-only wrappers or unmaintained.
- The protocol subset a file manager needs is small: one connection, one session, one tree, a request at a time.

## 2. What it speaks

`SmbConnection` (MS-SMB2):

- **Transport.** Direct TCP over any `Stream`: a zero byte, a 24-bit length, the message. The host tests use a
  `NetworkStream`; E2.2 gives it a stream over the network service's socket protocol.
- **Negotiation.** The dialects 3.0, 3.0.2 and 3.1.1, signing required, large MTUs; for 3.1.1 the pre-authentication
  integrity context (SHA-512 with a 32-byte salt) and the signing capabilities context (AES-CMAC). Encryption,
  multichannel, leases, DFS and durable handles are not offered. A server that answers another dialect, another hash or
  another signing algorithm is refused with a message that names what it chose.
- **Logon.** NTLMv2 under SPNEGO (`NtlmClient`, `Spnego`): the NEGOTIATE message offers Unicode, extended session
  security, signing, 128-bit keys and key exchange; the AUTHENTICATE message carries the NTLMv2 response built on the
  server's target information (the MIC flag set, `cifs/<server>` as the target name), the LMv2 response as 24 zeros
  when the challenge has a timestamp, the session key exchanged under RC4, and the MIC over the three messages; the
  last SPNEGO token adds the mechListMIC, NTLM's signature of the offered mechanism list, which Windows requires once a
  MIC is present. A guest or anonymous session is refused, since it cannot sign; a refused logon is `AccessDenied`
  with the server's status (`STATUS_LOGON_FAILURE`).
- **Signing.** The signing key is SP800-108's counter KDF with HMAC-SHA256 over NTLM's exported session key: for 3.1.1
  the label `SMBSigningKey` and the hash of the negotiation and the session setup up to the final request; for 3.0 and
  3.0.2 `SMB2AESCMAC` and `SmbSign`. Every request after the session setup is signed with AES-128-CMAC, and every
  response's signature is checked in constant time — the final session setup response first, which proves the server
  derived the same key. Only the refusal of a session setup comes unsigned, since the server has no key.
- **Requests.** One at a time, under a turn; each asks 64 credits, and a read or a write is charged a credit per 64
  KiB when the server offers large MTUs; an interim `STATUS_PENDING` is waited past; no oplock or lease is asked, so no
  break arrives.

`MD4`, `RC4` and `AES-CMAC` are written in `OutWit.OS`, since .NET has none of them; HMAC-MD5, MD5, SHA-512, AES and
the SP800-108 KDF are .NET's.

## 3. The filesystem

`SmbFileSystem.MountAsync(stream, server, share, credentials, readOnly)` logs on, connects the share's tree, asks its
size, and presents it as an `IFileSystem`:

- each operation is a CREATE of what it acts on (no oplock, sharing read, write and delete as a POSIX open does), its
  request and a CLOSE: a lookup reads the CREATE response's times, length and attributes; a listing is
  QUERY_DIRECTORY with `FileDirectoryInformation` in 64 KiB pages; a file opens by `FileMode` as CREATE's dispositions;
  a directory is made with every missing one above it; a deletion is `FileDispositionInformation`; a rename is
  `FileRenameInformation` without replacing; a mode sets or clears the read-only attribute alone, as on FAT
  (`NotPermitted` for any other mode); times are `FileBasicInformation`; space is `FileFsFullSizeInformation` (the
  units the account may still use as free);
- a handle reads and writes by offset in pieces of the server's largest read or write, at most a MiB, and keeps the
  length its own writes and cuts make; its flush is SMB's FLUSH;
- the volume's format is `SMB3`, its label the share's name, its identity a GUID of the SHA-256 of the server's GUID and
  the share's name, which another mount of the same share repeats; a share the account may not write, or a mount asked
  read-only, is read-only;
- each status the contract shares becomes its `FileSystemError` (`OBJECT_NAME_NOT_FOUND` `NotFound`,
  `OBJECT_NAME_COLLISION` `AlreadyExists`, `DIRECTORY_NOT_EMPTY` `NotEmpty`, `ACCESS_DENIED` `AccessDenied`,
  `SHARING_VIOLATION` `InUse`…); any other is an `IOException` naming the status, which the namespace service gives as
  `EIO`; a name holding `\` is `InvalidName`, since a share takes it for a separator.

## 4. The judge

`SambaServer` (`tests/OutWit.OS.Tests/FileSystems/Smb`) starts the Linux host's `smbd` without privileges on a free
loopback port, with a configuration of its own (one share, `server min protocol = SMB3_00`, `server signing =
mandatory`, `map to guest = never`, its directories under a temporary one) and an `smbpasswd` file it writes itself
with the NT hash of the current user's password, since `smbpasswd -a` adds an account as root alone. The tests:

- the crypto by its published vectors: MD4 (RFC 1320), RC4, AES-CMAC (RFC 4493), NTLMv2's key, proof and session key
  (MS-NLMP 4.2.4), the SPNEGO tokens read back;
- against Samba: the mount (dialect 3.1.1, format, label, identity repeated by a second mount, space); what the host
  wrote read through the share; 3 MiB and a bit written and read back across pieces and credits, a write past the end
  and a cut, checked in the host's directory; the open modes and their errors; directories made, moved and deleted,
  `NotEmpty`, `AlreadyExists`, `NotFound`; read-only and times; space after a write; a read-only mount; SMB 3.0 and
  3.0.2 with their key derivation; a wrong password and a missing share.

On 2026-10-28 in the Linux container with Samba 4.19.5: 27 passed as root and the 11 against Samba again as an
unprivileged user, as CI's runner runs them. A host without Samba skips the 11 (Windows). CI's `linux-host` legs
install `samba`, and so does `build/linux/Dockerfile`.

## 5. Limits kept explicit

- No encryption: a share or a session that requires it is refused with a message that says so. Windows and Samba do
  not require it by default.
- NTLMv2 alone, no Kerberos: a domain account logs on by NTLM as a workgroup account does.
- The server's mechListMIC is not checked; the final session setup response's signature authenticates the server's
  key instead.
- One request at a time on the connection; no reconnection after the server or the network drops it — a later request
  fails with `EIO` and the share is mounted again.
- Nothing is cached: each lookup is a round trip; a handle's length may lag another client's writes.
- A link on the share appears as what it points to; `ReadLinkAsync` is `NotALink`.
