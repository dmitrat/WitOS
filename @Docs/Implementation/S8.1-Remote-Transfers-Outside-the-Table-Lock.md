# S8.1 — Remote file transfers outside the libc's table lock

Plan step S8.1, a defect of the system layer found by the author's session of 2026-10-20 (C2.7: a `shell --accel`
session boots with four processors since P2): after `exit`, PowerShell printed `ESC[?1l` and nothing more, the
`[APPS-INIT] … exited` line never came, the services never stopped and QEMU never quit. The same session on one
processor exits 0.4 s after `exit`.

## 1. What was measured

The hang reproduces without the accelerator: the session typed into by a script (`exit` after an idle) hangs on four
processors under WHPX and under TCG alike, and exits on one processor under WHPX. The live guest was read through QEMU's
monitor over QMP (`info registers -a`, `xp` of the kernel's words by the link map's RVAs from the base the IDT register
names, `x` of the user stacks through each processor's paging):

- Every processor was in the kernel: `wit_cpus_lock` and `wit_arch_spin_pause` (spinning for the kernel lock),
  `read32` of the HPET (the acknowledgement wait of a request), `wit_cpus_serve`, or the idle halt, the CR3s changing
  between samples — no deadlock, a storm: the `cpus[]` acknowledgement counters rose by 200–400 RESCHEDULE requests per
  processor per half second in bursts, with a few FENCE requests (`PROCESS_WRITE_BARRIER`) between them.
- The pwsh process (slot 11) had 18 threads. Its main thread was parked in `call_with` of `namespace.c` ←
  `__wit_remote_write` ← `write_at` ← `dispatch` ← `__wit_syscall`, inside `__wit_lock(&tables)`: a
  `WIT_NAMESPACE_WRITE` of 4 bytes at an offset that advanced by some 45 bytes a second (11 writes a second, each
  ~90 ms). Three threads spun in `__wit_lock` with `THREAD_YIELD` for the tables (one of them in `__wit_pipe_write`,
  which takes the tables only to find the pipe); the rest were parked in futex waits. The namespace service's session
  thread sent and received on the block channel without a pause, and the data disk's image changed every second.
- The RESCHEDULE bursts are CoreCLR's suspension: `SuspendRuntime` injects an activation into every thread in
  cooperative mode that has not reached a safe point and waits `PING_JIT_TIMEOUT` = 1 ms before it injects again; each
  injection is `THREAD_ACTIVATE`, whose kick of a target another processor runs is a RESCHEDULE request with an
  acknowledgement wait under the kernel lock.
- The file was `/home/.cache/powershell/StartupProfileData-Interactive` (60,044 bytes on the volume after the hang):
  the MultiCoreJit profile `System.Runtime.ProfileOptimization` records, which CoreCLR writes at exit
  (`MulticoreJitRecorder::StopProfile` → `WriteOutput`) through a `CFileStream` one record at a time — 4 bytes a
  `write` — and only where `g_SystemInfo.dwNumberOfProcessors >= MultiCoreJitMinNumCpus` (2): on one processor no
  profile is written at all, which is why one processor never showed the defect.

## 2. The cause

`__wit_syscall` runs `read`, `write`, `readv`, `writev`, `pread` and `pwrite` of a file of a mounted volume
(`KindRemoteFile`) under the table lock, so the round trip with the namespace service — a channel send, the service's
transaction on the volume (a journaled write with its flushes through the block driver) and the wait for the reply —
holds the lock every other descriptor, mapping and package operation of the process needs. Pipes, the terminal and
sockets were already served outside the lock (N4.2, N4.3, W2.1a); volume files were not. On one processor a thread
that spins for the lock yields the processor to the holder and the services, and the round trip ends in well under a
millisecond of the guest's time. On several processors the spinners run on their own processors, every `THREAD_YIELD`
takes the kernel lock, the runtime's suspension kicks them every millisecond, and the holder's round trip crawls:
15,000 writes of 4 bytes at 90 ms each never end.

## 3. The change

- `namespace.c` gets the session's *turn*: a word a thread takes with an atomic exchange and parks on with a futex
  wait when the session is busy, as `socket.c`'s session does; it never spins. Every public `__wit_remote_*` call
  takes the turn around its request (a static `*_in_turn` body and a public wrapper), `__wit_remote_release` around
  its CLOSE, the connection around its MOUNTS request. `__wit_remote_read_in_turn`, `__wit_remote_write_in_turn` and
  `__wit_remote_fstat_in_turn` stay public for the transfers.
- `files.c` adds `__wit_remote_transfer_begin` (under the table lock: the descriptor found, its access checked, its
  remote record and open file description held), `__wit_remote_transfer` (outside the lock, holding the turn: the
  transfer at the offset given or at the description's position, `O_APPEND` at the file's end, the position advanced
  as `read_at` and `write_at` advance it) and `__wit_remote_transfer_end` (under the lock: the records let go, the
  last reference closing the handle).
- `syscall.c` adds `remote_transfer`, which `__wit_syscall` tries before the table lock for the six calls, after the
  pipe, terminal and socket transfers; `WIT_NOT_A_REMOTE` falls through to the dispatcher as before.
- The lock order is the tables, then the turn: a metadata call takes the turn under the table lock, a transfer takes
  the turn alone and never the tables while it holds it.
- The install's environment sets `DOTNET_MultiCoreJitNoProfileGather=1` (an existing runtime knob, RFC 0015 §4's
  second choice; `Compatibility-Differences.md`): with the storm gone, each of the profile's 4-byte writes is still a
  durable transaction of the namespace service's ext4 journal — the data block, the descriptor, the commit, the
  checkpoint, each followed by a flush the virtio driver turns into the host's `fdatasync` of the image — so pwsh's
  exit on four processors, which one processor ends in 0.4 s, still took tens of minutes (§5). A profile that exists
  is still played; none is gathered.
- The gate of the libc's part is the compatibility suite's `FileIO.SmallWritesUnderContention` check, which
  `runtime-compatibility` runs on four processors: one thread writes a file under `/tmp` (the namespace service's file
  system in memory, so that no journal's flushes take part) 500 times 4 bytes, unbuffered, while three threads stat
  `/dotnet/dotnet`, a file of the boot package, without a pause; the judge is the three's rate in the guest's clock,
  at least 1,000 stats a second. A stat of the package needs no service and takes the tables for microseconds, so it
  tells the libc that holds the tables through a write's round trip — the three then manage a few stats a second,
  waiting for each of the writer's 90 ms — from the libc that lets them go, whatever the writer's own pace, which the
  service's round trips under TCG on four processors make tens of milliseconds a write on ARM64 and riscv64. The
  writer's time was no judge: 2,000 writes to a volume's file on x64, and to `/tmp` on the slower ISAs, passed the
  suite's 60 s a check, since under `-icount` with `sleep=off` the guest's clock leaps to the next tick while the
  processors wait, and a round trip's wake-ups cost slices of every processor. `runtime-powershell` boots on four
  processors too (`RuntimeProcessors.PROCESSORS`), where pwsh's exit used to hang; `runtime-display` stays on one.

## 4. What the change does not do

- A metadata call (open, stat, mkdir, …) still holds the table lock while it waits for the service, and parks on the
  turn under the table lock while a transfer runs; the tables are then held for one transfer's round trip, as they
  were for every call before.
- `__wit_lock` is still a spin-yield lock; the transfers no longer give it a holder that waits for another process.
- The namespace service still makes a journaled transaction, with its flushes, of every `WRITE`, so a program that
  writes a file in small pieces pays a host `fdatasync` several times a write; Linux's page cache and its journal's
  5-second commits make the same program cheap. Write-behind in the service, with `fsync`, `close` and the stop
  writing back, is a storage step for the author to weigh against the durability D4.3 and D6.2 verify.

## 5. What ran

S8.1 closed on 2026-10-20.

- **The session (x64, the Windows host).** Before the change, `exit` typed into the session on four processors never
  ended within 180 s under WHPX and under TCG alike (three runs), and ended 0.4 s after `exit` on one processor under
  WHPX. With the libc's change alone the storm was gone — the processors halted between the service's transactions,
  with a request's acknowledgement wait now and then — but the exit still did not end within 20 minutes under WHPX
  and took 1,719 s of the guest's time under TCG in the container's gate, the profile's 15,000 writes each a
  journaled transaction with its flushes. With the knob the session on four processors ends 1.3 s after `exit`
  under WHPX.
- **The gates.** `runtime-compatibility`'s `FileIO.SmallWritesUnderContention` passes on x64 (500 writes in 4.1 s beside 894,419 stats, 220,617/s), ARM64
  (3.2 s, 152,342/s) and riscv64 (2.6 s, 61,751/s); `runtime-powershell` on four processors passes on the three ISAs,
  pwsh exiting with 0 after 345, 483 and 737 s of the guest's time; the layer-2 scenarios of `test`
  (`libc`, `libc-test`, `cxx`, `spawn`, `process`, `sysroot`, on one and two processors) and `runtime-devices` pass on
  the three ISAs; `libc` and `sysroot` pass on the Windows host; CI's `linux-host` legs run the rest.
