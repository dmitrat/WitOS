# E4.2 — The file manager

Plan step E4.2 (phase E, goal Ц6). The developer scenario ends in a file manager. In it, a program written on Windows is
copied in from a drive or a share, a folder is made for it, and the program is run, interactive as it was written.

The author's decisions:
- 2026-10-28: the file manager is Arlecchino.Commander, forked where it needs changes.
- 2026-10-29: the fork follows upstream for as long as upstream is maintained, since upstream is developed actively.

Step E4.1 gave WitOS pseudo-terminals. This step gives Commander the dialect that uses them, carries the fork onto
upstream's latest release, and gates the scenario on the screen.

## 1. The fork

`github.com/dmitrat/Arlecchino.Commander`, branch `witos`, holds upstream's release v2026.10.2 (`4e78a09`) and one commit
of WitOS's (`e71fd63`, "Run commands on a terminal of their own on WitOS").

Commander makes a command's terminal through `Ttys`: one dialect per system, picked once by the operating system. Linux,
macOS and Windows each have one; any other system gets `ForeignTtys`, which makes none, so its commands run on pipes.
.NET names WitOS apart from Linux (`WITOS`), so Commander ran on pipes there.

The commit adds `WitOsTtys`, a `PosixTtys` with Linux's numbers:
- `O_NOCTTY` 0x100;
- `POSIX_SPAWN_SETSID` 0x80;
- `TIOCGWINSZ` 0x5413 and `TIOCSWINSZ` 0x5414;
- `c_lflag` at offset 12.

These are what WitOS's libc answers on every ISA, since it is musl answering Linux's calls. The dialect is picked where
`OperatingSystem.IsOSPlatform("WITOS")`. The name is passed through a field rather than a literal, because the analyzers
(CA1418) know only the systems .NET ships for, and the build treats their warnings as errors. Commander's POSIX terminal
then works unchanged:
- `posix_openpt`, `grantpt`, `unlockpt` and `ptsname`;
- `posix_spawn` of `SHELL -c` with `addopen` of the slave and `adddup2`. `POSIX_SPAWN_SETSID` is refused, and Commander
  starts the child without it, as its code already does;
- the master's size and its echo turned off;
- `Passing.Between` for a program that claims the screen, which puts the real terminal in raw mode and carries bytes both
  ways under `poll`;
- `waitpid`.

Upstream's library is a submodule with a relative URL (`../Arlecchino.git`). A build from the fork therefore takes the
library from the author's fork `github.com/dmitrat/Arlecchino`. That fork was fast-forwarded to upstream (`gh repo
sync`), so that the library commit v2026.10.2 names (`52f72f0`) is reachable from its own branch, not only through
GitHub's shared objects.

`build/apps/Arlecchino.Commander.json` pins `e71fd63` as version 2026.10.29, the commit's date, from the fork's URL.

**Following upstream.** On each upstream release:
1. Carry the `witos` branch onto the release tag and push it to the fork.
2. Fast-forward the library's fork if the submodule moved.
3. Move the catalog's commit and version.
4. Run `runtime-commander`, `runtime-installer` and `runtime-file-manager` again.

Offering the dialect upstream is the author's decision; it would let the fork go.

## 2. What WitOS needed besides

- **Pseudo-terminals** (E4.1). These are `/dev/ptmx` and `/dev/pts/<n>` over the terminal service, a child started on the
  slave side, and its children inheriting the slave.
- **The shell's environment.** Commander runs every command through `SHELL`, which is PowerShell's launcher (C4.1). When
  started by another program, pwsh died in its login-shell check: `EntryPointNotFoundException` for `sysctl`. Every Unix
  that is not Linux takes the macOS path there (C1.1). Until now only the PowerShell scenarios' packages added the
  variable that skips the check, `__PWSH_LOGIN_CHECKED=1`. It now stands in the install's `/etc/environment` beside
  `SHELL`, for every program that starts the shell, and `RuntimePowerShell.PackageAsync` no longer adds its own.
- **The volumes** (E1). Commander's drive picker (Ctrl-F1, Ctrl-F2) lists `DriveInfo.GetDrives()`, which reads
  `/etc/mtab`, and the libc makes that file from the catalog. It shows `/`, `/boot`, `/fat`, `/data` and `/media/STICK`
  with their formats, sizes and free space. Since 2026.10.2 the picker narrows its list as a name is typed.
- **The terminal's poll** (E4.1's second commit). Arlecchino asks `Console.KeyAvailable` every 8 ms. Each answer was a
  round trip with the terminal service, and under TCG that took most of an idle Commander's processor time. Now the libc
  answers from the service's events.

## 3. The gate

`runtime-file-manager` (`RuntimeFileManager`, after `runtime-commander` in `runtime-witos`) boots the package with:
- the data volume's layer;
- the display;
- a USB keyboard and a USB drive on one QEMU `qemu-xhci` controller, the same on every ISA;
- 1 GiB.

The drive is a 64 MiB MBR disk with a FAT32 volume `STICK`. It holds `interactive/`, the publish of
`tests/Runtime.Witos/Interactive`: an ordinary console program published by the stock SDK without a RID. The program
asks for a name, then takes the alternate screen and holds it until a key, then gives it back and names the runtime
identifier.

Commander starts in `/data`. The runner types through QMP, each step once its line appeared:
1. Ctrl-F1 opens the drive picker for the left panel; "STICK" and Enter pick the drive.
2. End selects `interactive`; F5 copies it, and Enter confirms once the dialog says "a folder". The right panel is
   `/data`.
3. Tab moves to the right panel; F7 opens the new-folder dialog, where `made-here` and Enter make the folder.
4. `:dotnet /data/interactive/Interactive.dll` and Enter run the program on Commander's command line.
5. `WitOS` and Enter answer its question. By then Commander has handed the program the terminal, since .NET's console
   claims it with the keypad mode.
6. A screendump is taken while the program holds the screen; then `k` is typed.
7. F10 is pressed once Commander says the command is done ("Ctrl+O reads what it said"). A key sent before that goes to
   the program's terminal and is lost, as it would be on Linux.

The judge requires:
- the screendump equal to the frame the host renders from the mirror's transcript, with the program's screen in it;
- the copy of `Interactive.dll` on the clean ext4 volume equal to the publish;
- the program's lines, among them `[INTERACTIVE] Hello, WitOS!` and `[INTERACTIVE] the screen went back after 'k' on
  witos-<arch>`;
- Commander's exit with 0 through its launcher.

## 4. What ran

All runs were in the Linux container on 2026-10-29, on the fork's commit `e71fd63`:

| Scenario | x64 | ARM64 | riscv64 |
|---|---|---|---|
| `runtime-file-manager` | PASS, 126 s; transcript 33,834 bytes | PASS, 143 s; 34,562 bytes | PASS, 218 s; 32,347 bytes |
| `runtime-commander` | PASS, 76 s | PASS, 81 s | PASS, 80 s |
| `runtime-installer` | PASS, 721 s | PASS, 852 s | PASS, 158 s (the layer stays IL) |
| `runtime-powershell` | PASS, 135 s | PASS, 198 s | PASS, 487 s |
| `runtime-display` | PASS, 93 s | PASS, 110 s | PASS, 145 s |

The PowerShell, display, commander and installer scenarios ran again for two reasons: the shell's environment changed in
every package, and Commander's pin moved. `runtime-installer`'s x64 run is the one E4.1's poll was measured with.

The first trials found three things:
- **pwsh's login check.** In the first run of the program, Commander's output said
  `Unhandled exception. System.EntryPointNotFoundException … ManagedPSEntry.SysCtl`; the cause was pwsh's login check (§2).
- **The picker narrows by typing.** End and Enter picked `/` instead of the drive.
- **An early F10.** F10 sent at the program's last line went to its terminal, so Commander stayed. Waiting at the keys,
  it was ended by its tick budget after 4,680 s, which E4.1's poll change addresses.

## 5. Limits kept explicit

- **Free space in the panels.** The panels' status says "0 B free" on every volume. Commander asks `DriveInfo` of the
  path's root, `Path.GetPathRoot`, which is `/` on Unix and is the read-only package here. The drive picker shows each
  volume's own free space.
- **Stop (Esc).** It asks `kill` of the command's process group, then of the child, with `SIGTERM`. WitOS refuses both,
  since it has no process groups and sends other processes no signal but `SIGKILL` (N4.2). Ctrl-C typed while a program
  holds the screen reaches it through the slave's discipline.
- **No trash and no change notifications.** Folders are polled, as Commander's code does on a system it gives neither,
  since there is no inotify (C4.2).
- **The idle Commander under TCG.** It still asks for keys every 8 ms, which costs more than on hardware.
