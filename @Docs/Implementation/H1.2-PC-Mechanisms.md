# H1.2 — The PC's mechanisms of ABI-1 (ADR 0029)

Plan step H1.2 (phase H) implements [ADR 0029](ADR-0029-PC-Interrupts-Power-and-Device-Table.md) in two slices, each
raising ABI-1's minor version as it lands:

- **H1.2a** (§1, 2026-10-23): the device table of up to 64 descriptors without bridges, and the machine's end by the
  root task's exit status. ABI-1 1.5.
- **H1.2b** (§2, 2026-10-23): the binding of MSI and MSI-X messages to events, and the virtio drivers on MSI-X. ABI-1 1.6.

## 1. H1.2a: the device table and the machine's end

### The device table

| What | Before | Now |
| --- | --- | --- |
| Capacity | 16 descriptors (`WIT_DEVICE_CAPACITY`) | 64 |
| Where | one page the platform wrote | the kernel's own array; the kernel validates it and copies the header and `Count` descriptors into as many pages as they take, one for up to 17, four for 64 |
| The object | one page | those pages, one memory object of kind `TABLE`; a window beyond it is `TOO_LARGE` |
| Bridges | described like any function (VMware's 33 of 46) | described by no board: the walk still enters a bridge's bus, and a function whose header type is not 0 is skipped |
| Readers | mapped one page | map the first page, read `Count`, map the size it gives: `OutWit.OS.Hardware.DeviceTable.Read` (and `TableBytes`), the fixtures' `fixture_find_device` |

The kernel line now names the pages (`Devices: 8 in 1 page`), and the PC's names the walk
(`PCI: 7 functions, 7 described without bridges, ECAM 0x…`). The release root task (`tests/User/root.c`) maps the
whole table, requires its count again, and is refused a page beyond it.

### The machine's end

The root task already stops what it runs and ends, and the kernel already acted on its status; ADR 0029 adds no call.

| Status | The kernel | The PC | ARM64 `virt` | riscv64 `virt` |
| --- | --- | --- | --- | --- |
| 0 | `[TEST-PASS] Boot.RootTask`, then `wit_platform_finish(0x10)` | QEMU's exit port; without its device, ACPI's soft-off | semihosting's exit; then PSCI `SYSTEM_OFF` | the test finisher; then SBI's system reset, shutdown |
| `WIT_ROOT_EXIT_RESET` (0x52534554) | `[POWER] the root task asked for a reset`, then `wit_platform_reset()` | the FADT's RESET_REG, then the 8042's pulse where the FADT names an 8042 | PSCI `SYSTEM_RESET` | SBI's system reset, cold reboot |
| any other, or a fault | a panic: its line, then the test exit or a halt | halt | halt | halt |

The constant lies outside every status a program's exit yields (0–255, and `WIT_EXIT_SIGNAL`'s 0x10000 with the signal).
A reset the board cannot give returns, and the kernel panics with `The board cannot reset`.

**The PC without AML** (`src/Kernel.Platform.Pc/power.c`). At boot the platform reads the FADT (the PM1a and PM1b
control blocks, the 64-bit forms first, SMI_CMD and ACPI_ENABLE, IAPC_BOOT_ARCH's 8042 bit, the flags' RESET_REG_SUP
and HW_REDUCED_ACPI, the reset register and its value) and the DSDT it names (verified by length and checksum, up to
512 KiB), and finds `Name (_S5, Package (n) {a, b, …})` by its bytes: NameOp, the name, PackageOp, the length's
encoding, the count, then two integers of ZeroOp, OneOp or a byte, word or double word constant. It logs what it found:

```
ACPI power: PM1a_CNT I/O 0x0000000000000604, _S5 SLP_TYP 0/0, RESET_REG I/O 0x0000000000000CF9 value 15, an 8042
```

At the end a success writes SLP_TYPa (and SLP_TYPb to PM1b) and then SLP_EN, after the SMI command's ACPI_ENABLE when
the firmware left SCI_EN clear; a hardware-reduced FADT, a missing PM1a block or DSDT, or an `_S5` that is not a static
package gives no soft-off and the line `[POWER] no ACPI soft-off (…); halted`. A register in system memory is mapped at
boot; one in PCI configuration space is not served.

Measured on the boards:

| Board | What the platform reads |
| --- | --- |
| QEMU q35 (ICH9) | PM1a_CNT I/O 0x604, `_S5` 0/0, RESET_REG I/O 0xCF9 value 15, an 8042 |
| QEMU pc (PIIX3) | PM1a_CNT I/O 0xB004, `_S5` 0/0, no reset register and no 8042 bit: its FADT is of revision 1, which has neither field, so the PC platform cannot reset QEMU's pc machine |
| VMware (PIIX4, H0.1) | PM1a_CNT I/O 0x444, `_S5` a static `Package {0, 0}`, RESET_REG I/O 0xCF9 value 6, an 8042 |

### The gates

- **`release-pc-off-256`** (`release` on x64): QEMU's pc machine without the test exit device; the board turns itself
  off through PM1a_CNT and QEMU leaves with 0. The runner's `ExpectedOutcome.PoweredOff` requires the release suite's
  markers, `[POWER] off through ` and the scenario's lines (`ACPI power: PM1a_CNT I/O `, `[POWER] off through PM1a_CNT`);
  `BootRequest.WithoutTestExit` leaves the board's exit device out.
- **`reset`** (`test` of each ISA): the release kernel with the root task built with `WITOS_ROOT_EXIT_RESET`
  (`KernelImageBuilder.RESET_SCENARIO`); QEMU, started with `-no-reboot`, leaves with 0 on the guest's reset.
  `ExpectedOutcome.Reset` requires the markers through `Boot.RootTask`, `[POWER] the root task asked for a reset` and
  `[POWER] reset through `: RESET_REG on q35, PSCI on ARM64, SBI on riscv64.
- The ARM64 and riscv64 power off after the test exit is not judged: QEMU's runner always gives those boards their test
  exit, which ends QEMU first.

## 2. H1.2b: message interrupts

### The call

`INTERRUPT_BIND_MESSAGE` (86, `witos/message_interrupt.h`) takes `WitMessageBindRequest` (48 bytes: the version and
size, the device with `BIND`, the event with `SIGNAL`, flags and a reserved word that are zero, and the `Address` and
`Data` the kernel writes) and returns an interrupt handle with `QUERY`, `DUPLICATE` and `TRANSFER`. The request is
checked whole — its version (`UNSUPPORTED`), size, flags and reserved words (`INVALID_ARGUMENT`), the rights (`DENIED`),
the board's support (`UNSUPPORTED`) and the request's writability (`BAD_ADDRESS`) — before the board allocates a target;
a full table or board is `NO_MEMORY`. The binding shares the kernel's table with the lines (`WIT_INTERRUPT_CAPACITY`,
16 since H1.2b), names its target by a token from `WIT_PLATFORM_MESSAGE_BASE` (0x100) so that no line collides, sets
its event on each message, masks nothing, takes `INTERRUPT_ACK` as a success that does nothing, and frees the target
with its last handle. `QUERY` and the root task's startup descriptor report `WIT_ABI_FEATURE_MESSAGE_INTERRUPTS` (32)
where the board serves the call (`wit_user_abi_features`); the families every board has stay `WIT_ABI_FEATURES`.

The platform interface (`witos/platform.h`) gains `wit_platform_messages_supported`, `wit_platform_message_allocate`
(the address, the data and the token) and `wit_platform_message_free`. A board delivers a message as
`wit_user_interrupt` of its token, as it delivers a line.

### The PC

| What | How |
| --- | --- |
| Targets | the 32 vectors 0x30–0x4F of the boot processor's local APIC (`witos/x64_lapic.h`), a bitmap in `Kernel.Platform.Pc/interrupts.c` |
| Address and data | 0xFEE00000 with the APIC id in bits 19:12; the vector, fixed delivery, edge |
| The APIC | prepared with the board's devices (`wit_x64_lapic_boot_prepare`) whatever the number of processors; the timer's start no longer turns it off with one processor, and the PIC's line enters through LINT0 as ExtINT, as it did with secondary processors |
| Entry | the vectors 0x30–0x4F enter as device vectors (`entry.S`); `wit_x64_device_interrupt` ends one at the APIC and delivers the token `WIT_PLATFORM_MESSAGE_BASE` plus the vector |

The virt boards of ARM64 and riscv64 serve no message (`wit_platform_messages_supported` is zero): the call is
`UNSUPPORTED` there, and their drivers keep the INTx line. The Pi 5's platform will serve it through the BCM2712's MIP
(H9); `virt`'s GICv3 ITS and riscv64's IMSIC wait for a step that needs them.

### The drivers

`OutWit.OS` gives the drivers what they write into their functions: `PciConfiguration` (a capability by identifier, the
region of a BAR by the base the firmware assigned), `MsiX` (the capability, its table mapped through the BAR's region,
an entry programmed and unmasked, the function's enable and its mask cleared), `InterruptBinding.BindMessage` and
`InterruptBinding.MessagesSupported` over libwitos's `witos_interrupt_bind_message` and `witos_message_interrupts`.

`VirtioInterrupt` (`OutWit.OS.Hardware.Virtio`) is each virtio driver's interrupt: before the device's reset it binds a
message and programs MSI-X entry 0 where the kernel serves messages and the function has MSI-X, and the transport then
gives every queue it sets up that entry (`queue_msix_vector`, read back; the configuration change keeps `NO_VECTOR`);
otherwise, once the device is set up, it binds the INTx line as the drivers did. Reading its status is the ISR's read
for INTx and a queue for a message; its acknowledgement unmasks the line, or does nothing. The four drivers (block,
console, input, network) log what they interrupt through.

### Measured

| Where | What |
| --- | --- |
| `runtime-devices` on x64 (q35, five boots) | `[VIRTIO-BLOCK] … interrupts through MSI-X entry 0, message 30 at fee00000` and `… message 31` for the two disks, `[VIRTIO-NET] … message 32`; every boot passes as before, the scenario requiring the MSI-X lines |
| the interrupt fixture on x64 | the refusals, two targets with their address and data written and different messages, the acknowledgement that does nothing, the bindings' ends |
| the interrupt fixture on ARM64 and riscv64 | `UNSUPPORTED`, the feature bit clear |
| `runtime-devices` on ARM64 and riscv64 | the drivers keep `its INTx line` (CI) |

### What is not yet

- The runner still refuses a keyboard beside a network adapter (W1.1); on x64 both now interrupt by messages, so the
  refusal can leave there when a scenario needs both.
- VMware's AHCI, NVMe, e1000e and xHCI take their messages with their drivers (H2–H4).
