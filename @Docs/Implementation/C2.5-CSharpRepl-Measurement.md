# C2.5 — CSharpRepl on WitOS: the measurement

Plan step C2.5 (phase C, ADR 0027), its first measurement on 2026-10-18; the step is not closed. CSharpRepl 0.9.2 was
laid in the data volume's layer unchanged and started by its launcher on x64; it ran up to its first evaluation, which
needs the .NET SDK.

## 1. What the layer gained

- **The `tool` kind** (`AppToolPackage`): a .NET tool package of nuget.org, downloaded once and verified by its SHA-256,
  whose `tools/<framework>/any` directory is the application; its `DotnetToolSettings.xml` must name each command of
  the catalog with the same entry point, run by dotnet. A tool published per RID since .NET 10 — CSharpRepl's package is
  a pointer to `CSharpRepl.any`, `CSharpRepl.win-x64` and the others — names its portable package `<id>.any` in the
  catalog.
- **Packages for the global packages folder** (the catalog's `packages`): NuGet packages laid in
  `/data/home/.nuget/packages/<id>/<version>/` as a restore leaves them. CSharpRepl compiles against the reference pack,
  which it looks for under the install's `packs` and then there: `Microsoft.NETCore.App.Ref` 10.0.12, the runtime's
  version, pinned by its SHA-256.
- **`build/apps/CSharpRepl.json`** and the scenario `runtime-csharprepl`: `/data/apps/bin/csharprepl` on the terminal
  with `NO_COLOR`, a session typed at each `> `.

## 2. What ran

`runtime-csharprepl` on x64 in the Linux host's image: the REPL started from the layer through its launcher, printed its
banner (`Welcome to the C# REPL (Read Eval Print Loop)!`) and its prompt, and echoed the first input under PrettyPrompt;
the reference pack was found (a missing one fails earlier with "Could not determine the .NET SDK to use"). The first
evaluation failed:

```text
> "witos-" + (6 * 7)One or more errors occurred. (Could not load file or assembly 'NuGet.Versioning,
Version=7.6.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35'. The system cannot find the file specified.)
```

## 3. Why: CSharpRepl borrows NuGet from the SDK

CSharpRepl's services reference the NuGet client libraries with `PrivateAssets="all"` "so we load the nuget dlls that
are bundled from the host runtime instead" (`CSharpRepl.Services.csproj`): none of them is in the package or its
`deps.json`. At run time `MSBuildLocator.RegisterDefaults()` finds an installed SDK (through `DOTNET_ROOT`, the process's
`dotnet` or `PATH`, hostfxr's `hostfxr_get_available_sdks`, an `sdk/<version>/` with `dotnet.dll`, `Microsoft.Build.dll`
and `.version`) and resolves missing assemblies from its directory; without one, the failure is only logged. The script
runner is built in the background at start and always creates the NuGet package resolver, whose first fields are NuGet
types, so every evaluation awaits a faulted initialization. No option avoids it.

So CSharpRepl, unchanged, needs the .NET SDK beside the runtime, as its own documentation says. WitOS ships the runtime
alone. A directory that only looks like an SDK (an empty `dotnet.dll` and `Microsoft.Build.dll` beside NuGet's
assemblies) would satisfy both checks, which test that files exist, and is exactly the pretence WitOS refuses; changing
the tool's `deps.json` would change the application.

## 4. What it leaves to decide

- **The .NET SDK as a base application**: the SDK's managed part (`sdk/<version>/`: MSBuild, Roslyn, NuGet, the CLI)
  and its packs on the data volume beside the install's hosts, which would make `dotnet build` and `dotnet run` work in
  a session and CSharpRepl with them, unchanged — a larger step of its own (processes, pipes and files are there since
  N4.2; the measurements are MSBuild's node processes, restore from a folder feed without the network, and the time
  under TCG and under `shell --accel`).
- **Another REPL** that carries its own NuGet client, if one exists.

Until then C2.5 stays open with this measurement.
