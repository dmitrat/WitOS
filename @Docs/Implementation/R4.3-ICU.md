# R4.3 — ICU from source

R4.3 gives the system layer culture data. RFC 0015 §8 started .NET on WitOS in invariant mode, with ICU absent, and
named the condition for ICU: "ICU from source when a scenario needs culture data". N2.2, the libraries' own test
suites, is that scenario: xUnit's and NUnit's tests run in `en-US` and `fr-FR`, and invariant mode refuses to create
any culture but the invariant one (`CultureNotFoundException`).

## The libraries (`tools/WitOS.Dev/Substrate/Icu.cs`)

**The source.** ICU4C 78.3, the source tarball R1.2b pinned for the headers (`src/Substrate/icu.lock.json`). `setup`
now extracts more of it: the sources of `common/` and `i18n/`, the release's prebuilt little-endian data
(`data/in/icudt78l.dat`, 33 MB) and the license. Both ISAs are little-endian, so the one file serves both.

**The build.** WitOS.Dev builds the libraries after ICU's own Makefile rules for Linux, never by its build system, as
it builds musl:

- The rules are what `runConfigureICU Linux` writes into `icudefs.mk` and `config/mh-linux`:
  - the definitions `-D_REENTRANT -DU_HAVE_ELF_H=1 -DU_ALL_IMPLEMENTATION -DU_ATTRIBUTE_DEPRECATED=`;
  - `-O3`, `-std=c++17` and ICU's warnings;
  - `-DPIC -fPIC`;
  - each library's own definition: `U_COMMON_IMPLEMENTATION`, or `U_I18N_IMPLEMENTATION`.
- Every source the library's `sources.txt` lists is compiled unchanged by the pinned clang against the sysroot, with
  `Sysroot.DriverOptions`: 202 for `libicuuc`, 254 for `libicui18n`.
- Each library is linked as ICU links it: `-shared -Wl,-Bsymbolic` with its soname, `libicuuc` on `libicudata`,
  `libicui18n` on both, each with `-lpthread -lm`, and on libc++ through the driver.
- `libicudata.so.78` carries the data under ICU's entry point, `icudt78_dat`. ICU's `pkgdata` links it from the
  assembly `genccode` writes for gcc; WitOS.Dev writes the same header and section, `.incbin`s the data file in place of
  `.long` lines, and links it without the default libraries, as `LDFLAGSICUDT` says.

The build lives under `artifacts/icu/<arch>` and is kept while the pin, the options, the source lists and the
sysroot's libraries it links against are unchanged.

**The install.** The R5 .NET install (`RuntimeWitos.InstallFilesAsync`) carries the three libraries in `/usr/lib`, as
a Linux distribution installs them. That is musl's default library path, so `System.Globalization.Native` finds them
the way it does on Linux: `dlopen("libicuuc.so.78")`, for the major version of the headers it was compiled against,
then symbols with ICU's `_78` suffix. `libicudata` maps its 33 MB from the boot package without a copy (R3.1).

## Culture by default

The root task no longer puts `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` into the environment of the processes it starts
(R6 put it there). An application without a setting of its own gets culture data, as on Linux. Programs that run where
the install is absent keep invariant mode by their own configuration:

- **NativeAOT programs**, the services among them: `InvariantGlobalization` is a property of the generated project.
- **`corerun`'s scenarios** (R3.2a, R3.3, R7.2b): `System.Globalization.Invariant=true` on its command line.
- **R5's `App.dll`**: its runtimeconfig.

## The check: N1's Globalization area

The compatibility suite (N1) gains a twelfth area, Globalization, of eight checks:

- the specific cultures;
- `de-DE`'s number format;
- `de-DE`'s and `fr-FR`'s month and day names, and `ja-JP`'s;
- culture-aware comparison in `en-US` and `de-DE`, against ordinal;
- Turkish casing of `i` and `I`;
- normalization to form C;
- IDN;
- France's currency.

Each holds where ICU's releases agree, so the same checks pass on Windows, whose .NET uses Windows' ICU, on Linux's
system ICU and on WitOS's ICU 78.3.

## Defects found on the way

- **ICU's calls stayed unbound on ARM64.** On ARM64 the guest faulted at the first number format, in an instruction
  fetch at `0x374b00`, which `x17` held too: the start of `libicui18n`'s `.plt` before relocation.
  - The cause: `Sysroot.DriverOptions` compiles with `--rtlib=compiler-rt`, and clang then calls aarch64's outline
    atomics (`__aarch64_ldadd4_acq_rel` and its kin) for every atomic operation, expecting compiler-rt's builtins to
    define them. The sysroot's builtins did not, since nothing built with the driver had used an atomic before:
    CoreCLR and the C++ runtime are compiled without `--rtlib=compiler-rt` and call none.
  - Why it got that far: the globalization shim opens ICU with `RTLD_LAZY`, and musl's dynamic linker then defers a
    relocation whose symbol it cannot find instead of failing, so the GOT entry kept its link-time value.
  - The fix, in the substrate: the pinned compiler-rt files gain `aarch64/lse.S`, which WitOS.Dev assembles into its
    125 helpers as compiler-rt's CMake assembles its copies (`L_<operation>`, `SIZE`, `MODEL`, `HAS_ASM_LSE`), and
    `cpu_model/aarch64.c`, whose `__aarch64_have_lse_atomics` the helpers read. WitOS's `AT_HWCAP` is 0, so they take
    the load- and store-exclusive loops. An archive member joins an image only when the image calls it, so nothing
    built before changes.
  - The guard: ICU's libraries link with `--no-undefined` (beyond ICU's own options), so a symbol nothing defines fails
    the build instead of the guest.
- **A refused resume said too little.** The libc's message for a context the kernel refuses to resume now names the
  status and the program counter. It took one run to read `BAD_ADDRESS` and the PLT's address there.

## Limits kept explicit

- **The data is ICU's full release data,** 33 MB of every boot package that carries .NET. ICU's data filter would
  make it smaller, but it builds the data from its sources with ICU's tools, which WitOS.Dev does not build.
- **There is no tzdata.** `TimeZoneInfo` reads `/usr/share/zoneinfo`, which is absent, so `TimeZoneInfo.Local` stays
  UTC (Compatibility-Differences: Time). ICU's own time zone data serves its formatting only.
- **No ICU plugins** (`UCONFIG_ENABLE_PLUGINS` stays 0, as in ICU's release builds), and no `libicuio` or
  `libicutu`: the shim loads `libicuuc` and `libicui18n` alone.
