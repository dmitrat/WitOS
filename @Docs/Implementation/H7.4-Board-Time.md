# H7.4 — The board's time without a real-time clock

A Raspberry Pi has no real-time clock. The kernel never invents a time, so on such a board UTC is `UNSUPPORTED` until
the holder of the clock capability sets it (K6). Without UTC, the libc's `CLOCK_REALTIME` is `ENOSYS`, .NET's
`DateTime.UtcNow` is 1970, a file's time is 1970, and TLS cannot judge a certificate. On `raspi4b` the libc program
passed 174 of 175 checks; the failure was "real-time clock after 2026" (H7.2 §5).

The author decided on 2026-10-26: **the saved time and SNTP**, as Raspberry Pi OS's `fake-hwclock` does.
- The system saves the time on `/data` and sets it again at boot when the board has no clock.
- SNTP corrects it when there is a network.
- The alternatives were refused. SNTP alone leaves no time at all without a network. The epoch 1970, as Linux has it,
  gives wrong file dates and fails TLS until the first synchronization.

This step is that mechanism, judged on a board the gates see.

## 1. The time service

The service holds the clock capability and does five things.

- **At its start, on a board without a real-time clock.**
  - It sets UTC to the time saved in `/data/system/time`: an old time, but one the system lived, where 1970 is none.
  - The file is one ISO 8601 line to the tenth of a microsecond (`2026-11-04T12:34:56.7890123Z`). It is written to
    `time.next` beside it, flushed and renamed over it, so a cut leaves the old time or the new one whole.
  - A board without a clock, a saved time and a server keeps no time, and the service says so.
- **Where the package names time servers.**
  - The servers are listed in `/etc/witos/time-servers`: one `host` or `host:port` a line, an IPv6 address in brackets
    with a port.
  - The service asks them over SNTP in their order, and the first answer sets UTC.
  - It asks again every hour.
- **When it answers ready.** The answer comes once UTC holds the best time the system has. The root task starts
  `/bin/init` only after that answer, so a program never meets a board without UTC that the system could have given one.
- **What it saves, on a board without a clock.**
  - The time after an answer, every hour, and when it stops.
  - It stops before the device manager stops the namespace service, so `/data` is still there.
- **On a board with a clock.** It saves nothing: the kernel has no way to write the board's clock, and the clock is the
  better source at the next boot.

The service is .NET over the libc, like every application: `/data` through System.IO, the servers through
System.Net.Sockets and musl's resolver. Its nonce comes from `/dev/urandom`, which the libc serves from the kernel's
`RANDOM`. .NET's `RandomNumberGenerator` is OpenSSL's on Unix, and the boot package of the services carries no OpenSSL;
the first trial's service ended with "No usable version of libssl was found".

## 2. The root task and the process manager

- **The capability.** The root task keeps the clock capability, its fourth initial handle, unless the system keeps time.
  The system keeps time where the board has no real-time clock (`CLOCK_READ` of UTC is `UNSUPPORTED`), or where the
  package holds `/etc/witos/time-servers`.
- **The start.** In that case the root task prepares the time service as a second service after the device manager. It
  sends the start with the capability on the service's channel, as it sends the device table to the device manager, and
  keeps no other copy of the capability.
- **The order.** `witos_manager_run_services` starts the services in turn, each after the previous one answered.
- **The endpoints.** A service now gets the namespace's and the network service's clients' endpoints, as the first
  process does, once an earlier service offered them. The time service gets the device manager's. It never gets the
  terminal's, so its lines stay in the kernel log.
- **The stop.** `witos_manager_stop_services` stops the services the last first, so the time service saves the time
  before the device manager unmounts `/data`.
- **Existing scenarios.** Their boards have a real-time clock and their packages name no server, so they start no time
  service. Their process ids, memory and lines are unchanged.

## 3. SNTP

`OutWit.OS.Networking.Sntp` is RFC 4330's client over NTP version 4's 48-byte header.

- **The request.** Version 4, mode 3, and a random transmit timestamp, as RFC 9109's data minimization asks. A board
  without a clock has no time to send.
- **The reply must pass these checks:**
  - mode 4 and version 3 or 4;
  - no alarm in the leap indicator;
  - a stratum from 1 to 15 (stratum 0 is a kiss-o'-death, whose code is reported);
  - the origin timestamp equal to the request's;
  - receive and transmit timestamps, the transmit not before the receive.
- **The time at the answer's arrival.** It is the server's transmit time plus half the network's share of the round
  trip: the client's own measure, on the monotonic clock, less the time the server held the request.
- **Eras.** A timestamp before 2020 is read in era 1, so the client stays right past February 2036.

An exchange sends up to twelve requests and waits 5 s of the guest's time for each. An answer to any request of the
exchange counts, measured from that request's moment. This matters under QEMU's instruction clock: an idle guest's
time runs ahead of the host's, a try can pass in the guest before the host's answer arrives, and the device manager's
DNS probe needs the same allowance (W1.2b). On real hardware the first answer comes to the request it answers.

## 4. PCI BARs that nothing assigned

The gate's board is virt booted by the Linux protocol (§5). There no firmware enumerates the bus, and every memory BAR
reads zero; under UEFI, EDK II assigns them.

- **What the platform does.** It reads the generic ECAM bridge's `ranges` and takes its first 32-bit memory window. A
  memory BAR that reads zero takes the next address of that window aligned to its size, written while the function's
  decoding is off, as Linux's PCI core assigns what is unassigned.
- **I/O BARs** stay unassigned: no ARM64 board reaches ports (H5.2).
- **A 64-bit BAR** also takes the 32-bit window, with its upper half zero. The kernel's early map covers the low
  gigabytes alone.
- **The drivers** still turn on decoding and bus mastering themselves (`VirtioPciTransport`).
- **The log.** The kernel prints one line, `[DEVICES] PCI: N memory BARs nothing had assigned took addresses of the
  bridge's window at 0x...`.
- **Unchanged boots.** Under UEFI nothing reads zero, and nothing changes.

The Pi 4's VL805 and the Pi 5's RP1 sit behind Broadcom's PCIe root complexes, which are not the generic ECAM bridge.
Their resource assignment comes with H8 and H9.

The second finding of the Linux path was the INTx line. Without a boot disk, QEMU puts the entropy source at slot 1, not
slot 2, so the adapter at slot 6 shared the data disk's line. The kernel binds a line once, so the network driver failed
with `EBUSY`. `KernelArchitecture.EntropyLineSlot` now takes the boot disk into account: slot 5 on a board booted by the
Linux protocol.

## 5. The gate

`runtime-time` (`RuntimeTime`, after `runtime-smb` in `runtime-witos`) boots twice with one data disk. Its package holds
the device services, the time service, `/etc/witos/time-servers` naming the runner's server, and
`tests/User/time_check.c` as `/bin/init`. It carries no .NET install, so the Linux path's initial ramdisk stays at 33 MB.

- **The runner's time server** (`Host.TimePeer`) is an SNTP server on a free UDP port of the host's loopback.
  - The guest reaches it at `10.0.2.2` and the same port, since QEMU's user networking sends a datagram to its host alias
    to the host's loopback.
  - It answers as a server of stratum 1, with RFC 5905's layout written in the tool apart from the guest's client.
  - Its time is the host's plus three days, so the guest's clock shows whether the answer set it.
- **The ARM64 board** is virt booted by the Linux protocol with QEMU's own tree for that machine less its PL031
  (`BootRequest.WithoutRealTimeClock`).
  - QEMU dumps the tree of the same machine, processors, memory, image and ramdisk with `dumpdtb`.
  - `DeviceTreeBlob.WithoutCompatible` takes out the node compatible with `arm,pl031`, and the runner writes a fresh
    entropy seed.
  - The kernel then prints `UTC: no real-time clock`.
- **x64's and riscv64's boards** keep their real-time clocks: q35's CMOS clock and the goldfish clock.
- **`/bin/init`** prints UTC (`[TIME-CHECK] UTC <seconds>.<nanoseconds>`) and checks:
  - that `time()` and `gettimeofday()` agree with `CLOCK_REALTIME`;
  - that a second slept on the monotonic clock is a second of UTC;
  - that a file it writes on `/data` carries the clock's time within a minute. The namespace service stamps it with its
    own reading of the same kernel clock.

| Boot | Board without a clock (ARM64) | Board with a clock (x64, riscv64) |
| --- | --- | --- |
| 1, with the adapter | No saved time; SNTP sets UTC to the server's; saved after the answer and at the stop | The board's clock, then SNTP sets UTC to the server's; nothing saved |
| 2, without the adapter | UTC set to the time boot 1 saved last; the server is unreachable | The board's clock again; nothing saved |

The host judges boot 1's printed UTC within the server's time over the boot, 5 s behind to 10 minutes ahead. The guest's
time runs ahead while it idles, never far behind. On ARM64 the host requires three things:
- boot 2 set UTC to exactly the last time boot 1 saved;
- that time is not before boot 1's printed UTC;
- boot 2's printed UTC goes on from it.

On x64 and riscv64 the host requires boot 2's UTC within the host's time over that boot. This shows that SNTP's three
days lasted no longer than the boot, and that the board's clock rules.

## 7. What is not yet

- **The Pi itself.** The libc program on `raspi4b` waits for H8, which brings it `/data` (the SD card) or the network.
  Until then nothing on `raspi4b` sets its time.
- **A slewed clock.** SNTP steps the clock, as `fake-hwclock` and `ntpdate` do. A slewing discipline (`adjtime`, a
  frequency correction) would need a mechanism of the kernel's and a consumer that needs it.
- **The hour.** The hourly save is fake-hwclock's cron job. On an SD card it is a journal transaction an hour (H8
  measures what writes cost the card).
- **Default servers.** No package names a public server yet. The SD card's image (`image --rpi4`, H8) is the first that
  should, and a session's machine may follow.
- **Board clocks that the kernel could write** (the PC's CMOS clock, the PL031) keep the board's time as the kernel read
  it at boot. A correction by SNTP lasts until the next boot.
