# R4.2 — Shared mappings of a volume's file

R4.2 closes phase R. A shared `mmap` of a file of a mounted volume now behaves as on Linux:

- every shared mapping of the file shows the same pages, in every process;
- a write through a mapping reaches a `read` of the file, and a `write` of the file reaches the mapping;
- the namespace service writes the pages back to the file at `msync` and when the last handle that mapped it closes.

Until now, a shared mapping that was not writable was a copy taken when it was made (D5.3), and a writable one was
`ENODEV`.

## The protocol (`witos/namespace.h`)

- **`WIT_NAMESPACE_MAP`** (16) takes a handle of an open file, an offset that is a multiple of
  `WIT_NAMESPACE_CHUNK_BYTES` (64 pages), and `WIT_NAMESPACE_MAP_WRITE` for a writable chunk.
- **The reply's one handle** is a memory object of 64 pages that holds the file's bytes from the offset, zero past
  the file's end. Its rights are `MAP` and `TRANSFER`, plus `WRITE` for a writable chunk.
- **Refusals.** A writable chunk needs a handle opened for reading and writing, and any chunk needs a readable one
  (`EACCES`). A misaligned offset is `EINVAL`.

## The service (`src/Services/Namespace/Server`)

**The registry.** `MappedFiles` is the mount table's, shared by every session. It keeps one record per file, by mount
point and path:

- the chunks clients mapped;
- the handles that map the file writable;
- the count of open handles that mapped it.

**The first MAP of a chunk.** It makes the chunk: an anonymous memory object (`IChunkSource`; arrays in a host test)
filled from the file. Every later MAP of that chunk, from any session, gets a duplicate of the same object.

**Coherence.** While a file has chunks, the service's own operations go through them:
- **READ** copies the chunks' bytes over what the provider read, since a mapping may have written them.
- **WRITE** writes the provider and copies the bytes into the chunks.
- **TRUNCATE** zeroes the chunks past the new end.

**Write-back.** `SYNC` writes the chunks' changed blocks back to the file before it flushes, comparing each 4 KiB block
with the provider's bytes up to the file's end. The same happens when a handle that maps the file writable closes. When
the last handle that mapped the file closes, the record and its chunks go; the clients' mappings keep the objects alive
while they live.

**The stop.** The D6.1 stop closes every session's handles through the same path, so mapped files are written back
before the volumes unmount.

**Concurrency.** One gate per record serializes the service's uses of the chunks across sessions. Clients write the
pages whenever they like, as shared memory is written.

## The libc (`src/Substrate/libc`)

**A shared mapping is a shared memory file.** `mmap` with `MAP_SHARED` of a volume's file (`map_volume_shared`) makes a
shared memory file of the process (`__wit_shared_remote`) whose chunks are the service's:
- `__wit_shared_chunk` asks for each with `MAP` when a mapping first needs it, instead of creating an object.
- The file is then mapped as any shared memory file is (R3.2b), with per-page protections and partial unmaps.
- There is one such file per remote record and writability. It holds a reference of the remote record, so the
  service's handle stays open while the file is mapped, even after the descriptor closes.
- When the file ends, the reference goes. The last one sends `CLOSE`, and the service writes back.

**Refusals and copies.**
- A writable shared mapping needs a descriptor opened for reading and writing (`EACCES`).
- An executable mapping stays the private copy of D5.3.
- A private mapping stays the copy of D5.2.

**Replacing a range.** With `MAP_FIXED`, the range is freed only after the file and its chunk table exist, for the
reason D5.3 found.

**`msync`** with `MS_SYNC` sends `SYNC` for each volume file the range maps, once per file.

## Checks

**`/bin/init`** (both writable volumes) maps a file's first page shared and writable, then requires each of these:
1. A write through the mapping reaches `pread`.
2. A `pwrite` reaches the mapping.
3. `msync` and `munmap` succeed.
4. After `close`, the file holds both writes when it is read again.

**The .NET program's `memory map` area** writes a byte through a `ReadWrite` `MemoryMappedFile` view, flushes and
disposes it, then requires `File.ReadAllBytes` to show the byte and nothing else changed.

**Host tests** (`tests/OutWit.OS.Tests`, with a chunk source of arrays):
- A chunk holds the file's bytes and zeros past its end.
- A read sees what the mapping wrote, and a write reaches the mapping.
- `SYNC` and `CLOSE` write back, and the last close drops the chunk.
- Two sessions' handles share one chunk, which lives until the last of them closes.
- A writable MAP of a read-only handle is `EACCES`, and a misaligned offset is `EINVAL`.

## Results

`runtime-services` passes on both ISAs: the POSIX checks with the shared mapping's, the System.IO check with its
read-write view, CoreCLR's assemblies from the volume now as shared mappings, and every other boot of the five.

## Limits kept explicit

- **The registry knows a file by its path.** A file renamed while it is mapped gets a new record at its new path, and
  the old record writes back to the old path.
- **Write-back compares blocks.** No dirty bits reach user space, so a write-back reads the file's blocks to find
  those the mappings changed.
- **The mapping's size is fixed when it is made.** A shared mapping past the page that holds the file's end is `ENXIO`,
  as with a shared memory file (R7.2a), and a file that grows later does not grow the mapping.
- **No write-back without a writer.** Writes by `pwrite` are the provider's at once. Writes through mappings reach the
  file at `msync`, at the last close of a writable mapper, or at the service's stop. A cut before any of them loses
  them, as Linux can lose dirty pages.
