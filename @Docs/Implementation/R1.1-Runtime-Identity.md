# R1.1 — the runtime's build and identity for TargetOS=witos

Plan step R1 sets up the build of upstream .NET in its Unix form for WitOS (RFC 0015 §3–§4). R1.1 is its first slice.
On a Linux host, `runtime-witos` takes dotnet/runtime at the pinned commit and applies the `witos` patch set. It then
builds `System.Private.CoreLib` for `witos-x64` and `witos-arm64` with the runtime's own `build.sh -os witos` and
checks that CoreLib names its platform `WITOS`. The patch set is 7 files, none of them in CoreCLR or the native
libraries. R1.2 adds ILC's `TargetOS.WitOS` and R1.3 the native build's configuration.

## What changed

**The pin.** `build/runtime/runtime.lock.json` names dotnet/runtime `v10.0.8` at commit `b82454ca` and gives the
SHA-256 of every file the patch set changes, as the commit holds it. A file WitOS adds is pinned by the hash of no
bytes, so it must not exist upstream. The lock also records the budget of RFC 0015 §4: FreeBSD's 31 CoreCLR files and
62 native-library files, and Haiku's 18 and 11. The frozen line keeps its own pin in `experiments` until R2.

**The patch set.** The patches are in `patches/runtime`, beside the frozen line's NativeAOT overlay, which R2 removes.
A `witos` patch changes a file in place, so its name is the file's path with `/` as `.`
(`eng.RuntimeIdentifier.props.patch`). `RuntimeWitos.PATCHES` lists the set. Each patch says what it does and names
its step:

| File | Change |
| --- | --- |
| `eng/build.sh` | `--os witos` is accepted and named in the usage, as `haiku` is |
| `eng/RuntimeIdentifier.props` | `TargetsWitOS`, a Unix target beside FreeBSD and Haiku; the portable RID `witos-<arch>` comes from `TargetOS` |
| `…/System.Private.CoreLib.Shared.projitems` | `TARGET_WITOS` beside `TARGET_FREEBSD` and `TARGET_HAIKU`; `Environment.WitOS.cs` for `TargetsWitOS` |
| `…/System/OperatingSystem.cs` | `OSPlatformName` is `"WITOS"`: `IsOSPlatform("WitOS")` is true, every `Is<Platform>()` false, and there is no public `IsWitOS()` |
| `…/System/Environment.WitOS.cs` (added) | the per-platform member each Unix platform writes, as `Environment.FreeBSD.cs` does: `WorkingSet` is 0, what the Unix form returns where it cannot read a resident set, until System.Native reports WitOS's memory figures; there is no `/proc` |
| `…/runtime.json`, `…/PortableRuntimeIdentifierGraph.json` | `witos` imports `unix`; `witos-x64` and `witos-arm64` import `witos` and `unix-<arch>`, as `freebsd-x64` does |

**Upstream patches.** `UpstreamPatches` gains two exact cases that the runtime's tree needs:

- **A file WitOS adds.** The patch starts from no text: `Before` is the hash of the empty string, and the patch is
  one hunk of added lines.
- **A text without a final line end.** CoreLib's `.projitems` ends without one. The result keeps it missing, and a
  hunk that would reach that last line is refused, since a unified diff would have to mark it.

**The tool.** `runtime-witos [--arch x64|arm64]` runs on a Linux host and refuses elsewhere. It works in four steps:

1. **The checkout.** It keeps the commit as a shallow checkout in `.tools/upstream/runtime-witos-10.0.8` and
   verifies the remote, the revision, a clean tree and the pinned bytes of every patched file. It never builds there.
2. **The work tree.** It works in a Git worktree, `artifacts/runtime-witos/src`. Every run returns the worktree to the
   commit and cleans it, keeping only the build's `artifacts` and `.dotnet`, then applies the patch set.
3. **The build.** It runs `./build.sh clr.corelib -os witos -arch <arch> -c Release`.
4. **The checks.** CoreLib must load the string `"WITOS"`: the trimmed CoreLib keeps `OperatingSystem.OSPlatformName`
   only where `IsOSPlatform` uses it. The tool then measures the patch set by area against the budget and writes
   `artifacts/runtime-witos/patch-set.json`.

CI's `linux-host` job runs it for both architectures.

## Tests

On Linux (the container): `runtime-witos` and `runtime-witos --arch arm64` build `System.Private.CoreLib` for
`witos-x64` and `witos-arm64`, and both name `WITOS`. The output is:

`Patch set: 7 files (build 2, libraries 5); CoreCLR 0 of FreeBSD's 31 and Haiku's 18, native libraries 0 of 62 and 11.`

The host tests check the following:

- the tool's list and the pin name the same files;
- every patch is named by its path and made from the pinned bytes;
- the budget is recorded;
- the areas are counted as the budget counts them;
- an added file and a missing final line end apply exactly.

## Limits kept explicit

- Only CoreLib is built. Nothing runs yet; that is R2 and R3.
- `Environment.WorkingSet` is 0 on WitOS.
- ILC knows no WitOS yet (R1.2), and the native build has no WitOS configuration (R1.3).
- The runtime build downloads its own SDK and packages, as upstream's scripts do. The pin covers the source, not that
  toolset.
