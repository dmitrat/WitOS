# W1.3 — TCP: the window's right edge and the bounds of a retransmission

Plan step W1.3 (phase W) opened and closed on 2026-10-23. The suite's TLS echo over the loopback (`Network.TlsEcho`, a
mebibyte through `SslStream` both ways) sometimes reported no result within 60 s in the guest. W1.2b's TCP stack in the
network service caused it, and the cause was not timing: a right edge of the window that moved back, and four ways in
which a connection then refused the acknowledgments that would have reopened it (§3). The fix keeps the edge where it was
offered and follows RFC 9293, RFC 7323, BSD and Linux wherever a closed window or a retransmission meets an
acknowledgment. A host test now runs the echo under 900 random schedules (§4).

## 1. The occurrences

| When | Where | What |
| --- | --- | --- |
| 2026-10-23, CI's `published-on-windows` (x64) of PR #184 | `runtime-published`, 4 processors | `Network.TlsEcho: fail (no result within 60 s)`, the suite's one unexpected result |
| 2026-10-23, CI's `published-on-windows` (arm64) of PR #186 | the same | the same |
| 2026-10-23, the container, `runtime-compatibility` x64 | the suite with a probe that ran the check 40 times first | repeat 31 failed after 60606 ms; the others took 1.8–2.4 s, with outliers of 4.5, 6.1 and 13.4 s |

`Network.TcpEcho`, the same echo without TLS, once did not finish on ARM64 (2026-10-20, a known defect since). It has the
same shape: a server that reads 16 KiB and writes it back before it reads again, and a client that writes everything
while it reads.

## 2. What the stalled connections showed

When a client goes, the network service prints each connection its session still holds
(`NetworkStack.DescribeConnection`). The probe's failed repeat left these two connections:

```
tcp 100 Established …:49216 to …:49217: send 262144 bytes, 0 in flight, window 0, cwnd 196018;
    receive 262138 bytes, window 6, advertised 0; rto 200 ms, retransmit off, persist in 7013 ms; waits to write
tcp 99  Established …:49217 to …:49216: send 164462 bytes, 1 in flight, window 0, cwnd 1460;
    receive 0 bytes, window 262144, advertised 262144; rto 60000 ms, retransmit in 6865 ms; waits to read
```

Socket 100 is the echo server: its write waits for the client's window and its receive buffer is full, 6 bytes short,
which a shift of 3 advertises as 0. Socket 99 is the client: it has read everything and offers 262144 bytes. The server
still believes the client's window is 0. Meanwhile the client has one byte in flight that the server refuses, and its
retransmission timer has backed off to the minute's ceiling.

## 3. The causes

The stack reproduced the guest's state on the host: two connections over one stack's loopback, the echo driven by a
seeded random schedule. Seed 259 ended exactly as the guest did: `receive 262138 bytes, window 6, advertised 0` on one
side, and `1 in flight, window 0, cwnd 1460` on the other. Five defects took part:

| Defect | What it did | The fix |
| --- | --- | --- |
| **The right edge moved back.** With a shift of 3 the window field counts units of 8 bytes from RCV.NXT, which moves by any count. A window rounded down after a segment of an odd length set the edge up to 7 bytes behind the one offered before. `Transmit` compared the edges before it rounded. | A segment the peer had sent up to the edge it was offered lay wholly beyond the new edge, and the receiver refused it. | `Transmit` keeps the edge it offered, rounded up to the unit wherever the receive buffer holds that. Otherwise the window field shows up to a unit less, while `AdvertisedEdge`, the edge segments are judged by, never decreases. A receiver honours as in window every segment that was in window for an acknowledgment it sent (RFC 7323 appendix F; RFC 9293 section 3.8.6.2.2). The buffer holds every byte below that edge, since an edge is set within the buffer's room and data and reads change both alike. |
| **A segment at RCV.NXT in a closed window was dropped whole.** | The refused byte's retransmission at SND.UNA carried the client's window update, and the server ignored it. | With a zero window, a segment at RCV.NXT counts for its acknowledgment and its window; its data and FIN go, and the answer reports the window at once (RFC 9293 section 3.10.7.4; Linux's `tcp_sequence` accepts it). |
| **A pure acknowledgment carried SND.NXT.** The refused byte's retransmission set SND.NXT one past the server's RCV.NXT. A retransmission timeout sets SND.NXT back to SND.UNA, which is behind the peer's RCV.NXT once the peer holds the bytes. | Every window update the client sent was unacceptable to the server's closed window. Two sides that both timed out refused each other's acknowledgments until the connection failed. | A pure acknowledgment carries SND.MAX, as BSD's `tcp_output` sends one. |
| **A segment without data at the right edge was refused.** A peer that filled the window sends its acknowledgments at the edge while an earlier segment is still on its way. | Those acknowledgments and the windows they carried were lost. | A segment without data may lie at the window's right edge, as Linux's `tcp_sequence` takes it. |
| **A fast retransmission sent bytes that were never sent.** `RetransmitFirst` (fast retransmit, NewReno's partial acknowledgment) sent up to an MSS from SND.UNA out of the send buffer, past SND.MAX, and left SND.MAX where it was. | The peer acknowledged those bytes. The sender refused the acknowledgment for the rest of the connection, as one of data never sent. | A retransmission takes only bytes that were sent: below SND.MAX, or below the FIN. |

The ACK storm P3 removed came from the same family: a probe that consumed sequence space made every later pure
acknowledgment unacceptable to a closed window. P3 rate-limited the answers and made probes take no sequence space, but
the retransmission timer still retransmitted a byte into the closed window, and the rounding that moved the edge back
remained.

## 4. The tests

`TcpTests` (host, CI's x64 leg):

- **`AdvertisedEdgeNeverMovesBackTest`.** Writes of 1001 bytes with `TCP_NODELAY`, each one a segment acknowledged by
  itself, into a receiver that does not read. The edge must never move back, and once the buffer is full the sender has
  nothing in flight and no timeout. Before W1.3 the edge moved back by 7 bytes at the tenth write.
- **`EchoUnderRandomSchedulesCompletesTest`.** The TLS echo in the stack's terms: the client writes a mebibyte in records
  of 16406 bytes (a TLS 1.3 record of 16 KiB) while it reads at random sizes, and the server reads a record and writes it
  back whole before it reads again. Each step of either side happens at random, under 300 seeds in each of three modes:
  - over the loopback;
  - over the loopback, now and then holding the stack's thread off past a retransmission timeout;
  - between two stacks over a segment that loses and swaps 3% of its frames.

  A schedule stalls if 30 s pass without a byte coming back.

| Stalled schedules of 300 | Loopback | Loopback, held off | Lossy segment |
| --- | --- | --- | --- |
| Before W1.3 | 2 | 2 | 97 |
| W1.3 without the right edge's fix | 0 | 0 | 1 |
| W1.3 without the closed window's acknowledgment | 0 | 0 | 5 |
| W1.3 without SND.MAX in pure acknowledgments | 0 | 0 | 25 |
| W1.3 without the right edge's segment without data | 0 | 0 | 1 |
| W1.3 without the bound of a fast retransmission | 0 | 0 | 29 |
| W1.3 | 0 | 0 | 0 |

Every fix removes stalls that the others leave. The lossy segment exposes more of them, because losses lead to timeouts
and fast retransmissions.

## 5. In the guest

The container's `runtime-compatibility` on x64 with the probe of §1, which ran the check 40 times before the suite, was
run twice with W1.3's stack: the first with every fix but the reset at SND.MAX, the second with all of them. All 80
repeats passed. Each run's first repeat took 13.4 s, with the JIT's first compilations. The rest took 1.7–2.5 s, with
outliers of 3.5–6.2 s, where the run before W1.3 had stopped at its 31st. The suite after the repeats reported no
unexpected result. CI's `runtime-compatibility` and `runtime-published` run the check once on each ISA.

## 6. What is not done

- A sender does not move a pure acknowledgment's sequence number to the peer's window edge when the peer shrank its
  window below SND.MAX (Linux's `tcp_acceptable_seq`). The stack never shrinks a window, and a peer that does is
  answered by the closed-window rule of §3.
- A bare FIN into a closed window is dropped with its window's answer; Linux queues it. The peer retransmits it until the
  window opens.
- The sender has no silly-window avoidance of its own beyond Nagle's algorithm: a window that opens by a few bytes is
  filled by a segment of a few bytes, as before.
