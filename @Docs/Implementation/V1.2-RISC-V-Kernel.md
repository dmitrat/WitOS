# V1.2 — The RISC-V kernel: Sv48 tables, traps, the timer and the kernel foundation's self-tests on riscv64

Plan step V1.2, the second slice of V1 (the RISC-V kernel), 2026-10-17. V1.1 ([V1.1-RISC-V-Loader.md](V1.1-RISC-V-Loader.md))
booted the converted ELF image under EDK II over OpenSBI to the architecture's bring-up and left every operation of
`witos/arch.h`, `witos/virtual.h` and `witos/platform.h` as a stub that panics by name. This slice replaces the stubs the
kernel foundation needs — the translation tables, the trap vector and its frames, the interrupt flag and the idle path,
the timer, the clock, the device lines, the processors, the device table — enters `wit_kernel_entry`, and proves the
result in the guest: the self-test kernel of riscv64 runs the shared foundation tests and the architecture's own (virtual
mappings, the memory permission faults, the CPU fault scenarios, kernel-worker preemption) to `Hello from WitOS`, the
release kernel boots alone, and the common kernel again compiled for the third ISA without a change. User mode (the
`ecall` path, U-mode frames and contexts, user translation tables) is V1.3 and the other harts V1.4; what belongs to them
still panics by name.

## 2. The translation tables (Sv48)

`wit_virtual_initialize` builds one root table for both halves of the 48-bit space and installs it in `satp` (mode 9)
after a `fence` and before an `sfence.vma`; until then the kernel runs in the bare physical space V1.1's bring-up left
(the firmware's own identity mapping outlives `ExitBootServices` but maps nothing the firmware did not drive).

- The low half's first root entry (512 GiB) is the kernel's identity map: every page of usable RAM writable and not
  executable, the image's headers and gaps read-only, each image section with the rights the loader read from the PE
  headers (W+X refused), and the board's boot devices — the 16550 UART and, new in this slice, the `sifive,test` finisher,
  which a panic writes after the switch and which the firmware's tables did not map (V1.1's finding). Page 0 stays
  unmapped.
- The high half holds the boot package's extents at `0xFFFFA00000000000` (root entry 320) and the root task image 128 MiB
  above, the same addresses the x64 and ARM64 kernels use, so that `wit_virtual_boot_storage` and `wit_virtual_view`
  mean the same thing on the three ISAs. The root task is optional and absent on riscv64 until V1.3.
- The stack guards — one page below and one above the boot stack, the two worker stacks and the kernel stack of every
  user thread of every registry slot (`wit_rv64_user_kernel_stacks`, sized by `WIT_PROCESS_CAPACITY` and
  `WIT_PROCESS_THREAD_CAPACITY` as ARM64's) — are unmapped after the identity map is built; the self-test reads their
  leaves back and requires them absent.
- A kernel leaf is `V|R|G|A` plus `W|D` when writable and `X` when executable; `U` is never set, so U-mode reaches no
  kernel page. A and D are set by the kernel because the privileged specification lets an implementation raise a page
  fault instead of updating them (Svadu makes it optional). Branch entries are `V|G` with the next table's PPN. The base
  ISA gives a page no memory attribute (Svpbmt would), so a device page is an ordinary mapping; the platform's physical
  attributes decide the access order, and `wit_arch_map_device_page` keeps its checks (page-aligned, below 512 GiB, apart
  from the image and from usable RAM, not mapped twice).
- `wit_arch_space_install_kernel` (for V1.3's user roots) copies root entry 0 and the high half's entries, so a user
  space shares the identity map and the windows; `wit_arch_space_kernel_ready` requires both branches present.
- Code publication is `fence rw, rw` then `fence.i` on the one hart that runs threads until phase P
  (`wit_arch_publish_code`; a per-page clean is nothing on RISC-V, since the instruction fetch is made coherent by
  FENCE.I alone); `wit_arch_process_write_barrier` is `fence rw, rw`; a translation changes are followed by
  `sfence.vma address, zero`.

## 3. Traps and the frame

`stvec` holds `wit_rv64_trap_vector` in direct mode. One entry serves both privilege modes through `sscratch`: it is zero
while the kernel runs and the running user thread's kernel stack top while U-mode runs (V1.3), and the entry swaps it
with `sp`, so a trap from S-mode stays on the interrupted stack and a trap from U-mode lands on that kernel stack. The
frame (`WitRv64Frame`, 560 bytes, 16-byte aligned) holds x1–x31 with x2 the interrupted stack pointer, sepc, sstatus,
scause, stval, f0–f31 and fcsr; `wit_rv64_resume_frame` restores it and returns with `sret`, writing the frame's top
back into `sscratch` when the frame returns to U-mode. `sstatus.FS` is set to Initial at `wit_arch_initialize`, so the
entry's `fsd` never traps; SUM and MXR stay off (the kernel reads user pages through its own view, never through the
user mapping); `scounteren` is zero, so U-mode reads no counter directly.

`wit_rv64_trap` sends an interrupt to `wit_rv64_interrupt` and reports a synchronous exception taken in S-mode as
`[EXCEPTION] cause= sepc= stval= sstatus= sp= stack=kernel|unknown` before panicking with the cause's name
("Breakpoint", "Illegal instruction", "Load page fault", "Store page fault", "Instruction page fault", the access and
alignment faults); a trap from U-mode panics by name until V1.3. The exception classes the common kernel counts map as
on ARM64: a load fault at address zero is a null read, a store one a null write, an illegal instruction is illegal, and
there is no divide class, since integer division by zero does not trap on RISC-V.

The idle path is `wfi` followed by `csrsi sstatus, 2` at `wit_rv64_idle_resume`, then `csrci sstatus, 2`: WFI must be
unaffected by the global interrupt enable and honour the individual enables, so a pending timer wakes the hart while
SIE is clear and the interrupt is taken exactly at the resume label, as x64's `sti; hlt; cli` and ARM64's `wfi; msr daifclr`.

## 4. The board

- **The device tree.** `fdt.c` walks the firmware's tree once (version 17 header, the structure and strings blocks mapped
  page by page unless the kernel maps them already) and keeps `/cpus`'s `timebase-frequency` and each `cpu` node's `reg`,
  `status`, and whether `riscv,isa` names `sstc` among its underscore-separated extensions or `riscv,isa-extensions`
  lists it. `wit_platform_processors` reports the harts in the tree's order.
- **The processor.** S-mode reads neither `mhartid` nor `misa`, so the boot hart's identity is the hart the SBI hart
  state machine (`hart_get_status`) reports STARTED while every other hart is stopped — OpenSBI starts the next stage on
  one hart and parks the rest until `hart_start` (V1.4); the probe runs once and is cached. The features word and the
  cache size are zero: the base ISA has no identification the kernel can read, and V1.4 may report the ISA string as
  bits.
- **The clock.** `rdtime` is the monotonic domain at the timebase frequency (10 MHz on virt); `Clock.Counter64` and
  `Clock.IrqIndependent` hold as on ARM64. UTC is the goldfish RTC at `0x101000`: nanoseconds since 1970 in two words,
  the high one latched by the low one's read, divided to seconds.
- **The timer.** The scheduler tick is the supervisor timer interrupt at 100 Hz: `stimecmp` where the boot hart's ISA
  names `sstc` (QEMU's `rv64` CPU does; OpenSBI 1.8 enables it in `menvcfg`), SBI `set_timer` otherwise, each tick re-armed
  relative to the counter at acknowledgement; stopping writes the never value. The kernel logs which path it took
  (`Timer: stimecmp (sstc), PLIC context 1`).
- **Device lines.** The PLIC at `0xC000000` signals the hart's supervisor context, number `2 × hart + 1`, as the external
  interrupt; its sources 1–95 (`riscv,ndev` 95) are the device lines of RFC 0011 §7.7: `wit_platform_line_unmask` gives
  a source priority 1 and sets its enable bit for the context, mask clears the bit, the claim register names and claims
  the pending source (zero when none, which the dispatcher ignores), and complete writes it back. The three pages the
  context needs (the priorities, the context's enables, its threshold and claim) are mapped on demand when the clock
  initializes; the threshold is zero. `wit_platform_timer_start` enables the timer and external interrupts in `sie`.
- **Devices.** The table holds the firmware's framebuffer (C2.1) when the boot has one and nothing else: the PCI
  functions behind the ECAM bridge need the interrupt map read for PLIC sources (the ARM64 reader expects GIC cells),
  which comes with V1.3's drivers. The kernel says so (`[DEVICES] No bus enumerated on riscv64 (plan step V1.3)`).

## 5. The self-tests and the tool

The self-test kernel links `kernel-selftest-shared` (the physical pages, the clock, the processors, SMP) and
`kernel-selftest-rv64` (`tests/Kernel.RV64`): `kernel_tests.c` runs the clock, processor, SMP, memory, virtual, fault
and scheduler tests in the foundation's order and no user suite; `fault_tests.c` triggers `ebreak`, `unimp` and a load
from the unmapped probe `0x400000000000`; `self_test.S` holds the triggers and `wit_rv64_worker`, whose sentinels live in
s2, s3, f8, f16 and the rounding mode `frm` (round up for worker 0, round down for worker 1), which every preemption must
preserve. The preemption test prepares each worker's frame in S-mode with SPP and SPIE set and the floating-point unit
on, enables SIE and waits in `wfi` until both workers are done; the dispatcher checks that each interrupt frame lies on
the running context's stack.

`tests/Expectations/riscv64-foundation.json` names the same 19 markers as ARM64's foundation, since the tests are the
shared ones and the architecture's. The tool reads the foundation expectation by architecture
(`KernelArchitecture.FoundationExpectation`), judges a riscv64 fault scenario with `Rv64FaultExpectation` (the cause, the
trigger, the panic, stval equal to the fixed probe or the `[FAULT-PROBE]` line, SPP set, the stack pointer within the
kernel stack) and requires no user suite or `Boot.RootTask` of an ISA whose port boots the kernel alone
(`KernelArchitecture.KernelOnly`). `test --arch riscv64` runs `KernelTestSuite.RunKernelOnlyAsync`: `boot-128`,
`boot-512`, `invalid-boot-info`, `overlapping-map`, nine fault scenarios (`breakpoint` → cause 3, `undefined-instruction`
→ 2, `data-abort` → 13 at the probe, `write-code`, `guard-low`, `guard-high` and `readonly-alias` → 15, `execute-data` →
12, `unmapped-alias` → 13) and `timeout` — 14 scenarios, with `boot-smp2` and the layer-2 scenarios joining at V1.4 and
V2. `release --arch riscv64` boots the release kernel. `BootSuite.Loader`, `EvaluateLoader`, `RiscV64Port` and the
`riscv64-loader` command are gone; CI's `boot` and `linux-selftest` jobs run `test --arch riscv64` and
`release --arch riscv64` in their place.

## 6. Results

`test --arch riscv64` on the Windows host (the pinned QEMU 11.1.0, EDK II's RiscVVirt DEBUG firmware over OpenSBI 1.8.1,
`-icount shift=2`): all 14 kernel-only scenarios passed — `riscv64-boot-128`, `riscv64-boot-512`,
`riscv64-invalid-boot-info`, `riscv64-overlapping-map`, the nine fault scenarios and `riscv64-timeout`. A boot with
256 MiB reports 197 MiB usable in 17 regions, 50,507 free pages, `Kernel satp: 0x9000000000080060`, the kernel stack at
`0x8D059000`–`0x8D069000`, `Timer: stimecmp (sstc), PLIC context 1`, `Counter frequency: 10000000`,
`Processors present/online: 1/1`, `Devices: 0`, the preemption test with 7 ticks, 7 context switches, 3 slices and about
166,600 iterations per worker, then `Hello from WitOS` and exit 33. The fault scenarios report, for `write-code`,
`[EXCEPTION] cause=0x000000000000000F sepc=0x000000008CA1F68A stval=0x000000008CA06BBA sstatus=0x0000000200002100
sp=0x000000008D068F60 stack=kernel` then `[PANIC] Store page fault`; for `execute-data` cause 0xC with `sepc` equal to
`stval` at the data page; for `data-abort` cause 0xD with `stval` `0x0000400000000000`. `sstatus` shows SPP set (0x100),
FS Initial (0x2000) and UXL 64-bit.

`release --arch riscv64`: `riscv64-release-128`, `riscv64-release-512` and `riscv64-release-display-256` passed. The
display boot found that the firmware drives ramfb on the RISC-V board too: `[BOOT] Framebuffer: 800x600, stride 800,
BGRX at 0x000000008DFD1000 of 3145728 bytes, mode 1 of 3`, `[BOOT] Framebuffer memory type 0, reserved`, `Devices: 1`
(the framebuffer descriptor of C2.1, on the third ISA without a change). The release image is 147,456 bytes of PE32+
(the ELF with DWARF 1,336,824), the self-test image 159,744.

Host: the tool's 96 tests pass, among them the riscv64 fault judge
(`Riscv64ExceptionJudgeRequiresTheCauseTheModeAndTheStackTest`), the manifests with the new self-test layer and the
layering of the third architecture; `release` on x64 passes under the shared release judge. CI runs `test --arch riscv64`
and `release --arch riscv64` in the `boot` job on Windows and in `linux-selftest` on Linux, where `riscv64-loader` ran.

## 7. Findings

- **The common kernel ran unchanged.** V1.1 proved it compiles for the third ISA; this slice proves the mechanisms behind
  `witos/arch.h` and `witos/platform.h` are the whole ISA dependence of the foundation: the page allocator, the random
  generator, the clock, the processor table, the device table and their self-tests passed on riscv64 at the first boot
  of the ported kernel.
- **A panic needs the finisher mapped.** After the switch to the kernel's tables, `wit_platform_finish` writes
  `sifive,test`; on ARM64 the exit is a semihosting instruction and on x64 a port, neither of which needs a mapping. The
  board therefore names the finisher a boot device beside the UART, or a panic would fault into a second panic.
- **The device tree may lie in mapped memory.** The ARM64 reader maps the tree's pages as device pages; on riscv64 the
  reader first asks `wit_virtual_view` whether the kernel maps a page already and maps only the pages it does not,
  so a tree in usable RAM is read through the identity map and a tree in firmware memory through device mappings.
- **sstc is there.** QEMU's `rv64` CPU names `sstc` in its ISA string and OpenSBI delegates the supervisor timer, so the
  kernel arms `stimecmp` itself and no `ecall` sits on the tick path; the SBI path stays for a board without it and is
  one `ecall` per tick.
- **The boot hart is a question for the firmware.** Without `mhartid`, the kernel asks SBI HSM which hart is started;
  the probe over 64 hart ids costs 64 `ecall`s once. V1.4 will know the harts it started itself.
- **No divide fault.** RISC-V's integer division by zero returns a defined value; the `WitArchExceptionDivide` class has no
  cause, as the ARM64 port found before.

## 8. What V1.3 inherits

The `ecall` path (`WIT_RV64_EXCEPTION_ECALL_USER`, a7 the number, a0–a2 the arguments, the status in a0 and the value in
a1 as `witos/syscall.h` already transports), U-mode frames (`sscratch` protocol in place, `wit_arch_frame_*`,
`wit_arch_run_user`, the per-thread kernel stacks already sized and guarded), thread contexts (the RISC-V block of
`witos/thread_context.h`, 568 bytes), user translation tables (`wit_arch_page_*` over the Sv48 leaves with `U` set,
`wit_arch_space_install_kernel` ready), `tp` as the TLS register the thread writes itself, the mechanism fixtures and the
shared user tests unchanged, the ECAM enumeration with a PLIC interrupt map, and `riscv64-users.json`. Every operation of
that list panics by name in `src/Kernel.Arch.RV64/stubs.c` today.
