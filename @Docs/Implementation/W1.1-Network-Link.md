# W1.1 — the link: user networking and the virtio network driver

Plan step W1.1, the first slice of `W0-Network-Inventory.md`. It gives a board a network adapter on QEMU's user
networking on both hosts, adds a NativeAOT driver for the adapter, and specifies the packet protocol the driver serves.
The device manager's probe exchanges ARP with the board's gateway through that driver. Made on 2026-10-19. It takes W0's
decision 7 (user networking on both hosts) as recommended. Decision 2 (the TCP/IP stack) belongs to W1.2 and is not
needed here.

## 1. The board's network

- **User networking on both hosts.** QEMU's user networking (slirp) gives the guest a gateway at 10.0.2.2, a DHCP
  server that leases 10.0.2.15 first, a DNS forwarder at 10.0.2.3 and NAT to the host. The Windows package's QEMU has
  always had it. The Linux build had none, because no libslirp was present when it was configured. Now:
  - the image and CI install `libslirp-dev`;
  - `Toolchain.QEMU_CONFIGURE` says `--enable-slirp`, so a build without the library fails rather than silently drops
    the backend;
  - the options are part of the build's stamp, so `setup` rebuilds QEMU;
  - CI's cache key for the built QEMU gains `-slirp`.
- **The adapter's slot.** `BootRequest.Network` adds `-netdev user` with `virtio-net-pci`. A board's four INTx lines
  rotate by slot, and the kernel binds a line once. The adapter therefore takes the slot whose line is the entropy
  source's, which no driver binds (`KernelArchitecture.EntropyLineSlot`):
  - slot 7 on q35 without a display, where the VGA card holds slot 1 and the entropy source is at slot 3;
  - slot 6 everywhere else, as the keyboard has done since C2.2.

  A keyboard and an adapter would need the same line, so the runner refuses a request for both until a line can serve
  several bindings.

## 2. The packet protocol

`witos/packet.h`, with its codec in `OutWit.OS.Hardware.PacketMessages`. It is RFC 0007's `NetworkQueueDevice`
contract over a channel, shaped like the serial and input protocols:

- The client attaches a window, a memory object of at most 16 pages, which the driver maps and copies through.
- `INFO` answers the MAC address, the MTU and the link state.
- `SEND` transmits a count of frames packed in the window and answers once the device took them.
- `RECEIVE` answers with as many whole frames as its bytes hold, at least one. The driver holds the one `RECEIVE` until
  a frame arrives, unless `NONBLOCK` asks for an immediate answer.
- A packed frame is an 8-byte header holding the frame's length, followed by an Ethernet II frame without its check
  sequence (14 to 1514 bytes). The next header starts at the next multiple of 8.
- The driver copies a `SEND`'s bytes out of the window and checks every frame before the device sees any of them.
- The driver keeps at most 256 received frames for a slow client and drops the newest beyond that, as a full receive
  ring does.
- Errors are errno values, as in the other protocols, plus `EMSGSIZE` for a frame outside the MTU and for a `RECEIVE`
  too small for the oldest frame waiting.

## 3. The driver

`/system/Drivers/VirtioNet` (`src/Services/Drivers/VirtioNet`) is a NativeAOT program, like the other virtio drivers
(ADR 0025). The device manager starts it with the device moved over the grant channel.

- **Initialization.** It checks that the device's configuration space reads the identity its descriptor names. It then
  negotiates `VIRTIO_F_VERSION_1` with `VIRTIO_NET_F_MAC`, which the device must offer, and `VIRTIO_NET_F_STATUS` when
  the device offers it. It reads the address under the configuration generation.
- **Memory.** It sets up queue 0 (receive) and queue 1 (transmit) on one pinned window of 30 pages. That window holds
  32 receive buffers and 16 transmit buffers of 2048 bytes. Each buffer holds the 12-byte virtio-net header and a frame.
- **Interrupts.** It binds its line to an event. It returns the receive buffers to the device as it takes their frames,
  and frees a transmit buffer when the device completes it.
- **No offloads.** No checksum or segmentation offload, no mergeable buffers and one queue pair, so a frame is whole in
  one buffer.
- **Serving.** It answers ready with the other end of the packet channel and serves the protocol to one client. It
  stops at the device manager's request (D6.1) once the device is reset.

The device manager's driver table maps Virtio's `NetworkQueueDevice` to the driver. `runtime-witos` and
`runtime-services` publish it with the other services.

## 4. The probe

`NetworkProbe` runs after the storage probes on every network driver that answered ready. It:

1. takes the driver's packet channel and attaches a window of four pages;
2. reports `INFO`;
3. sends an ARP request (RFC 826) for 10.0.2.2 from 10.0.2.15;
4. keeps a `RECEIVE` outstanding until the gateway's reply comes, with a deadline of 10 seconds.

It then closes the channel, and the driver keeps serving the device manager. From W1.2 the network service takes the
channel instead.

## 5. What ran

In the Linux host's image, with the final code. The `runtime-devices` scenario now boots with the adapter, each of its
five boots, and requires:
- the adapter's discovery;
- the driver's lines;
- `MTU 1500, link up`;
- `ARP reply from 10.0.2.2 at 52:55:0a:00:02:02` (slirp's gateway: `52:55` and its address);
- `3 drivers ready`.

Results:
- `runtime-services --arch x64`: PASS, all five boots. The adapter is at `00:07.0` on line 6 beside the entropy source,
  with address `52:54:00:12:34:56` and queues of 128 entries.
- `runtime-services --arch riscv64`: PASS, all five boots; the adapter at `00:06.0`, the same exchange.
- ARM64: pending. The container's tree holds no ARM64 NativeAOT pack of 10.0.12 to publish the driver with, so a
  `runtime-witos --arch arm64` runs, and CI's `linux-host` leg runs the scenario too.
- `OutWit.OS.Tests` with the packet codec's tests: 244 passed. `WitOS.Dev.Tests`: 121 passed. `format` is clean.

## 6. Left for later

- A line that serves several bindings, so that a keyboard and an adapter can share one board (and more devices than
  four lines can be bound).
- `VIRTIO_NET_F_MTU`, mergeable buffers, offloads and several queue pairs. The network service needs none of them to
  run TCP/IP.
- Frames copied through the client's window. A pin of the client's window, as the block protocol has, would spare the
  copy once throughput matters.
