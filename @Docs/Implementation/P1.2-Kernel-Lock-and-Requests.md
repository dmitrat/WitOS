# P1.2 — the kernel lock and the request fabric

Plan step P1.2 (phase P, `P1.0-SMP-Inventory.md` section 6): every entry into the kernel's state takes one kernel
lock, and any processor sends any other a request through a pending set and one doorbell, served while the target
spins for the lock. Threads still run on the boot processor alone (`wit_processors_scheduling()` stays 1); what
changes is that the serialization the kernel's rules assume — interrupts disabled on the one processor that takes
calls — now holds across processors, and that the requests P1.3 needs (RESCHEDULE, STOP, a shootdown from whichever
processor holds the lock) exist and are tested. Made on 2026-10-18.

## 1. The kernel lock

`wit_cpus_lock` and `wit_cpus_unlock` (`witos/cpu.h`, `cpus.c`): one word holding its holder's number plus one, taken
by compare-and-exchange with acquire ordering and released with release ordering. The holder takes it again for
nothing, so a path that already holds it may call a function that takes it; the release is not counted, and the paths
that release it are the ones that leave the kernel.

`user.c` takes it in `enter()`, which every call, tick, device line and fault of a thread passes through, and in
`wit_user_run` once the root task's start was checked. It gives it up in `leave()`, through which every frame those
entries return goes, and before each path that leaves without returning: the dispatcher's resume of a ready frame from
the idle path or after a created process ended (`wit_arch_resume_frame`), the root task's start (`wit_arch_run_user`),
the root's end (`wit_arch_leave_user`), and the idle halt, after which the idle path takes it back. A tick or a line
that wakes the halt takes it on its own entry like any other. The rules of serialization the kernel's mechanisms were
written to — "with interrupts disabled", "memory calls run one at a time on the one processor that takes calls" — stay
true as written: a processor holds the lock wherever it ran with interrupts disabled in the kernel's state, so a second
processor that enters waits.

## 2. Requests

Any processor sends any other a request, and only while it holds the kernel lock, which keeps the sender's side
simple — one sender at a time, an argument written in the target's record without a race — and costs nothing while the
lock is the kernel's one serialization. A request has a kind, a bit of the target's pending set:

| Kind | Argument | What the target does |
| --- | --- | --- |
| `WIT_REQUEST_FENCE` | — | the acknowledgement's acquire-release counter update fences it (`PROCESS_WRITE_BARRIER`) |
| `WIT_REQUEST_INVALIDATE` | the address | drops the translation of one page (`wit_arch_invalidate_local`) |
| `WIT_REQUEST_RESCHEDULE` | — | acknowledges; the dispatcher's action arrives with P1.3 |
| `WIT_REQUEST_STOP` | — | acknowledges; leaving its thread and halting arrives with P1.3 |
| `WIT_REQUEST_RUN` | a function | acknowledges, then calls it (the self-tests) |

The sender writes the argument, sets the kind's bit with an atomic or, and rings the target's doorbell, the one
inter-processor interrupt that remains (`WIT_IPI_DOORBELL`): vector 0xF0 by the local APIC's interrupt command
register on x64 (0xF1 enters the same way and is unused), SGI 0 through ICC_SGI1R_EL1 on virt, the supervisor software
interrupt through SBI `send_ipi` on riscv64. The doorbell says only that the set changed; the vector no longer carries
the kind, so `wit_x64_ipi_vector`, the global in which the x64 entry noted it, is gone. The target takes the whole set
with one atomic exchange and serves each kind it holds, then raises that kind's acknowledgement counter, which the
sender waits on within one second of monotonic time and panics without. A RUN request is acknowledged before its
function runs, since the function may want the kernel lock that its sender holds until the acknowledgement.

A target serves its set in three places:

- the doorbell's interrupt, on any processor: the boot processor's interrupt controller takes the doorbell too once
  others are online (`wit_platform_ipi_enable_boot`: nothing on q35, whose local APIC came on with the first
  secondary's start; SGI 0 in its redistributor on virt; `sie.SSIE` on riscv64). A doorbell from a thread's user mode
  serves and resumes the same frame. On riscv64 `sip.SSIP` is cleared before the set is served, so that a doorbell rung
  meanwhile raises it again; on x64 and virt the controller keeps a second doorbell pending while the first is in
  service.
- the spin for the kernel lock: a processor that waits for the lock serves its set on every failed attempt, so a holder
  that waits for an acknowledgement from a processor spinning for the lock — the processor it would otherwise wait for
  forever, since that processor spins with interrupts disabled — is answered.
- the wait for an acknowledgement of its own, for the same reason across two holders in turn.

A kind's bit is set once whatever the number of senders before it is served, so the set is no queue: a sender waits
for its acknowledgement before it sends the next of that kind to that target, and two senders never send at once.

## 3. Spinning, and the clock from every processor

Guest boots run in virtual time (`-icount`), under which QEMU runs the processors one at a time, round-robin, each for
a slice of up to the next timer deadline divided among them, and a processor that spins keeps the one it waits for from
running until its slice ends. The first run of the contention test spun so and did not finish within two seconds on
ARM64 and riscv64. Every spin-wait now takes one step of `wit_arch_spin_pause()` per round: PAUSE on x64 and YIELD on
ARM64, which QEMU turns into the end of the slice (`helper_pause`, `HELPER(yield)` when not in parallel TCG), and on
riscv64, whose PAUSE only ends a translation block in QEMU, a WFI with the hart's own software interrupt set pending:
WFI returns at once when an enabled interrupt is pending, on hardware and in QEMU, and QEMU ends the slice on every
WFI. Clearing the bit afterwards loses no doorbell, since every spin serves the pending set itself and a sender holds
the lock until its request was served. The lock's spin, the wait for an acknowledgement and the wait for a starting
processor pause so.

The q35 monotonic clock checked that the HPET never moved backwards against a plain global of the last value read,
written by whoever read; with two processors reading, one could store a later value between the other's read and its
check, and `boot-smp2` panicked with `HPET reset or moved backwards`. The last value is now loaded before the counter
is read and raised with a compare-and-exchange, so the check holds for every reader of the one counter. The virt
boards' counters (CNTVCT, `time`) keep no such state.

## 4. Device lines on the boot processor

Device lines reach the boot processor alone in phase P, which takes them while it runs threads (P1.3 adds a tick on
each processor, not their lines). On virt the distributor routed each SPI to "any processor" (`IROUTER.IRM`), which
QEMU happened to deliver to processor 0; now `wit_platform_line_unmask` routes it to the boot processor's affinity
read at the interrupt controller's mapping. On q35 the PIC's line enters through the boot processor's LINT0 as ExtINT
alone. So the x64 global in which a device vector's entry notes its vector (`wit_x64_device_vector`) keeps one writer
with interrupts disabled; the plan's slice had it passed on the stack, which a line routed to another processor will
need, and nothing in P1 routes one there.

## 5. The self-tests

`tests/Kernel/smp_tests.c`, run in `boot-smp2` on the three ISAs:

- `Smp.Online` and `Smp.Identity` as before.
- `Smp.Ipi`: the boot processor, holding the lock, fences every other processor twice and invalidates a page once;
  each acknowledged exactly two fences and one invalidation.
- `Smp.LockContention` (new): the boot processor has the first secondary run, through a RUN request, a loop of 64
  rounds that takes the lock, counts and fences every other processor — the boot processor among them — and releases
  it, while the boot processor runs the same loop. The count comes out exactly 128, and each processor acknowledged
  exactly 64 fences from the other, which it could only do while it spun for the lock or waited, since both run the
  loop with interrupts disabled. So this one test is a request from a secondary to the boot processor, the serving
  while spinning, and the lock's mutual exclusion under contention. The plan's acceptance also named requests "from two
  senders at once"; with requests sent only by the lock's holder, two senders never send at once, and the test sends
  in turn from both under contention instead.

## 6. What ran

In the Linux host's image, with the final code:

- `test --arch x64`: PASS, all 27 scenarios — `boot-128` and `boot-512` with the user suites, `boot-smp2` with
  `Smp.Online`, `Smp.Ipi`, `Smp.Identity` and `Smp.LockContention` on two processors, `boot-intel`, the layer-2
  scenarios (`libc`, `libc-test`, `cxx`, `spawn`, `process`, `sysroot`) and the fault and refusal scenarios.
- `test --arch arm64`: PASS, all 21 scenarios; `test --arch riscv64`: PASS, all 21; `Smp.LockContention` in
  `boot-smp2` on both.
- `release` on the three ISAs: `release-128`, `release-512` and `release-display-256` pass.
- `runtime-terminal --arch x64`: PASS, 20 checks (the services take the lock on every call and give it up in the
  idle halt and on every return).

The first run panicked on x64 (`HPET reset or moved backwards`) and timed out the contention test on ARM64 and
riscv64 (`The contending secondary processor did not finish`); section 3 has both causes. CI's `linux-host` legs run
every runtime scenario on the three ISAs.
