# C2.4 — the screen console in a QEMU window

Plan step C2.4 (phase C, RFC 0009 §26, RFC 0020 §28 and §34), the author's decision of 2026-10-17: the screen and the
keyboard of C2, by hand. C1.4's `shell` command opens PowerShell on the host's console through the serial terminal;
C2.3 proved PowerShell on the display service's screen with keys typed through QMP and a headless QEMU. This step joins
the two: the same session on the screen, in QEMU's window, with the window's keys. It is not a gate — `runtime-display`
stays the screen's judge — and closes with the author's session on both ISAs. Built and tried on 2026-10-18.

## 1. The window

`shell --window` boots the session with the display and the keyboard of `runtime-display`: the board's `ramfb`, a
`virtio-keyboard-pci` and the mirroring virtio console. The image is the shell's own (C1.4): the device manager's policy
makes the display the main console whenever the board has a framebuffer and a keyboard driver (C2.2), so the image
needs nothing new and the same image boots with or without the window.

- **`BootRequest.Window`** asks the runner for QEMU's GTK display (`-display gtk,zoom-to-fit=on`) instead of
  `-display none`. GTK scales the framebuffer to the window and keeps QEMU's menus (pause, reset, power down, zoom,
  full screen); SDL was tried too and works the same way, without either.
- **The window's keys are the input.** QEMU sends them to the virtio keyboard, whose driver passes them to the display
  service's US layout (C2.2) and on into the terminal's one line discipline, as the QMP keys of `runtime-display` go.
- **The console shows the mirror and types nothing** (`TerminalRelay` with `keys: false`). The host's terminal answers
  the queries the mirror shows, the cursor position report among them; the display answers them already, and two
  answers garble the input (C2.3), so the relay forwards no key, leaves the console's Ctrl-C to the tool, and drops the
  host terminal's answers when the session ends instead of leaving them to the shell the tool returns to.
- **An interactive clock.** A session a person works in keeps the instruction clock but lets QEMU sleep while the
  guest idles (`-icount shift=2,sleep=on`, for both `shell` forms): the guest's time follows the host's between keys
  instead of racing ahead, and the host's processor rests. Scenarios keep `sleep=off`, which makes their timing a
  function of the instructions alone.

## 2. Prepared on one host, booted on another

The session's image carries the .NET install and the services, which only a Linux host builds (`runtime-witos`), and its
data disk holds an ext4 volume that the host's e2fsprogs make; the window needs a screen, which the Linux container
does not have. So the command splits:

```text
# On the Linux host (the container), after runtime-witos:
dotnet run --project tools/WitOS.Dev --configuration Release -- shell --arch x64 --window --prepare <directory>
# On a host with a screen (Windows with the pinned QEMU), from the repository root:
dotnet run --project tools/WitOS.Dev --configuration Release -- shell --arch x64 --image <directory>/WitOS-x64-shell.img --disk <directory>/data-x64.img --window
```

`--prepare <directory>` builds the image and the data disk as a session would and writes them there
(`WitOS-<arch>-shell.img`, `data-<arch>.img`) instead of booting them, printing the command that does. `--image` boots
a prepared image with its `--disk`, which the session then keeps as `--disk` always does: what one session writes on
the volume is there for the next. `--image` refuses `--publish` and `--prepare`, which build an image, and needs
`--disk`. Without `--window` the prepared image opens the serial session of C1.4 on the console.

## 3. What ran

On 2026-10-18 the sessions were prepared in the Linux host's image from CI's .NET install and services of each ISA (the
artifacts the `linux-host` legs upload for the NuGet suites, laid where `runtime-witos` leaves them) and booted on the
Windows host with the pinned QEMU 11.1.0, whose Windows build carries the GTK and SDL displays:

- **x64**: the window showed the console mark and `PS /data>` on the display service's screen; typed in the window,
  `Get-Date; 6 * 7` and a listing of `/data` printed there, and `exit` ended PowerShell, `/bin/init`, the services and
  the machine (`PASS: x64-shell-1024`, `Session ended.`).
- **ARM64**: the same, with `$PSVersionTable.OS` printing `WitOS 0.1 ABI-1` and the mark naming the Arm64 kernel.

The keys were injected through Windows' `SendInput` with set-1 scan codes. Virtual-key input without a scan code — what
`WScript.Shell.SendKeys` and UI automation's typing send — reaches neither QEMU display (`[VIRTIO-INPUT] key` lines
stay absent): QEMU's GTK and SDL displays translate the scan code, which a physical keyboard always gives. That matters
only to automation; the scenarios type through QMP.

## 4. Limits

- The display's emulator draws white on black and ignores SGR and the private modes (C2.2): PSReadLine's colours, the
  alternate screen and the cursor's visibility are not shown. Until the emulator learns them, a full-screen console
  application looks right on the serial mirror alone.
- The display is 800 by 600 (100 by 37 cells), the firmware's mode; the window scales it.
- One keyboard layout, the US one (C2.2), until M9.
- Closing the window powers the machine off without stopping the services, as pulling the plug would; the ext4 journal
  replays the volume at the next session's mount (D6.2).

## 5. Closing the step

The author's sessions came on 2026-10-20, on x64, from the images a Linux container prepared and the Windows host
booted with the pinned QEMU:

- **Under TCG** the console was unusable by hand: seconds a character, with the echo arriving well after the key, as
  C2.7 had measured (7 to 16 s a key). The author typed `get-date` through it, backspacing what had not yet appeared.
- **Under WHPX** (`--accel`) the session worked and was faster, but stuttered enough to make testing hard. The latency
  was then measured rather than guessed (C2.7 §4a): about 85 ms a key, of which the guest takes 10 to 60 ms and QEMU's
  display refresh the rest, with hiccups of up to half a second on one processor and 184 ms on four, so an accelerated
  session now boots on four processors.

The author closed the step on that: the console works, and its speed is a question for the hardware track, where WitOS
boots on VMware and other hypervisors closer to a real machine. ARM64's session was prepared and booted to its prompt
and typed through `SendInput` (§3); by hand this host offers it TCG alone, which is no use, so the ARM64 session by hand
waits for a host of that ISA or its hardware virtualization.
