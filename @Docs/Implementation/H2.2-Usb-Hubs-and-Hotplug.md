# H2.2 — USB: hubs, keyboards by their report descriptor, devices that come and go

Plan step H2 gives WitOS a USB host stack (phase H, ADR 0029: the keyboard of every target is USB). H2.1 drove an xHCI
controller and the boot keyboards on its root ports. H2.2 adds the rest of what a keyboard on real hardware needs:

- hubs, with route strings and the Transaction Translator of a high-speed hub;
- HID keyboards read by their report descriptor, Report IDs and bitmaps of every key among them;
- devices that arrive after the driver started, and devices that go;
- the recovery of a halted endpoint.

The driver is now a USB core over the controller. The core keeps the tree of devices as ports change, and the
controller serves the core through an interface that a fake controller also serves in the host tests.

## 1. The pieces

| Where | What |
| --- | --- |

| `IUsbHost` | What the core asks of a controller: root ports (read, acknowledge, reset), a device addressed at a location, control transfers, interrupt IN endpoints and their transfers, a hub declared, an endpoint recovered, a slot disabled, a delay. A device is its slot. |

| `UsbHub`, `UsbSetup` | The hub class of USB 2.0 §11: the hub descriptor, a port's status and change, the changed ports of a status report, and the class requests (`GetHubDescriptor`, `GetHubStatus`, `GetPortStatus`, `SetPortFeature`, `ClearPortFeature`, `ClearHubFeature`). ## 2. The tree

- **At the start** the core reads every root port, acknowledges its changes and takes the device on each connected one.
  A USB 2 root port is reset first; a USB 3 port enables itself once its link trained.
- **A root port's change** (Port Status Change Event): the core reads the port and acknowledges its change bits (written
  1 to clear, the port's enable left alone). A connection change, a lost connection or a port the controller disabled
  detaches the device there. A connection change with a device connected takes it. The change that the core's own reset
  causes carries no connection change and takes nothing.
- **A device** is addressed where it sits, its device and configuration descriptors read and logged. A device whose class
  or interface is the hub's becomes a hub. A device with HID interfaces gets its keyboards. Anything else stays
  addressed and unconfigured, so that its port's change lets its slot go. A device that fails after its address stays in
  the tree for the same reason.
- **A hub** (USB 2.0 §11), in Linux's order:
  1. its status change endpoint is configured;
  2. `SET_CONFIGURATION`;
  3. its hub descriptor is read;
  4. the controller is told it is a hub — Configure Endpoint with the slot's add flag alone and the Slot Context's Hub
     flag, number of ports and, at high speed, TT Think Time, as Linux's `xhci_update_hub_device` sends it;
  5. every port is powered, then the core waits the descriptor's power-on time, at least Linux's 100 ms below the root;
  6. each port with a device is served;
  7. a status change report is asked for: one bit a port from bit 1, bit 0 the hub's own, `(ports + 8) / 8` bytes.
- **A hub's port.** Every change feature the port reports is cleared before the core acts. A connection change, a lost
  connection or a port the hub disabled detaches the device there; a connected port with a new connection, or with a
  device just detached for a disabled port, is taken. Taking a device:
  1. 100 ms for the connection to settle (TATTDB);
  2. `SetPortFeature(PORT_RESET)`, then the port's status every 10 ms until the reset's change, at most 500 ms;
  3. the reset's and the enable's changes cleared, while a connection change that came meanwhile stays for the port's
     next report;
  4. 10 ms of recovery (TRSTRCY);
  5. the device addressed at the hub's location with the port as the next tier, at the speed the port reports.
  A port beyond the route string — a sixth tier, or a port above 15 — is logged and left.
- **The Transaction Translator.** A full- or low-speed device below a high-speed hub is reached through that hub's
  translator: its Slot Context names the hub's slot and port. Below a full-speed hub the device inherits the translator
  the hub is reached through, none on a root port. The driver keeps a hub of several translators on its single one
  (alternate setting 0), so the Slot Context's MTT stays clear.
- **A device that goes** takes the devices below it, the lowest first. Every key a keyboard held is released, so the
  client sees no key stay down. Its slot is disabled with Disable Slot. Its structures return to the controller's pools
  and its events not yet taken are dropped.

## 3. Keyboards

- **Every HID interface** of the configuration's alternate setting 0 with an interrupt IN endpoint has the endpoint
  configured before `SET_CONFIGURATION`, as xHCI asks (Linux configures every endpoint of a configuration so). After it,
  each interface's report descriptor is read, at most 1024 bytes, the device's control buffer.
- **The report descriptor** (HID 1.11 §6.2.2) is read as Linux's hid-core reads it:
  - the global state with Push and Pop;
  - the local usages a main item takes and clears, Usage Minimum and Maximum expanded;
  - the usage page joined at the main item to every usage of two bytes or less, while a usage of four bytes carries its
    own page;
  - the Logical Maximum unsigned unless the minimum is negative, so `0x25 0xFF` after a minimum of 0 is 255;
  - each Input item a field at its bit offset in the report its Report ID names.

  Bounds refuse a descriptor that ends inside an item, leaves a collection open, names Report ID 0, or exceeds 4096
  usages a main item, 4096 elements or 256 bits an element, 32768 bits a report, or 32 levels of nesting.
- **A keyboard** is every report that holds an input field of the keyboard page (usages 0x04–0xE7). A variable field
  holds its usage while its element is nonzero (the modifiers' bits, or a bitmap of every key). An array's element names
  the usage it holds from the logical minimum on. A report of ErrorRollOver changes nothing. A report of another Report
  ID — a mouse's, a consumer control's beside the keyboard in one interface — changes nothing either. Keys become evdev's
  codes by Linux's `hid_keyboard` table, as in H2.1, in the same order: modifiers released, keys released, modifiers
  pressed, keys pressed, a SYN.
- **The protocol.** A reset leaves a HID device in the report protocol (HID 1.11 §7.2.6), so the core sends no
  `SET_PROTOCOL` for it. A boot keyboard whose report descriptor cannot be read or parsed is set to the boot protocol
  and read by the boot layout. `SET_IDLE(0)` follows, and a refusal is logged.
- **The transfer** asks for the keyboard's largest report or the endpoint's packet, whichever is larger, at most 1024
  bytes.

## 4. A halted endpoint

- **An interrupt endpoint** whose transfer completes with an error — a STALL, a babble, a transaction error — is taken
  back:
  - Reset Endpoint where its context is Halted (Transfer State Preserve clear, so its data toggle starts again);
  - Stop Endpoint where it is still Running;
  - then Set TR Dequeue Pointer to the ring's next TRB with its cycle state, skipping every TRB the ring holds;
  - then `CLEAR_FEATURE(ENDPOINT_HALT)` on the device, which resets the device's toggle as well;
  - then the transfer is asked for again.

  A device that refuses to clear its halt is logged and asked again all the same. After three failures in a row, the
  fourth leaves the endpoint until its port changes. An endpoint the controller cannot reset is left at once.
- **The default control endpoint** halts on a STALL as well, and xHCI then refuses every later request on it. A control
  transfer that fails or times out therefore takes the endpoint back the same way before it throws, so the device's next
  request starts on its own.
- **Stopped transfers.** The Transfer Events a Stop Endpoint leaves (codes 26 and 27) are the driver's own doing and
  dropped. An event of a control endpoint that names none of the current request's stages is a request's that ended
  before, and dropped too.

## 5. Measured

**QEMU's devices** (11.1.0, read in `hw/usb/` and seen in the runs):

- `usb-hub` is a USB 1.1 hub at full speed (0409:55aa): 8 ports, characteristics 0x000a (no power switching unless
  `port-power` is set), 2 ms power-on time, a status change endpoint of two bytes at bInterval 255. A port reset sets
  the reset's and the enable's changes together. A hub's own reset leaves every port powered and gives a connected port
  its connection change.
- `usb-kbd` answers its report descriptor (63 bytes, the boot layout without Report IDs), `SET_PROTOCOL`, `SET_IDLE`,
  `GET_REPORT` and `SET_REPORT`, and stalls `CLEAR_FEATURE(ENDPOINT_HALT)`, which `dev-hid.c` does not serve. Behind the
  full-speed hub it runs at full speed with its full-speed descriptor (endpoint 0x81 of 8 bytes at bInterval 10).
- QEMU's xHCI finds a device by its root port and route string as a path (`xhci_lookup_uport`: root port 6, which is the
  bus's second USB 2 port, with route 1 is the bus port "2.1"). A STALL leaves the ring's dequeue pointer at the failed
  transfer and the endpoint Halted. Reset Endpoint of an endpoint that is not Halted, and Set TR Dequeue Pointer of one
  that is not Stopped, complete with a Context State Error. Configure Endpoint requires the slot's add flag and refuses
  the default endpoint's.
- QEMU gives a key event to the keyboard realized last: `hid_init` activates each keyboard's input handler, and a removed
  device's handler goes with it. The runner therefore types on the keyboard it plugged in last. Each key line of the
  driver names the keyboard's port, so the log shows which keyboard typed.
- `device_del` of a hub removes the devices on its ports as well: the hub's unrealize unregisters its ports, whose
  devices go.

**The gate.** `runtime-display` boots with the keyboard on the bus's first port (root port 5). The runner then acts:

1. it types the terminal probe's line on that keyboard;
2. once `display_check` asks for its line, it plugs `usb-hub` into the bus's second port (root port 6);
3. once the driver watches the hub's ports, it plugs `usb-kbd` into the hub's first port (6.1);
4. once that keyboard reports keys, it types the check's line on it;
5. once the check echoed the line, it unplugs the hub, which takes the keyboard with it;
6. it types PowerShell's commands on the first keyboard again.

The scenario requires the hub's and the keyboard's lines, `key 31 down (port 6.1)` for the check's `s`, both detaches
and `key 42 down (port 5)` for the first command's Shift. The screendump at the last prompt equals the host's frame,
as in H2.1.

| ISA | `runtime-display` | Key transitions logged |
| --- | --- | --- |
| x64 (container), MSI-X | passed: the hub at root port 6 and the keyboard at 6.1 attached and detached, `s` typed on 6.1, the commands on 5 | 160 |
| ARM64 (container), INTx | passed, the same lines | 160 |
| riscv64 (container), INTx | passed, the same lines | 160 |

`runtime-services` booted `runtime-devices` with the new services on the three ISAs as well.

**Host tests.** `UsbBusTests` run the core over `FakeUsbHost`, which answers as QEMU's devices do. They cover:

- a root keyboard by its report descriptor, with no `SET_PROTOCOL`;
- a hub with a keyboard below it, and keyboards that come and go on a hub's port and on a root port;
- a hub that goes with its devices, the lowest first;
- a stall taken back, `CLEAR_FEATURE` refused as QEMU's keyboard refuses it, the fourth failure leaving the endpoint,
  and an endpoint that cannot be reset;
- the boot protocol after a failed report descriptor;
- the translator of a high-speed hub two tiers down, and the route string's last tier;
- a device that is neither a hub nor a keyboard;
- the Slot Context's fields.

`HidReportDescriptorTests` read QEMU's keyboard, a TinyUSB composite (keyboard with Report ID 1 beside a consumer
control with Report ID 3), a bitmap keyboard of 98 keys and a mouse, and refuse nine malformed descriptors.

## 6. What is not yet

- **High-speed hubs and their translators** are tested on the host alone: QEMU has no high-speed hub, so the TT fields
  and the TT Think Time reach no controller in a gate. VMware's two hubs (0e0f:0002, H2.1 §3) are the first to try in
  H5.
- **SuperSpeed hubs.** A USB 3 hub on a USB 3 port asks for the SuperSpeed hub descriptor (0x2A) and its own port
  status; the core asks for the USB 2 one and leaves the hub with the failure logged. Its USB 2 half, on the companion
  USB 2 port, enumerates as a high-speed hub.
- **A halted endpoint in the guest.** QEMU offers no way to make a running keyboard stall its interrupt endpoint, so the
  recovery runs in the host tests alone. The default control endpoint's recovery runs wherever a device refuses a request.
- **The PocketTerm35's keyboard** (RP2040) is measured on the device (H0.3); the TinyUSB composite of the tests is how
  such firmware commonly describes itself, not a measurement.
- **Report descriptors beyond 1024 bytes** are cut at the control buffer and then fail to parse, which leaves a boot
  keyboard to the boot protocol and any other keyboard unserved.
- **Keyboard LEDs** (output reports), suspend and remote wakeup, and the hub's over-current beyond acknowledging it.
- **Several controllers** and **USB storage**, as in H2.1.
