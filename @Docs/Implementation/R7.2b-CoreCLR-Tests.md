# R7.2b — Slices of CoreCLR's src/tests in the guest

R7.2b runs slices of upstream's runtime tests (`src/tests`) for the JIT, the GC and exception handling in the guest
under CoreCLR, on both ISAs.

```
[CORECLR-TESTS] CoreCLR's tests on x86_64: all 52 runs exited with 100
[CORECLR-TESTS] CoreCLR's tests on aarch64: all 52 runs exited with 100
```

Those 52 runs cover 258 tests of the JIT in two merged groups and 50 process-isolated tests of the GC and of exception
handling. No test failed. The JIT groups hold 31 process-isolated tests they cannot start, and 9 tests are left out
with a reason.

## Building the tests for witos

`src/tests/build.sh <arch> Release -os witos -skipnative -skipgeneratelayout -test:<group>.csproj` builds a merged test
group and the test projects it references:

- **managed only** (`-skipnative`);
- **without upstream's Core_Root layout** (`-skipgeneratelayout`), whose place the guest's package takes.

Its restore asks for `witos-<arch>`, which the SDK's own identifier graph does not know. The build takes the witos
tree's graph through `RuntimeIdentifierGraphPath`, as a program's project does (R2.3b). `runtime-witos` builds the
groups of `build/runtime/coreclr-tests.json` after the portable application of R6.

## How the tests run

Upstream groups most tests into merged test runners: one assembly whose generated `Main` runs every test merged into it.
It prints `Passed test: <name>` or `Failed test: <name>` for each, writes three log files into the current directory and
returns 100 whatever its tests did. The selection has two kinds of entries.

- **`groups`** are merged runners the guest runs whole. They are `JIT/Methodical/Methodical_d1` and `_r1`: the
  methodical JIT tests in debug and release code, 289 tests between them.
  - `tests/User/coreclr_tests_runner.c` starts each group under upstream's `corerun`, in `/dev/shm`, the directory a
    process writes in (R7.2a).
  - `TestExclusionListPath` names the tests left out, which the group skips.
  - `runtime-witos` reads each test's line from the log.
- **`standalone`** are merged runners whose process-isolated tests the guest runs one by one: `GC/GC` and
  `baseservices/exceptions`.
  - A merged runner starts such a test through its shell script, and WitOS has no shell. It prints `Test executable …
    not found, skipping.` and reports the test passed.
  - So the tool reads each script for its assembly (`ExePath`), its default arguments (`CLRTestExecutionArguments`) and
    its expected exit code (100 for every one of them).
  - The runner starts each test in its own directory, as the script changes to it, and requires 100.

The report, `artifacts/runtime-witos/coreclr-tests-<arch>.json`, has three parts:

- the passed and failed tests of each group;
- each process-isolated test's result;
- the process-isolated tests the groups could not start, counted apart from the passes.

A failed test fails `runtime-witos`. So does an exclusion with no reason, or one that names a process-isolated test that
does not exist.

## Found and changed

| Found | Cause | Change |
| --- | --- | --- |
| Both JIT groups faulted in nested exception handling (`throwinfinallynestedintry_30`, 30 levels deep, faulted at the 16th). | A process's first stack was 256 KiB, one object of 64 pages, where Linux gives 8 MiB and Windows 1 MiB. A merged runner runs every test on the main thread. | The process manager maps a 2 MiB first stack as eight objects at adjacent addresses. A new flag of `THREAD_CREATE`, `WIT_THREAD_STACK_ADJACENT`, makes the thread's stack the run of adjacent committed writable reservations that ends with the one under its stack pointer. `THREAD_QUERY` reports the whole run, so musl's `pthread_getattr_np` and CoreCLR see 2 MiB. |
| Groups and allocation tests ended part way, with exit code 0. | A system layer process had a tick budget of 3000 ticks, 30 seconds of processor time. `PROCESS_QUERY` reported a process its budget ended as `EXITED` with code 0, which `waitpid` read as success. | The budget is an hour of processor time (`WIT_PROCESS_TICK_BUDGET` 360000). `PROCESS_QUERY` reports such a process as `BUDGET` (4), and the libc's `waitpid` reports it as killed by `SIGXCPU`, as Linux ends a process past its CPU limit. |
| Each test's output reached the log a character at a time, every character prefixed by `[USER] `. | The merged runner records the console and writes it one character at a time, and every `DEBUG_WRITE` took the prefix. | The kernel gives the prefix to a write that starts a line of the console, not to one that continues a line. |
| Groups failed to load `xunit.assert`. | Upstream's Core_Root carries the test build's dependencies. | The package takes every library the tests reference, from the framework or from the test build's `TargetingPack`. |
| Process-isolated tests reported usage errors. | Their scripts give them default arguments. | The runner passes the arguments the script names. |

The two kernel changes, the `BUDGET` state and the `STACK_ADJACENT` flag, are additive, so ABI-1 is 1.1. The processes
fixture checks both: a third child spins on a stack of two adjacent objects until its tick budget ends it, `THREAD_QUERY`
reports the run of both, and an unknown flag is refused. `process_init.c` checks that the main thread's stack holds
2 MiB.

## Left out, with the reason

| Test | Reason |
| --- | --- |
| `stackoverflowtester`, `unhandledTester` | Each starts a process. `System.Diagnostics.Process` is unsupported (RFC 0015 §8). |
| `Collect_Optimized_2`, `Collect_Optimized_3` | Each reads `Process.GetCurrentProcess()`. |
| `Callback_Svr` | It needs the server GC, which its script sets through `DOTNET_gcServer`. One processor schedules threads until phase P. |
| `ReliabilityFramework` | It writes its logs into its own directory, which is the read-only package. |
| `460373` | It keeps 500 MB live, past a process's page quota (256 MiB before N2.2) and the guest's 512 MiB. |
| `494226` | It allocates until the GC's hard limit, where upstream's GC with background collection may creep to the out-of-memory end in full compacting collections, on Linux too; under TCG a creep outlives the tick budget (P6, `P6-GC-Cache-Size.md`; on riscv64 alone since V2.4). |
| `Refresh` | It calls `GC.RefreshMemoryLimit`, which the GC turns off under `DOTNET_GCTotalPhysicalMemory`, the knob the root task sets for every process since N2.2. |
| `gettotalmemory` | It reads the physical memory from `/proc/meminfo`, which WitOS does not have, and so asks for 2 GB. On ARM64 the GC commits the process's whole quota before the allocation fails, and the runtime then has no memory to raise `OutOfMemoryException`. |
| `NoGC`, `LargeObjectAlloc` | Both fault in the GC's handle table while freeing a handle (`TableFreeSingleHandleToCache`). `NoGC` always faults there, after it starts no-GC regions of 200 MB beside its heap. `LargeObjectAlloc` faults only now and then, and passes when it runs alone. This is an open question (see below). |

## Open

- **The fault in `TableFreeSingleHandleToCache`.** It always happens in `NoGC` and only now and then in
  `LargeObjectAlloc`, at the same instruction with a different bad pointer each time. On ARM64, `LargeObjectAlloc` once
  faulted in JIT-compiled code instead. Both tests allocate heavily and run a worker thread beside the main one. A
  failed commit at the page quota is one candidate cause. A register the libc's signal path does not preserve when the
  GC suspends a thread is another. Neither is shown yet.
- **The page quota and the GC's view of memory.** The GC sizes itself by the guest's physical memory (`sysinfo`), while
  a process commits at most 256 MiB. Upstream's large-memory tests then meet the quota before the GC expects to run out.
  N2.2 answers it: a process may own 1 GiB, and the root task gives the GC the smaller of that and the memory free when
  the system started (`DOTNET_GCTotalPhysicalMemory`). The knob turns `GC.RefreshMemoryLimit` off, so `GC/API/Refresh`
  leaves the selection on x64 and arm64, the ISAs upstream builds it for: an exclusion names its architectures where
  upstream's build has the test on some alone (V2.4). The exclusions that name 256 MiB were measured before N2.2.
- **The JIT groups' 31 process-isolated tests** do not run, since their merged runners start them through a script. A
  later slice can run them as `standalone` tests.
