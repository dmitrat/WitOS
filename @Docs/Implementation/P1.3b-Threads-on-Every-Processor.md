# P1.3b — threads on every processor

Plan step P1.3, second half (phase P, `P1.0-SMP-Inventory.md` section 6; P1.3a gave each processor its entry state
and tick): the dispatcher runs threads on every online processor, `wit_processors_scheduling()` is the online count,
and the libc's `sched_getaffinity` reports them through `MEMORY_QUERY`. The kernel's self-test suites and the root task
run on two processors in `boot-smp2` on the three ISAs. The layer-2 scenarios on two processors are P1.3c. Made on
2026-10-18.

## 1. The dispatcher on several processors

- A secondary processor enters `wit_user_processor_main` once it is ready and lives in the idle loop on its own stack:
  during a run it starts its tick, looks for a ready thread and resumes it, or halts; between runs it parks — no
  component, its tick stopped (`Parked`, `Ticking`). `wit_user_run` sends every secondary a RESCHEDULE, so that each
  joins the run.
- A thread records the processor that runs it (`WitUserThread.Processor`, the record's former reserved word); `pick`
  skips a running thread and counts it as something an idle processor waits for, so that a processor with nothing to
  run idles instead of reporting a deadlock.
- When a thread becomes ready while another processor idles, the processor that leaves the kernel kicks one idle
  processor with a RESCHEDULE (`leave()`, once per idle period, `Kicked`).
- A doorbell that carried RESCHEDULE and interrupted user mode enters the dispatcher (`wit_user_reschedule`): the
  thread's frame is saved, it becomes ready and the processor dispatches — which leaves a suspended thread, delivers a
  pending activation, and leaves a component another processor ended.
- Each processor's tick charges the component it runs (P1.3a's tick, `wit_user_is_active()` now meaning that a run is
  on); an idle tick charges nobody while a thread runs elsewhere (`idle_can_wake`).

## 2. The lock goes on the frame's stack

P1.2 released the kernel lock in `leave()`, before the architecture's return. With threads on several processors that
leaves a window: the processor still runs on the kernel stack of the thread it left ready or waiting, and another
processor that takes the lock may resume that thread, whose next entry writes its frame where the first processor's
return path still runs. The lock now goes in the architecture's return to a frame, once the stack pointer is the
frame's (`wit_cpus_release`, called by `wit_x64_restore_context`, `wit_a64_resume_frame` and
`wit_rv64_resume_frame`); `wit_user_run` releases it on the host's stack when the run returns, and the idle loop on
the processor's own stack around its halt.

The lock also became fair enough to share (`wit_cpus_lock`): a processor that waits marks itself, and the holder that
releases the lock while others wait takes it again only after one of them took it. The SMP fixture's two spinning
threads, one calling the kernel in a loop, never let the second processor in before: the first took the lock back the
moment it released it — on hardware nothing makes a compare-and-exchange fair, and under QEMU's round-robin TCG the
waiter runs only once the holder's slice ends, mostly inside the kernel. A request served while waiting may take the
lock itself (a RUN of the self-tests), so the mark counts its nesting.

## 3. Ending a component another processor runs

A component ends (`end()`: an exit, a fault, a budget, `PROCESS_KILL`, the root's end) in three steps:

1. Every other processor that has it active gets a RESCHEDULE. A request returns once the target took the doorbell,
   so when the last one returns none of them runs the component's user code any more — the guarantee capabilities
   need before its references go.
2. Its threads end and its references go (`settle`), as before.
3. Its address space stays until no processor has it active. A processor that enters the kernel for a component that
   ended under it abandons the entry (`abandon()`: a call, a tick, a device line after its delivery, a fault, a
   doorbell) and leaves the component (`drop_component`: the kernel's root, no TLS); the idle loop and `pick` leave it
   too; the last processor to leave it retires it (`retire`), which tears the space down.

The root's end ends every created process the same way. The boot processor ends the run (`finish_run`): it waits,
without the lock, which the others need, until every secondary left what it had active and parked, then requires that
no created process survived and returns to the host. A root that ends on a secondary kicks the boot processor, whose
idle loop ends the run.

## 4. Shootdown, code, suspension and contexts

- **Shootdown**: `wit_arch_page_invalidate` drops the translation where the space is active on the calling processor
  and, on x64 and riscv64, whose INVLPG and SFENCE.VMA are local, on every other processor that has the space active
  by an INVALIDATE request (`wit_user_space_shootdown`, `wit_cpus_invalidate`), which returns once the target dropped
  it. ARM64's TLBI VAAE1IS reaches every processor of the inner shareable domain, and is now issued whatever space is
  active locally.
- **Code**: `wit_user_space_publish_code` (`CODE_PUBLISH` and an image's creation) publishes on the calling processor
  and then on every other by a PUBLISH request (`wit_cpus_publish_all`), since RISC-V's FENCE.I is local and a thread
  may run anywhere; `CODE_PUBLISH` no longer refuses several processors.
- **Suspension** (`THREAD_SUSPEND`) counts as before and kicks a target another processor runs, which leaves it at
  once; an **activation** kicks it too, so that it is delivered now rather than at the target's next tick.
- **Contexts**: a target another processor runs has a stale saved frame. `THREAD_CONTEXT_GET` and `SET` of a suspended
  one run again once the caller is dispatched anew (`WIT_USER_CALL_RESTART`, an internal status: the syscall layer puts
  the number and the arguments back in their registers and the PC on the call instruction,
  `wit_arch_frame_restart_call`, and yields); `GET` of an unsuspended one is `BUSY` — RFC 0011 section 7.3 requires the
  target to be suspended or the caller, which one processor never had to enforce. The root task's mechanism check
  accepts `BUSY` there. `CONTEXT_PROFILE` no longer refuses several processors.

## 5. Tests that counted one processor's preemption

The self-tests' assertions that counted preemption on one processor keep their thresholds there and drop them on
several, where threads run side by side (AGENTS.md: keep preemption assertions diagnostic): the thread suite's timer
switches, the active timeout's preemption and idle ticks, the endpoint wait's parks. The processor fixture's
`Current` is any online processor; the processor self-test requires the scheduling count to be the online count.

## 6. The acceptance

`tests/User/Fixtures/smp.c` with `tests/Kernel/user_smp_tests.c`, in every self-test boot:

- `User.SmpThreads`: the first thread and one it creates spin on `PROCESSOR_QUERY` until together they saw every
  online processor (two at most) within 40 ms, the fixture's tick budget being ten ticks that both processors charge;
  they see `0x1` with one processor and `0x3` in `boot-smp2` on each ISA.
- `User.SmpShootdown`: a thread reads a page in a loop while the first thread, spinning beside it, protects the page to
  no access; the reader faults on the page (`wit_test_faulted`, the reader's index, the page's address), which a reader
  on another processor reaches only through the shootdown; the first thread checks that the reads stopped.

## 7. What ran

In the Linux host's image, with the final code:

- `test --arch x64`: PASS, all 27 scenarios; `boot-smp2` runs the user suites, the SMP fixture and the root task on
  two processors (`User threads saw processors: 0x3`), the other scenarios on one as before.
- `test --arch arm64`: PASS, all 21 scenarios; `test --arch riscv64`: PASS, all 21; `0x3` and the shootdown in
  `boot-smp2` on both.
- `release` on the three ISAs: `release-128`, `release-512` and `release-display-256` pass.
- `runtime-terminal --arch x64`: PASS, 20 checks, on one processor.

Before the lock's handoff, the x64 spin fixture saw `0x1` alone: the second processor took threads in the user
suites, but never the lock while the first thread called the kernel in a loop. The handoff then changed the timing of
the endpoint wait test, whose parks one processor guaranteed and two do not.
