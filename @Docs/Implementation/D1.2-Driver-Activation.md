# D1.2 — The device manager starts a driver and moves the device to it

D1.2 completes D1, the device manager of M4. The device manager matches a driver to a device, acquires the device,
starts the driver through the process manager, and moves the device to it. The driver becomes the device's holder and
proves the capability it received. Both ISAs pass.

```
[DEVICES] Device discovered: Class: BlockStorageController, Provider: Virtio, DeviceId: pci/00:02.0/1af4:1001, Regions: 4, Lines: 1
...
[VIRTIO-BLOCK] driver of pci/00:02.0/1af4:1001: holds the device, its configuration space reads 1af4:1001, as descriptor 2 names it
[DEVICES] driver /system/Drivers/VirtioBlock of pci/00:02.0/1af4:1001: ready
[DEVICES] device manager on X64: 7 devices discovered, 1 drivers ready, DMA isolation: none (no IOMMU), ready
[DEVICES-INIT] /bin/init started after the device manager answered
```

This meets points 3 and 4 of M4's definition of done (Implementation Strategy §45): a driver is selected, and it
receives narrow capabilities, which are one device and none of the table. Point 5, a basic I/O operation, is D2's.

## The kernel: a device may change its process (ABI-1 1.2)

K3 made a device handle process-bound: the kernel refused to deliver it to another process (K5.2c). ADR 0025 needs
the device manager to move a device to a driver, so the rule now has one exception.

- `CHANNEL_RECEIVE` in another process delivers a device handle when the message holds its origin's last reference
  to the device. At that point no handle, binding or pin of the origin's refers to the device, and the origin still
  holds it.
- At delivery the holder changes. The origin's reference and ownership go, the receiver's begin, and the device is
  still held by one process at a time (`wit_user_device_movable`, `wit_user_device_adopt`).
- A device its origin still refers to stays queued with `UNSUPPORTED`, as before. A dropped message gives the device
  back to its origin, and an origin's end voids it.
- Interrupt bindings and pins stay process-bound. A driver makes its own.

The change is additive: what was refused is now delivered under the condition above. ABI-1 is 1.2.

**The test.** The device fixture's new mode `User.DeviceMove` runs on both ISAs. The fixture moves the virtio block
device to a child process, whose program receives a message of one handle, calls `DEVICE_MEMORY` on what it
received and reports both statuses.
- While the fixture keeps a duplicate, the child's receive is `UNSUPPORTED`. The child's end drops the message, and
  the fixture's duplicate keeps the device until it closes.
- With the last reference, the child receives the device and maps its configuration region. The fixture cannot
  acquire the device while the child holds it, and can again after the child's end.

The child sleeps after its report, instead of spinning, because a spinning child spends the tick budget it took from
the fixture.

## The system layer

- **`witos_manager_spawn`** (`witos/spawn.h`, `libwitos/manager_client.c`) is the process manager's client that
  grants the new process a capability, which the libc's `posix_spawn` never does. It builds the libc's spawn request
  and sends it with the grant as the third handle.
- **`witos_device_acquire`** and **`witos_device_memory`** join `witos/capabilities.h`.
- **The driver protocol** (`witos/driver.h`). The device manager's start carries the device's descriptor in its
  bytes and the device handle in its one handle slot, 248 bytes in all. The driver answers with a `WitServiceStatus`.

## The managed side

- `OutWit.OS`:
  - `Device.Acquire` and `Device.Memory`;
  - `Channel.Create`;
  - `ServiceLauncher.Start` (namespace `Execution`), which moves the grant into the new process's start message;
  - `ServiceStatus`, which moved here from the device manager because the driver answers with it too;
  - `DriverStart`. A descriptor read from the table now keeps its bytes (`DeviceDescriptor.Bytes`), and
    `DeviceTable.ParseDescriptor` reads them back.
- **The device manager.** `Drivers/DriverTable.cs` maps a provider and a contract to a driver program. For now that
  is Virtio's `BlockStorageController`, served by `/system/Drivers/VirtioBlock`. `Drivers/DriverActivation.cs` then
  runs one activation:
  - it acquires the device and creates a channel;
  - it sends the start with the device, before the driver runs;
  - it starts the driver with the other end as its grant and the device's identity as its argument;
  - it waits for the driver's answer.

  A device without a driver stays in the table. The device manager keeps each driver's channel and process.
- **The driver** (`src/Services/Drivers/VirtioBlock`) takes the start and the device. It maps the device's
  configuration region through `DEVICE_MEMORY`, requires that the region's first word is the identity the descriptor
  names, answers that it is ready, and serves its channel until the device manager closes it.

`runtime-witos` publishes both services. The `runtime-devices` scenario's package carries
`/system/Drivers/VirtioBlock`, and the scenario requires the driver's line and the device manager's report of it.

## Limits kept explicit

- The device manager starts its drivers one at a time and does not restart one that ends. RFC 0007 §106–107's restart
  comes with the lifecycle work.
- The driver proves its capabilities and does no I/O. D2 binds the device's line, pins memory for DMA and reads the
  disk.
