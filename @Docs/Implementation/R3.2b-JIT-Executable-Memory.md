# R3.2b — Executable memory for the JIT, and the first managed Main

[R3.2a](R3.2a-PAL-Prerequisites.md) took CoreCLR's `coreclr_initialize` as far as the JIT's executable memory. This
slice gives the system layer that memory. With it, upstream's `corerun` runs a managed `Main` through the JIT on both
ISAs:

```
[CORERUN] managed Main through the JIT on X64
[CORERUN] managed Main through the JIT on Arm64
```

This completes R3.2.

## Why shared memory

CoreCLR turns W^X on by default. It writes code through a writable view and runs it through an executable view of the
same pages; this is its double mapper (`minipal/Unix/doublemapping.cpp`). On Unix that mapper needs a shared memory
file:

- `memfd_create` on Linux;
- `shm_open(SHM_ANON)` on FreeBSD;
- POSIX's `shm_open("/shm-dotnet-<pid>")` anywhere else, `witos` included.

It sizes the file with `ftruncate` and maps windows of it with `MAP_SHARED`. Without such a file, CoreCLR falls back to
read-write-execute pages. WitOS never grants those (RFC 0011 §7.2), and the RFC already names the intended way: a JIT
maps one memory object twice.

So the libc provides POSIX shared memory over memory objects, and CoreCLR's existing POSIX path works unchanged. No
runtime patch is needed.

## Shared memory within the process (`shared.c`)

- **Names and descriptors.**
  - musl's `shm_open` opens `/dev/shm/<name>`. `open` with `O_CREAT` creates a file there, `O_EXCL` refuses one that
    exists, and `O_TRUNC` empties it.
  - `unlink` (`shm_unlink`) takes the name away. The file lives on while a descriptor or a mapping refers to it.
  - `memfd_create` makes an anonymous file and honours `MFD_CLOEXEC`.
  - Each of these returns a descriptor of the file. `dup` shares it, `fstat` reports a regular file of its size, and
    `ftruncate` sizes it, up to 16 GiB.
- **Chunks.** A file is a sequence of chunks. Each chunk is one anonymous memory object of `WIT_MEMORY_OBJECT_PAGES`
  (64) pages, created zeroed the first time a mapping shows any of it. The file holds the chunk's handle until the file
  ends.
- **Mappings.**
  - `mmap` with `MAP_SHARED` maps one object window per chunk it covers, at consecutive addresses. Every mapping of the
    same offsets therefore shows the same pages.
  - A view may be `READ|WRITE` or `READ|EXECUTE`. The chunk handle carries both rights, and `MEMORY_PROTECT` keeps
    each mapping within them.
  - `mprotect` splits a chunk's mapping at the ends of its range, so every mapping keeps one protection.
  - `munmap` or `MAP_FIXED` over part of a chunk's mapping maps the rest again as it was.
  - The libc's mapping table has a kind for these mappings, which holds a reference to the file.
- **What is refused:**
  - reads and writes of the descriptor (`EINVAL`), since a shared memory file is used through its mappings;
  - `MAP_PRIVATE` of a file (`ENOSYS`);
  - a mapping past the file's end (`ENXIO`);
  - a writable mapping through a descriptor opened read-only (`EACCES`).

  A file never crosses a process.

`libc_hello.c` checks the facility on both ISAs:

- `shm_open` creates a file, `O_EXCL` refuses it once it exists, and `shm_unlink` takes the name.
- `ftruncate` and `fstat` agree on the size.
- Two mappings cross the boundary of two chunks and show the same bytes.
- Code written through the writable view runs through the executable one, after `__builtin___clear_cache`.
- `mprotect` and `munmap` of part of a chunk's mapping leave the rest working.
- The refusals above hold.
- `memfd_create`'s file keeps its mappings after its descriptor closes.

## The kernel

- **EL0 cache maintenance on ARM64.** The JIT publishes its code with `__builtin___clear_cache`. In CoreCLR's images
  that is compiler-rt's `__clear_cache`, which reads `CTR_EL0` and issues `DC CVAU` and `IC IVAU` at EL0. The kernel
  now sets `SCTLR_EL1.UCT` and `UCI`, as Linux does. These operations act only on addresses EL0 may read. `DC ZVA`
  stays refused (DZE). `CODE_PUBLISH` remains for code mapped from the package.
- **1024 reservations for a system layer process** (`WIT_PROCESS_RESERVATION_CAPACITY`, previously 256). The libc's
  mapping table grows to 1024 entries with it.

  CoreCLR with its JIT had taken 249 of the 256 reservations before musl's dynamic linker loaded `libclrjit.so`. That
  library alone needs 14 package mappings of 64 pages, so `dlopen` failed with `ENOMEM`. The rest were CoreCLR's many
  small reservations, its shared memory chunks and `libcoreclr.so`'s package mappings.

  The teardown's list of a space's mapped objects moved from the kernel stack into a static array, since it now holds
  1024 entries.

## The scenario

`runtime-corerun` (R3.2a) now passes. `runtime-witos` boots it on each ISA after the shared framework is built, and
requires the program's line and the root task's report of status 0. The `runtime-corerun` command boots it again from
the built tree.

Hello World creates 13 chunks, which is 3.25 MiB of executable memory. A boot of both ISAs takes about a minute in the
Linux container.

## Limits kept explicit

- **Chunks are eager.** A chunk's 64 pages exist from the first mapping of any of them, and they stay until the file
  ends. CoreCLR's `ReleaseDoubleMappedMemory` zeroes them, as on Linux, where the file keeps its pages too.
- **Quotas are tight.** A system layer process may hold 32 live memory objects and 64 handles, and the kernel's object
  table holds 64. Hello World needs 13 chunks. Larger programs (R3.3) will raise these quotas with their measurements.
- **Shared memory stays within the process.** There is no `ppoll` signal mask, no `select` and no stat of a
  `/dev/shm` path.
- **Every method is JIT-compiled.** The assemblies for `witos` carry no ReadyToRun code, since crossgen does not target
  `witos`.
