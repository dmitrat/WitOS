# V1.1 — The RISC-V loader: an ELF kernel image as PE32+, booted by EDK II over OpenSBI

Plan step V1.1, the first slice of V1 (the RISC-V kernel), 2026-10-16. The measurement of V0
([V0-RISC-V-Measurement.md](V0-RISC-V-Measurement.md)) decided the image format: the pinned LLVM links no PE/COFF for
riscv64, UEFI loads PE32+ alone, so the kernel and its loader are one position-independent ELF the tool converts. This
slice builds that path end to end and proves it in the guest: the converted image boots under EDK II over OpenSBI on
QEMU's `virt` board, the unchanged UEFI loader reads its own headers, publishes the device tree, reads the boot package,
leaves the firmware and enters the architecture's bring-up, which ends the machine through the board's test finisher
with the success code. The kernel's own initialization — translation tables, traps, the clock, user mode — is V1.2 and
later; nothing of it pretends to work here.

The common kernel — `boot-uefi`, `kernel-boot`, `kernel-foundation`, `kernel-common`, 37 sources — compiled and linked

first slice; the three header additions are the per-ISA constants RFC 0011 §7 provides for (the architecture id, the
context's register block, the transport), each additive.

## 2. The image

The kernel is compiled by the pinned clang 20.1.8 for `riscv64-unknown-elf` with `-march=rv64gc -mabi=lp64d
-mcmodel=medany -mno-relax -fPIE -fno-asynchronous-unwind-tables -fno-unwind-tables` beside the kernel's common options
(`-ffreestanding -nostdinc -fno-stack-protector -O0 -g -std=c17 -Wall -Wextra -Werror`; DWARF in place of CodeView), and
linked by `ld.lld -pie --no-dynamic-linker -z separate-loadable-segments -z max-page-size=4096 -z norelro
--build-id=none -T src/Kernel.Arch.RV64/kernel.ld -e efi_main -Map`. The script starts every section at 0x1000, leaving
the first page to the ELF's headers in the file and to the PE's headers in the converted image, and defines
`__ImageBase` section-relative so that the loader's own header check (`src/Boot.Uefi/image.c`, unchanged) reads the PE
headers of the loaded image through it.

`ElfToPe.Convert` (282 lines; the plan asked for this measurement first) takes a 64-bit little-endian `ET_DYN` for machine
243, makes a section of each `PT_LOAD` segment at its address (a segment that starts in the first page gives that page
up; a writable and executable segment, an unaligned one or an entry outside executable code is refused), reads the
dynamic section's `RELA` table and turns every `R_RISCV_RELATIVE` into a 64-bit base relocation (`DIR64`) with its addend
written in place for an image base of zero (any other relocation type, or one with a symbol, is refused: the firmware
could not apply it), and writes the PE32+: machine 0x5064, subsystem 10 (EFI application), section and file alignment
0x1000, the headers in the first page, `.text`/`.rodata`/`.data` sections with the segments' rights, `.reloc` last and
discardable, an empty import directory. The host test builds a tiny riscv64 PIE with a pointer in data through the same
clang, lld and script and checks the converted image with `System.Reflection.PortableExecutable` and by hand (the
pointer's fixup in the table, its addend the target's RVA).

The release image: the ELF 1,156,368 bytes with its DWARF, the PE32+ 131,072 bytes on disk and 8,040,448 bytes in
memory — the common kernel's static tables (process records, the per-thread kernel stacks of the self-test and release
profiles are the architecture's and do not exist yet) fill the data section's uninitialized part.

## 3. The boot

`riscv64-loader` builds the release scenario's image for riscv64 (no root task: the port has no user space, so
`FatImage` writes the disk without `WITROOT.BIN` and the loader reports "No root task image") and boots it as every
scenario boots: `qemu-system-riscv64 -machine virt,acpi=off -accel tcg,thread=single -icount shift=2,sleep=off -cpu rv64
-smp 1 -m 256`, EDK II's `edk2-riscv-code.fd` and a copy of `edk2-riscv-vars.fd` as pflash, the FAT disk on
`virtio-blk-pci`, `virtio-rng-pci`, the serial to a file. The serial log of the passing boot (1,166 lines):


The firmware applied the base relocations (the image runs at 0x8DB26000, its headers say 0), set each section's memory
attributes by the characteristics the converter wrote (the headers read-only, the code executable, the data writable),
found the device tree (ACPI is off) and the virtio RNG, and left. The loader suite (`BootSuite.Loader`,
`BootValidation.EvaluateLoader`) requires the request's lines in order (the adapter, the device tree, ExitBootServices,
the bring-up's line), exit 33, no `[PANIC]` and no `[EXCEPTION]`; the banner, the boot contract and the kernel's
markers, which come from `wit_kernel_entry`, are not required, since the slice does not reach it. CI runs the command in
the Windows `boot` job (the QEMU package carries `qemu-system-riscv64` and the EDK II images) and in `linux-selftest`
(the Linux QEMU build adds `riscv64-softmmu` to its target list; the cache keys of the built QEMU were renewed). The x64
and ARM64 release boots pass unchanged after the builder's and the FAT image's changes, and the tool's 96 host tests
pass.

## 4. Findings

1. **The firmware's translation outlives ExitBootServices and maps only what the firmware drove.** EDK II's RISC-V
   port runs S-mode with Sv paging over an identity mapping of RAM and of the devices it used (the UART among them).
   The bring-up's first write to the test finisher at 0x100000 took `EXCEPT_RISCV_STORE_ACCESS_PAGE_FAULT` with `stval`
   0x100000, reported by the firmware's trap handler, which stays installed. The bring-up now writes `satp` = 0 (the
   bare physical space, which that identity mapping equals — the image's virtual address was its load address) and
   `sfence.vma` before anything else; V1.2 installs the kernel's own tables (Sv48 by V0's decision) in their place. On
   x64 and ARM64 the kernels run under the firmware's tables until `wit_virtual_initialize`; RISC-V needs the switch
   earlier only because the exit device is not among the firmware's mappings.
2. **The UEFI removable-media name of RISC-V is not an 8.3 name.** `BOOTRISCV64.EFI` needs VFAT long-name entries: two
   entries of 13 UCS-2 characters each before the short alias `BOOTRI~1.EFI`, carrying the alias's checksum. EDK II's FAT
   driver opened it by the long name (`FSOpen: Open '\EFI\BOOT\BOOTRISCV64.EFI' Success`). The x64 and ARM64 disks keep
   one short entry.
3. **QEMU 11.1.0's `sifive,test` carries an exit code in both of its forms.** The device's "fail" (0x3333) and "pass"
   (0x5555) writes take the upper half of the word as the process's exit code, so the finisher reports WitOS's status
   as isa-debug-exit and semihosting do (0x10 → 33, 0x11 → 35) without any QEMU argument; the board's `ExitDevice` is
   empty.
4. **lld places the ELF headers in a loadable segment of their own**, which the converter drops in favour of the PE
   headers; `-z separate-loadable-segments` makes every segment's file offset congruent with its address, so a section
   is its segment's bytes without copying.
5. **The firmware image in the QEMU package is a DEBUG build**: its `DEBUG` output goes to the same serial as the
   kernel's (1,100 of the 1,166 lines). The judge matches lines, not positions, so this costs nothing; a release firmware
   would be quieter.
6. **The EFI calling convention on RISC-V is the psABI**, the compiler's native convention for `riscv64-unknown-elf`:
   `uefi.h` needed no attribute, as on the other two targets.

## 5. What V1.2 inherits

- `wit_virtual_*` (the kernel's translation tables: Sv48, the identity map of usable memory, the storage window, the
  device pages of `wit_platform_boot_devices`), `wit_arch_initialize`, the trap vector and the frames of
  `wit_arch_frame_*`, the clock (`time` CSR and `sstc`), the PLIC behind `wit_platform_interrupt_claim`, the per-thread
  kernel stacks, the processors through SBI HSM — each replacing its stub in `stubs.c`, so that the common kernel's
  entry runs (`wit_kernel_entry`, which the bring-up skips today) and prints the banner; the kernel suite
  `tests/Kernel.rv64` with `tests/Expectations/riscv64-foundation.json`, `boot-128`, and the release suite's judge for
  riscv64, after which `BootSuite.Loader` and the `riscv64-loader` command leave.
- Until the trap vector is the kernel's, a fault in the bring-up prints the firmware's register dump (as the finding
  above shows), which is a usable debugging aid.
- The device tree is published (`WitBootInfo.DeviceTree`), the firmware tables are reachable in the bare space, and
  the boot contract carries 17 memory regions of the 256 MiB board.
