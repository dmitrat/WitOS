# R8.1 — The patch set carried to a servicing release

R8.1 is the first half of R8, the upgrade rehearsal of RFC 0015 §4. It moves the pin from dotnet/runtime `v10.0.8` to
`v10.0.12`, the latest 10.0 servicing release on 2026-10-11, with a tool that carries the witos patch set from one
tag to another. No line of the set was written by hand:

```
The witos patch set from dotnet/runtime v10.0.8 to v10.0.12 (4271d88e0aeb): 1 added, 0 conflicts, 0 gone, 3 merged,
22 unchanged; +180/-22 lines at the pin, +180/-22 carried
```

With the new pin, `runtime-witos` passes every guest gate of phase R on both ISAs, as it did with 10.0.8:

```
[M3] NativeAOT on x86_64: 32 runs passed, 0 failed
[M3] CoreCLR on x86_64: 32 runs passed, 0 failed
[R4] System.Native under CoreCLR on X64: 12 areas passed, 0 failed

```

The same lines come on aarch64. The 11 `try_run` probes answer in the guest as `tryrun.cmake` does on both ISAs, and
the library tests ran 2460 and 2627 tests, as on 10.0.8.

## The tool

`runtime-rebase --tag v<version>` carries the set to another tag of dotnet/runtime. It changes nothing in the
repository unless `--apply` is given.

- **Fetch.** It fetches the pinned commit and the tag into `.tools/upstream/runtime-rebase`, shallowly.
- **Read.** It reads each file's bytes as git stores them. A patch applies to the file's text as `runtime-witos`
  reads it from the tree: without a byte order mark and with LF line ends. The pin holds the bytes, so a file that
  upstream only re-encoded keeps its patch and changes its hash in the pin.
- **Classify.** For each patch of `RuntimeWitos.PATCHES` it compares the file at the pin and at the tag:
  - *unchanged*: the tag's text is the pinned one, so the patch carries over byte for byte;
  - *added*: a file WitOS adds, which the tag still lacks, carries over as it is;
  - *merged*: upstream changed the file, and `git merge-file` merges the patched text, the pinned text and the tag's
    text without a conflict;
  - *conflict*: the merge conflicts, or upstream now has a file WitOS adds. The file is left with its markers as
    `<patch>.patch.conflict` for a person;
  - *gone*: the tag has no such file.
- **Write.** A merged file gets a new patch: the header with the tag's hashes, the purpose as it was written, and a
  `git diff` of the tag's text and the merged one. Before writing it, the tool parses the new patch with
  `UpstreamPatches` and applies it to the tag's exact text. The result must be the merged text, since that is how
  `runtime-witos` will apply it.
- **Report.** The patches and `report.json` go to `artifacts/runtime-rebase/<tag>`. The report lists the files by kind
  and the size of the set in lines it adds and removes, at the pin and carried.
- **Apply.** With `--apply`, a carry with no conflict and nothing gone replaces `patches/runtime` and moves the pin:
  the tag, the version, the commit and the hash of every file the set changes in `build/runtime/runtime.lock.json`.
  `runtime-witos` then proves the new pin on both ISAs.

The tool reproduces this step byte for byte. Run from the 10.0.8 pin with `--tag v10.0.12 --apply`, it writes the
same lock and the same 26 patches as this commit.

## What upstream changed under the set

Three of the 26 files changed between 10.0.8 and 10.0.12. In each, git merged the witos lines beside upstream's.

| File | Upstream's change | The witos lines |
| --- | --- | --- |
| `eng/common/cross/toolchain.cmake` | OpenBSD's rootfs is recognized, and FreeBSD's triple names version 14 (+27/−13 lines). | The `etc/witos-release` marker, the WitOS system and the sysroot's options, moved by up to 14 lines. |
| `src/coreclr/gc/unix/gcenv.unix.cpp` | The GC sizes its processor sets by `minipal_get_cpu_max_possible_count`, and gives `madvise` `MADV_DONTDUMP` and `MADV_FREE` in separate calls (+70/−40 lines). | musl's `<sys/membarrier.h>` and its two-argument `membarrier`, moved by one line. |
| `src/native/corehost/apphost/static/CMakeLists.txt` | The single-file host keeps the runtime's exported symbols with `-u` options (+18 lines). | No GSSAPI or OpenSSL shim, unchanged. |

`minipal_get_cpu_max_possible_count` reads `/sys/devices/system/cpu/possible` under `__linux__`, which the layer-2
triple defines. On WitOS the file does not exist, and the function falls back to `sysconf(_SC_NPROCESSORS_CONF)`,
which musl answers with `sched_getaffinity`. That fallback needs no patch, and nothing emulates `/sys`.

## What the run found

The patch set needed nothing. One of upstream's tests changed under it, and the guest's test runner did not keep up. The
build of the library tests also stopped for a reason that has nothing to do with the release: the day of the restore.

| Found | Cause | Change |
| --- | --- | --- |
| `libs.pretest` failed with NU1903 for `Microsoft.DiaSymReader.Native`. The same build had passed on 10.0.8 hours before. | NuGet's audit reads the advisories published up to the day of the restore. That package, a Windows library of upstream's `externals.csproj`, gained high-severity advisories, and the build treats the warning as an error. | The builds of the pinned tree run with `NuGetAudit=false`, also in R7.3's own PR: the pin fixes upstream's dependencies, and WitOS neither builds that package into anything nor ships it. |
| `GC/API/GC/GetConfigurationVariables` failed with 101: "The expected value of GCHeapAffinitizeRanges is 1". | In 10.0.12 the test's project gives it an environment variable (`CLRTestEnvironmentVariable` `DOTNET_GCHeapAffinitizeRanges=1`), which its script exports. The runner of R7.2b took a script's arguments and exit code, but not its variables. | `runtime-witos` reads the variables a script exports at the start of a line, and `coreclr_tests_runner.c` gives them to the test's process, written before the assembly in `/tests/standalone`. A value that would need a shell is refused at build. |
