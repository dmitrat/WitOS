# H5.2 — The PC's PS/2 keyboard

VMware gives a guest its keys through its PS/2 keyboard, from the VNC server and from the Workstation console alike, and
none through the USB keyboard it also presents ([H5-VMware-Session.md](H5-VMware-Session.md) §1.4). So WitOS on VMware
needs the i8042. [ADR 0031](ADR-0031-PC-PS2-Keyboard.md) decided the shape. This step implements it: one ABI-1 call on a
device's port region, the PC platform's descriptor of the controller, a driver service on the input protocol, and a
display service that takes two keyboards.

## 1. `DEVICE_PORT` (ABI-1 1.7)

`DEVICE_PORT(device, WitDevicePortRequest, 32)` is call 87 of the device family (`src/Kernel/user_device.c`,
`wit_user_device_port`). The request is `{ Version, Size, Region, Operation, Width, Offset, Value, Reserved }`.

The kernel checks the whole request before it touches a port:

- the device handle's `BIND`, the right `DEVICE_MEMORY` and `INTERRUPT_BIND` need;
- the call's size and the request's `Size`; a version other than 1 is `UNSUPPORTED`;
- an operation of `READ` (1) or `WRITE` (2), a width of 1, 2 or 4 that divides the offset, a read's zero value, a
  written value that fits the width, and the zero reserved word;
- a region of the device's descriptor; a memory region is `UNSUPPORTED`, since it maps through `DEVICE_MEMORY`;
- the access within the region, and the region within the 16-bit port space.

Then the architecture makes the one access (`wit_arch_port_read`, `wit_arch_port_write`). x64 uses `IN` and `OUT` of the
width. ARM64 and riscv64 have no port space: `wit_arch_ports_supported` is zero there, the call is `UNSUPPORTED` after
the same checks, and `QUERY` leaves the feature bit `WIT_ABI_FEATURE_DEVICE_PORTS` (64) clear. The minor version is 7:
the call, the bus, the device kind, the line kind and the bit are each an addition.

libwitos gives `witos_device_port_read` and `witos_device_port_write`; OutWit.OS gives `Device.PortRead8` and
`PortWrite8`, the widths the i8042 uses.

`INTERRUPT_BIND` takes a line of the new kind `WIT_DEVICE_LINE_EDGE` as it takes a `LEVEL` line. The first boot of
`runtime-devices` showed that it did not: the driver's bind was `UNSUPPORTED`. The mechanism is the same for both kinds.
The kernel masks the line and sets the event on each interrupt, and the driver's `INTERRUPT_ACK` unmasks it. A PIC
latches an edge that comes while the line is masked in its request register, and delivers it once the line is unmasked.
So no key is lost between an interrupt and its acknowledgement.

## 2. The platform's descriptor

The PC platform reads the FADT's `IAPC_BOOT_ARCH` already, for the reset through the 8042. It now describes the
controller as a device of the new legacy bus (`Kernel.Platform.Pc/devices.c`, `describe_i8042`) when:

- the flag names an 8042, or
- the FADT predates the flag (its revision below 3, ACPI 1.0's table), as QEMU's `pc` machine's FADT does. A PC of that
  time had an 8042 whatever its tables said.

| Field | Value |
| --- | --- |
| `Bus` | `WIT_DEVICE_BUS_LEGACY` (3) |
| `Identity[0]` | `WIT_LEGACY_DEVICE_I8042` (1) |
| Region 0 | port 0x60, one byte: data |
| Region 1 | port 0x64, one byte: status and command |
| Line 0 | ISA line 1, the keyboard's, `WIT_DEVICE_LINE_EDGE` (2) |
| Line 1 | ISA line 12, the auxiliary device's, edge |

The descriptor follows the bus's functions and comes before the framebuffer. The boot log prints `Legacy devices: an
i8042 at ports 0x60 and 0x64, lines 1 and 12`. The platform reads nothing of the controller: a status of 0xFF, which an
absent controller reads, is the driver's to find.

## 3. The driver

`OutWit.OS.Hardware.I8042` holds the controller and the code translation. Both are tested on the host against a model
of the controller (`tests/OutWit.OS.Tests/Hardware/I8042`).

`I8042Controller.Open` takes the controller as the firmware left it. It never resets the controller or the keyboard:
the firmware's keyboard works, and VMware drops every key once a guest disables the keyboard's scanning or its port
(H5 §1.4). In order, it:

1. refuses a status of 0xFF;
2. flushes the output buffer, at most 32 bytes;
3. reads the configuration byte and writes it back with the keyboard's interrupt, the translation to set 1 and the
   auxiliary device's clock disable set, and the auxiliary device's interrupt and the keyboard's clock disable clear;
4. enables the keyboard's port (0xAE) and asks the keyboard to scan (0xF4), noting its acknowledgement (0xFA).

OVMF leaves 0x67 on q35: both interrupts, the system flag, the auxiliary clock disable and the translation. Step 3 makes it 0x65.

`ScanCodeSet1` turns set 1's bytes into evdev's key events:

- A code below 0x80 is a press and the same code with bit 7 its release. The main block's codes 1–0x53 are evdev's
  own, which Linux took from set 1. 0x56, 0x57 and 0x58 are `KEY_102ND`, F11 and F12.
- 0xE0 introduces the enhanced keys, which have their own table: the keypad's Enter and slash, the right Ctrl and Alt,
  Print Screen, the cursor and editing blocks, and the Windows and menu keys.
- The shifts a keyboard fakes around an enhanced key (0xE0 0x2A, 0xE0 0x36 and their releases) and the controller's
  answers give nothing.
- 0xE1 starts Pause's six bytes, which the keyboard sends at its press alone. The class reports a press at the first
  byte and a release at the last.
- A press of a key already down is the keyboard's typematic repeat, evdev's value 2. The display's layout types it again.

The service `/system/Drivers/I8042` (`src/Services/Drivers/I8042`) takes the device from the device manager, as every
driver does (D1.2). It reaches the controller through `I8042DevicePorts`: region 0 the data, region 1 the status and
command. It binds the keyboard's line to an event and serves the input protocol (`witos/input.h`) through OutWit.OS's
`InputServer`, as the xHCI driver does.

On each interrupt it reads every byte the controller holds, reports each key to the log (`[I8042] key <code>
down|up|repeat`) and to its client with a `SYN`, and acknowledges the line. A byte of the auxiliary device is read and
left: its interrupt is off, and the console has no pointer. A controller that does not answer is `ENODEV`.

## 4. The device manager and the display

The device manager gives the legacy bus's devices to `LegacyTranslator`. The i8042 is a `KeyboardController` of provider
`Legacy`, `legacy/i8042` in the log. The driver table maps it to `/system/Drivers/I8042`, and `ServesInput` names it
among the keyboards.

The display's start (`WIT_DISPLAY_START`) carries up to two keyboard channels, in slots 1 and 2
(`WIT_DISPLAY_KEYBOARDS`, `DisplayStart.KEYBOARDS`). The device manager passes the input drivers' channels in the
table's order, a virtio keyboard's first. The display service waits on its manager, its client and each keyboard in one
`OBJECT_WAIT`, whose four handles hold that. One layout serves every keyboard, so a modifier on one applies to a key on
the other, as on Linux. A PC with a USB keyboard and a PS/2 one types into the same console with either.

## 5. The runner

`BootRequest.Ps2Keyboard` boots q35 without a keyboard device. QMP's `input-send-event` then reaches the board's PS/2
keyboard, as VMware's keys do. The runner waits for each key's report in the log, as it does for the virtio keyboard's,
by `[I8042] key `. The request is refused off x64 and beside `Keyboard`.

q35 carries its i8042 only with that request: otherwise the runner turns it off (`-machine q35,…,i8042=off`), as it
adds a USB keyboard only when a request asks for one. QEMU's FADT then clears `IAPC_BOOT_ARCH`'s 8042 flag, so the
platform describes no i8042. The first boots of `runtime-devices` showed why. With the i8042
on every q35, every boot of the services had a keyboard. The device manager then started the display service on q35's
VGA framebuffer and made it the terminal's main console. `/bin/init` wrote to the screen, and the runner's typing on the
virtio console reached nobody. A board with a screen and a keyboard has its console on the screen, which is right for a
PC. The gates' boots without a display are headless boards, and stay so. QEMU's `pc` machine keeps its i8042: no
service boots there.

`runtime-commander` runs on the PS/2 keyboard on x64: End, Enter, F3, F5, F10 and text through set 1. It requires:

- the driver's line;
- its configuration line;
- the display's line with `legacy/i8042`;
- `[I8042] key 107 down`, End, an enhanced key behind 0xE0.

ARM64 and riscv64 keep the virtio keyboard. `runtime-devices` asks for no PS/2 keyboard, so its boots have no i8042.

The interrupts fixture (`tests/User/Fixtures/interrupts.c`, `port_test`) checks on every ISA that `DEVICE_PORT` refuses:

- the virtio function's memory region;
- a region beyond the descriptor;
- a width of 3, a read's value and an operation of 3;
- a version of 2 and a short request;
- a duplicate without `BIND`.

Where the architecture has ports, it requires the feature bit, reads the i8042's status, has an access past its one
byte refused (checks 40 and 41), and binds the keyboard's edge line once (`BUSY` the second time).

### 6.1 VMware's first input

On two boots, the first line typed through VMware's VNC after the prompt left no key in the log of either keyboard, and
the second line arrived whole. The first line's bytes did not arrive with the second either, so they never reached
the 8042: VMware dropped them. Typing while another VNC connection took a frame lost nothing. The author's session met
it at the prompt, and H5 §2.2 measured it: with VMware's virtual USB keyboard (`keyboard.vusb.enable = "TRUE"`) the first
second of input after a boot's first key reaches neither keyboard, and without it every key arrives from the first, so a
session's machine goes without the virtual USB keyboard.

## 7. What is not yet

- **The mouse** on line 12: the console has no pointer, and its interrupt stays off.
- **Keyboard LEDs.** Caps Lock's light stays as the firmware left it: the driver sends the keyboard no command but 0xF4.
- **A PC without legacy hardware.** A firmware that clears `IAPC_BOOT_ARCH`'s 8042 flag gets no descriptor, and its USB
  keyboard stays the keyboard, as ADR 0029 decided.
