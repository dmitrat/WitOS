# V1.3 — User mode on riscv64: `ecall`, U-mode frames and contexts, the processes' tables, the ECAM bridge and the shared user suites

Plan step V1.3, the third slice of V1 (the RISC-V kernel), 2026-10-17. V1.2 ([V1.2-RISC-V-Kernel.md](V1.2-RISC-V-Kernel.md))
brought the kernel foundation to riscv64 and left every operation of user mode — the frame of a thread, its contexts,
the translation tables of a process, the launch of a component — and of the secondary harts as a stub that panics by
name. This slice replaces the user-mode stubs, gives the virt board its PCI enumeration, compiles the mechanism fixtures
and the root task for the third ISA, and proves the result in the guest: the self-test kernel of riscv64 runs the user
suites shared with x64 and ARM64 — isolation, threads, waits, exceptions, channels, memory objects, devices, interrupts,
the second thread form, processes, processors, the root task — to `Hello from WitOS` with every expected fault
accounted, and the release kernel starts the root task. The common kernel and the shared self-tests again compiled for
riscv64 without a change; the other harts are V1.4 and still panic by name.

## 2. The frame and the system call

A user thread runs in U-mode with its frame at the top of its own kernel stack, as on ARM64. `wit_arch_frame_create`
builds the frame zeroed with a0 the argument, `sepc` the entry, sp the 16-byte aligned stack top less 16 bytes (the
psABI has no red zone; the zeros above sp end a frame-pointer walk) and `sstatus` for U-mode: SPP clear, SPIE set, FS
initial and UXL as the hart reports it. The trap vector of V1.2 already served both modes through `sscratch`: zero while
the kernel runs, the thread's kernel stack top while U-mode runs. This slice adds the two sides of it.

- **The launch.** `wit_rv64_run_user` saves the host's callee-saved state (ra, sp, s0–s11, fs0–fs11, fcsr and `satp`;
  224 bytes) on the kernel's stack, remembers sp in `host_stack`, switches `satp` to the component's root after a `fence`
  and an `sfence.vma`, and jumps into `wit_rv64_resume_frame`. `wit_rv64_leave_user` disables interrupts, zeroes
  `sscratch`, restores the kernel root and the host state and returns from `wit_rv64_run_user`; the abandoned kernel
  stack belongs to the finished component (K5.2c). `wit_arch_space_switch` changes `satp` for the dispatcher when the
  root differs, with the same fences.
- **The resume.** `wit_rv64_prepare_resume` is the last check before any frame is resumed, from the dispatcher or the
  trap return: a U-mode frame must sit at the top of the selected kernel stack (`wit_arch_select_thread_stack`), and a
  fresh frame takes the thread pointer (below). On the way to U-mode the resume path writes `sscratch` and then clears the
  interrupted thread's load reservation with a dummy `sc.d` to a kernel word: TCG drops a reservation at every trap, but
  the architecture allows one to survive it, and a reservation that paired with another thread's store-conditional after
  a switch would be a wrong success.
- **The system call.** A trap from U-mode whose cause is `ECALL` is a system call (`wit_rv64_user_trap`): a7 is the number
  and a0–a2 the arguments, as `witos/syscall.h` already transported; `sepc` moves past the `ecall` before anything else,
  so that a frame the dispatcher resumes later — or a thread the call suspended — returns after the instruction; the
  status returns in a0 and the value in a1 (`wit_arch_frame_status`, `wit_arch_frame_value`), and
  `wit_arch_frame_prepare_return` sets the U-mode `sstatus` again, since RISC-V has no condition flags to clear. Every
  other synchronous cause is a user fault for the common kernel: the vector and the error are the cause (`scause`), the
  address is `stval` for the memory faults (alignment, access and page faults of instructions, loads and stores) and
  zero otherwise, and the raw state is the frame's `sstatus`; the `[USER-FAULT]` line of a contained fault carries
  `sepc`, `sstatus`, `scause` and `stval`, and the host judge requires SPP clear in each, the error equal to the cause
  and the cause equal to the vector.
- **The callback.** `wit_arch_frame_enter_callback` sets `sepc`, sp (`wit_arch_callback_stack`: 16-byte aligned, 16 bytes
  of call frame, the return address in ra), the U-mode `sstatus`, a0–a2 and ra = 0, so that an accidental `ret` from a
  callback faults at address zero instead of running on.

## 3. The thread pointer

RISC-V's `tp` (x4) is the thread pointer the psABI gives TLS: an ordinary register the thread writes itself, with no
privileged counterpart. The slice keeps the rule of ARM64's TPIDR_EL0 — `tp` is the thread's — and adds one thing the
other ISAs did not need: a thread that has never run must start with the TLS base its creator named, which on x64 is the
FS base the kernel switches and on ARM64 the TPIDRRO_EL0 the trampoline reads. The frame's `Reserved` word marks a frame
no return has resumed yet (`WIT_RV64_FRAME_FRESH`); at its first resume `wit_rv64_prepare_resume` writes the thread's TLS
base into x4 and clears the mark. Afterwards the kernel never touches x4: it is saved and restored with the frame, a
context reports and applies it like every other general register (`wit_arch_context_apply` clears the mark, since the
context's `tp` is the thread's, not the TLS base), `wit_arch_user_tls_settable` is false and `THREAD_SET_TLS` is
`UNSUPPORTED`, as on ARM64. The thread fixture checks both halves: a worker reads its record's TLS base in `tp` before any
call, writes another value, yields and finds it preserved; the entry fixture plants a sentinel in `tp` at `wit_user_start`
and requires it after every return to U-mode (`User.PreemptionState`, `User.ThreadPreemptionAndTls`).

## 4. Contexts and the CPU profile

A thread context is the RISC-V block of `witos/thread_context.h` the V0 decisions fixed: `X[i]` is x(i + 1) — x0 is zero
and absent, so `X[1]` is sp, `X[3]` is `tp`, `X[9]` is a0 — then `Pc`, `Fcsr` and the 32 floating-point registers `F`;
the profile is `WIT_THREAD_CONTEXT_FPREGS`. `wit_arch_context_capture` copies the frame, `wit_arch_context_apply` writes
it back with x0 forced to zero and the U-mode `sstatus`; the mode and the interrupt state are no part of a context. The
validation of `THREAD_CONTEXT_SET` and `EXCEPTION_CONTINUE` holds `Fcsr` within its eight architectural bits — the
accrued exception flags and the rounding mode — with a rounding mode of at most 4, since 5 and 6 are reserved and 7 is
only an instruction's "dynamic"; the exception fixture's privileged-state case sets a reserved rounding mode and requires
`INVALID_ARGUMENT`. No probing is needed: the FCSR bits are architectural, where ARM64 measures the FPCR mask at boot.
`CONTEXT_PROFILE` reports `EnabledState` `WIT_CPU_CONTEXT_FPREGS` (new, 16), `LegacySaveBytes` 256 (the F block), zero
selectors, hardware debug disabled and `FloatControlMask` 0xFF.

## 5. The tables of a process

`page_table.c` is the ARM64 file over Sv48 leaves. A user leaf is `V|R|U|A` plus `W|D` when writable and `X` when
executable, with A and D set by the kernel as the kernel leaves have them (V1.2). A no-access page is an invalid entry
(V clear) that keeps its frame and its software bits: the walker ignores it, and the kernel still knows the page is
committed. The two RSW bits (9:8) say what a leaf is — 0 plain, 1 an OWNED frame, 2 an ALIAS of a memory object's page,
3 an ALIAS of a device region's page (DEVICE) — since a leaf is at most one of these and the base ISA gives a page no
memory attribute (Svpbmt would), so a device page is a plain mapping as on the kernel side. The decoder reports kind 3
as `ALIAS | DEVICE`, because the common kernel marks every device page an alias and `unmap_page` requires one of OWNED
and ALIAS (finding 7.2). A branch of the user's own is valid, no leaf bits and not global; the kernel's branches (root
entry 0 and the high half, copied by `wit_arch_space_install_kernel`) are global, so walks of user tables never enter
them; `wit_arch_page_next` skips absent tables for the K9 teardown; `wit_arch_page_invalidate` issues `sfence.vma` for
the address when the space's root is installed, since one processor and no ASIDs mean an inactive root is flushed when
it is installed.

## 6. The board: the ECAM bridge

`wit_platform_devices` now enumerates the PCI functions behind the generic ECAM host bridge the device tree describes
(`pci.c`) and then appends the firmware's framebuffer (C2.1). The reader is the ARM64 board's walk with the PLIC's cells
in place of the GIC's and one difference: the bridge is found at any depth, since QEMU's riscv64 virt board puts
`pci@30000000` under `/soc` (depth 3) where the ARM64 board has `pcie@10000000` at the root. The tree's `reg` names the
ECAM window (0x30000000, 256 MiB), `bus-range` 0–255 and `interrupt-map` 16 entries of 6 cells — the child's three
address cells, its pin, the parent's phandle (the PLIC, `#address-cells` 0, `#interrupt-cells` 1) and the source — under
`interrupt-map-mask` `0x1800 0 0 7`, so that a function's INTx line is the PLIC source its slot and pin name directly:
`0x20 + (slot + pin - 1) % 4`, lines 32–35, which `wit_platform_line_valid` admits and the PLIC code of V1.2 enables,
claims and completes. The ECAM pages are mapped on demand through `wit_arch_map_device_page` as the FDT pages are (only
when `wit_virtual_view` says unmapped); the BARs are read as the ARM64 reader reads them, with the firmware's
assignments kept. The two readers are one layer's worth of code to share once a third board arrives.

The 256 MiB boot sees three functions: the host bridge (1b36:0008, the configuration region alone), the virtio block
device (1af4:1001, four regions, one line) and the virtio entropy device (1af4:1005, four regions, one line). The device
suite acquires the block device, maps its regions through `DEVICE_MEMORY`, binds its line, pins a window, reads sector 0
through virtio and sees the interrupt (`Interrupts delivered: 1`), and the device move of ABI-1 1.2 passes between two
components, all with the fixtures' sources unchanged.

## 7. The fixtures, the root task and the tool

### 7.1 One source for three ISAs

Each fixture had an x64 and an ARM64 branch where it needs assembly: the entry with the sentinels, the system-call
wrapper, the privileged and undefined instructions, the bad return, the preemption spin, the thread workers, the fault
sites of the exception fixture, the children of the device and process fixtures, the barrier, the code the memory-object
fixture publishes. The slice adds the riscv64 branch as the `#else` of each: a7 and `ecall`; sentinels in s2–s5 and fs0
and in `tp` since the entry; `csrci sstatus, 2` as the privileged instruction and `csrr satp` as the privileged register
(both illegal in U-mode: cause 2); `unimp` as the undefined instruction; sp = 0x0000800000000000 as the bad return;
`fence` as the barrier; `lui a0, 1; addi a0, a0, 0x234; ret` as the published code; `amoadd.d` in the wait fixture; the
exception fixture's marker in s6 (`X[21]`), its fault a load from address zero (vector and error 13), the context's sp
`X[1]`. The root task names its ISA (`started by clang 20.1.8 for riscv64`) and reads a suspended thread's sp and pc from
`X[1]` and `Pc` and redirects it through `Pc` and a0 (`X[9]`). `tests/Kernel.RV64/user_arch_tests.c` gives the shared
user suites their fault table: a load from a page U-mode may not reach is a load page fault (13), a store a store page
fault (15), an instruction fetch an instruction page fault (12) — kernel pages lack U, unmapped and no-access pages are
invalid, a read-only page lacks W, a data page lacks X — and a supervisor CSR or `unimp` an illegal instruction (2);
the record carries the cause as both the vector and the error, and `wit_test_user_fault_state` reads the pc from `sepc`
and the mode from SPP.

### 7.2 Building for riscv64

Two things the other ISAs never needed. Clang refuses `-fno-plt` for RISC-V as an unused argument, which `-Werror` makes
an error, so `UserImage` omits it there and keeps `-mcmodel=medany`, since the image window lies above 2 GiB. Clang's
RISC-V backend calls `memset` and `memcpy` for the aggregate initializations and copies the x64 and ARM64 backends inline,
and a fixture links no libc: `tests/User/compiler_rv64.c` gives the three byte-loop helpers and `UserImage` links it
into every riscv64 fixture and the root task (the kernel's own are `compiler.S`). The fixtures stay one executable
segment each, converted by `FlatImage` as before; `KernelImageBuilder` embeds them when the image is a self-test and
places the root task on every riscv64 disk, release included.

### 7.3 The tool

`KernelArchitecture.KernelOnly` is gone: a port now says what it still lacks — `SystemLayer` (false for riscv64 until V2:
no libc, so no layer-2 scenario and no `LibcPassedLine`) and `SecondaryProcessors` (false until V1.4: no `boot-smp2`) —
and `UsersExpectation` names `<isa>-users.json`. `KernelTestSuite.RunFoundationAsync` serves ARM64 and riscv64 alike:
boot-128 with the root task's lines and boot-512 (both judged against the users expectation), `boot-smp2` where the port
starts secondary processors, the layer-2 scenarios where it has a system layer, the rejected contract and map, the
ISA's fault scenarios (nine on riscv64, judged by `Rv64FaultExpectation`) and the timeout; riscv64 keeps its 120-second
boot limit and 60-second hang limit, since the firmware's debug build prints some 1,150 lines first.
`BootValidation.ValidateFoundationUsers` requires the users expectation's 80 markers in order and, on riscv64, every
`[USER-FAULT]` line in the riscv64 form with SPP clear, the error equal to `scause` and `scause` equal to the vector,
and the summary's count equal to the lines; the release judge requires `Boot.RootTask` on every ISA again.

## 9. Findings

1. **The bridge lies under `/soc`.** The ARM64 reader found the ECAM bridge among the root's children; the riscv64 virt
   board nests it under `/soc` with the PLIC. The first boot enumerated nothing (`[DEVICES] No generic ECAM bridge in the
   device tree`) until the reader tracked a candidate per open node and took the first compatible one at any depth.
   `qemu-system-riscv64 -M virt,dumpdtb=` with the scenario's devices is the quickest way to see what the firmware
   publishes.
2. **A device leaf is an alias.** With two RSW bits a leaf has one kind, and the first encoding decoded kind 3 as
   `DEVICE` alone; `unmap_page` of the common kernel requires `OWNED` or `ALIAS` and panicked with
   `Missing owned user mapping` the moment the device suite released a `DEVICE_MEMORY` mapping. The common kernel always
   marks a device page `ALIAS | DEVICE`, so the decoder reports kind 3 as both. Nothing in the common kernel changed.
3. **`-fno-plt` and the compiler helpers.** Clang's RISC-V driver rejects `-fno-plt` ("argument unused during
   compilation") under `-Werror`, and its backend emits calls to `memset` and `memcpy` for what the other backends inline;
   a freestanding image needs the helpers linked in (`compiler_rv64.c`), where x64 and ARM64 needed none.
4. **`tp` is the one register the kernel writes once.** TLS on x64 and ARM64 is a privileged base the kernel switches or
   a read-only register a trampoline reads; on RISC-V the TLS base must land in an ordinary register the thread then
   owns. Marking the fresh frame in its `Reserved` word and writing x4 at the first resume keeps `THREAD_CREATE`'s TLS
   base meaningful without a `THREAD_SET_TLS` that would overwrite what the thread wrote itself.
5. **The reservation survives a trap on hardware.** TCG clears the load reservation at every trap, so the suites would
   pass without the dummy `sc.d` at a U-mode resume; the privileged specification does not promise it, and a surviving
   reservation would let another thread's `sc` succeed wrongly. The clear stays, since the kernel is written for the
   architecture, not the emulator.
6. **No condition flags, no red zone.** `wit_arch_frame_prepare_return` has nothing to clear, the entry fixture's
   preemption spin keeps its sentinel in `tp` instead of the flags, and the callback stack leaves 16 bytes of call frame
   rather than x64's 128-byte red zone.
7. **Firmware output grows with the self-test.** The 256 MiB boot reports 190 MiB usable where V1.2 reported 197: the
   self-test image with the fixtures is 7 MiB larger, since each registry slot's kernel stacks are static.

## 10. What V1.4 inherits

The secondary harts: `wit_arch_secondary_prepare` and `wit_arch_secondary_start` through SBI HSM `hart_start` with a
hart's own stack and `satp`, `wit_arch_ipi` through the SBI IPI extension (the supervisor software interrupt, SSIP, as
the fence and page-invalidation requests of K7.2), the board's `wit_platform_processor_prepare` and
`wit_platform_processor_interrupts_enable` (a hart's PLIC context mapped and its threshold set) and `wit_platform_ipi`
with `wit_platform_ipi_complete` (clearing SSIP), the `boot-smp2` scenario with `Processors present/online: 2/2`, and
`KernelArchitecture.SecondaryProcessors` true for riscv64. Those seven operations panic by name in the two `stubs.c`
today. Beyond V1: V2 compiles layer 2 for `riscv64-unknown-linux-musl` and sets `SystemLayer`.
