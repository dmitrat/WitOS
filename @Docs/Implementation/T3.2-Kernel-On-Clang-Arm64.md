# T3.2 — the ARM64 kernel on clang

Plan step T3.2 completes T3: the ARM64 kernel and its EFI loader are now compiled by the pinned clang 20.1.8 and
linked by the pinned `lld-link`, as the x64 kernel has been since T3.1. Their assembly is GNU syntax. MSVC no longer
builds any part of the kernel on either ISA, and the tool's MSVC path for the kernel is gone. MSVC stays on the
development host only for the frozen line's fixtures (x64 C and MASM, ARM64 armasm64), which leave at K8. The
kernel's behaviour, its ABI and its boot contract do not change.

## What changed

**The target.** `KernelArchitecture.Arm64.KernelTriple` is `aarch64-unknown-windows`: PE/COFF, the Microsoft ARM64
convention and the same options as x64 (C17, `-ffreestanding -nostdinc`, `-fno-stack-protector`, `-O0`,
`-Wall -Wextra -Werror`, CodeView). clang reserves x18 on this target as the platform register, as MSVC did, so the
kernel never allocates the register it sets to the compiler TLS on every return to EL0. The kernel's C on ARM64 used
no MSVC intrinsic: its system registers were always read and written in assembly.

**GNU assembly, checked against armasm64.** The architecture's five armasm64 files (`entry`, `vectors`, `compiler`,
`processor_registers`, `secondary_entry`), the virt board's three (`semihosting`, `counter`, `gic`) and the ARM64
self-test became `.S` files. The mechanical part of the translation was done by a script:

- `AREA` became a section directive, with `ALIGN=11` as `.p2align 11` for the 2 KiB vector table;
- `EQU`, `DCQ`, `EXPORT`, `PROC`/`ENDP`, labels and `LTORG` became their GNU forms;
- the vector `MACRO` became `.macro` with `.balign 128`;
- `DCD 0`, which stood in for `UDF #0` because armasm64 does not name it, is now `udf #0`.

Every file was then assembled by both assemblers and the objects compared. Their instruction streams are identical,
including every relocation, with two exceptions. The literal pools that `ldr x, =symbol` loads from hold the same
entries in reverse order, so the load offsets differ. Between the vector entries, armasm64 pads with zeros and clang
with `nop`, padding no path ever executes.

**The tool.** `KernelImageBuilder` compiles and links the kernel with clang and `lld-link` alone. `KernelTriple` is
no longer optional, and the MSVC compile and link of the kernel are removed. A scenario still finds MSVC, for the
frozen line's fixtures it builds. `doctor` names both kernel triples.

**The ARM64 release kernel.** `release --arch arm64` used to boot the release kernel under the foundation suite,
whose self-test markers a release kernel never prints, so it could not pass. It now keeps the release suite, which
both ISAs share: the boot contract, the exception tables, kernel paging, the clock, `Hello` and the root task, with
no self-test and no fault. CI runs it after the ARM64 suite.

**Warnings clang adds.** As on x64, the self-test helper `require` of `scheduler.c` is defined under
`WITOS_SELFTEST` alone. The execute-data probe page of `paging.c` exists only in the scenario that executes it.

## Tests

The ARM64 suite passes with the clang kernel: `dotnet run --project tools/WitOS.Dev -- test --arch arm64`, every
boot, fault and layer-2 scenario. So does `release --arch arm64`. The x64 suite, host tests and `format-check` pass.

## Limits kept explicit

- The kernel is still unoptimized (`-O0`) on both ISAs.
- MSVC, MASM and armasm64 remain on the development host for the frozen line's fixtures until K8. A Linux host builds
  the kernel and layer 2 only after T2.
