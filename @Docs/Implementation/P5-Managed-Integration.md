## P5.1 completed implementation

ExceptionProbe runs four rounds per invocation. An exception carries a managed payload through two filters (the first throws and is treated as false), native-resource finally, catch/rethrow, a nested exception inside finally and the outer handler. Six compacting collections per round retain payload/exception identity. The required callback sequence is 0x123456789A. Each round allocates a 4 KiB native page through existing VirtualAlloc bindings, verifies sentinels after collection and checks successful VirtualFree in finally.

The same code runs once in hosted Main and three times per positive guest execution (Main, normal worker and detached worker). The native fixture only emits worker evidence after checked managed return values. RuntimeBootProtocol requires that evidence separately at both bases; mutations reject missing/duplicated markers. Final wmain exit 42 additionally requires Main's checks. This explicit platform interop probe is not a portable-IL application contract or a replacement allocator/CoreLib.

## Upstream paths inspected before later stages

`FinalizerHelpers.cpp` creates the real finalizer thread and its request/done events. `Runtime.Base/.../__Finalizer.cs` drains the queue and reports observed full-GC counts. `GC.WaitForPendingFinalizers` uses that handshake; the finalizer loop does not return. Acceptance will explicitly drain work before normal component shutdown, not promise automatic finalization of every live object at process exit. Separate Windows-only draft probes pass suppression, resurrection/re-registration and native-resource cleanup; these are not guest evidence.

`Thread.NativeAot.Windows.cs` calls CreateThread with CREATE_SUSPENDED and STACK_SIZE_PARAM_IS_A_RESERVATION, stores the resulting SafeWaitHandle, applies priority and calls ResumeThread. Its entry is the actual ILC ThreadEntryPoint, and StartCore checks thread startup through JoinInternal(0). Existing native worker fixtures do not supply that platform creation contract. P5.3 must publish a kernel-owned reference and initial suspended state atomically, reject unsupported stack/priority modes without fake success, preserve generation-bearing identity and arrange actual user-space TLS/runtime exit cleanup. The existing normal-only scheduler remains explicit.

The original [M3 definition of done](<../WitOS — Implementation Strategy & Milestone Plan.md>) also requires an isolated C# component that can write to the terminal and whose failure does not crash the kernel. Existing GetStdHandle/WriteFile bindings can let the managed acceptance code itself emit checked bounded reports through the captured console capability. This is explicit system-component interop; ordinary portable application compatibility remains P6. The final audit must review the small-kernel/managed-system hypothesis and describe actual upstream corrections and unsupported features.

## P5.2 completed implementation

FinalizationProbe runs three waves of four finalizable objects. Each owns a real native page and a managed payload. Its actual destructor executes on one native thread distinct from Main, frees the page and performs a compacting collection while retaining its payload. WaitForPendingFinalizers must observe exactly 12 completions and releases. A suppressed object must never run its destructor. Another object resurrects itself and re-registers once; a collection while strongly rooted must not finalize it again, then releasing that root permits exactly one second finalization. Repeated empty-queue waits must finish without extra callbacks.

The positive Main drains this workload before returning and writes a bounded report itself using existing GetStdHandle/WriteFile capability bindings. The exact same executable source passes Windows NativeAOT reference; all four guest profiles at both image bases pass. RuntimeBootProtocol requires the report independently at both bases and before wmain return; mutation tests reject omitted/incorrect finalization evidence. Existing orderly, OOM, hardware fault, initialization failure and abrupt cases remain mandatory.

## P5.3 completed implementation

Experimental user ABI v37 adds reference-bearing creation with a copied request, whole native-ID destination validation, atomic initial suspension and independent observer lifetime. Runtime.Native enters/leaves compiler TLS and delivers the real runtime exit notification before THREAD_COMPLETE. CreateThread uses the correct DWORD callback ABI; normal-only priority is explicit. ResetEvent and single-object wait bindings reuse actual existing event/object wait semantics. Native tests include suspended/non-suspended creation, close/duplicate/reuse, invalid output/flags/stack size, handle-quota recovery and failure at each stack/raw-TLS/compiler-TLS allocation.

The standard Thread/Monitor workload passes Windows NativeAOT. Its guest image measures 1,060,864 mapped bytes (906,240 file bytes), exceeding the former 1 MiB mapped cap by three pages. The private full-runtime image cap is now 1,114,112 bytes (1088 KiB), the next 64 KiB boundary. Ordinary image/file limits, 8 MiB backing quota, fixed VA window and stack limits remain unchanged. Guarded PE tests retain the original corpus and add exact-cap acceptance / cap-plus-page rejection; ordinary-profile rejection remains mandatory.

An initial native fixture link omitted the already implemented Suspend/Resume transport objects. RuntimeThreadFixture now includes and hashes exactly those existing objects. This was a test-image dependency gap, not an unresolved runtime OS implementation. Actual guest threading and final regressions remain pending.

The next native matrix exposed a test-image dependency issue: adding new imports to shared binding objects grew the legacy CPU fixture to 133 unwind entries, exceeding its deliberate 128-entry plain profile. The new CreateThread/priority/single-wait/reset bindings are now a separate C++/architecture object pair, included in the full runtime and the thread fixture. The legacy CPU fixture and its 128-entry admission check are retained. This refactoring does not relax legacy validation. The boundary PE fixture also had to extend its last section along with SizeOfImage; the parser's exact mapped-end check remains intact. All 529 guarded PE inputs pass.

After separation, the legacy CPU image contains 124 unwind entries and the thread image 123, both within their unchanged 128-entry plain limit. The first native qemu64/128 MiB profile passes the new creation/rollback fixture at both bases. The managed guest matrix and remaining required regressions are still running; P5.3 remains open.

## P5.4 completed implementation

The full runtime's private stack-overflow image enters a real managed recursive method with a 4 KiB stack allocation per frame, an escaping buffer and no tail call. It emits bounded frame progress through the actual console binding. The kernel must capture a CPL3 nonpresent page fault in the fixed stack's lower guard, with executable fault RIP, reclaim the whole component and run later cases successfully. Managed finally and native atexit markers must be absent. No native fault instruction or synthetic StackOverflowException substitutes for stack exhaustion; automatic stack growth/catchable overflow is not provided by this profile.

A separate positive workload starts two managed workers alongside Main and the actual finalizer, reaches the four-thread guest quota, catches the real Thread.Start OutOfMemoryException and confirms the attempted Thread remains unstarted. Both parked workers retain live roots through collection. After orderly completion frees slots, the same previously failed Thread object starts and joins successfully. A kernel counter distinguishes the actual capacity failure from an unrelated managed allocation failure. The Windows reference exercises the ordinary three-worker path without imposing the guest's private quota.

All earlier heap-limit/backing-pressure OOM recovery, GC initialization failure, native fatal and abrupt worker components remain mandatory in the enlarged executable. The full stage remains open until its guest matrix and regressions pass.

P5.4 integration exposed two issues. The runner originally counted the two new stack faults against the 51 legacy faults; it now checks legacy and following fault counts separately, preserves exact total/CPL3 validation and rejects malformed lines. A new host regression rejects attempts to compensate a missing legacy fault with an extra runtime fault.

An intermittent component budget expiration was captured without changing the managed PE. Main was joining a worker; the runnable worker's RIP mapped to metadata_read inside wit_unwind_metadata_function. The checked adapter rescanned the complete ~3000-entry image for every unwind frame. The fix adds a per-thread validated-image token only in the guest adapter, after confirming the kernel-published immutable image and a valid stack scope. It uses no shared gate and is reset by fresh compiler TLS. Complete validation happens once per thread; selected-record/chain validation, canonical entry identity, bounded reads and transactional outputs remain on every call. The original uncached API still revalidates hosted/mutable descriptors. Windows reference now requires 40 cached comparisons and 40 forged-entry rejections in addition to the original 20 comparisons and 13 transactional failure cases. Guest regression of this fix remains pending.

The first full four-profile guest matrix with cached image validation passes, including all previous workload and P5.4 stack/quota cases. Kernel budget remains 3000 delivered ticks and the host watchdog remains 120 seconds. Positive execution now reports its actual ticks/limit for the final audit. Full native and repeated managed regressions are pending before P5.4 closure; the original budget-expiration logs and symbol map are retained.

## P5.5 completed implementation

Each positive component now performs four combined cycles of hardware/managed exceptions, compacting GC, finalization/resurrection, standard Thread/Monitor/TLS and thread-quota recovery. A previously exited Thread observer remains live while the next kernel slot is reused; old Join(0) must stay completed while the new worker remains live. After finalizers are drained, the existing private native callback audits the actual locked ThreadStore: exactly Main and the real g_pFinalizerThread, both initialized and not detached. The callback adds no public application API.

The guest matrix now runs four positive components per profile (base A, base B, base A, base B), with full handles/events/backing/page-table reclamation between components. Each component must complete 41 orderly workers (13 native acceptance workers plus 28 managed workers), observe four real thread-capacity failures/recoveries, and pass four ordered ThreadStore/cycle audit pairs. Hardware counters are 12 reads / 12 writes / 12 divides / 36 continuations per execution. Original negative components remain in every profile. All budgets and prototype resource limits are retained.
