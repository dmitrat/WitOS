# N4.5: The M6 summary — the compatibility matrix, the profile by fact, Gate B

The last step of phase N's first pass (PLAN.md N4.5; Implementation Strategy §60, §61, §145; RFC 0015 §8, §9;
RFC 0011 §9.1, §10.2). It states what the gates of phases R and N prove, in the one place an outsider reads, and
records the three decisions the plan left to this step in [ADR 0026](ADR-0026-M6-Summary.md).

## The compatibility matrix

`@Docs/Implementation/Compatibility-Matrix.md` is written by the tool, never by hand:

```
dotnet run --project tools/WitOS.Dev --configuration Release -- compatibility-matrix
```

- **The areas.** The suite lists its own checks (`dotnet DotNetCompatibility.dll --list` prints each check's id and
  runs none), so the matrix has a row per area with the number of checks and, per platform, *Supported* when no check
  of the area is a recorded difference on that platform and *Partial* with the checks named otherwise. The platforms are
  the keys of `expectations.json`: Windows, Linux and WitOS, where WitOS means both ISAs, since a step closes only when
  both pass.
- **The recorded differences.** Every entry of `expectations.json` with its reason; each has its row in
  [Compatibility-Differences.md](Compatibility-Differences.md) with the check that verified it.
- **Beyond the suite.** `build/compatibility-matrix.json` names each capability the suite does not cover with a status
  (*Supported*, *Partial*, *Absent*, *Planned*), the step or milestone and the fact behind it; the hardware matrix of
  Strategy §146 follows. The tool refuses a status it does not know or an entry without its fact.
- **Kept current.** `CompatibilityMatrixTests` renders the matrix from the built suite and requires the committed file
  to equal it, so a check added to the suite, a difference recorded or a status changed re-renders the matrix in the
  same change.

## The documents by fact

- **RFC 0015 §8** states the feature profile as of N4 (the GC, ICU, cryptography, networking, files, processes, the
  console, diagnostics, compression, time, dynamic code, several runtimes, the published application), each with the
  step that proved it, in place of v2's table of phases; §4 fixes the upstream proposal at T4; §9 records N4's gates.
- **RFC 0011 §9.1 and §10.2** name the capability API `libwitos`, static and outside ABI-2 1.0 until its first
  consumer outside the system layer, and keep the rule for `libwitos.so.1` with symbol versions for that day.
- **ADR 0026** records the three decisions with their alternatives: the profile by fact, the static `libwitos`, the
  upstream proposal together with T4.

## Gate B

Strategy §61 lets WitOS claim "WitOS runs .NET" once M6 is done. The claim rests on the gates, each passed on both ISAs:

| Gate | What it proves | Step |
| --- | --- | --- |
| The Unix-form runtime builds and runs | CoreLib, CoreCLR and the JIT, NativeAOT, the hosts and the shared framework for `TargetOS=witos` | R1–R5 |
| An ordinary application runs unchanged | published by the stock SDK without a RID, `dotnet App.dll` | R6 |
| Upstream's own tests pass in the guest | the PAL suite, slices of `src/tests`, the library tests | R7 |
| The port survives upstream's moves | a servicing upgrade by `runtime-rebase`, the next major rehearsed | R8 |
| The compatibility suite | 88 checks of 14 areas, no unexpected result on Windows, Linux and WitOS | N1 |
| Real libraries | NUnit, xUnit, MessagePack, MemoryPack, Math.NET and Roslyn, their own suites as on Linux | N2 |
| Several runtimes | .NET 8 and .NET 10 side by side | N3 |
| The application environment | time zones and `/tmp`, processes with pipes, the terminal, the Windows publish run as those bytes | N4.1–N4.4 |

The README states the claim with the matrix as its meaning and the recorded differences as its limits.

## Limits kept explicit

- The matrix states what the suite checks and what a step verified; a capability outside both is not in it.
- *Supported* in the suite's areas means the sample of checks the area holds, not the BCL's whole surface (N1's
  limits).
- The upstream proposal is a decision about when, not a filing: it waits for T4.
