# H5.3 — The session's speed: the clock and the namespace service's cache

The author's VMware session took 15–19 seconds from the services' readiness to PowerShell's prompt. The author asked
for ReadyToRun to cut it. Measured first, the JIT turned out to be the smaller part. The larger part was two costs the
QEMU gates cannot see:

- every read of the monotonic clock left the guest three times;
- every lookup and every read of the data volume went to the disk.

This step removes both. ReadyToRun follows as its own step (R9).

## 1. How it was measured

Everything was measured on VMware Workstation, a machine with two vCPUs and 1 GiB, on the session's disk that
`shell --pc --prepare` writes. The host is an AMD Ryzen 9 5950X. Three scratch tools, never committed, did the work:

- `prompt_time.py` starts the machine without a window and stamps its serial log. It hashes a VNC frame every second
  and reports when the screen first showed what it shows at the end, which is the prompt.
- `probe.sh` boots the machine and types PowerShell lines at the prompt through VMware's VNC, whose keys reach the
  PS/2 keyboard (H5.2). It takes the screen after each line.
- The same lines ran in the PowerShell 7.6 of the Linux container on the same processor, under WSL2's hardware
  virtualization, as the reference.

`[System.Runtime.JitInfo]` gives a process's JIT compilations and their time. `Measure-Command` and `Stopwatch` give
the rest.

## 2. What was found

### 2.1 The JIT is the smaller part

PowerShell's archive is IL alone (C1.3), and the guest's framework is IL too: CoreLib and every library of
`runtime-witos` lack a ReadyToRun header, because crossgen2 knows no witos. Compiling both with the tree's crossgen2 in a
scratch copy showed:

| A child `pwsh -NoProfile -Command exit` | IL | ReadyToRun |
| --- | --- | --- |
| Methods compiled by the JIT | 10,192 | 464 |
| The JIT's time | 7.5 s | 1.5 s |
| The start | 6.7–7.3 s | 5.8 s |
| `pwsh -Version` | 3.4 s | 4.3 s |

Six seconds of compilation became one second of the start. `-Version` got slower, because ReadyToRun images are about
2.5 times larger and a volume's file is copied whole into the process.

### 2.2 The data volume had no cache

`File.Exists` 200 times on each of these:

| Path | Each |
| --- | --- |
| A file of the boot package (no request) | 0.07 ms |
| `/tmp/x` (the namespace service, its memory volume) | 0.56 ms |
| `/data/global.json` (ext4, one level) | 2.5 ms |
| `/data/apps/PowerShell/7.6.7/pwsh.dll` (ext4, four levels) | 6.5 ms |

Reading PowerShell's 59 assemblies (39 MB) from `/data` took 4.0 s, about 10 MB/s. The namespace service mounted its
volumes straight over the block channel. Every path component read its directory and inode blocks from the disk through
the driver, and every read of a file went the same way.

### 2.3 A clock read left the guest

The same loops in the guest and on Linux:

| | Linux | WitOS (HPET) |
| --- | --- | --- |
| 100,000 empty iterations of a loop | 145 ms | 170 ms |
| 100,000 reads of `Environment.TickCount64` | 98 ms | **8,654 ms** |
| 20,000 steps of a pipeline | 0.17 s | 2.05 s |
| JIT per method at a start | 0.11 ms | 0.73 ms |
| Filling 128 MB | 61 ms | 49 ms |

Computation and memory ran at the host's speed, so neither the processor nor the memory's cache type was at fault. One
read of the clock cost 85 µs.

The PC's monotonic clock was the HPET (H1.1). A read of its 64-bit counter is three loads of a device register (high,
low, high), and on VMware each of them is an exit to the hypervisor. Under QEMU's TCG a device register is no dearer
than memory, so no gate noticed. The kernel reads the clock on every pass of the dispatcher (`expire_waits`) and in the
waits for another processor's acknowledgement. So every call that waits, wakes or yields paid it: the namespace
service's 0.56 ms, the JIT's code allocations, `Thread.Yield` at 75 µs against Linux's 14 µs. Linux on VMware reads the
time stamp counter, which costs no exit.

### 2.4 A ReadyToRun image of more than a chunk did not load from a volume

The first ReadyToRun trial failed: `FileLoadException` for `Microsoft.PowerShell.ConsoleHost` with "The access code is
invalid".

- The libc copies an executable mapping of a volume's file into a shared memory file of the process's own (D5.3), as
  one object mapping per chunk of 64 pages.
- It then published the whole copy with one `CODE_PUBLISH`, and that call covers one reservation. A copy of more than
  256 KiB failed with `NOT_RESERVED`, which the libc answered with `EACCES`.

The dynamic linker's libraries on volumes had been small, so nothing had hit it.

## 3. The changes

- **The monotonic clock is the time stamp counter** where it runs at a constant rate (`Kernel.Platform.Pc/hpet.c`).
  - **When.** CPUID names it invariant (leaf 0x80000007, EDX bit 8), or the processor runs under a hypervisor (leaf 1,
    ECX bit 31), which keeps a guest's counter constant.
  - **Its rate.** The hypervisor's timing leaf 0x40000010 where it has one: VMware's, in kHz, gives 3,393,655,000 Hz on
    the measuring host. Otherwise the rate is measured against the HPET over 50 ms, each end the HPET read inside the
    narrowest of eight pairs of counter reads.
  - **The shift.** The counter is shifted right until its rate is at most 10⁹, the bound within which the kernel's UTC
    conversion and the libc's stay in 64 bits.
  - **Several processors.** Their counters may stand a little apart. A read below the last value any processor saw
    gives that value, and a read behind the origin gives zero.
  - **The HPET** stays the reference, and the clock where the counter's rate is unknown or outside 0.1–20 GHz.
  - **Where it shows.** The boot log names the source (`Monotonic clock: the time stamp counter at …`). QEMU's TCG has
    no invariant counter but sets the hypervisor bit, so every x64 gate runs the new clock: about 10⁹ Hz there, since
    under `-icount` the counter follows virtual time and the gates stay deterministic.
- **The namespace service's cache** (`VolumeMounter`): each volume reads and writes through a `CachedBlockStorage`.
  - **Its size.** Blocks of 4 KiB; 32 MiB for an ext4 volume, 4 MiB for a FAT one.
  - **Durability.** Written through, so a write is on the disk when it completes, and D6's cuts and replays hold
    unchanged.
  - **What it logs.** The mount line names the cache. At the stop the service prints how many blocks it read from the
    cache and how many from the disk.
- **`CachedBlockStorage`** (`OutWit.OS.Storage`):
  - its block may be a multiple of the resource's alignment, and its memory is segments of a mebibyte taken as it
    fills, with an LRU over index arrays, so that a large cache costs no object per block;
  - a run of misses is read in requests of the resource's transfer limit, and the resource's last block may be short;
  - a write through refreshes a block the cache holds and leaves one it does not hold out unless it covers the block
    whole; a write back into part of an absent block reads that block first;
  - a discard writes a dirty block it covers in part before forgetting it.
  - The cache's tests cover these cases, and the conformance suite runs over three more providers: blocks of four
    sectors written through, written back, and over a channel whose transfer limit is the block.
- **The libc** (`memory.c`) publishes an executable copy of a volume's file window by window. `futex.c` and `process.c`
  convert nanoseconds to the clock's counts in whole seconds and the remainder: a product of nanoseconds and the
  frequency passed 64 bits beyond 184 s at the HPET's 10⁸ and would beyond 18 s at 10⁹.

## 4. The result

| On VMware | Before | After |
| --- | --- | --- |
| A clock read (`TickCount64`) | 85 µs | 3.6 µs |
| 20,000 pipeline steps | 2.05 s | 0.25 s |
| `File.Exists` on `/tmp` | 0.56 ms | 0.08 ms |
| `File.Exists` four levels into `/data` | 6.5 ms | 0.22 ms |
| JIT per method at a start | 0.73 ms | 0.29 ms |
| A child `pwsh -NoProfile -Command exit` | 6.7–7.3 s | 2.2–2.5 s |
| The prompt after the machine starts | 25–29 s | 17 s |

The cache alone, before the clock, already cut `File.Exists` four levels into `/data` to 1.5 ms and the 39 MB read to
1.8 s. It served 87% of `/data`'s blocks in `runtime-devices`' first boot.

## 6. What is not yet

- **ReadyToRun.** At 0.29 ms a method, the JIT's 10,197 compilations are again the largest part of a start. ReadyToRun
  of the framework is R9. ReadyToRun of the base applications is an amendment of ADR 0027, to decide by the measurement
  after R9.
- **A volume's file is copied into each process that maps it.** The namespace service's chunks could be mapped
  without a copy, as R4.2 maps a shared mapping.
- **The time to the services, 9 s.** Five seconds of it are VMware's firmware before the loader.
- **A request costs 78 µs, and the JIT a method 0.29 ms.** Linux takes a fraction of each. The kernel is built with
  `-O0` (the rule from MSVC's `/Od`), which is a candidate for a measurement.
