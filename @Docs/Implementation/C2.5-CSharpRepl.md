# C2.5 — C# in the console: CSharpRepl over the .NET SDK as a base application

Plan step C2.5 (phase C, ADR 0027), the author's decisions of 2026-10-18 (CSharpRepl, an upstream global tool, laid
unchanged in the data volume's layer) and 2026-10-20 (the .NET SDK as a base application, so that the tool runs as its
authors wrote it, rather than a faked SDK directory or another REPL). The measurement that led here is
[C2.5-CSharpRepl-Measurement.md](C2.5-CSharpRepl-Measurement.md): CSharpRepl 0.9.2 starts on WitOS and fails at its
first evaluation, since it borrows NuGet's assemblies from an installed .NET SDK through MSBuildLocator.

## 1. The SDK as a base application

`build/apps/DotNet.Sdk.json` lays the .NET SDK in the layer as RFC 0010 lays an application:
`/data/apps/DotNet.Sdk/10.0.300/` with `witos-app.json` and `current`.

- **The source** is the SDK's own release archive of each architecture, `dotnet-sdk-10.0.300-linux-x64.tar.gz` for
  x64 and `dotnet-sdk-10.0.300-linux-arm64.tar.gz` for ARM64, each pinned by the SHA-256 of its bytes
  (`source.architectures` of the catalog, an archive per architecture where a publication is per RID; the layer of an
  architecture the entry names no archive for leaves the application out, `AppCatalog.Serves`). The SDK is published
  per RID and has no portable archive, and its assemblies are not IL alone: they carry the RID's ReadyToRun code over
  the IL (the PE machine of the x64 archive's `NuGet.Versioning.dll` is 0xFD1D, AMD64 under the Linux mark, without the
  IL-only flag). The first form laid the x64 archive for every ISA, and on ARM64 and riscv64 CSharpRepl died at its
  first evaluation with `FileLoadException: Could not load file or assembly 'NuGet.Versioning' … The access code is
  invalid`. With the arm64 archive laid for ARM64 the same exception stayed, and its cause is measured: the arm64
  images carry 12 base relocations in `.text` (the x64 images none, their 329 all in `.data`), the image never loads
  at its preferred base `0x180000000`, and CoreCLR's `ApplyBaseRelocations` opens an executable section for writing
  with `PAGE_EXECUTE_READWRITE` on every Unix but Apple's ARM64 ("on SELinux, we cannot change protection that doesn't
  have execute access rights to one that has it"), which WitOS's `mprotect` refuses with `EACCES`: writable and
  executable at once is never granted (`ERROR_INVALID_ACCESS`). The fix is S8.2, a `TARGET_WITOS` branch beside
  Apple's that writes the relocations through a writable window and restores the section's protection, with the libc
  publishing a mapping `mprotect` makes executable; until then `runtime-csharprepl` reports on ARM64 that it does not
  run. No SDK is published for riscv64, so that architecture's layer has no SDK and no C# REPL.
- **Laid in part.** An archive entry may name the directories to lay (`lay`) and, within them, those left out
  (`leave`), each a path within the archive (`AppArchive`, `AppCatalog`). The SDK lays `sdk/10.0.300` (MSBuild,
  Roslyn, NuGet, the CLI) and `packs/Microsoft.NETCore.App.Ref/10.0.8`, the reference pack it compiles against, and
  leaves `AppHostTemplate` (a Linux apphost) and `TestHostNetFramework` (the .NET Framework's test host), which are no
  .NET IL of this platform. The archive's muxer, hostfxr and shared runtime are not laid: WitOS's install has its own
  (R5), and the SDK's `dotnet.dll` asks for runtime 10.0.8, which the install's 10.0.12 serves. The Linux host pack is
  left out too; a build that wants an apphost for `witos-x64` would need WitOS's own pack, which is not in the layer.
- **The version** is the SDK the repository builds with (`global.json`, 10.0.300): its NuGet is 7.6, the version
  CSharpRepl 0.9.2 references, and its runtime 10.0.8 is below the install's. The channel's latest SDK, 10.0.402, ships
  with runtime 10.0.13, which the install does not have: an SDK must not be newer than the runtime it runs on.
- **No command.** The SDK provides no launcher; an application may have an empty list of commands when others reach
  it. `dotnet` reaches it through `global.json`.

## 2. global.json beside the layer

hostfxr 10 reads `global.json` from the working directory upwards and takes `sdk.paths`: each path, relative to the
file, is a root under which it looks for `sdk/<version>/` (`sdk_resolver.cpp`). The layer writes `/data/global.json`
(`SdkRoots`): the roots of every application whose current version holds `sdk/`, in the applications' order, so
`{"sdk": {"paths": ["apps/DotNet.Sdk/10.0.300"]}}`. The host's tool writes it when it lays or updates a disk's layer
(`AppsLayer.WriteSdkRootsAsync`), and the guest's installer when it puts a version in use (`AppsDirectory.Use`), which
removes the file once no current version holds an SDK. The file belongs to the layer, as the launchers do.

A process whose working directory lies under `/data` therefore finds the SDK: sessions start in `/data`, and
`dotnet --list-sdks` there lists `10.0.300 [/data/apps/DotNet.Sdk/10.0.300/sdk]`. A process elsewhere sees the install
alone, which has no SDK; `DOTNET_ROOT` does not help, since the muxer looks for SDKs beside itself or where
`global.json` says.

## 3. CSharpRepl

`build/apps/CSharpRepl.json` is as the measurement left it: the `tool` kind (`AppToolPackage`), the portable package
`CSharpRepl.any` 0.9.2 pinned by its SHA-256, the command `csharprepl`, and the reference pack `Microsoft.NETCore.App.Ref`
10.0.12 in the user's global packages folder, where the tool looks for the pack of the runtime it runs on. At start the
tool's MSBuildLocator asks hostfxr for the SDK of the working directory (`hostfxr_resolve_sdk2`), which `global.json`
resolves to the layer's, and resolves NuGet's assemblies from there; every evaluation then goes through Roslyn's
scripting as on Linux.

## 4. The acceptance

`runtime-csharprepl` (`RuntimeCSharpRepl`, in `runtime-witos` after `runtime-installer`): the package of the application
scenarios with the terminal, a data disk of 1.5 GiB with the layer (the SDK takes 400 MiB of it; every disk with the
layer grew from 1 GiB, and stays below 2 GiB, since the tool writes a disk from one array), `/bin/init` running `dotnet --list-sdks` and then the REPL's launcher from `/data` with
`NO_COLOR`, and the runner typing at each prompt an expression, a class and a call, the platform's description, a file
of the volume, a script loaded with `#load`, a compilation error and `exit`. The scenario requires dotnet's listing of
the layer's SDK, each answer, the compiler's `CS0029` and the REPL's exit with 0, on x64; on ARM64 it reports that it
does not run until S8.2 (§1), and on riscv64, whose layer has no SDK, that none is published. The runner types each input's text at the prompt
and its Enter by itself once the REPL echoed the text: keys that arrive together PrettyPrompt takes for a paste, whose
Enter starts a new line instead of submitting (on the Linux host the first expression typed at once was never
evaluated in 150 s, and with the keys 50 ms apart it answered in 3 s).

## 5. What ran

C2.5 closed on 2026-10-20 with its acceptance on x64 and ARM64 (ARM64 after S8.2); riscv64 has no SDK publication.

- **Host tests.** `OutWit.OS.Tests` 269 and `WitOS.Dev.Tests` 124 pass on the Linux host (among them the catalog's
  `lay`, `leave` and the archives per architecture, `AppCatalog.Serves`, `AppArchive.Select`, an application without a
  command and the `global.json` the layer writes, on a directory and on an ext4 volume through debugfs);
  `WitOS.Apps.Tests` 10 pass (the guest installer writing and removing `global.json` as versions come into use); the
  format check is clean.
- **Guest.** `runtime-csharprepl` passes on x64: `dotnet --list-sdks` from `/data` lists
  `10.0.300 [/data/apps/DotNet.Sdk/10.0.300/sdk]`, and the REPL, started by its launcher, answers `"witos-42"`,
  `"hi witos"` from a class typed at the prompt, the platform's description starting with `"WitOS`, the volume's file,
  the script's variable, and `CS0029` for `int wrong = "text";`, then exits with 0 after 2620 s of the guest's time
  under TCG, Roslyn, its workspaces and MEF going through the JIT; on ARM64, after S8.2, the same answers and an exit
  with 0 after 2746 s. On riscv64 the scenario reports that no SDK is published.
- **The forms that failed on the way.** Without the SDK the first evaluation threw
  `Could not load file or assembly 'NuGet.Versioning, Version=7.6.0.0'` (the measurement); with the x64 archive laid
  for every ISA, ARM64 and riscv64 died at the first evaluation loading that same assembly with `The access code is
  invalid`, and with the arm64 archive ARM64 still does, for the cause §1 measures (the relocations of ReadyToRun code
  through a writable and executable window); and with each input's Enter typed in the same burst as its text, x64
  waited an hour at the first expression, which PrettyPrompt had taken for a paste (§4).
- **What C2.5 leaves.** `dotnet build` in a session is a measurement, not a gate: the SDK's workload
  manifests (`sdk-manifests`) and templates are not laid, and a build that wants an apphost needs WitOS's own host
  pack, which no feed offers in the guest, so a project builds with `UseAppHost=false`; `#r "nuget:"` without the
  network needs a feed on the volume, and with it the network of phase W; `connect` to a process needs the Unix domain
  sockets of W4; a C# REPL on riscv64 needs an SDK publication for it.
