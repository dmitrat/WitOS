# N3.2 — The witos target on release/8.0

RFC 0015 §7 builds each .NET version from its own release branch, and N3 installs .NET 8 LTS beside .NET 10. Upstream
.NET 8 has no `witos` target. N3.2 backports it to dotnet/runtime `v8.0.31`, the latest servicing tag of
`release/8.0`, with a pin and a patch set of its own (N3.1's layout). It builds from that what the shared framework of
.NET 8 needs, and runs an application built for .NET 8 on it in the guest.

## What .NET 8 needs

The shared framework needs these parts:

- CoreLib;
- CoreCLR's runtime and JIT;
- the libraries with their native part;
- `hostpolicy`.

The muxer and `hostfxr` are 10.0's. One `hostfxr` serves every framework of an install, and the newest one is the one
an install keeps. So N3.2 builds no NativeAOT, no ILC, no single-file host and no PAL suite for 8.0. The 10.0 patches
for them stay out of the 8.0 set.

## The patch set (`patches/runtime/release-8.0`, 25 files)

N3.1's trial carry of the 10.0 set to `v8.0.31` brought 9 files over without a conflict. Each conflicting file got the
10.0 patch's intent rewritten against 8.0's text. The rest are what 8.0 shapes differently, found by building:

| Area | Files | What differs from 10.0 |
| --- | --- | --- |
| The platform's identity | `Directory.Build.props`, `eng/build.sh`, the RID graph's `runtime.json`, CoreLib's project items, `OperatingSystem.cs`, `Environment.WitOS.cs` | 8.0 has no `eng/RuntimeIdentifier.props`; `Directory.Build.props` says the same there: witos is a target and a Unix one. |
| The native build | the cross toolchain file, `configurecompiler.cmake`, `configureplatform.cmake`, `tryrun.cmake` | 8.0 has no `CLR_CMAKE_CXX_STANDARD_LIBRARY` knob, so the toolchain file passes `-stdlib=libc++` itself. `tryrun.cmake` carries three more measured answers (below). |
| CoreCLR | `CMakeLists.txt` (no single-file host), the DAC's CMake, `crosscomp.h`, the PAL's `configure.cmake` and `pal.cpp`, `gcenv.ee.cpp`, libunwind's CMake, `minipal/Unix/doublemapping.cpp` | `crosscomp.h` needs the DAC's critical section size for each platform; pal.h sizes it for the layer-2 triples as for Linux. The PAL's configure required LTTng whenever event tracing is on; 8.0 builds the LTTng provider for Linux hosts alone. The 1.5 MiB thread stacks come without `ENSURE_PRIMARY_STACK_SIZE`. |
| The libraries | `System.Net.Http.csproj`, the cryptography project, the native libraries' CMake, Globalization's, the compression shim's two files, `pal_networkchange.c` | 8.0 links the system's zlib on Unix; WitOS builds the in-tree zlib, as 8.0 does for the browser. Http's trimming substitutions name a type its platform-neutral flavor lacks. |

Two upstream changes that 10.0 holds are backported unchanged:

- **`pal_networkchange.c`.** The listener fails with `EAFNOSUPPORT` on a platform with neither netlink nor routing
  sockets. 8.0 did not compile there.
- **`doublemapping.cpp`.** The shared memory file of the JIT's double mapping is sized to the physical memory and the
  process's limits. 8.0 sized it at 2 TB, which the libc refuses past 16 GiB, so CoreCLR failed to start
  (`0x8007000C`).

The process barrier needs no patch on 8.0. The GC and the PAL issue `membarrier` as a system call on `__linux__`, which
the layer-2 triples define, and the libc serves `SYS_membarrier` with the kernel's process barrier.

## The build (`runtime-side-by-side`)

`runtime-side-by-side --arch <isa>` runs on a Linux host, after `runtime-witos` has built .NET 10:

1. It checks out the 8.0 pin under `.tools/upstream` and lays a work tree at `artifacts/runtime-witos/release-8.0`
   with the 8.0 set applied.
2. It builds CoreLib, which must name `WITOS`.
3. It builds CoreCLR's runtime and JIT, the native libraries and `hostpolicy`. These are cross-compiled with the
   pinned clang against the sysroot.
4. It builds the shared framework with the tree's own identifier graph (`/p:RuntimeIdentifierGraphPath`, as R7.2b
   passes it for the tests). 8.0 chooses each library's flavor by the SDK's bundled graph otherwise. That graph does
   not know witos, so every library came out platform-neutral.

`System.Net.Http` has no Unix flavor on either version. witos takes its platform-neutral flavor on 8.0 as on 10.0, so
`HttpClient` throws `PlatformNotSupportedException` until WitOS has networking.

**The configure's answers, measured.** 8.0's native configure asks 30 `try_run` questions on x64 and 29 on ARM64;
10.0's asks 22. The tool
collects the probes, the guest runs them, and the tool requires `tryrun.cmake` to answer as the guest does. 8.0's
generic answers differed from the guest's in three:

| Probe | Generic | WitOS |
| --- | --- | --- |
| `SSCANF_SUPPORT_ll_EXITCODE` | 0 | 1 |
| `HAVE_COMPATIBLE_ILOGB0_EXITCODE` | 1 | 0 |
| `FILE_OPS_CHECK_FERROR_OF_PREVIOUS_CALL_EXITCODE` | 1 | 0 |

The measured values are now in the 8.0 set's witos block. The tool also learned probe names in lower case
(`SSCANF_SUPPORT_ll`).

## In the guest

The `runtime-side-by-side` scenario boots .NET 10's install, `runtime-witos`'s, with .NET 8's framework beside it.
Two frameworks are installed: `shared/Microsoft.NETCore.App/10.0.12` and `8.0.31`. `/app` holds
`tests/Runtime.Witos/SideBySide/App.cs`, which the 8.0 tree's compiler builds against 8.0's reference pack. Its
runtimeconfig asks for framework 8.0.0.

`tests/User/dotnet_init.c` starts it through `/dotnet/dotnet`. 10.0's `hostfxr` resolves the runtimeconfig to 8.0.31,
whose `hostpolicy` starts 8.0's CoreCLR. The application runs ten checks on 8.0:

- the framework's directory and version;
- the platform `WITOS`;
- tasks, threads and a monitor;
- exceptions with a filter;
- a finalizer after a collection;
- a file in `/dev/shm`;
- `fr-FR` culture data through ICU 78;
- JSON;
- a compiled regular expression.

The scenario requires `[SIDE-BY-SIDE] App.dll on .NET 8.0.31, <ISA>: 10 of 10 checks passed`. It passed on both ISAs
locally, with the guest answering every probe as `tryrun.cmake` does. CI's `side-by-side` job runs it on both ISAs.

## Limits kept explicit

- The selection of a framework by `rollForward`, the install's other combinations and ABI-2's declaration are N3.3.
- No NativeAOT, ILC, PAL suite or upstream tests for 8.0: the shared framework is what N3 needs.
- Servicing: `runtime-rebase` carries the 10.0 set within its branch. The 8.0 set has no rebase of its own yet; a newer
  8.0 tag needs its pin and its set moved by a person.
