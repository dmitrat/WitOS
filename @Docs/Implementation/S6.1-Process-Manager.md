# S6.1 — the process manager and posix_spawn

Plan step S6.1 gives the system layer its root task and process manager
([RFC 0011 v3 §7.8, §9.3](../RFC-0011-Kernel-Architecture-and-ABI.md)). Processes start through the process manager
with a `posix_spawn`-shaped API; there is no `fork` and no `exec`. A process receives one capability at creation, and
everything else arrives in its start message. ABI-1 stays at v68; the kernel gains one quota. The current directory and
the console as a capability follow in S6.2.

## What changed

**The root task (`src/RootTask/root_task.c`).** The system layer's first component is a static program over the libc
and libwitos. It runs the process manager, which starts `/bin/init` from the boot package with the initial
environment (`PATH=/bin:/usr/bin`). The root task ends with `/bin/init`'s status once `/bin/init` ends, and the
kernel ends every remaining process with it. A nonzero status is a failed boot. The kernel scenarios keep their ABI-1
fixture, `tests/User/root.c`, as their root task; the `process` scenario boots the system layer's.

**The process manager (`src/Substrate/libwitos/manager.c`, `witos_manager_run`).** The manager owns one channel. It
receives on one end, and every process it starts gets a duplicate of the other end with `SEND` alone. All processes
share one queue, and the manager waits on that queue beside its first process; the kernel's wait holds four handles,
so a wait per process could not scale. A request (`witos/manager.h`) carries its data in a memory object, since a
message holds 256 bytes, and the end of a fresh channel for the reply. The manager checks the message, maps the object
read-only and checks every offset and string of the spawn request inside its bytes before anything starts. It starts
the program with the loader and its own endpoint (`witos_spawn_ex`). The new process's handle moves back over the
reply endpoint without `MANAGE`, and the manager keeps no handle of it. The manager knows no requester; a request is
the capabilities it carries, so a grandchild asks exactly as a child does.

**The start message, version 2 (`witos/start.h`).** It adds the manager's endpoint as an optional third capability;
the libc keeps it in its process context. Arguments and the environment stay on the initial stack, where musl reads
them; a message of 256 bytes could not hold them.

**posix_spawn and waitpid (`src/Substrate/libc/process.c`).** musl's `posix_spawn.c` (clone with `CLONE_VFORK`, a
pipe, exec) leaves the build. `posix_spawn` builds the request, asks the manager and records the child under a
library-local id, starting from 2; `posix_spawnp` searches `PATH` first. Attributes a new process satisfies by itself
pass: default dispositions, an empty mask, the one user. File actions, process groups, sessions, scheduling and a
process without a manager (the root task) get `ENOSYS`. `wait4` serves `waitpid` and `wait`. It waits with
`OBJECT_WAIT` on up to four children; with more, it waits on four with a 10 ms deadline and looks again. It reads
`PROCESS_QUERY` and closes the reaped child's handle. An exit code from 0 to 255 is an exit status.
`WIT_EXIT_SIGNAL(sig)`, which the libc's default signal actions now exit with instead of 128 + the signal, is a death
by that signal. A fault no handler took ends the process as the kernel's fault report; `waitpid` reports it as
`SIGSEGV`, since the kernel's record does not keep the cause.

**The live objects of a system layer process (`WIT_PROCESS_OBJECT_CAPACITY`).** The manager creates the writable
segments and the first stack of every process it starts. That is two memory objects or more while each process lives,
all charged to the creator, so eight objects held at most three programs. The root task and the processes it creates
may hold 32 live objects; other components keep 8 (`ObjectLimit` in the process record).

## Tests

The `process` scenario of both suites boots the system layer's root task with `/bin/init`
(`tests/User/process_init.c`, 36 checks) and `/bin/child` (`tests/User/process_child.c`) in the package. `/bin/init`
checks:

- the root task's environment arrives;
- an exit status is reported, and `posix_spawnp` finds `child` through `PATH`;
- a passed environment reaches the child;
- a child starts a grandchild through its own capability to the manager and reports the grandchild's status;
- an aborting child is reported as `WIFSIGNALED` with `SIGABRT`;
- five children run at once, more than one kernel wait holds, and `wait` reaps each once, then reports `ECHILD`;
- `WNOHANG` returns 0 while a child sleeps, and the blocking wait then returns its status;
- a missing file is `ENOENT`, a text file is `ENOEXEC`, and file actions are `ENOSYS`.

The suite requires `/bin/init`'s last line and the root task's report of status 0. The `spawn` scenario now expects
an aborted child's exit code to be `WIT_EXIT_SIGNAL(SIGABRT)`.

## Limits kept explicit

- No file actions, so no redirected standard streams; there are no pipes yet. The console as a capability and the
  current directory are S6.2.
- No `SIGCHLD`, no `waitid`, and no `kill` of another process; the parent ends a child only through its process
  handle, which the libc does not expose.
- Child ids are each process's own numbering; `getpid` is 1 in every process.
- The kernel's eight processes bound the system, and the root task and `/bin/init` hold two of them.
- Memory objects of a started program stay charged to the process manager while they live (RFC 0011 §12 keeps
  hierarchical accounting open).
