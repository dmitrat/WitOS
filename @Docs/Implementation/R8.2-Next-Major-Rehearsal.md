# R8.2 — The patch set rehearsed on .NET 11 RC1

R8.2 is the second half of R8, the upgrade rehearsal of RFC 0015 §4. It carries the witos patch set from the pin,
dotnet/runtime `v10.0.12`, to the newest .NET 11 preview, `v11.0.0-rc.1.26425.128` (commit `ab19415702aa`). It then
builds the result with `runtime-witos` and runs its guest gates. The pin stays at 10.0.12; the rehearsal measures what
the move to .NET 11 will take.

The result: .NET 11 RC1 runs on WitOS with a patch set of the same size, 27 files and +186/−22 lines. Every gate of
phase R passes on both ISAs, with one exception. R6 needs the stock SDK of .NET 11, which the host does not have yet.

## What was carried, and how

`runtime-rebase --tag v11.0.0-rc.1.26425.128` (R8.1) classifies the 26 patches:

```
1 added, 11 conflicts, 0 gone, 12 merged, 2 unchanged; +180/-22 lines at the pin, +113/-13 carried
```

Git merged 12 files. The 11 conflicts sit beside one upstream change: .NET 11 adds an OpenBSD port, whose lines go
exactly where the witos lines went, beside FreeBSD's and Haiku's. Each conflict was resolved by intent: upstream's side
was kept, and the witos line was added again in its place.

line ends. That re-encoding found a fault in the first version of `runtime-rebase`, which R8.1's commit already fixes.
The tool had hashed the pin from decoded text, while `runtime-witos` hashes the bytes. It now reads git's bytes, hashes
them for the pin, and gives a patch the text without the mark and with LF line ends, as `runtime-witos` reads it.

## What the carry could not see

The build and the guest found the rest. Each item is a change the move to .NET 11 makes, beyond the carried text.

| Found | Cause | Change |
| --- | --- | --- |
| The GC's barrier patch merged into nothing. | .NET 11 moved the process-wide barrier from `gc/unix/gcenv.unix.cpp` to `src/native/minipal/memorybarrierprocesswide.c`, which includes `<linux/membarrier.h>` under `__linux__`. | The patch moves with the code: `TARGET_WITOS` takes musl's `<sys/membarrier.h>` and its two-argument `membarrier`, and `gcenv.unix.cpp` leaves the set. |
| `pal_io.c`: "Platform doesn't support fstatfs or fstatvfs". | .NET 11 asks System.Native whether a file system supports shared locks for writing (`SystemNative_FileSystemSupportsLocking`). The witos target is neither Linux nor a platform with `f_fstypename`. | A `TARGET_WITOS` branch beside Haiku's answers yes: the system layer's files are the boot package and its shared memory files, and the libc's `flock` locks every one of them. |
| "The current CPU is missing one or more of the following instruction sets: SSE, SSE2, SSE3, SSSE3, SSE4.1, SSE4.2, POPCNT". | .NET 11 raises the x64 baseline to x86-64-v2. The guests boot QEMU's `qemu64`, which has neither SSSE3 nor SSE4 nor POPCNT. | x64 guests boot `Nehalem`, which the kernel suite already boots as `boot-intel`. These extensions keep their state in the XMM registers, which FXSAVE already saves, so the kernel needs no change. AVX would need XSAVE, and .NET 11 does not require it. |
| ILC: "Unknown stack trace data: --scanreflection". | `--stacktracedata` takes a value in .NET 11 (`frames`, `lines` or `none`). The R2.1 program's ILC arguments follow the 10.0 targets, where it was a flag. | The R2.1 arguments follow the new targets: `--stacktracedata:frames`. |
| On ARM64, the R2.1 program did not link: `IsSupportedInstructionSet` and `do_vxsort_neon` were undefined. | .NET 11's GC sorts with vxsort on ARM64 too, through NEON. The targets link the vxsort support library on ARM64 as well as on x64, and the R2.1 program's library list had it for x64 alone. | The R2.1 program links `libRuntime.VxsortDisabled.a` wherever the runtime built it, as the targets do: x64 in 10.0, both ISAs in 11. |
| The library tests asked for `Microsoft.NETCore.App` 11.0.0, and the install had `11.0.0-rc.1.26425.128`. | The tree builds its test applications against its product version without a preview's label, as upstream's testhost lays the framework out. A release reference never rolls forward to a preview. | `runtime-witos` names the install after the tree's product version, the pin's version without a preview's label (`RuntimePin.ProductVersion`). For 10.0.12 that is the pin's version, as before. |
| R6: "You must install or update .NET", for `Microsoft.NETCore.App` 10.0.0. | R6 publishes the application with the stock SDK, which is 10.0 on the host. A `net10.0` application does not roll forward to an 11.0 preview, and that is correct behaviour. | R6 waits for the stock SDK of .NET 11. The rehearsal left it out. |

`runtime-witos` also took the target framework from the pin. It had written `net10.0` in nine places, and now takes
`RuntimePin.TargetFramework`. The tool keeps three generalizations: the target framework, the install's version and the
vxsort library where the runtime built one. They do not change what the 10.0.12 pin builds. The other changes above
depend on .NET 11 and wait for the move: the two patches, the x64 guest's CPU, ILC's option and the selections.

## What the tests' selections need

Upstream's tests changed between the releases, so the selections change with them.

- **The PAL suite** no longer has four of the tests R7.1 leaves out: `MapViewOfFile/test1`, `CreateProcessW/test1` and
  `test2`, and `NamedMutex/test1`. Their exclusions go, and 21 remain.
- **`src/tests`** gained two tests that WitOS leaves out, each with its reason:
  - `GC/API/GC/Collect_Aggressive_LargePages` is new. It asks for large pages with a 3 GiB heap hard limit, which the
    GC commits at its start. That is past the pages a process commits, 256 MiB.
  - `baseservices/exceptions/OutOfMemoryException` now starts processes, and `System.Diagnostics.Process` is
    unsupported on WitOS (RFC 0015 §8).
  - `GC/Regressions/v2.0-beta1/289745` fails on ARM64 alone. It allocates until `OutOfMemoryException`, prints that it
    passed, and then the process's exit cannot allocate either. On 10.0 it passes on both ISAs. The cause is the open
    question of R7.2b: the GC sizes itself by physical memory, while a process commits 256 MiB.

  .NET 11 also merged more of its tests into the groups: the GC and exception handling groups run 25 process-isolated
  tests where 10.0 ran 50, and every test of the JIT groups starts.
- **The library tests** gained `ParseWithNBSPAsGroupSeparator`, which parses in the en-US culture. Globalization is
  invariant, since the system layer has no ICU, so it is left out like `RunRegionSpecificStandardFormatToStringTests`.


The NativeAOT acceptance was published by the .NET 11 SDK's own targets, with `dotnet publish -r witos-x64`. The library
tests ran 2466 and 8423 tests; .NET 11 has three times as many numerics tests. The native configure asks the same 11
`try_run` questions, and the guest gives the answers `tryrun.cmake` has.

On ARM64 the same gates pass: M3 under NativeAOT and under CoreCLR, System.Native, the hosts, all 251 tests of the PAL
suite, all 26 runs of `src/tests`, and the libraries' 2466 and 8423 tests. The ARM64 acceptance was published with
`dotnet publish -r witos-arm64`. .NET 11 keeps ARMv8.0 as the ARM64 baseline: the guests' `cortex-a72` runs it unchanged.

The set stays inside the budget of RFC 0015 §4: 9 files of CoreCLR and 3 of the native libraries, where the FreeBSD port
touches 31 and 62 and the Haiku port 18 and 11. The rehearsal took ten builds of `runtime-witos` on x64 and three on ARM64, each after the previous
one stopped on one of the findings above. A servicing release took one build and no change to the set (R8.1). The next major
release's conflicts will gather
where this one's did, beside the other Unix ports: a witos line beside FreeBSD's and Haiku's is the order of
preference of RFC 0015 §4 working as intended.
