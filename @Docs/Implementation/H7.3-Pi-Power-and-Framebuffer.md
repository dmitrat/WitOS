# H7.3 — The Raspberry Pi's power, its test exit and its framebuffer

H7.2 booted the Raspberry Pi 4 on QEMU's `raspi4b` as far as the root task. H7.3 gives the board what the end of a boot
and a display need, from the same device tree and with no board named in the kernel:

- the test exit only where the board has one;
- off and reset through the Pi's watchdog, where the board has no PSCI;
- the firmware's framebuffer in the boot contract, as the UEFI loader records GOP's.

The board's time without a real-time clock needs a decision and is a step of its own (H7.4).

## 1. The test exit

ARM64's test exit is Arm semihosting's `HLT #0xF000`, which QEMU serves when it runs with `-semihosting-config`. On a
board without a debugger, HLT is an undefined instruction: the kernel's end would fault on a real Pi.

`power.c` therefore decides from the early tree, which the boot paths hand over before their first line (H7.2). The
test exit is taken on QEMU's `virt`, whose tree's root is compatible with `linux,dummy-virt`, and on any board whose
`/chosen` `bootargs` hold the word `witos.test-exit`. The runner passes that word to `raspi4b` with `-append`, unless a
boot asks for no test exit (`BootRequest.WithoutTestExit`). On every other board, the end of a boot goes straight to the
board's power.

## 2. Off and reset

After the test exit, or without it, the end of a boot goes by the first means the board has (ADR 0029):

- **PSCI**, through the conduit the tree's `/psci` names (H7.2): `SYSTEM_OFF` for a success, `SYSTEM_RESET` for the
  root task's reset;
- **the Raspberry Pi's watchdog**, the power management block the tree names `brcm,bcm2835-pm-wdt` (`/soc/watchdog@7e100000`,
  0xFE100000 through `/soc`'s ranges), driven as Linux's `bcm2835_wdt` drives it:
  - a reset writes `PM_WDOG` with a timeout of ten ticks (about 150 µs), then `PM_RSTC` with the full reset, each with
    the password 0x5A in the top byte;
  - a power off first writes partition 63 into `PM_RSTS` (0x555, its bits spread over every other bit), which the Pi's
    firmware takes for a halt and QEMU's `raspi4b` for a shutdown, then resets;
- **neither**: the kernel says so and halts.

The clock's start maps the watchdog's page. A failure halts without turning the board off, as before.

## 3. The framebuffer

`wit_platform_framebuffer_tree` is a new platform call. The Linux entry calls it while building the boot contract, and
the PC's and riscv64's platforms provide it empty. It fills the contract's framebuffer fields from the tree:

- **a `simple-framebuffer`** that is not disabled: its `reg` (translated), `width`, `height`, `stride` in bytes and
  `format` (`x8r8g8b8` or `a8r8g8b8` as BGRX; `x8b8g8r8` or `a8b8g8r8` as RGBX), as a firmware sets it up;
- **the Raspberry Pi firmware's framebuffer** (`brcm,bcm2708-fb`), which the firmware allocates on request through the
  VideoCore's mailbox (`brcm,bcm2835-mbox`, 0xFE00B880) and its property channel, as Linux's and U-Boot's drivers ask:
  1. the display's size (`0x00040003`; 800 by 600 where the firmware reports none);
  2. one message with the physical and virtual size, 32 bits a pixel, BGR order, the allocation with page alignment and
     the pitch.

**Addresses.** The mailbox reads its message from memory as its bus sees memory. The platform translates the message's
address through the `dma-ranges` of the mailbox's bus: `/soc`'s, bus 0xC0000000 for physical 0 over one gigabyte. The
message is cleaned from the data cache before the request and invalidated before the answer is read. The base the
firmware answers with is translated back through the same window, and taken as physical when it lies outside it: QEMU
answers so, and U-Boot masks the bus alias off.

**What the kernel takes.** A framebuffer of 32-bit pixels on a page boundary, whose pitch holds its width, rounded up to
whole pages. The Linux entry adds it to the reserved ranges of the memory map whatever the tree's memory says. The
kernel then validates and publishes it as the firmware bus's framebuffer device, as for ramfb (C2.1), so the display
service needs nothing new.

## 4. Measured

| Boot | What ran |
| --- | --- |
| `release-raspi4b` | `[BOOT] Framebuffer: 640x480, stride 640, BGRX at 0x000000003C100000 of 1228800 bytes, from the firmware through the VideoCore's mailbox`: QEMU's default display size, in the VideoCore's share above the tree's memory. `Devices: 1 in 1 page`: the framebuffer. The semihosting test exit, which the runner's `bootargs` ask for. |
| `release-raspi4b-off` | No `bootargs`: the end of the boot takes no semihosting, writes `[POWER] off through the watchdog`, and QEMU exits with 0. |
| `reset-raspi4b` | The root task asks for a reset; `[POWER] reset through the watchdog`, and QEMU leaves with 0 under `-no-reboot`. |

## 6. What is not yet

- **The board's time** (H7.4): a decision, recorded in the plan.
- **The display service on the Pi.** It needs a keyboard, which comes with DWC2's driver (H8).
- **The framebuffer's size on a real Pi.** The firmware answers the display's size from its HDMI or DPI configuration;
  the PocketTerm35's DPI panel is H9's on the Pi 5.
- **A real Pi's power off.** Partition 63 halts in the Pi's firmware, which keeps the board powered in a low state; H0.3
  measures what the board does.
