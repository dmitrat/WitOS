# H7.2 — The Raspberry Pi 4 on QEMU's raspi4b

H7.1 made the ARM64 platform one platform for every board a device tree describes. H7.2 boots the same kernel image on
QEMU's `raspi4b`, a model of the Raspberry Pi 4 Model B. The image is entered by the Linux arm64 protocol (H6) with the
Raspberry Pi firmware's own device tree. The platform takes three more things from the tree:

- the console;
- how the other processors start;
- the PSCI conduit, where the board has PSCI.

The kernel does not know it runs on a Pi. It knows the tree's bindings: a PL011 or the Pi's mini UART, a GIC-400 below
`/soc`'s `ranges`, a spin table. No `Kernel.Platform.Bcm2711` exists.

## 2. The console

`wit_platform_console_tree` resolves the console in this order:

1. `/chosen`'s `stdout-path`, without its options (`:115200n8`);
2. where the tree names none, the alias `serial0`.

Either value may be an alias, which `/aliases` resolves to a path, or a path itself. The node at the path must be one of:

- a PL011 (`arm,pl011`): QEMU's `virt` and the Pi's `uart0`;
- the Pi's mini UART (`brcm,bcm2835-aux-uart`), a 16550-like UART. A byte goes to `AUX_MU_IO` once `AUX_MU_LSR` bit 5 says
  the transmitter takes one.

Its `reg` is translated through `/soc`'s `ranges`. The firmware has set the line up, so no register of either UART's line
is written.

The Raspberry Pi firmware's tree names no `stdout-path`. Its `serial0` is the UART on the GPIO header's pins 8 and 10:
the mini UART by default, and the PL011 when `config.txt` gives the PL011 to the header (`dtoverlay=disable-bt`), when the
firmware swaps the aliases. QEMU's `raspi4b` connects its first serial port to the PL011 and its second to the mini UART,
so the runner gives it `-serial null` before the log's port.

**When the platform reads it.** The Linux entry hands the tree over before its first line. The UEFI loader hands it over
as soon as it has read the configuration tables; until then the console is `virt`'s PL011, the address of every board the
UEFI path boots today. A tree that names no UART the platform drives leaves the console silent rather than writing where
nothing is known. The page of the UART is the boot device the kernel maps across its switch to its own tables.

## 3. The processors

Each child of `/cpus` starts by its own `enable-method`, or `/cpus`'s where it names none:

- **`psci`**: CPU_ON through the conduit `/psci`'s `method` names: `hvc` on QEMU's `virt`, `smc` on `virt` with an EL2.
  The entry `wit_a64_secondary_entry` takes the kernel's number of the processor as its context.
- **`spin-table`**: the processor waits at its `cpu-release-addr` (QEMU's `raspi4b` and the Pi 4's firmware name 0xd8,
  0xe0, 0xe8 and 0xf0 for the four, the boot processor's first). The platform writes the address of
  `wit_a64_secondary_spin_entry` there and sends an event. A spin table passes no context, so that entry finds the
  processor's number by its MPIDR among the identities the architecture recorded when it prepared each processor.

**The release word.** It lies in page 0, which the firmware reserves (`/memreserve/` 0–0x1000). No translation of the
kernel holds page 0, so that a null pointer faults. `wit_a64_write_physical` maps that page as device memory at its own
address for the one write, which the waiting processor reads with its MMU off, and takes it away again. It refuses usable
memory, the kernel image and a page already mapped.

**EL2.** A processor of a spin table starts at the level its firmware left it in: EL2 on the Pi and in `raspi4b`. Both
entries therefore call `wit_a64_leave_el2`, the way out of EL2 that the Linux entry used to carry inline (H6) and now
calls too. It returns to its caller at EL1, or returns at once at EL1.

**PSCI at EL2.** `virt,virtualization=on` names PSCI by `smc`. `release-linux-el2-128` boots two processors now, where
H6 had one; its second processor starts by an SMC CPU_ON.

The processor line says how the board starts its processors:

```
Processor start: 2 by PSCI, 0 by spin table; PSCI conduit HVC        (virt, two processors)
Processor start: 0 by PSCI, 4 by spin table; PSCI conduit none       (raspi4b)
```

A board without PSCI cannot turn itself off or reset through it. The end of a boot then says so and halts after the test
exit, which QEMU still serves through semihosting. The Pi's watchdog is H7.3.

## 4. The root task on a board without devices or a clock

The root task (`tests/User/root.c`) assumed what `virt`, q35 and `pc` have. Neither assumption holds on `raspi4b`:

- **Devices.** The device table may be empty. `raspi4b`'s tree names no PCI bridge, and its devices join the table with
  their drivers (H8). The table is still checked: its version, a count within the kernel's 64 descriptors, its size in
  pages.
- **The clock.** UTC may be `UNSUPPORTED`: the board has no real-time clock, and the kernel never invents a time. A set
  through the clock capability makes it available, which is how SNTP will set it (H7.3). The root task now sets the
  time before it reads the frequency and the reading the set continues from.

`release-128` requires the kernel's `UTC at boot:` line on every ISA, so the boards that have a real-time clock are still
held to it.

## 7. What is not yet

- **The self-test kernel on `raspi4b`.** Its device fixtures drive the virtio block function by its ECAM configuration
  space, which a board without PCI does not have. As with QEMU's `pc` (H1.1), the board's gate is the release kernel's.
  The plan's `boot-128` and `boot-smp4` of `raspi4b` are therefore `release-raspi4b` on the board's four processors.
- **Time** (H7.3): SNTP of the network service through `CLOCK_SET`. The libc program then passes on `raspi4b` too.
- **The framebuffer and the board's power** (H7.3): the VideoCore's mailbox, and the watchdog for off and reset.
- **Devices from the tree** (H8): SD, DWC2 USB, GENET, PCIe.
- **The UEFI path on a Pi.** Its loader writes its first lines before it has the tree, to `virt`'s PL011. A Pi boots by
  the Linux protocol (ADR 0030), so nothing boots that way today.
- **The mini UART on a real Pi.** The firmware sets it up with `enable_uart=1`, which also fixes the core clock it runs
  from. Without that, the line is not set and nothing writes it. H0.3's session on the board measures it.
