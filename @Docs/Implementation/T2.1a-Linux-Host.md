# T2.1a — the Linux host

Plan step T2 builds WitOS on a Linux host as well as on Windows. Full parity waits for K8. Every scenario except the
release kernel boots a self-test kernel, and every self-test kernel embeds the frozen line's fixtures, which MSVC
builds. Until K8 removes the frozen line, Linux can therefore build everything except those fixtures. T2 is split
accordingly:

- **T2.1a** (this step) makes WitOS.Dev work on Linux: the tool, its process runner, the pinned LLVM and QEMU, layer 2's
  toolchain and the release kernels of both ISAs, with a Linux CI job and a container for local work.
- **T2.1b** runs the layer-2 scenarios on the release kernel, so that both hosts run them.
- **T2.2** brings full parity after K8.

R1 follows on the same host.

## What changed

**Processes.** The tool's child processes ran under Windows job objects alone, and every other host was refused.
On Linux, `UnixChildProcess` starts the program through `setsid`, so it leads a new session and process group. One
`SIGKILL` to the group then stops the whole tree, as terminating the job does on Windows. The runner confirms the end
by waiting until no process of the group exists.

The contract is the Windows runner's:

- output is captured bounded, at 8 Mi characters a stream, and an oversized stream ends the run at once;
- a timeout calls the stop callback, then stops the tree;
- a normal exit also stops what the root left behind;
- the file-backed form copies the pipes into the files QEMU's logs need;
- a program that does not exist fails as `Process.Start` reports it, a `Win32Exception`. The program is resolved first,
  since `setsid` would start anything.

The tool needs an init process that reaps orphans: `docker run --init` locally, and systemd on CI. Otherwise the zombie
of a stopped process keeps its group from emptying. The global refusal of non-Windows hosts is gone. A command that
needs MSVC fails where it looks for MSVC, saying that the frozen line's fixtures build on Windows until K8. `doctor`
reports that there is no MSVC, and a scenario looks for MSVC only when it builds fixtures, so the release kernel needs
none.

**Tools.** `Toolchain` names host executables with `Executable` (`.exe` on Windows alone) and finds QEMU's programs and
firmware through `QemuExecutable` and `QemuShareDirectory`. On Linux, `setup` does the following:

- **LLVM:** it verifies the LLVM 20.1.8 Linux x64 archive by SHA-256 (`LLVM_LINUX_ARCHIVE_SHA256`) and extracts the
  same tools the Windows host extracts from the installer: clang, lld (as `ld.lld` and `lld-link`), llvm-ar,
  llvm-objcopy, llvm-readobj, clang-format and the compiler's headers;
- **QEMU:** it builds QEMU 11.1.0 from download.qemu.org's source release, also by SHA-256, for the two system
  emulators, with no tools, no documentation and no user-mode emulation, into `.tools/qemu-11.1.0`. A stamp of the
  source hash and the options keeps a finished build;
- **substrate sources:** it fetches musl, compiler-rt, the LLVM runtimes and libc-test as on Windows. `tar` is the
  host's own on either host.

Decompressing one member of the 2 GiB archive takes minutes, so `format` pins clang-format by the SHA-256 of its own
bytes. A copy is used only while its bytes are the pinned ones.

**Images are the same on both hosts.**

- The EDK II images QEMU's install produces are byte for byte the Windows package's (`edk2-x86_64-code.fd`,
  `edk2-aarch64-code.fd` and their variable templates).
- The kernel's link records the PDB's name alone (`/pdbaltpath:%_PDB%`), so the image no longer depends on the
  directory it was built in. With that, `fingerprint` finds the x64 release kernel's code and data sections built on
  Linux equal to those built on Windows.
- The root task's flat image is identical byte for byte.

**QMP.** On Linux, QEMU 11.1 may close the QMP connection after its `SHUTDOWN` event and before the reply to `quit`.
The quit is now acknowledged by either the reply or that event with the reason `host-qmp-quit`. The timeout cleanup
test passes its 12 rounds on both hosts.

**Host tests.** Tests that need Windows carry NUnit's `[Platform(Include = "Win")]` with a reason
(`TestPlatforms`):

- MSVC's native images and their Windows references (`Native/*`, the STL and character-class differentials, the
  guest driver's quoted profile, the runtime boot evidence);
- contracts of the Windows API itself: the command-line round trip and a job with an external pipe owner.

The test child's no-pipes modes have a Unix branch: close-on-exec on descriptors 1 and 2 stands for a handle that is
not inheritable. On Linux, all 70 host tests that apply pass.

**The container and CI.** `build/linux/Dockerfile` is the local Linux host. It is the .NET SDK of `global.json` on
Ubuntu 24.04, by digest, plus what building QEMU needs and the libxml2 that the official lld loads. Copy the working
tree into a volume rather than building in the Windows checkout, so that each host keeps its own `.tools` and
`artifacts`:

```sh
docker build -t witos-linux build/linux
docker run --rm --init -v <checkout>:/host:ro -v witos-linux-work:/work witos-linux bash -c \
  "rsync -a --delete --exclude .tools/ --exclude artifacts/ --exclude bin/ --exclude obj/ /host/ /work/witos/ &&
   cd /work/witos && dotnet build WitOS.slnx -c Release &&
   dotnet run --project tools/WitOS.Dev -c Release --no-build -- setup"
```

CI's `linux-host` job on `ubuntu-24.04` runs the following, caching the two pinned archives and the built QEMU:

- the build;
- the host tests and the QEMU cleanup test;
- `setup` and `doctor`;
- the x64 and ARM64 release kernels;
- `format-check`.

## Tests

On Linux (the container and CI):

- the host tests: 70 pass, and the Windows-only ones are reported by platform;
- `QemuCleanup`: 12 rounds;
- `release` and `release --arch arm64` pass at 128 and 512 MiB;
- `format-check` is clean;
- `setup` takes about five minutes with the QEMU build.

On Windows, the x64 and ARM64 suites, both release kernels, the host tests, `QemuCleanup` and `format-check` pass
unchanged.

## Limits kept explicit

- No self-test scenario builds on Linux until K8, because their kernels embed the frozen line's MSVC fixtures. T2.1b
  moves the layer-2 scenarios to the release kernel.
- QEMU on Linux is built with the host's compiler and libraries: the source is pinned, the build environment is the
  container's or the runner's.
- A descendant that starts a session of its own escapes the process group. The tools WitOS runs never do.
