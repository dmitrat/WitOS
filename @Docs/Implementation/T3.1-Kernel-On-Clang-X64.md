# T3.1 — the x64 kernel on clang

Plan step T3 moves the kernel to the toolchain that already builds layer 2, so that one compiler, one assembler and
one linker build all of WitOS and a Linux host can build it too (T2). T3.1 moves the x64 kernel and its EFI loader.
They are now compiled by the pinned clang 20.1.8 and linked by the pinned `lld-link`, and their assembly is GNU syntax
for clang's integrated assembler. The ARM64 kernel keeps MSVC and armasm64 until T3.2. The fixtures of the frozen line
keep MSVC and MASM until they go at K8. Nothing in the kernel's behaviour, its ABI or its boot contract changes: the
same image format, the same calling convention and the same scenarios pass.

## What changed

**The target.** The kernel and the loader are linked into one UEFI application, so the image stays PE/COFF and the
code stays in the Microsoft x64 convention that UEFI and the kernel's assembly use. clang compiles for
`x86_64-unknown-windows` (the MSVC environment): C17, `-ffreestanding -nostdinc` (the kernel includes no header but
its own), `-fno-stack-protector`, and `-O0`, as MSVC's `/Od` built it. Warnings are `-Wall -Wextra -Werror`, and
`-g -gcodeview` gives the linker the records of its PDB. `lld-link` takes `link.exe`'s options unchanged:
`/subsystem:efi_application`, `/entry:efi_main`, `/nodefaultlib`, `/fixed:no`, `/dynamicbase:no`, the map and the
PDB. The image check after the link is the same (EFI subsystem, x64 machine, no imports), and so is the release
kernel's map check for self-test code.

`KernelArchitecture.KernelTriple` names the kernel's triple, and null keeps an architecture on MSVC; ARM64 has null
until T3.2. `setup` now also extracts `lld-link.exe` from the verified LLVM installer, and `doctor` reports each
kernel's compiler. A scenario's `build.txt` names the kernel's compiler and, separately, the MSVC tools of the
fixtures.

**No MSVC intrinsics.** The x64 architecture and the q35 board used MSVC's intrinsics (`__readcr3`, `__writemsr`,
`__outbyte`, `_enable` and the rest), each declared locally under `#pragma intrinsic`. They are now the inline
functions of `src/Kernel.Arch.X64/include/witos/x64_instructions.h`: `wit_x64_read_cr3`, `wit_x64_write_msr`,
`wit_x64_out8`, `wit_x64_enable_interrupts` and so on, clang inline assembly in the architecture's directory, where
x64 instructions belong. Every function that changes processor state or reaches a device is a compiler barrier, so no
load or store moves across it. The debug registers, whose number is encoded in the instruction, are read and written
through a switch on the number.

**GNU assembly.** The five MASM files of the architecture and the self-test's became GNU syntax (`.S`,
`.intel_syntax noprefix`), instruction for instruction:

- `entry.S`: the 256 vectors come from one `.altmacro` macro and `.rept`, as MASM's `REPT` produced them, and the
  table of their addresses is 256 absolute relocations;
- `context.S`, `user_entry.S` and `secondary_entry.S`: MASM's `db 048h` before `fxsave` is `fxsave64`, the far return
  that reloads CS stays the bytes `48 CB`, and a variable is reached RIP-relative, as MASM reached it;
- `tests/Kernel.X64/self_test.S`: the fault triggers and the preemption workers.

**The compiler's helpers.** clang calls `memcpy` and `memset` for structure copies and initialization and `__chkstk`
for frames larger than a page, as ARM64's MSVC does. `src/Kernel.Arch.X64/compiler.S` holds all three in assembly,
so that no C body can be lowered into a call to itself. `memcpy` and `memset` save RDI and RSI, which the Microsoft
convention keeps. `__chkstk` is the probe the kernel linked before, unchanged.

**The frozen line's probe.** `src/Kernel.Arch.X64/chkstk.asm` was the one file of the architecture that user images
shared: the host runtime fixture, the storage image, the NativeAOT overlay (`runtime-overlay.cmake`) and its probes
assemble it with ml64. The kernel no longer links it. The rule that every file of the architecture links into the
kernel (`ArchitectureHoldsOnlyKernelSourcesTest`) therefore moved it to `src/Runtime.Native/X64/chkstk.asm`, the
frozen line's native runtime. Its bytes are unchanged, and every user names the new path.

**Warnings clang adds.** clang flagged three things MSVC passed:

- a mixed `&&` and `||` in `cpu_cache.c`, now parenthesized;
- the self-test helper `require` of `scheduler.c`, now defined under `WITOS_SELFTEST` alone;
- the execute-data probe page of `paging.c`, now defined only for the scenario that executes it.

## Tests

The x64 suite passes with the clang kernel: every boot, self-test, fault and layer-2 scenario of
`dotnet run --project tools/WitOS.Dev -- test`. The ARM64 suite is unchanged and passes. Host tests and
`format-check` pass.

## Limits kept explicit

- The kernel is still unoptimized (`-O0`), as it was under MSVC. Optimizing it is a step of its own, with its
  timing and its latent assumptions checked.
- The ARM64 kernel is T3.2. The frozen line's fixtures, MASM and ml64 stay until K8.
- MSVC is still required on the development host, for the ARM64 kernel and the frozen line.
