# W3.2 — ASP.NET Core: the shared framework in the install, a Kestrel application answers the runner

Plan step W3.2 (phase W, M7; Implementation Strategy §67 and §68, item 5; W0 decision 9). After W3.1 the Unix form of
.NET on WitOS has sockets, names, HTTP and TLS; this step adds the ASP.NET Core shared framework to the .NET install and
proves it with the gate the strategy names: an ordinary Kestrel application, published by the stock SDK without a RID,
runs unchanged in the guest and answers requests from outside.

## 1. What was measured

- **What an application needs.** A web project's publish without a RID leaves `Microsoft.AspNetCore.App` to the install:
  its runtimeconfig names the framework at `10.0.0` with the roll-forward of the SDK, and hostfxr resolves it under
  `/dotnet/shared/Microsoft.AspNetCore.App/<version>/`, reading that directory's `Microsoft.AspNetCore.App.runtimeconfig.json`
  for the framework's own reference to `Microsoft.NETCore.App` and hostpolicy its `Microsoft.AspNetCore.App.deps.json` for
  the assemblies. The framework is managed alone: upstream's runtime packs for Linux hold 141 assemblies, a deps.json and a
  runtimeconfig and nothing native.
- **Why not upstream's packs.** W0 decision 9 planned to take the framework from the stock SDK's packs. Measured against
  the three ISAs, that does not hold: upstream publishes `Microsoft.AspNetCore.App.Runtime.<rid>` per RID (10.0.12:
  linux-x64 12.9 MB, linux-arm64 12.4 MB, every assembly with ReadyToRun code over its IL, 25.7 and 28.6 MiB of assemblies),
  and none for riscv64. CoreCLR is strict about such code: `PEImageLayout::Load` refuses an image whose ReadyToRun header
  is for another machine (`LoadedImageLayout`: `COR_E_BADIMAGEFORMAT` when `IsNativeMachineFormat()` is false), and
  `ReadyToRunInfo::Initialize` throws the same for a layout that reached it ("be strict about disallowing machine
  mismatches"), with no fall back to the IL. The machine's OS override is Linux's (`IMAGE_FILE_MACHINE_NATIVE_OS_OVERRIDE`
  0x7B79, since the layer-2 triple defines `__linux__`), so a Linux pack's code is native on WitOS of the same ISA (C2.5's
  SDK), but an x64 pack on riscv64 does not load, as C2.5 saw with the SDK. The official pack's `versions.txt` names the
  commit `95017c71…` for 10.0.12, where the public tag `v10.0.12` is `cb21a42e…`.
- **The framework from its source.** dotnet/aspnetcore at `v10.0.12` builds its runtime pack with the repository's own
  build, IL alone: `eng/build.sh -c Release --no-build-nodejs --no-build-java --no-build-native --projects
  src/Framework/App.Runtime/src/Microsoft.AspNetCore.App.Runtime.sfxproj /p:CrossgenOutput=false
  /p:DotNetFinalVersionKind=release /p:TargetRuntimeIdentifier=linux-x64 /p:NuGetAudit=false`. The shallow clone is
  24 MB with one submodule the managed build needs (`src/submodules/MessagePack-CSharp`, SignalR's MessagePack protocol;
  googletest serves the native tests alone); Arcade bootstraps the SDK the repository's `global.json` names (10.0.111,
  702 MB under `.dotnet`); the restore and the build take some three minutes on the Linux host (1:07 incremental) and
  leave the checkout clean (`artifacts/` and `.dotnet/` are ignored). Without `NuGetAudit=false` the restore fails:
  `System.Security.Cryptography.Pkcs` and `Xml` 10.0.12 have advisories of the day, which the repository treats as
  errors (NU1902, NU1903; R8.1's reasoning). The pack holds 141 assemblies, 12.15 MB, none with a managed native header;
  the repository's own assemblies carry Arcade's placeholder file version `42.42.42.42424`, as the install's
  `Microsoft.NETCore.App` already does for 172 of its files, and the `Microsoft.Extensions.*` assemblies the build takes
  from dotnet/runtime's packages `10.0.1226.42308`; `versions.txt` names `cb21a42e…` and `10.0.12`; the runtimeconfig names
  `Microsoft.NETCore.App` `10.0.12` with `LatestPatch`. `TargetRuntimeIdentifier` names the pack's path alone: the IL does
  not depend on it.
- **The package.** The framework adds 143 files and some 12 MB to a package. The largest package of the gates is the
  NuGet libraries' scenario's (N2.1: xUnit's application carries Roslyn), 130 MB on x64 with W3.1's install, 142 MB with
  the framework — over `WIT_PACKAGE_MAX_BYTES`, 128 MiB, which CI's three legs met at that scenario after the ASP.NET Core
  scenario passed. The limit was the loader's: it reads the package into the boot contract's 128 extents
  (`WIT_MAX_STORAGE_EXTENTS`) of a MiB each; the extents' count is the contract's, their size the loader's.
- **Kestrel on the loopback and the any address.** `ListenAnyIP` binds `[::]` with dual mode and, where IPv6 is not
  supported (`Socket.OSSupportsIPv6` was false on WitOS until W4.3, since when the line reads `http://[::]:8080`),
  `AnyIPListenOptions` binds `0.0.0.0` instead and says so;
  HTTPS is `SslStream` on the server's side with the certificate the application makes, through OpenSSL (W3.1).
- **The first boot.** The application died in `WebApplication.CreateBuilder`: the host adds `appsettings.json` with
  `reloadOnChange`, `PhysicalFileProvider.CreateFileWatcher` constructs a `FileSystemWatcher`, and that is
  `PlatformNotSupportedException` on WitOS (N1's recorded difference: the namespace service sends no notifications).
  `DOTNET_USE_POLLING_FILE_WATCHER=1`, the runtime's own knob for file systems without notifications, makes the provider
  poll and construct no watcher (`ReadPollingEnvironmentVariables` sets `UsePollingFileWatcher` and `UseActivePolling`
  together). The same boot showed the device manager's TCP probe listening 300 s of the guest's time for a runner that
  never connects: W1.2b ran it in every boot with the adapter, when `runtime-devices` was the only one, and the
  compatibility and published scenarios boot with the adapter since W3.1.

## 2. The change

- **The pin.** `build/runtime/aspnetcore.lock.json`: dotnet/aspnetcore `v10.0.12` by its commit, the release that pairs with
  the runtime's pin (a host test requires the versions equal), with the submodule the build needs by its commit, MIT.
- **`AspNetCoreFramework`.** `BuildAsync` on the Linux host, once for the pin and the options: the commit fetched shallow
  with its submodule under `.tools/upstream/aspnetcore-<version>` (as the runtime's checkout is), the repository's own
  build of the runtime pack with ReadyToRun off, the pack's assemblies, runtimeconfig and versions file extracted under
  `artifacts/aspnetcore/<version>`; every assembly must be IL alone (the CLI header's ILONLY flag, no managed native
  header), at least a hundred of them. `runtime-witos` builds it before the first scenario that lays the install.
  `FrameworkFilesAsync` lays it under `/dotnet/shared/Microsoft.AspNetCore.App/<version>/` for every ISA: the assemblies,
  the runtimeconfig the build wrote, which must name the install's `Microsoft.NETCore.App`, and a deps.json the tool writes
  for the architecture as it writes `Microsoft.NETCore.App`'s (R5, `FrameworkDeps`); a build of another commit is refused.
  CI uploads the framework with the install.
- **The runner.** `BootActionKind.Http` (`BootAction.Http`): an HTTP request to the guest's forwarded port, GET or POST,
  answered with 200 and the expected text, or the boot ends, through `NetworkPeer.HttpAsync` on one `HttpClient` for the
  boot, since Kestrel keeps the connection alive. `RuntimeApps.BootAsync` takes a forward and actions and boots with the
  adapter when it serves HTTPS or reaches a port.
- **The application and the scenario.** `tests/Runtime.Witos/WebApp`: the web SDK's minimal API on Kestrel, in the
  solution, with the template's `appsettings.json`; it serves `/` (a text), `/json` (`Results.Json`), `/echo` (a POST's body
  back) and `/stop` (`IHostApplicationLifetime.StopApplication` once its own check ended), reports the addresses it listens
  on, requests its own `/json` over HTTPS with a certificate it makes at start, trusted by thumbprint, counts the requests it
  served and exits with 0; the ports come from the configuration, so that the host test runs it on free ones. The
  `runtime-aspnetcore` scenario (`RuntimeAspNetCore`, after `runtime-compatibility` in `runtime-witos`) publishes it with
  the stock SDK and no RID, runs it through `dotnet` beside the device services on four processors (P2) with the adapter and
  a forward of port 8080, and the runner requests `/`, `/json`, a POST to `/echo` and `/stop` once the application reports
  listening; the scenario requires the listening line, the HTTPS check, `served 5 requests, exit 0` and the exit with 0.
  Host tests cover the actions, the peer's request through the forward and the application on the host.
- **The install's environment.** `DOTNET_USE_POLLING_FILE_WATCHER=1` in `/etc/environment`, beside the GC's and the
  JIT's knobs: every process polls for file changes through `PhysicalFileProvider`, and `FileSystemWatcher` itself stays
  the recorded difference.
- **The package's quota.** The loader reads the package into extents of `WIT_PACKAGE_EXTENT_BYTES`, 2 MiB, so that the
  contract's 128 extents hold `WIT_PACKAGE_MAX_BYTES` of 256 MiB (the root task's image keeps its extents of a MiB); the
  kernel's validation of the contract (each architecture's `paging.c`) takes the two constants where it took a MiB and
  128 MiB, the tool's writer refuses the same quota, and the native harness of the loader's storage expects the extents
  the constant gives. The boot contract's layout is unchanged. The boot disk (`FatImage`) grows with its files: the 32 MiB
  layout, then FAT16 volumes of 128, 256 and 512 MiB whose clusters grow with them (8, 16 and 32 KiB), the FAT keeping its
  64 sectors; the libraries scenario's 142 MB took the 256 MiB volume.
- **The TCP probe's mark.** The device manager's probe listens for the runner only where the package holds
  `/etc/witos/tcp-probe-inbound`, which `runtime-devices`' package does; a scenario with the adapter for the runner's
  servers or a port of its own reports that no connection is expected and goes on.
- **The records.** `build/compatibility-matrix.json` (ASP.NET Core Supported), the matrix, `Compatibility-Differences.md`
  (an ASP.NET Core row and the polling of file changes), AGENTS.md, the plan, the completed log and W0 decision 9's note.

## 3. What ran

- **The hosts.** The tool's suite: 139 passed, among them the pin paired with the runtime's, the install's files and
  deps.json from a build (a build of another commit or for another runtime refused), the actions, the peer's request
  through the forward against a local server, and the application on Windows answering the scenario's requests with its
  own HTTPS check over Kestrel; CI's `boot`, `boot-arm64` and `windows-publish` jobs green on the step's first commits.
  CI's three Linux legs of those commits passed `runtime-aspnetcore` on x64 and met the package's quota at
  `runtime-libraries` (§1), and the run of the quota's first form panicked at the contract's validation, which the
  change took along with the boot disk and the loader's harness (§2).
- **The first boot** (x64, the container) died in `WebApplication.CreateBuilder` with `PlatformNotSupportedException`
  from `FileSystemWatcher` and showed the TCP probe's 300 s (§1); the second passed with the environment's knob and the
  probe's mark.
- **x64** (the container, on the tree of W3.1's run, `runtime-services`, `runtime-aspnetcore` and `runtime-libraries` in
  nine minutes): the framework built from `cb21a42e…` — 141 assemblies, IL alone — and the services published again; the
  package of 970 files and 116 MB; `[DEVICES] network TCP probe: no connection of the runner expected`; Kestrel
  `listening on http://0.0.0.0:8080 and https://0.0.0.0:8443`; the runner's `GET /` (32 characters), `GET /json` (91),
  `POST /echo` (26) and `GET /stop` (8) answered 200 from `10.0.2.2` through the forward; `https self-check: ok, 91
  characters`; `served 5 requests, exit 0`; the command exited with 0. `runtime-libraries` with the package of 1059 files
  and 142.2 MB in the 256 MiB volume: NUnit's 7 and xUnit's 6 tests passed.
- **ARM64** (eleven minutes): the same lines, `/json` and the self-check of 93 characters, the libraries' package of
  142.6 MB; **riscv64** (twelve minutes): 95 characters, 144.0 MB. Every scenario passed on the three ISAs.
