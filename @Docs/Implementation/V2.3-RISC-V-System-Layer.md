# V2.3 — The system layer on riscv64: libwitos, started programs, the shared library, libc-test and the sysroot on the third ISA

Plan step V2.3, the third slice of V2 (layer 2 on riscv64), 2026-10-17. V2.1 and V2.2 brought musl and the C++ runtime
to `riscv64-unknown-linux-musl`; this slice brings the rest of the system layer — libwitos with its loader and the
process manager, started programs static and dynamic, `libc.so` as the dynamic linker at `/lib/ld-musl-riscv64.so.1`,
the shared C++ runtime, libc-test, and the sysroot with its ABI-2 check — and proves it with the four scenarios the two
other ISAs have had since phase S: `process`, `spawn`, `libc-test` and `sysroot`, all under `test --arch riscv64` now
that `KernelArchitecture.SystemLayer` holds for riscv64. Layer 2 is whole on the three ISAs; the runtime is V2.4.

## 3. ABI-2 1.1

Every sysroot build requires `libc.so` to export exactly the names `build/abi2.json` records for the ISA. riscv64's
`libc.so` exports arm64's 1,644 names and three more — `__riscv_flush_icache` and `riscv_flush_icache`, Linux's riscv
interface musl gives every program (the flush takes the system call path, `ENOSYS` on WitOS until the runtime maps it to
`CODE_PUBLISH`, V2.1), and `__longjmp`, which musl's riscv64 `longjmp.S` leaves visible — so the record takes riscv64's
list as ABI-2 1.1: an addition, x64's and arm64's names unchanged, as RFC 0011 §10.2 has it. The host test requires the
three ISAs' lists.

## 5. Findings

1. **An alternate stack of exactly `SIGSTKSZ` bytes.** musl's `SIGSTKSZ` is 8,192 on x86_64 and riscv64, the kernel's
   `WIT_EXCEPTION_STACK_MINIMUM`; the libc rounded the range's base up to 16 bytes and its end down, so a stack that
   is not 16-byte aligned lost bytes and fell under the minimum (`ENOMEM`). x86_64 and aarch64 never showed it: clang
   aligns a large `char` array to 16 bytes there, and aarch64's `SIGSTKSZ` is 12,288. On RISC-V clang aligns the array
   to one byte, and libc-test's `regression/sigaltstack` failed in its dynamic form by its layout alone. The base now
   rounds down: the kernel and the library write at the top of the range only, so the bytes below `ss_sp` within its
   16-byte unit are never touched and only widen the bound; when they lie in a page that is not the program's, the range
   starts at `ss_sp` rounded up as before. The program reads its own `ss_sp` and `ss_size` back. The change runs on the
   three ISAs and libc-test passes on all.
2. **`math/powf` on riscv64.** The same regression of musl's `powf` as on the other ISAs (`ucb/powf.h:103`) and four
   subnormal cases of the same function; the test leaves the selection on riscv64 with the reason recorded in the S7.2
   document.
3. **The ISA name of every program.** Seven layer-2 programs and the root task named `aarch64` as their fallback ISA;
   the runtime's six runners did too and are named now, for V2.4.
4. **musl's `crti` and `crtn` on riscv64 are empty C files**, not assembly: the sysroot builds the objects from
   whichever the tree has.
5. **libc.so exports three names more on riscv64**: `__riscv_flush_icache` and `riscv_flush_icache`, Linux's riscv
   interface, and `__longjmp`, which musl's riscv64 `longjmp.S` leaves visible; ABI-2 1.1 records them.
6. **Nothing of the loader, the process manager or the dynamic linker needed a riscv64 change**: the started programs,
   `libc.so`, `dlopen`, the TLS descriptors and the shared C++ runtime ran at their first boot.
