# R3.3 — CoreCLR's M3 acceptance, and x18 freed

R3.2 ran a managed `Main` under CoreCLR through the JIT. This slice runs the M3 acceptance under CoreCLR on both ISAs
and frees x18 for ARM64 code. Together these complete R3.

```
[M3] CoreCLR on x86_64: 32 runs passed, 0 failed
[M3] CoreCLR on aarch64: 32 runs passed, 0 failed
```

## The acceptance under CoreCLR

`tests/Runtime.Witos/Acceptance` is the program NativeAOT's acceptance compiles ahead of time ([R2.2](R2.2-M3-Acceptance.md)).
It runs four cycles of eight probes:

- hardware faults, made managed exceptions;
- two-pass exception dispatch with filters and `finally`;
- finalization with resurrection;
- managed threads stopped for the GC, both in a loop without calls and in `Monitor.Wait`;
- thread creation beside parked threads;
- an allocation the GC cannot serve;
- the thread pool;
- waits.

The runtime is the only change. The SDK's C# compiler builds the same sources against the reference pack, and
`corerun` runs the assembly, so the JIT compiles every method.

The program names its runtime in its last line. It prints `CoreCLR` when `RuntimeFeature.IsDynamicCodeCompiled` is
true and `NativeAOT` otherwise. NativeAOT's required line is unchanged. The program used to return 101 when dynamic
code was supported; that guard is gone, because the two required lines now tell the runtimes apart.

### The package

The scenario `runtime-coreclr-acceptance` boots the same layout as `runtime-corerun`. Two things changed:

- **The framework's libraries are computed.** The tool takes every library the program reaches through its assembly
  references, transitively, by reading their metadata with `System.Reflection.Metadata`. This replaces R3.2's hand
  list. `corerun`'s TPA list is every assembly of its directory, so the package carries only these libraries. CoreLib,
  which every assembly references, comes apart.
- **`corerun` receives the properties a host takes from a program's `runtimeconfig.json`.**
  - `System.Globalization.Invariant=true`, since the system layer has no ICU. RFC 0015 §8 takes invariant mode until
    R4.
  - `RUNTIME_IDENTIFIER=witos-<arch>`. `RuntimeInformation.RuntimeIdentifier` read `unknown` without it.

`corerun_init.c` names the program through `CORERUN_ASSEMBLY`, which the package's build defines.

### What it found

The first run ended in `FailFast`: "Couldn't find a valid ICU package". The fault probe's `NullReferenceException` had
loaded its message resources, and resource lookup asks globalization for the neutral language. With invariant mode
set, all 32 runs passed on both ISAs at the next attempt.

The probes exercised a lot of the system layer underneath CoreCLR:

- the PAL's signal handling (a `SIGSEGV` handler on the guarded alternate stack, R3.2a);
- the PAL's exception unwinding through CoreCLR's libunwind;
- the GC's thread suspension through activations;
- futex waits, the thread pool's worker threads and timed waits.

None of them needed a change.

## x18 freed

Until K8.4b the kernel reset x18 to its compiler TLS on every return to EL0, so layer 2 compiled with `-ffixed-x18`.
K8.4b made x18 an ordinary register of a thread, which the kernel saves and restores like the others. R3.3 removes the
flag in two places:

- **`KernelArchitecture.ClangOptions`** is now empty for both ISAs. Every layer-2 build rebuilds: musl, compiler-rt's
  builtins, LLVM's runtimes, the sysroot's objects, the root task and the mechanism fixtures.
- **The runtime's toolchain patch** (`eng.common.cross.toolchain.cmake`) no longer adds the flag for `witos-arm64`. The
  native runtime rebuilds.

Compiled C and C++ code may now allocate x18. Both acceptances pass without the flag.

## The CPU features user code sees

R3's plan entry asked for ISA extensions masked by the kernel's context profile. The kernel's context saves x87/SSE on
x64 and V0–V31 with FPCR and FPSR on ARM64, and both ISAs hide everything beyond that:

- **x64.** The kernel keeps `CR4.OSXSAVE` clear, so CPUID reports no OS support for extended state. CoreCLR checks
  that bit before it uses AVX.
- **ARM64.** libwitos passes `AT_HWCAP` 0, so CoreCLR uses its baseline.

## The scenario

`runtime-witos` boots `runtime-coreclr-acceptance` on each ISA after `runtime-corerun`. It requires
`[M3] CoreCLR on <isa>: 32 runs passed, 0 failed` and the root task's report of status 0. The command of the same name
boots it again from the built tree.

## Limits kept explicit

- **Quotas are still tight.** Each shared memory chunk costs one of a system layer process's 32 objects and 64
  handles. The acceptance fits in them.
- **Every method is JIT-compiled.** No ReadyToRun code exists for `witos`.
- **Globalization is invariant** until R4, which brings culture data or keeps invariant mode as a decision.
- **There are no hosts yet.** `dotnet`, `hostfxr` and `hostpolicy` arrive in R5. Until then `corerun` stands in for
  them, and the properties a runtimeconfig would give come on its command line.
