# S7.2 — libc-test's math suite

Plan step S7.2 completes the substrate's acceptance (phase S, S7). libc-test's math suite (`src/math`, 199 tests)
now runs the way the rest of libc-test has run since S7.1: every test is a program of its own in a process of its
own, built dynamically, as libc-test builds the math tests. Passing the suite took one kernel change, four of musl's
own fixes from after the 1.2.5 release and one compiler option. Three tests stay out on an ISA, each for a recorded
reason. ABI-1 becomes v69; nothing of libc-test is patched.

## What changed

**The selection.** `tests/User/libc-test.json` lists every test of `src/math` at the pinned commit (`math`) and adds
libc-test's `src/common/mtest.c` to the support sources. `LibcTestSuite.BuildProgramsAsync` builds the math tests
dynamically alone, beside the `dynamicOnly` tests. `mathExcluded` maps a math test to the ISAs on which it stays out,
and the tool refuses an entry that names no listed test or an unknown ISA.

**`MEMORY_PROTECT` over adjacent reservations (ABI v69).** The root task's loader (S5.2) maps a writable segment as
anonymous objects of at most 64 pages, and each object's mapping is a reservation of its own. `ld.so` makes a
program's RELRO range read-only with one `mprotect`, and the libc hands memory it did not map to the kernel as it
stands. In `math/sin` that range is 110 pages of tables, so it spans two mappings. `MEMORY_PROTECT` answered
`NOT_RESERVED`, and the dynamic linker stopped with "RELRO protection failed" in `atan`, `cos`, `pow`, `sin` and
`tan`.

`MEMORY_PROTECT` now covers one reservation or a run of adjacent ones, as Linux's `mprotect` covers adjacent mappings:

- it first checks that the run covers the whole range (a gap is `NOT_RESERVED`);
- it then checks each part, with a mapping of an object held to its own rights;
- only after both checks does it change a page, so a refused call still changes nothing.

No composition of existing calls does this atomically, and the libc does not know where the loader's reservations
end. `tests/User/root.c` checks the call on both ISAs with two plain pages followed by a read-only mapping of an
object:

- a writable protection of the run is `DENIED` and leaves the plain pages read-only;
- `NONE` and `READ` over the run succeed;
- after the mapping is released, the gap makes the call `NOT_RESERVED` and the plain pages stay writable.

The test reads each page's protection through `MEMORY_QUERY`, which writes into the first page.

**musl's own fixes (`patches/musl`).** Four failures on x86_64 are bugs of musl 1.2.5 that musl fixed after the
release. Their commits are backported unchanged, one patch per file, and `src/Substrate/musl.lock.json` pins the bytes
each patch starts from:

| Patch | musl commit | Fault | libc-test |
| --- | --- | --- | --- |
| `fma.c` | 9683bd62 (2024-03-14) | `fma(x, y, 0)` added the zero and lost the sign of a product that rounds to -0 | `math/fma` |
| `fmaf.c` | a9764402 (2026-08-11) | an inexact halfway result in the float's subnormal range was rounded twice | `math/fmaf` |
| `powl.c` | ec9daea2 (2026-08-25) | an overflow or underflow of a negative x to an odd integer lost its sign | `math/powl` |
| `expl.x86_64.s` | 27b485a2 (2026-08-26), x86_64 part | `expl(x)` for x <= -16384 returned 2^trunc(x) instead of zero | `math/expl` |

The library compiles a patched file from its patched text under `artifacts/substrate/<isa>/patched`, at its path in
musl's tree, in `libc.a` and in `libc.so` alike. An architecture's file that replaces a patched generic file is
compiled from an unchanged copy beside the patched text, because musl's architecture files include the generic one by
its relative path where the instruction is missing: x86_64's `fma.c` includes `"../fma.c"` without FMA.

**Contraction off (`-ffp-contract=off`).** `atanh` and `yn` of aarch64 missed libc-test's error bounds (1.6 and 2.2
ulp). Under `-std=c99`, GCC, musl's compiler, never contracts `a*b+c` into a fused multiply-add, while clang contracts
in every language mode. musl's sources assume no contraction, so the library's options now include
`-ffp-contract=off`, which gives clang GCC's reading of musl's options. A configure change to the same effect was
proposed on musl's list in 2025 and is not in musl yet; Rich Felker prefers `#pragma STDC FP_CONTRACT OFF` in the
sources, with the option as a fallback. x86_64 is unaffected, since its baseline has no FMA instruction. The libc-test
programs keep libc-test's own options.

## Left out, by ISA

- **`math/remquol` on x86_64: QEMU's x87 emulation.** musl's x86_64 `remquol` takes the low bits of the quotient
  from the C0, C1 and C3 flags that `fprem1` sets. Under QEMU's TCG, `fprem1` leaves those flags clear. A temporary
  probe in the guest read the status word `0x3000` after `fprem1` of -1.75 by -0.5 (quotient 4, so C0 must be set).
  After `fprem` of 5 by 1 (quotient 5) it read `0x2b00`, with C0 and C1 set. The remainders were right, and every
  quotient the test checks came back 0. `fprem`'s flags survive, so the kernel's preservation of the x87 state is not
  the cause. The test passes on aarch64, whose `remquol` is generic C.
- **`math/fmal` on x86_64: the underflow flag.** In round-to-nearest,
  `fmal(-0x1p-10000, 0x1.0000000000001p-6445, 0x1p-16382)` returns the right subnormal
  `0x1.fffffffffffffffcp-16383`, but raises `INEXACT` without `UNDERFLOW`. musl's 80-bit `fmal` leaves the underflow
  flag to the x87's own arithmetic in `add_and_denormalize`, and its final scaling into the subnormal range can be
  exact. QEMU's x87 emulation is the other suspect. Without a run on hardware the cause stays open. The test passes on
  aarch64, whose `fmal` is the 128-bit one.
- **`math/powf` on both ISAs: musl's `powf`.** In upward rounding, `powf(0x1.fffffep+127, 1)` raises
  `INEXACT|OVERFLOW` (`ucb/powf.h:103`), identically on both ISAs. This regression has been reported against libc-test
  since musl 1.1.23 introduced the current `powf` ("math/powf regression on d28cd0ad commit", musl list, 2019-12-04),
  and musl has not changed it.

## Tests

The `libc-test` scenario requires `[LIBC-TEST] musl 1.2.5 on <isa>: all ` on both ISAs:

- x86_64: 375 runs, the 179 of S7.1 and 196 math tests, all pass;
- aarch64: 377 runs, the 179 of S7.1 and 198 math tests, all pass.

The root task's run check passes in every scenario of both suites.

## Limits kept explicit

- No run of libc-test on Linux hardware backs the analysis of `fmal` and `remquol` yet.
- The backports go when musl's pin moves to a release that contains them.
- `-ffp-contract=off` is WitOS's reading of musl's options until musl settles the question (a pragma or the option).
- libc-test's API checks (`src/api`) are not selected.
