# D6.1 — Stopping the services, and a disk across reboots

D6.1 is the first step of D6 and does two things:

- **An orderly stop.** The system's services now stop before the root task ends, so a volume is unmounted rather than
  cut off.
- **A disk across reboots.** The runtime-devices scenario boots twice with one data disk: the first boot writes it,
  and the second finds what the first wrote.

This is M5 §51's persistence test: boot, write `/data/...`, shut down, boot again, read. It also covers the storage
document's §98, unmounting: stop new operations, complete the active ones, flush the filesystem's metadata, flush the
block layers, release the capabilities.

## Why a stop was needed

When the root task ended, the kernel ended every created process where it stood (K5.2c). The namespace service held
the ext4 volume mounted, with `needs_recovery` set since its mount (D4.3). So every boot ended with:

- an ext4 volume flagged as needing recovery;
- FAT volumes the namespace service never flushed;
- devices left running with pinned queues.

Every change was a whole transaction with an empty journal after it, so nothing was lost, but nothing said so either.

## The stop protocol (`witos/manager.h`)

**The message.** A creator asks its service to stop with a `WitServiceStop` on the channel it granted the service:

- `Version` and `Size`;
- `Operation` = `WIT_SERVICE_STOP`;
- `Deadline`, the absolute monotonic deadline of the answer.

It is 24 bytes, so it cannot be mistaken for the 16-byte `WitServiceStatus`.

**What a service does.** It:

1. stops the services it started, passing the deadline on;
2. ends its own work so that nothing of it is lost;
3. answers a `WitServiceStatus`: zero, or the errno value of what it could not finish;
4. ends.

**The parts.**
- `OutWit.OS.Communication.ServiceStop` encodes and checks the message. Its `Request` sends a stop and waits for the
  answer or the service's end. An answer left before the end is still queued; an end without one is `ECHILD`.
- libwitos's `witos_manager_stop_services` stops what `witos_manager_run_services` started, the last first, with a
  deadline in seconds.

**The chain.**
1. **The root task** stops the device manager once `/bin/init` has ended, allowing 60 s of guest time. It prints
   `[ROOT-TASK] /system/DeviceManager stopped`. A service that does not stop fails the boot, as a nonzero exit of
   `/bin/init` does.
2. **The device manager** stops the namespace service first, since its volumes lie on the drivers' disks. Then it
   stops each driver, then answers with the first error of theirs.
3. **The namespace service** stops every session:
   - Each session finishes the request it is serving, behind the session's own lock.
   - It closes the files it opened, so FAT records their sizes.
   - It refuses every later request with `ESHUTDOWN`.

   Then it disposes what it mounted, the last opened first: each volume before its partition, each partition before
   its disk.
   - ext4 writes its superblock with `needs_recovery` clear, between flushes.
   - FAT flushes.
   - Each disk's block channel closes.

   Then it answers.
4. **Each virtio block driver** answers once its queue is disposed, which resets the device before the pin goes.

## A disk across reboots

**The two boots.** `RuntimeDevices.BuildAsync` boots the scenario twice with the same data disk. The host judges the
disk after each boot, and requires that the guest unmounted the ext4 volume: `dumpe2fs -h` must show no
`needs_recovery` before `e2fsck -fn` runs.

**On the second boot**, every part that wrote the disk on the first finds what it left:
- **The storage probe** (D3.2) reads the test partition before it writes: `holds the 327680 bytes a previous boot
  wrote`.
- **The FAT probe** (D4.1) reads back the previous boot's `/guest` files before it writes them again.
- **The ext4 probe** (D4.2, D4.3) sees `/guest` and does not write again. It reports how the previous boot left the
  volume, reads back the previous boot's changes and checks the volume.
  - The report comes from `Ext4FileSystem.WasCleanlyUnmounted` and `ReplayedTransactions`, which are new.
  - The line is `a previous boot wrote the volume and unmounted it cleanly: no transaction to replay`.
- **`/bin/init`** counts boots in `/data/boots.txt`, which the host reads back after each boot. From the second boot
  on, it requires `/data/posix-kept.txt` and `/data/dotnet-kept.txt` to hold what the previous boot wrote.

## Tests

- **`tests/OutWit.OS.Tests`:**
  - The stop message's layout and refusals.
  - On e2fsprogs' volumes, how a mount reports the last writer: clean after an unmount; not clean after a writer that
    stopped without unmounting; and one transaction replayed after a cut before a checkpoint.
- **`tests/WitOS.Dev.Tests`.** The data disk's check covers the unmounted volume.

## Results

`runtime-services` passes on both ISAs, each with two boots of one data disk:

- **Both boots** stop the services in order:
  - the namespace service with `1 sessions stopped, 3 volumes unmounted` (the session is the root task's, from D5.3);
  - each driver with its device reset;
  - the device manager;
  - the root task's report.
- **The second boot**:
  - finds the test partition's 327,680 bytes;
  - reads back the FAT files;
  - finds the ext4 volume cleanly unmounted with no transaction to replay;
  - reads back the probe's changes, with a clean check (465 files, 10 directories);
  - confirms `/bin/init`'s and the .NET program's files.
- **After each boot**, the host finds the ext4 volume unmounted and clean, and `/boots.txt` counts the boots.

## Limits kept explicit

- **A stop is asked for, not forced.** A service that does not answer within the deadline fails the boot. Nothing
  kills it, so its volumes are left as a cut-off would leave them, for D6.2's recovery.
- **One level of order.** The device manager stops the namespace service before the drivers, because it knows what
  it started. There is no general graph of dependencies between services.
- **FAT has no clean flag here.** `OutWit.Common.Fat` flushes on unmount, but no dirty bit records an unclean end.
  The FAT check and the guest's read-back are the evidence.
- **Clients see `ESHUTDOWN` after the stop.** Only the root task's own session is open by then, since `/bin/init` and
  its children have ended. A process still running at the stop would find its files refused.
