# W2.2 — HTTP

Plan step W2.2, the fourth slice of `W0-Network-Inventory.md`. `HttpClient` works over HTTP: upstream's
`System.Net.Http`, built unchanged but for its project's list of targets, sends its requests through
`SocketsHttpHandler` over the sockets of W2.1.

## 1. Two flavors for witos

Before this step `System.Net.Http` had no flavor for witos. The build took its platform-neutral flavor, whose types
throw `PlatformNotSupportedException`, so `HttpClient` failed at its first request (W0, N3.2). Two patches of the 10.0
set give witos the unix flavors, as N4.2 gave one to `System.Diagnostics.Process`:

- **`System.Net.Http.csproj`.** The project targets `$(NetCoreAppCurrent)-unix` when `TargetOS` is `witos`, beside
  Linux's, FreeBSD's and the other Unix flavors. Every source of the unix flavor is the one Linux compiles: the
  project's conditions name the platforms that differ (Windows, the browser, WASI and Apple's), never Linux alone.
- **`System.Net.Security.csproj`.** The same line. HttpClient's unix flavor reaches `System.Net.Security`'s types on
  every request, plain HTTP too: its connection pool keeps the application protocols of TLS (`SslApplicationProtocol`)
  in static fields. The platform-neutral flavor throws `PlatformNotSupportedException` from each of them, so the first
  trial's requests failed with "System.Net.Security is not supported on this platform".

What the unix flavors find on witos:

- **HTTP/1.1** goes through `SocketsHttpHandler` over `System.Net.Sockets`, its connections kept alive in the pool.
- **HTTP/3** stays off: `SocketsHttpHandler` asks for QUIC only on Linux, Windows and macOS, and witos is none of them,
  so `System.Net.Quic`'s platform-neutral flavor is never reached.
- **TLS** goes through OpenSSL's shim, and Negotiate through GSSAPI's. The witos build makes neither (R1.2b), so
  `SslStream`, `HttpClient` over HTTPS and `NegotiateAuthentication` fail explicitly when they are used, until W3.1
  pins OpenSSL. Plain HTTP reaches neither shim.

## 2. A pinned file with a byte order mark

`System.Net.Http.csproj` is the first file of the patch set that starts with a byte order mark. The tool read an
upstream file as text with `File.ReadAllText`, which drops the mark, while the lock records the file's bytes: the
patch's base hash could not be both. `UpstreamPatches.Text` now decodes the bytes as UTF-8 with the mark kept as the
text's first character (U+FEFF), so that the text hashes as the pinned bytes do and writing it back writes the mark
again. The tree's preparation, `runtime-rebase` and the host test that reproduces each patch read upstream files so.

## 3. The acceptance

The Network area of the compatibility suite (N1) gains three checks against a small HTTP/1.1 server of the suite's own
on the loopback (`LoopbackHttpServer`, written over `TcpListener` so that the checks test `HttpClient` alone), with no
proxy whatever the environment names:

- **`Network.HttpGet`.** A GET answered with a `Content-Length`: the status, the text and its media type.
- **`Network.HttpPostChunked`.** A POST of 256 KiB, which the server sends back with `Transfer-Encoding: chunked`.
- **`Network.HttpKeepAlive`.** Three GETs and a request the server answers 404, all over one connection.

The suite runs them on the hosts and in the guest alike; `runtime-compatibility` requires no unexpected result on the
three ISAs.

## 4. What the acceptance found

The first guest runs passed the three checks on x64 and ARM64, while riscv64 stalled a POST now and then. A run of the
POST thirty times a boot stalled it on every ISA within ten rounds, and three faults came out, each fixed with its
evidence:

- **TCP's advertised edge** (W1.2b's code). The right edge of the window a connection advertises started at zero, which
  lies ahead of RCV.NXT for half the peers' random initial sequence numbers: the first acknowledgment's window was garbage
  and the edge, which never moves back, stayed at 65535 << 3, twice the buffer. The edge now starts at RCV.NXT when the
  SYN arrives; a host test of 32 connections fails at the first without it. The network service now prints each
  connection still open at its stop and at a session's end, which showed it: the client had 70 bytes left, the window
  closed, its probes backing off to 51 s.
- **Stale registrations in epoll** (W2.1b's code). Those 70 bytes were the request's whole head: the server had accepted
  nothing (its journal: 0 connections accepted). A closed socket's number named the next `TcpListener`, whose
  `EPOLL_CTL_ADD` met the closed socket's entry and got `EEXIST`, which CoreCLR's socket engine throws as an
  `InternalException`; the asynchronous accept died unseen. `epoll_ctl` now drops every registration whose descriptor no
  longer names what it registered before it looks, and wakes a parked wait after a registration (W2.1b's PR carries
  both).
- **The suite's own server** recorded nothing of a failed accept, since its filter caught `SocketException` alone. It now
  keeps a journal of how each connection and its accept loop ended, with the connections accepted and the bytes read,
  and the POST check reports it when it gives up after 40 s.

With the fixes thirty POSTs a boot passed on x64 and twice on riscv64.

## 5. What ran

W2.2 closed on 2026-10-20 with its acceptance on the three ISAs.

- **Host tests.** On the Linux host `OutWit.OS.Tests` passes 269 tests and `WitOS.Dev.Tests` 123, among them the test of
  a byte order mark kept in a pinned file's text; the format check is clean. On the Windows host the compatibility suite
  reports 100 checks, 0 recorded differences and 0 unexpected, its three HTTP checks passing.
- **Guest.** With the shared framework built from the patched projects (`libs.sfx` for the three ISAs), `runtime-services`
  and `runtime-compatibility` pass on x64, ARM64 and riscv64, and ARM64's suite once more. On four processors the suite
  reports 100 checks, 3 recorded differences and 0 unexpected on each ISA: the GET answers its 34 characters of
  `text/plain`, the POST's 256 KiB come back chunked, and four requests share one connection.
- **What W2.2 leaves.** HTTPS (W3.1, OpenSSL); HTTP/2 and HTTP/3, which no check exercises (HTTP/3 stays off on witos);
  the runner's server outside the guest, which W3.1's test CA brings with HTTPS.
- **Seen once, apart from the network.** One ARM64 boot of the thirty-round experiment ended the suite at its fifth second
  in an early process check with CoreCLR's "Failed to create RW mapping for RX memory" (the JIT's double mapping, a
  `MAP_SHARED` of a shared memory file), while two .NET processes ran; it did not come back in the two ARM64 boots after it and
  is left to a step of its own if it recurs.
