# R1.2b — dotnet/runtime's native build for witos

Plan step R1.2 cross-compiles upstream dotnet/runtime's native parts for WitOS. R1.2a gave layer 2 a sysroot in the
layout of a Linux musl rootfs. R1.2b teaches the runtime's native build to target it:

- CMake learns the system WitOS.
- The runtime's build scripts learn the platform `witos`.
- NativeAOT's native part, its `AsmOffsets.cs` and its CoreLib build for both ISAs.

The answers the configure takes from `eng/native/tryrun.cmake` are not reasoned but measured: every probe the
configure compiles for witos runs in the guest, and `runtime-witos` requires that the file answers as the guest does.
The measurement found two faults in the system layer's libc, which this step removes: a pretended processor-time clock
and a `readlink` that answered differently on the two ISAs.

## What changed

### CMake's system WitOS

The sysroot now carries CMake's platform modules for WitOS (`src/Sysroot/cmake` → `usr/share/cmake/Platform`):

- `WitOS-Initialize.cmake` sets `CMAKE_EFFECTIVE_SYSTEM_NAME` to Linux. CMake does the same for Apple's platforms,
  which share the Apple rules. WitOS's programs are ELF images of the layer-2 triples, built by clang and lld as Linux
  musl ones are, so CMake's compiler rules (`Linux-Clang-C` and the rest) are the right ones.
- `WitOS.cmake` includes `Platform/Linux`: the rules for sonames, run paths, link groups and the Unix search paths.

`CMAKE_SYSTEM_NAME` stays `WitOS` and `LINUX` stays unset. A project tells the two systems apart. dotnet/runtime does
so through `CLR_CMAKE_HOST_OS`, which it derives from the system name.

### The runtime's build scripts

The patch set grows from 7 to 15 files. The eight new ones are:

| File | Change |
| --- | --- |
| `eng/common/cross/toolchain.cmake` | Recognizes the sysroot by `etc/witos-release`, as FreeBSD's rootfs is recognized by `bin/freebsd-version`. Names CMake's system WitOS and adds the sysroot's modules to the module path. Builds for the layer-2 triple against the sysroot and its own resource directory. Links C++ with libc++ through the existing `CLR_CMAKE_CXX_STANDARD_LIBRARY` knob, reserves x18 on ARM64, and links with lld against compiler-rt and libunwind with 4 KiB pages and separate loadable segments. |
| `eng/native/configureplatform.cmake` | `CLR_CMAKE_HOST_WITOS` (x64 and ARM64) and `CLR_CMAKE_TARGET_WITOS` with `CLR_CMAKE_TARGET_UNIX`, beside Haiku's branches. |
| `eng/native/configurecompiler.cmake` | A non-executable stack for assembly, build ids and full RELRO, as on Linux, since the dynamic linker is musl's. The detection message (`Detected WitOS x86_64`). `TARGET_WITOS` beside `TARGET_HAIKU`. |
| `eng/native/tryrun.cmake` | Detects the sysroot. A block at the end gives witos's 16 measured answers; see below. |
| `src/coreclr/gc/unix/gcenv.unix.cpp` | The GC's process-wide barrier through musl's `<sys/membarrier.h>`, as FreeBSD's, with musl's two-argument `membarrier`. |
| `src/native/libs/CMakeLists.txt` | No `System.Net.Security.Native` and no `System.Security.Cryptography.Native`: WitOS has no GSSAPI and no OpenSSL (RFC 0015 §8). |
| `src/native/libs/System.Globalization.Native/CMakeLists.txt` | Looks for no ICU library: the sysroot carries ICU's headers alone. |
| `src/native/corehost/apphost/static/CMakeLists.txt` | The single-file host links neither the GSSAPI nor the OpenSSL shim. |

The changes follow RFC 0015 §4's order of preference:

1. An existing configure check where one decides. The rest of the native configure reads the sysroot and needs no
   change.
2. An existing knob: `CLR_CMAKE_CXX_STANDARD_LIBRARY`.
3. A witos branch beside the other platforms' branches.

Measured against the ports' budget, CoreCLR has 1 file of FreeBSD's 31 and Haiku's 18, and the native libraries 2 of
62 and 11. The other new files are the build (4) and the hosts (1).

**`__linux__` and the GC's barrier.** The layer-2 triple is `<arch>-unknown-linux-musl` until WitOS has its own (T4),
so clang defines `__linux__`. The GC's OS layer includes `<linux/membarrier.h>` under `#ifdef __linux__`, but the
sysroot holds no Linux UAPI headers, and that is deliberate. It was the one compile error of the whole NativeAOT
runtime. The patch sends witos down the branch FreeBSD takes, musl's `<sys/membarrier.h>`, and maps the GC's
three-argument call onto musl's `membarrier(cmd, flags)`. The configure finds the header (`HAVE_SYS_MEMBARRIER_H`).
The system layer serves the query, the registration and the private expedited barrier, the last with the kernel's
`PROCESS_WRITE_BARRIER` (S5.3).

**Globalization.** CoreCLR links `System.Globalization.Native` on every platform, so the shim has to build for witos.
On Linux it compiles against ICU's headers and loads ICU's libraries with `dlopen` at run time. That is what witos
needs while ICU is absent: the shim reports that it found no ICU, and .NET runs in invariant mode, which RFC 0015 §8
prescribes. The sysroot therefore takes ICU's public headers alone:

- the `unicode/` headers of ICU4C's common and i18n libraries;
- from ICU 78.3, the latest stable release, pinned by the SHA-256 of its source tarball in
  `src/Substrate/icu.lock.json`;
- extracted by `setup` (`Substrate.IcuHeaders`).

The shim accepts ICU from version 60 to the version it was built against plus 30, so ICU built from source later fits
these headers.

### The try_run measurement

Some configure checks run a program they compiled (`check_c_source_runs`, `check_cxx_source_runs`). A cross build
cannot run it, so `eng/native/tryrun.cmake` holds each platform's answers. Without a witos branch, witos took the
generic Linux answers, which claim, among other things, that `/proc/self/stat` exists. `runtime-witos` measures
WitOS's answers instead:

1. **Collect.** It configures CoreCLR for witos with a second initial cache, `build/runtime/tryrun-measure.cmake`,
   that forgets every answer `tryrun.cmake` gave. Cross-compiling without answers, CMake keeps each probe it compiled
   and lists it in `TryRunResults.cmake`. The configure stops for want of the answers; any other configure error
   fails the measurement. The probes are copied to `artifacts/runtime-witos/tryrun/<arch>`, and the build directory
   is removed before the build configures again.
2. **Run.** The `runtime-tryrun` scenario boots the release kernel. The system layer's root task starts
   `tests/User/tryrun_init.c` as `/bin/init`, built against the sysroot by clang's plain driver. It runs every probe
   in a process of its own and prints how each ended. The probes are dynamic programs on musl's `libc.so` and the
   shared C++ runtime, as the configure linked them.
3. **Compare.** A probe that exited answers its status; one that a signal ended answers `FAILED_TO_RUN`, as CMake
   records it. `runtime-witos` requires that the build's cache holds the same answer for every probe and writes both
   to `artifacts/runtime-witos/tryrun-<arch>.json`.

The configure compiles 16 probes for witos-x64: 12 of the PAL, 3 of the native libraries and 1 of the GC. witos-arm64
has 15, since the PAL runs its robust-mutex probe on no ARM target. A variable that two configure files share is
answered once:

- The PAL reads the `HAVE_CLOCK_MONOTONIC` the native libraries measured.
- The GC's `HAVE_SCHED_GETCPU` probe never runs. The native libraries' symbol check answered it first: musl declares
  `sched_getcpu` only with `_GNU_SOURCE`, which that check does not define for witos.

The other answers `tryrun.cmake` holds belong to probes the witos configure does not reach, such as the kqueue FIFO
probes, and are never read. WitOS answers:

| Probe | WitOS | Linux (generic) | Why |
| --- | --- | --- | --- |
| `HAS_POSIX_SEMAPHORES` | 0 | 0 | `sem_init` works. |
| `HAVE_CLOCK_MONOTONIC`, `HAVE_CLOCK_REALTIME` | 0 | 0 | Both clocks exist. |
| `HAVE_WORKING_CLOCK_GETTIME`, `HAVE_WORKING_GETTIMEOFDAY` | 0 | 0 | |
| `HAVE_CLOCK_THREAD_CPUTIME` | 255 | 0 | The kernel reports no processor time; see below. |
| `HAVE_FUNCTIONAL_PTHREAD_ROBUST_MUTEXES` | 1 | 0 on x64 | The probe abandons a process-shared mutex in a forked child; WitOS has no `fork`. |
| `HAVE_PROCFS_CTL`, `HAVE_PROCFS_STAT`, `HAVE_PROCFS_STATM` | 1 | 1, 0, 0 | WitOS has no `/proc` and never emulates one. |
| `HAVE_SCHED_GET_PRIORITY` | 1 | 0 | The system layer serves no scheduling policy or priority (`ENOSYS`). |
| `HAVE_SHM_OPEN_THAT_WORKS_WELL_ENOUGH_WITH_MMAP` | 255 | 0 | No writable file and no shared memory file system. |
| `ONE_SHARED_MAPPING_PER_FILEREGION_PER_PROCESS` | 1 | 1 | The probe cannot create its file. |
| `PTHREAD_CREATE_MODIFIES_ERRNO`, `SEM_INIT_MODIFIES_ERRNO` | 1 | 1 | |
| `REALPATH_SUPPORTS_NONEXISTENT_FILES` | 1 | 1 | `realpath` of a missing file fails with `ENOENT`; see below. |

The witos block lists all 16 answers for both ISAs, so that it does not depend on the generic branch; ARM64 never
reads the robust-mutex answer. It sits at the end of the
file, after the line that answers robust mutexes for every x64 target. The answers describe the system layer as it
is: the read-only package and no `fork`. When the system layer changes, the measurement fails until the block follows
it, and that is its purpose.

### The libc's processor-time clocks

The first measurement answered `HAVE_CLOCK_THREAD_CPUTIME` with 0. The libc served `CLOCK_PROCESS_CPUTIME_ID` and
`CLOCK_THREAD_CPUTIME_ID` with the monotonic clock: elapsed time presented as processor time, a pretended success the
rules forbid. ABI-1 has UTC and the monotonic domain and reports no thread's or process's processor time. Both clocks
are now `EINVAL` in `clock_gettime` and `clock_getres`, as Linux refuses a clock it lacks.

musl's `clock()` now returns `(clock_t)-1`, which C allows when processor time is not available. No libc-test of the
selection reads these clocks; `pthread_condattr_setclock` only checks that a condition variable refuses them. A
processor-time call joins ABI-1 when a consumer with a test needs it (RFC 0011 §5).

### The libc's `readlink`

The first measurement on ARM64 answered `REALPATH_SUPPORTS_NONEXISTENT_FILES` with 0 where x64 answered 1, although
layer 2 is one source for both ISAs. musl's `realpath` calls `readlink` on each prefix of the path. It takes `EINVAL`
for "not a link" and continues, and it fails on any other error. The libc answered the two system calls differently:

- `readlinkat`, the only call ARM64 has, was `EINVAL` for every path, so `realpath` of a missing file succeeded there.
- x86_64's `readlink` was not dispatched at all, so it was `ENOSYS`, and `realpath` failed for every path on x64,
  existing ones included.

Both now go to `__wit_readlinkat` in `files.c`. The package has no symbolic links, so a path that names a file or a
directory is `EINVAL` and a path that names nothing is `ENOENT`, as Linux answers. `realpath` now resolves an
existing path on both ISAs and refuses a missing one.

### `runtime-witos`

The command now does the following for an architecture, on a Linux host:

1. Builds CoreLib and checks its platform name (R1.1).
2. Builds the sysroot.
3. Collects the probes.
4. Runs `build.sh clr.nativeaotruntime+clr.nativeaotlibs -os witos -arch <arch> -c Release -cross`. The environment
   carries the pinned clang first on `PATH`, `CLR_CC`, `CLR_CXX` and `ROOTFS_DIR`.
5. Requires `AsmOffsets.cs`, the runtime library and an `aotsdk` CoreLib that names `WITOS`.
6. Measures the probes in the guest and compares them.
7. Reports the patch set against the budget.

On Linux, `setup` extracts `clang++` and the LLVM tools the runtime's `configuretools.cmake` requires (`llvm-nm`,
`llvm-ranlib`, `llvm-strings`, `llvm-link`, `llvm-objdump`, `llvm-readelf`), and fetches ICU's headers on either
host. The development image and CI's `linux-host` job add `cmake`.

## Tests

- **Linux (the container).** `runtime-witos` and `runtime-witos --arch arm64` pass:
  - `Detected WitOS x86_64` and `Detected WitOS aarch64`;
  - the NativeAOT runtime libraries, `AsmOffsets.cs` and CoreLib for both ISAs, with no compile error;
  - `[TRYRUN] 16 probes on x86_64: 16 ran` and `[TRYRUN] 15 probes on aarch64: 15 ran`, each answer equal to
    `tryrun.cmake`'s.
  - The layer-2 scenarios (`libc`, `libc-test`, `cxx`, `spawn`, `process`, `sysroot`) pass on both ISAs with the
    final libc.
- **Windows.** `PASS: all 27 kernel integration scenarios` and `PASS: all 21 arm64 foundation scenarios`, with the
  layer-2 scenarios of both ISAs on the final libc and the sysroot's new content.
- **Host tests.** Pairing a probe with its executable in `TryRunResults.cmake`, reading the guest's answers and the
  ICU pin are tested. 98 tests pass on Windows and 78 on Linux; `format-check` is clean.

## Limits kept explicit

- NativeAOT's runtime is compiled but not linked into a program or run. ILC for witos is R1.3, and the first
  NativeAOT program in the guest is R2. The host JIT and ILC built by the pinned clang move to R1.3, where ILC needs
  them.
- `__linux__` stays defined until T4. The native build compiles other upstream code under `#ifdef __linux__`; no
  other such path failed to compile, and the paths that read Linux-only files fail at run time as a system without
  them does. R2 and R3 meet them.
- CoreCLR, the native libraries and the hosts are configured but not built; that is R3 to R5.
- The native libraries' configure defines `_GNU_SOURCE` for Linux and Haiku alone, so for witos it finds none of the
  GNU functions musl declares only under it (`sched_getaffinity`, `sched_getcpu`, `fallocate` and others). Whether witos
  defines it is decided with `System.Native` in R4.
- There is no ICU, no GSSAPI and no OpenSSL: globalization runs in invariant mode, and Negotiate authentication and
  cryptography fail explicitly.
