# V2.4 — The runtime on riscv64: TargetOS=witos for the third ISA

Plan step V2.4, the fourth slice of V2 (layer 2 and the runtime on riscv64), 2026-10-17. V2.1–V2.3 brought the whole
system layer to `riscv64-unknown-linux-musl`; this slice brings upstream .NET in its Unix form: the witos patch set
names a third architecture, `runtime-witos --arch riscv64` builds on the Linux host against the riscv64 sysroot, and the
runtime's scenarios run on the third board one by one, as far as this slice reaches (section 5). V0 named this the first
measurement of V2 (`V0-RISC-V-Measurement.md` §4, §6.7): whether `build.sh -os witos -arch riscv64` configures and builds
CoreCLR, the native libraries and NativeAOT against the sysroot, and whether the community JIT passes the acceptance.

## 2. Publishing the code a JIT writes

A JIT writes code through a writable view and must publish it for instruction fetch before it runs. On x64 nothing is
needed; on ARM64 EL0 cleans and invalidates caches by address itself (R3.2b), which compiler-rt's `__clear_cache` does;
on RISC-V a `fence.i` reaches the local hart alone, so Linux gives user space the `riscv_flush_icache` system call, which
fences every hart, and both runtimes use it: CoreCLR's PAL (`pal/src/thread/context.cpp`) calls `syscall(259)` directly,
NativeAOT's (`unix/PalUnix.cpp`) calls `__builtin___clear_cache`, which is compiler-rt's `__clear_cache`, whose RISC-V
Linux branch issues the same system call with an inline `ecall`. WitOS has no Linux system call instruction contract:
an `ecall` with a Linux number reaches the kernel's ABI-1 dispatch and is refused. V0 §6.5 decided the shape: the
system call is the kernel's `CODE_PUBLISH`.

- **The libc** (`memory.c`, `__wit_flush_icache`): `SYS_riscv_flush_icache` is served by the mapping table. Code runs
  only from an object mapping made executable — a package mapping, or a chunk of a shared memory file, which is what
  CoreCLR's double mapping and D5.3's executable copies are — so the executable mappings the range touches are
  published through `CODE_PUBLISH` (a package mapping whole within the range; a shared mapping by its runs of
  executable pages, since the library keeps a shared mapping's protection page by page), the kernel's cache maintenance
  for this hart (`fence.i`) and, from phase P, the others. A range holding no executable page has nothing to publish
  and succeeds, as Linux's call succeeds for any range. The flags are Linux's: 0 for every hart, 1 for the caller's
  alone, which the one scheduling processor makes the same thing; anything else `EINVAL`. musl's `__riscv_flush_icache`
  (`src/linux/cache.c`) asks `__vdsosym` for the vDSO's symbol first — none on WitOS, which the V2.1 patch of
  `syscall_arch.h` keeps possible by leaving `VDSO_USEFUL` — and takes the system call path.
- **compiler-rt** (`patches/compiler-rt/clear_cache.c.patch`, the substrate's first patch outside musl): the RISC-V
  Linux branch of `__clear_cache` calls musl's `__riscv_flush_icache(start, end, 0)` in place of the inline `ecall`,
  and the Linux header it included for the number, which musl does not install, gives way to the declaration. The
  builtins' build applies the patch through `UpstreamPatches` as the libc's build applies musl's, compiles the copy
  in the source's place and stamps the archive with the patch text; `clear_cache.c` joins riscv64's builtins in the
  lock, where V2.1 had left it out. Nothing else of compiler-rt changes.
- **The kernel** is unchanged: `CODE_PUBLISH` publishes through `wit_arch_publish_code`, `fence.i` on riscv64 since
  V1.3.

The libc scenario proves the path on riscv64 (`libc_hello.c`, 167 checks since this slice): the file's code mapped
executable runs, is published again through `__riscv_flush_icache` and runs, and a flush with unknown flags is
`EINVAL`.

## 3. CoreCLR's thread statics under musl's dynamic linker

The first boot of `runtime-coreclr` on riscv64 stopped at the load: `dlopen /coreclr/libcoreclr.so: Error relocating
/coreclr/libcoreclr.so: fscanf: initial-exec TLS resolves to dynamic definition`. The library had one
`R_RISCV_TLS_TPREL64` relocation among 37 general-dynamic ones (its ARM64 build has 37 `TLSDESC` and no initial-exec):
`GetThreadStaticsVariableOffset` in `vm/riscv64/asmhelpers.S` reads the thread pointer offset of `t_ThreadStatics` with
`la.tls.ie`, the initial-exec model, where ARM64's helper uses TLSDESC and LoongArch64's `la.tls.desc`. musl's dynamic
linker gives a library that `dlopen` opens dynamic TLS alone and refuses an initial-exec relocation against it
(`dynlink.c`: `def.dso->tls_id > static_tls_cnt`); glibc serves it from its static TLS surplus, which is why
linux-riscv64 loads (the symbol musl names, `fscanf`, is the previous relocation's: the TLS relocation names no symbol).

The offset exists for the JIT's inlined thread static access: `GetThreadLocalStaticBlocksInfo` hands it over as a
constant, valid for every thread only when the runtime's TLS is static. Upstream already disables the optimization where
that fails (`CanJITOptimizeTLSAccess`: linux-musl ARM64, FreeBSD ARM64, ARM64 with a dynamic TLSDESC resolver, which is
how WitOS ARM64 runs today). Two patches of the set, `TARGET_WITOS` branches beside the platforms' (RFC 0015 §4):

- `asmhelpers.S`: on WitOS the helper takes the general-dynamic model the library's C++ thread locals use —
  `la.tls.gd`, `__tls_get_addr`, less `tp` — so no initial-exec relocation is left and `libcoreclr.so` loads; the
  value is the current thread's offset.
- `threadstatics.cpp`: `CanJITOptimizeTLSAccess` answers false for WitOS riscv64, as for linux-musl ARM64, so the JIT
  reaches thread statics through the helper calls and never treats that offset as every thread's.

NativeAOT's runtime for riscv64 asked for one more symbol: `PalInterlockedCompareExchange128` compiles to
`__atomic_compare_exchange_16`, which Linux takes from libatomic (`Microsoft.NETCore.Native.Unix.targets` links
`-latomic` on riscv64 and loongarch64). The sysroot has no libatomic: compiler-rt's `atomic.c`, the out-of-line atomic
operations clang calls where the ISA has no instruction for the size, joins riscv64's builtins in the pin (compiled
unchanged; its 16-byte case takes a lock, as on every ISA without a 16-byte compare-exchange), and the targets' witos
branch leaves `-latomic` out.

### A hardware exception caught by `PAL_TRY`

With the runtime loading, the PAL suite ran on riscv64 and 279 of its 280 tests passed; `exception_handling/pal_sxs/test1`
failed. The test faults inside a `PAL_TRY` of each of two libraries with their own PAL; the second library's
`PAL_EXCEPT` ran and reported success, then the process took a second `SIGSEGV` outside any `PAL_TRY`: a store to
address zero, which a fault trace in the libc placed in musl's `__stack_chk_fail` — the stack protector of the test's
own `DllTest2` found its canary slot changed at the function's return, and the stack pointer at that check was the
faulting function's, not `DllTest2`'s own.

The PAL throws a hardware exception as a C++ exception from a frame it builds below the faulting one:
`ThrowExceptionFromContextInternal` restores the callee-saved registers, the frame pointer and the stack pointer from
the signal's context and tail-calls `ThrowExceptionHelper`, which throws, so the unwinder must pass through the
faulting function's frame to reach the `PAL_TRY` above it. ARM64's helper sets the return address to the faulting
instruction (`CONTEXT_Pc`) and x64's pushes `CONTEXT_Rip`: the unwinder then applies the faulting function's own rules,
frame pointer based since the runtime is built with frame pointers, and restores its caller's registers from where that
frame saved them. The RISC-V helper (the community port's, LoongArch64's alike) loaded `CONTEXT_Ra`, the faulting
function's own return address: the unwinder stepped straight to the `PAL_TRY`'s function with the faulting function's
frame pointer and stack pointer in place of its own, and everything that function addressed through its frame pointer
afterwards — the canary among it — was read from the wrong frame. The patch sets the return address to `CONTEXT_Pc`,
as on ARM64; clang's RISC-V code defines the CFA by `s0` once the frame pointer is set, so the faulting frame unwinds
exactly. A bug of the community port rather than of WitOS, to be proposed upstream with the `TargetOS=witos` proposal
(T4): on Linux the same throw crosses the same frames.

### W^X on riscv64

With the PAL suite passing, `corerun` ended with an unhandled `SIGSEGV` before its managed `Main` ran: a `memcpy` in
`InitThreadManager` wrote into the first pages of the executable allocator's reservation (819 MiB of `PROT_NONE`, 20% of
the address space `getrlimit(RLIMIT_AS)` reports, reserved right after `libcoreclr.so`'s code), where the write barrier
code is copied for patching. Upstream turns W^X off by default on riscv64 (`clrconfigvalues.h`, dotnet/runtime issue
103465), so the allocator committed that page as writable and executable at once — which WitOS never grants (plain
memory never executes, a JIT writes through the RW view of a double mapping and the RX view is published) — and the
commit's refusal went unchecked. The runtime's own `SIGSEGV` handler took the fault first, found no managed frame and no
`PAL_TRY`, restored the default disposition and let the instruction fault again, which ended the process; a fault trace
in the libc showed both deliveries. The patch keeps W^X on for WitOS riscv64 as on the other ISAs, a `TARGET_WITOS`
branch beside the platform's own default (RFC 0015 §4): the knob exists, and WitOS has one mode.

### NativeAOT's interface dispatch without linker relaxation

NativeAOT's first program on riscv64, `Platform.cs`, ran at once; the M3 acceptance did not. It ended with
`Access Violation` in `DispatchResolve.FindImplSlotForCurrentType`, reading the interface type of the program's first
interface call (a `Dictionary` insertion in `AppContext`'s static constructor). The dispatch cells were right: decoded
from the executable, each named its interface's `MethodTable`, and their stubs had their dynamic relocations, with or
without ILC's dehydration. The cache miss stub was not: `RhpInterfaceDispatchSlow` puts the cell in t1, the universal
transition's parameter, and reaches the transition with the `tail` pseudo-instruction, which assembles to an `auipc` and
a `jr` through t1 itself — in the executable, `mv t1, t5` followed by `auipc t1, 0`. A linker that relaxes the pair into
one `jal` keeps t1, which is why Linux builds work; WitOS links layer 2 without relaxation (`-mno-relax`, since nothing
may address through `gp`, V2.1), so `RhpCidResolve` received the transition's own address as its cell. .NET 11 writes the
tail call as an explicit `auipc` and `jalr` through t2; the patch takes that form with 10.0's symbol. The other `tail`
calls of the RISC-V runtime assembly keep nothing live in t1, and CoreCLR's write barriers count t1 among the registers
they trash.

### A device interrupt the PLIC kept

The terminal scenario hung on riscv64 at a different input from run to run, its transcript ending at a prompt the runner
had answered. A diagnosis build of the virtio console driver that also woke every two seconds and collected what the
device had received found bytes there with no interrupt delivered, and answered the held `READ` from them; the boot then
went on. The interrupt was lost between QEMU's PLIC and the kernel, not in the driver or the services.

A device line (K3.2) is claimed and masked by the trap, delivered to the bound event, and unmasked by the driver's
`INTERRUPT_ACK` once it read the device's interrupt status. A device that asserts while its line is masked leaves the
source pending, and the unmask must raise it. The board's unmask wrote the source's priority, then the context's enable
bit; QEMU's PLIC (`hw/intc/sifive_plic.c`) looks at what is pending again on a write of a priority, a threshold or the
claim register, never on a write of an enable word, so the interrupt waited for the next activity of any line — the
timer's never counts — and a console whose input came only after its own output waited for ever. The unmask now writes
the enable bit first and the priority after it, which raises such an interrupt at once.

The trap's order changed too: it completed the claim after masking the source, and the PLIC specification says that a
completion naming a source not enabled for the context is ignored. QEMU completes it anyway, so nothing failed here, but
a PLIC that follows the specification keeps that source claimed for ever (Linux's driver met it in 2023 and enables a
masked source around its completion). The trap now completes, then masks. The x64 and ARM64 boards are unchanged: their
controllers re-evaluate on an unmask.

### Upstream's tests on the third ISA

The slices of CoreCLR's `src/tests` (R7.2b) ran on riscv64: in the first run 50 of the 51 runs (the two merged JIT groups
and the process-isolated tests) exited with 100. Two entries of the selection needed the architecture, so an exclusion may
now name the ISAs it applies to (`"architectures"`), and each ISA's run takes its own exclusions for the isolated list,
the exclusion file and the report:

- `GC/API/Refresh/Refresh`, left out on x64 and ARM64 since N2.2, is not built for riscv64 at all
  (`CLRTestTargetUnsupported` names x64 and arm64), so riscv64's build has nothing to leave out and the tool's check
  that every exclusion names a test of the build refused the selection.
- `GC/Regressions/v2.0-rtm/494226` allocates 20 million small arrays until the GC's limit inside a `try` and writes
  "Test passed" after the `catch`. On x64 and ARM64 the arrays are unreachable once the block ends and the console's
  first allocations find memory; on riscv64 the console's first allocation found the heap full, and its
  `OutOfMemoryException` left the test (exit 101). The card table assert the test exists for was not hit. It leaves the
  selection on riscv64, an open question below.

The libraries' test projects (R7.3) ran under `dotnet` on riscv64: `System.Collections.Concurrent.Tests` passed its
2,460 tests, and `System.Runtime.Numerics.Tests` failed 10 of 2,628, every one an `OverflowException` from BigInteger's
explicit conversion to `sbyte` for a negative value (`TryConvertToCheckedSByteTest` and the shift, rotate and cast
tests whose helper narrows a remainder). A program under `corerun` reproduced it: four threads converting
BigIntegers to `sbyte` in a loop failed tens of thousands of times once the loop's code was replaced, with no failure
on ARM64, none on riscv64 with `System.Runtime.TieredPGO`, tiered compilation or `QuickJitForLoops` off, and none at
tier 0 or fully optimized from the start. It is a bug of the community RISC-V JIT, not of WitOS: it needs dynamic PGO
and code the JIT replaced, the garbage collector's suspensions do not cause it (as many collections ran without a
failure with PGO off), and only negative values fail, which points at an `int` whose upper half is not sign-extended
reaching the checked narrowing (`slli`/`srai` and a compare with the register) — as a BigInteger passed in registers
carries its memory image, which the psABI does not extend; the disassembly that would show the instruction is the
upstream report's to give. The ten tests leave the selection on riscv64 with that reason; the bug is to be reported
upstream with a reproduction that needs no WitOS, and no knob of the runtime hides it, since WitOS runs upstream's JIT
as Linux does.

## 4. What ran

The step was measured in the Linux host's image (`build/linux/Dockerfile`, a 32-processor container) on a copy of the
tree with the step's change alone. Each stage was first driven by its own command on the runtime an earlier run had
built, so that a finding cost one stage, not the whole run (section 3 is that order); then the whole command ran once
more on a runtime tree emptied first:

```text
dotnet run --project tools/WitOS.Dev --configuration Release -- runtime-witos --arch riscv64
runtime-witos riscv64 exit 0, 96 minutes
```

On the Windows host, `test --arch riscv64` checks the kernel the PLIC change touches (`PASS: all 21 riscv64 foundation
scenarios`). The x64 and ARM64 runtimes are CI's to prove: the patches this step regenerated change only the
architecture lists their hunks carry, and the new ones are riscv64 branches or `TARGET_WITOS` branches whose other
ISAs keep upstream's code.

## 6. Findings

- The community RISC-V port is close to Linux-ready but was never run under musl's dynamic linker or without linker
  relaxation: two of its five patches (the initial-exec thread statics and the `tail` through t1) are exactly that, and
  Alpine riscv64 would meet the first. Two more are bugs of the port that Linux hides less well than it seems — the
  exception helper's return address and W^X off by default — and one is WitOS's single mode (W^X on).
- `-mno-relax` makes every `tail` and `call` pseudo-instruction a two-instruction sequence through t1 (and ra). A
  hand-written stub that keeps a value in t1 across one breaks only where the linker does not relax; the RISC-V
  assembly of both runtimes was audited for that pattern and the dispatch stub was the one case.
- The third ISA showed what two could not in the board as well: QEMU's PLIC re-evaluates on a priority write, not on an
  enable write, so the unmask order mattered, and the specification's rule about completions does on real hardware.
- The community RISC-V JIT has a bug of its own under dynamic PGO (section 3); WitOS runs upstream's JIT unchanged and
  leaves the tests out with that reason rather than turning a knob that Linux does not turn.
- The run takes 96 minutes in the 32-processor container from an empty runtime tree; the guest stages run at TCG's
  speed in virtual time on every ISA.

Open questions:

- `GC/Regressions/v2.0-rtm/494226` on riscv64: why the console's first allocation after the test's `catch` finds the
  heap full on riscv64 alone (a question for the GC's own trace; nothing in the run points at a WitOS mechanism).
- The JIT's BigInteger narrowing under dynamic PGO, to report upstream with a reproduction on Linux riscv64.
- The exception helper and the dispatch stub to propose upstream with the `TargetOS=witos` proposal (T4); .NET 11
  already carries the stub's form.
