# R3.1 — CoreCLR's native part

R3 brings CoreCLR to WitOS (RFC 0015 §5–§6). Its first slice builds CoreCLR's native part for `witos` and loads it in
the guest. Nothing of the runtime runs yet: `coreclr_initialize` and a managed `Main` through the JIT are R3.2.

## The build

After the NativeAOT step, `runtime-witos` builds upstream's `clr.runtime+clr.jit` subsets for `witos` on both ISAs:

```
./build.sh clr.runtime+clr.jit -os witos -arch <arch> -c Release -cross
```

The build uses the pinned clang and lld against the system layer's sysroot (`ROOTFS_DIR`), the same way R1.2b built
NativeAOT's native part. Its output in `artifacts/bin/coreclr/witos.<arch>.Release` includes:

- `libcoreclr.so`, the runtime with the PAL;
- `libclrjit.so`, the JIT;
- `libmscordaccore.so`, the DAC;
- `corerun`.

These are dynamic ELF images for musl's dynamic linker, linked against libc++. `runtime-witos` requires the runtime,
the JIT and `corerun`.

`clr.runtime` does not build two upstream parts for `witos`:

- **CoreCLR's build tools** (ilasm, ildasm). The host's own tools serve the build, as they do for Android and the
  browser, and ilasm's signing needs OpenSSL headers that the sysroot does not carry.
- **The single-file host.** It links the static cryptography shim, and `witos` builds no OpenSSL shim (R2.3b). Apple's
  mobile targets and WebAssembly skip it too.

## The patches

The layer-2 triple is `<arch>-unknown-linux-musl`, so clang defines `__linux__`. Most upstream code that tests
`__linux__` means Linux's libc interfaces, which musl provides. Where it means the Linux kernel or a Linux-only
facility, the site needs `!defined(TARGET_WITOS)`.

The patch set grows by five files, and one existing patch gets a new hunk:

| Patch | Why |
| --- | --- |
| `src/coreclr/pal/src/thread/process.cpp` | The sysroot carries no Linux kernel headers, so `<linux/membarrier.h>` stays Linux's. musl's `membarrier` takes two arguments, so the PAL's call drops the processor argument, beside the browser's branch. The libc serves the private expedited barrier with `PROCESS_WRITE_BARRIER` (S5.3). |
| `src/coreclr/vm/gcenv.ee.cpp` | The GC's event status asks the LTTng and user_events providers. Their generated headers exist only for `CLR_CMAKE_TARGET_LINUX`, so `witos` takes the other platforms' branch. |
| `src/native/external/libunwind.cmake` | The PAL unwinds native frames through CoreCLR's copy of libunwind, whose stepper calls the OS part. `witos` builds Linux's `os-linux.c`. Its `/proc` reader, which finds the image of an address, fails explicitly on WitOS. |
| `src/coreclr/CMakeLists.txt` | The single-file host is not built for `witos` (see above). |
| `src/coreclr/dlls/mscordac/CMakeLists.txt` | `witos` is not Linux, so the DAC's exports file comes from its export list, as on the other Unix hosts. |
| `eng/native/configureplatform.cmake` (new hunk) | `CLR_CMAKE_BUILD_TOOLS` is not set for `witos`. |

The patch set is now 23 files. Its CoreCLR part is 8 files, against FreeBSD's 31 and Haiku's 18.
`build/runtime/runtime.lock.json` pins the five new upstream files.

## The libc: package mappings without a copy

musl's dynamic linker first maps a whole library read-only, then maps each segment over it. Until R3.1 the libc made a
committed copy of every private file mapping that was not executable. For CoreCLR this meant megabytes of copied
read-only data.

- **No copy for read-only mappings.** A private mapping of a page-aligned package file that is not writable is now
  made of package object mappings, like code. Read-only data and the dynamic linker's first mapping cost the process
  no pages.
- **Eager copy-on-write.** When `mprotect` makes part of a package mapping writable, the libc first gives that part a
  private copy, as Linux's copy-on-write would. It reads the bytes through a temporary window of the package, since the
  mapping itself may be `PROT_NONE`, then replaces that part with plain memory holding the same bytes. The package
  stays read-only.
- **Code stays the package's.** A mapping made with `PROT_EXEC` is never copied: plain memory never executes, so the
  code could not run again. The write is refused with `EACCES`, as before.
- Writable private mappings, and mappings that are not page-aligned, are committed copies as before.

## What the load found: K9

With the copies gone, `dlopen` of the JIT after the runtime still failed with `ENOMEM`. The kernel recorded every alias
entry of an address space in an array sized by the process page quota (2048 entries), and counted aliases against that
quota. Step [K9](K9-Page-Table-Accounting.md) made the page tables the record and raised the quota to 65536 pages. R3.1
is stacked on it.

## The scenario

`runtime-coreclr` boots the system layer's root task with `tests/User/coreclr_init.c` as `/bin/init`. The package
holds:

- the runtime and the JIT under `/coreclr`;
- musl's `libc.so` as the dynamic linker;
- the shared C++ runtime in `/lib`.

The program `dlopen`s `libcoreclr.so` and resolves the host's entry points: `coreclr_initialize`,
`coreclr_execute_assembly`, `coreclr_create_delegate` and `coreclr_shutdown_2`. It then `dlopen`s `libclrjit.so` and
resolves `jitStartup` and `getJit`. Loading runs both libraries' relocations, their TLS and their initializers.

The scenario requires `[CORECLR] libcoreclr.so and libclrjit.so loaded with their entry points` and the root task's
report of status 0. `runtime-witos` boots it for each ISA after the build. The `runtime-coreclr` command boots it
again from the built tree. It is not a suite scenario, since the libraries come from the runtime's build on a Linux
host.

Both ISAs pass. `tests/User/libc_hello.c` checks the copy-on-write in the `libc` scenario of both suites: one page of
a read-only mapping of `code.bin` is made writable and written, while a second mapping and a later one still show
the package's bytes.

## Limits kept explicit

- No runtime code runs yet. `coreclr_initialize`, CoreCLR's CoreLib for `witos`, and the JIT's executable memory are
  R3.2. The kernel executes only memory objects that are mapped `READ|EXECUTE` and published, so the JIT needs the
  double mapping of `minipal/Unix/doublemapping.cpp` over memory objects.
- `corerun` and the DAC are built but not run.
- libunwind's `/proc` reader fails, so nothing that needs the image of an address (a remote unwind, a symbol lookup)
  works.
- The layer-2 code and the runtime's toolchain patch still compile with `-ffixed-x18`. That flag goes in a later R3
  slice.
