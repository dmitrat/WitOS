# R7.2a — A writable /dev/shm within the process

R7.2 runs slices of upstream's `src/tests` in the guest. Their merged test runners write three files into the current
directory: `<group>.tempLog.xml`, `<group>.testStats.csv` and `<group>.testResults.xml`. On WitOS the boot package is
the whole file system and is read-only until the namespace service (D5). The PAL suite of R7.1 left out 41 tests for
the same reason.

R7.2a gives a process a directory to write in, without a new file system. The shared memory files of R3.2b already
lived on memory objects within the process. They lacked what Linux's tmpfs gives the files of `/dev/shm`: a descriptor
that reads and writes them.

## What a process gets

- **Reads and writes.**
  - `read`, `write`, `pread`, `pwrite`, `readv`, `writev`, `lseek` and `O_APPEND` work on a shared memory file.
  - The libc keeps its own read and write view of one chunk of the file at a time, and replaces the view when another
    chunk is touched.
  - A chunk that nobody mapped or wrote reads as zeros.
  - A write past the end grows the file. A chunk gets its memory object when a mapping or a write first needs it.
  - `fsync` and `fdatasync` succeed, since memory has nothing to write back.
- **A directory.**
  - `/dev/shm` is the one directory in which a process creates files. `chdir` and `posix_spawn`'s `addchdir_np` take
    it, and `getcwd` reports it.
  - A relative name there names a shared memory file. `stat` and `access` see the directory and its files, and
    `unlink` removes a file.
  - `/dev` answers `access` and `readlink` as a directory. musl's `realpath` reads every directory of a path as a link,
    and CoreCLR's PAL canonicalizes a path through it before it creates a file.
  - `mkdir` under `/dev/shm` is `ENOSYS`, because the directory holds files alone.
- **Mappings.**
  - The page that holds a file's end maps whole, as on Linux. Before, a mapping had to lie within the file's bytes.
  - A `MAP_PRIVATE` mapping is a copy of the file's bytes, taken when it is made, as a writable private mapping of the
    package is (R3.1). Before, it was `ENOSYS`.
- **Limits.** A process holds up to 64 files, with names of up to 255 bytes. The limit used to be 8 files of 64 bytes.

Each process has its own `/dev/shm`. A file never crosses a process, and a process starts with the directory empty.
That is what a test runner needs: a private, writable working directory.

`libc_hello.c` checks the reads and writes, the growth, a sparse chunk reading as zeros, the private copy, `chdir`
into `/dev/shm`, appending to a relative name, `stat`, `access`, `fsync`, the refusal of `mkdir` and `unlink`.

## The PAL suite in /dev/shm

The runner now starts each test in `/dev/shm`, as `runpaltests.sh` gives each test a writable directory of its own.
34 of the 41 tests left out for writing files pass. Two more fixes were needed for them: the page that holds a file's
end (`MapViewOfFile` maps a 2 KiB file) and the private copy (`FILE_MAP_COPY`). Seven tests stay out:

| Tests | Reason |
| --- | --- |
| `MapViewOfFile/test1`, `SearchPathW/test1` | Each writes a file outside its working directory, under `/var/tmp` or `/tmp`. |
| `GetFullPathNameA` and `GetFullPathNameW` tests 3 and 4 | Each creates a directory. `/dev/shm` holds files alone. |
| `WriteFile/test1` | It makes a file read-only with `chmod`. The files of `/dev/shm` keep the mode they were created with. |

The exclusions are 25 instead of 59. The suite runs 280 tests and passes all of them on both ISAs.

## Limits kept explicit

- `/dev/shm` is no namespace service. Files of other directories stay read-only, there are no subdirectories, no
  `rename` and no `chmod`, and nothing outlives the process. D5 replaces all of it.
- A private mapping of a file is a copy taken when it is made, so it does not see later writes to pages it has not
  written, as Linux's does.
- A mapping that reaches past the page holding a file's end is `ENXIO`. On Linux it succeeds, and touching those pages
  raises `SIGBUS`.
