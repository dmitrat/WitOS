# R1.2a — the system layer's sysroot

Plan step R1.2 cross-compiles upstream dotnet/runtime's native parts for WitOS. Upstream builds a Unix target against
a rootfs (`ROOTFS_DIR`) with clang's own driver, so R1.2a gives layer 2 one. `Substrate.Sysroot` lays the substrate
out in the layout of a Linux musl rootfs under `artifacts/sysroot/<arch>`: the C library, the C++ runtime, compiler-rt
and the WitOS headers. A program built against it with the plain driver (`--sysroot`, compiler-rt, libunwind, libc++,
lld) runs on WitOS as any dynamic program does. The `sysroot` scenario proves it on both ISAs and both hosts. R1.2b
configures dotnet/runtime's native build against this sysroot.

## What changed

**The layout.** Everything comes from the substrate's own builds of S1–S5; nothing is a system copy.

- **`usr/include`**:
  - musl's headers as its `install-headers` lays them out: `include`, the generic `bits`, the architecture's `bits`
    over them, and the generated `alltypes.h` and `syscall.h`;
  - libunwind's headers;
  - `witos/`: the system layer's headers (`syscall.h`, `start.h`, `spawn.h`, `manager.h` and the rest) together with
    the kernel's ABI-1 headers they include.
- **`usr/include/c++/v1`**: libc++'s headers with the configured `__config_site` and `__assertion_handler`, and
  libc++abi's `cxxabi.h` and `__cxxabi_config.h`.
- **`usr/lib`**:
  - `Scrt1.o` and `rcrt1.o`. There is no `crt1.o`, since a program another component starts is position-independent
    (S5.2).
  - musl's `crti.o` and `crtn.o`, which the driver links around every image.
  - `libc.a` and `libc.so`, and the empty `libm`, `librt`, `libpthread`, `libcrypt`, `libutil`, `libxnet`, `libresolv`
    and `libdl` archives that musl installs.
  - The C++ runtime static and shared, and `libwitos.a`. Each shared library is its versioned file with an
    unversioned linker script. `libc++.so` reads `INPUT(libc++.so.1 -lc++abi)`, as LLVM's own install writes it, since
    the driver links `-lc++` alone. Linker scripts stand in for the symbolic links a Linux install has.
- **`usr/lib/clang/20`**: the sysroot's compiler resource directory. It holds clang's own headers and, in
  `lib/<triple>`, the objects `--rtlib=compiler-rt` makes the driver link: `libclang_rt.builtins.a`,
  `clang_rt.crtbegin.o` and `clang_rt.crtend.o`. A per-sysroot resource directory keeps generated objects out of the
  pinned `.tools`.
- **`etc/witos-release`**: the marker a build recognizes the sysroot by, as FreeBSD's rootfs is recognized by
  `bin/freebsd-version`.

**The driver's options.** `Sysroot.DriverOptions` gives every option that builds for WitOS:

- the layer-2 triple, `--sysroot` and `-resource-dir`;
- `--rtlib=compiler-rt`, `--unwindlib=libunwind`, `-stdlib=libc++` and `-fuse-ld=lld`;
- the layout every image another component maps needs (S5.3): `-Wl,-z,max-page-size=4096` and
  `-Wl,-z,separate-loadable-segments`;
- the architecture's own options, such as ARM64's `-ffixed-x18`.

The driver supplies the rest as it does for Linux musl: PIE by default, `Scrt1.o`, `crti.o` and `crtn.o`, and the
dynamic linker `/lib/ld-musl-<arch>.so.1`.

**compiler-rt's end object.** `crtend.c` joins the compiler-rt pin by its canonical bytes. It is compiled as
`crtbegin.c` is, position-independent with init and fini arrays, and both stay out of `builtins.a`.

**The scenario.** In the `sysroot` scenario, the system layer's root task starts `tests/User/sysroot_init.cpp` as
`/bin/init`, with `libc.so` as its dynamic linker and the shared C++ runtime in `/lib`. The program is built by one
driver invocation, `clang --driver-mode=g++` with `Sysroot.DriverOptions`, `-std=c++20 -O2 -Wall -Wextra -Werror`. It
checks:

- libc++'s strings, containers and algorithms;
- an exception across four frames;
- a thread with a mutex;
- `std::filesystem` over the boot package;
- the sysroot's WitOS headers: the ABI-1 version it was compiled with is the one the kernel reports through `QUERY`.

The scenario boots the release kernel and runs in both suites, in its own command (`sysroot [--arch]`) and in CI's
`linux-host` job.

## Tests

- **Windows:** `sysroot` and `sysroot --arch arm64` pass with `[SYSROOT] clang driver program on <isa>: 6 checks passed,
  0 failed`. The x64 suite now has 27 scenarios and the ARM64 suite 21.
- **Linux (the container):** both architectures pass the same way.
- The host tests and `format-check` pass.

## Limits kept explicit

- There is no `crt1.o`, so a non-PIE static program cannot be built against the sysroot.
- The triple is still the Linux musl one; WitOS's own triple is T4.
- The sysroot holds no Linux kernel headers. Code that includes `<linux/…>` does not build for WitOS, and that is
  deliberate.
