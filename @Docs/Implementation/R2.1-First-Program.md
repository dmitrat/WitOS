# R2.1 — the first NativeAOT program on WitOS

Plan step R2 brings NativeAOT's Unix form to WitOS. R2.1 is its first slice: the program R1.3 compiled is linked with
the NativeAOT runtime and System.Native and runs in the guest on both ISAs. `tests/Runtime.Witos/Platform.cs` runs as
`/bin/init` under the system layer's root task, and its `Main` returns 0.

Each failure on the way pointed at either the system layer or the way the program was compiled, never at the
runtime. This document records them in the order they appeared and how each was answered.

## What changed

### The program as a publish compiles it

R1.3 gave ILC the least it needed for an object. Run, that object failed in two ways that a real publish never meets:

- **No initialization roots.** Without `--initassembly` for CoreLib, StackTraceMetadata, TypeLoader and
  Reflection.Execution, ILC found no write to `ClassConstructorRunner`'s lock. It folded the never-written static to
  null, and the first class constructor threw `NullReferenceException` before the exception machinery existed.
- **No feature switches.** Without the SDK's switches, `EventSource` initializes at startup. Its EventPipe provider
  (the runtime links `libeventpipe-disabled`) throws, and exception dispatch faults on the event source it is still
  constructing.

ILC now gets what a publish passes:

- **What `Microsoft.NETCore.Native.targets` adds to a program:** `--dehydrate`, `-O`, `-g`, the four `--initassembly`,
  `--generateunmanagedentrypoints:System.Private.CoreLib,HIDDEN`, `--stacktracedata`, `--scanreflection`,
  `--methodbodyfolding:generic`, `--resilient`, the debug header's dynamic symbol and
  `--runtimeknob:RUNTIME_IDENTIFIER=witos-<arch>`.
- **Direct P/Invokes:** `System.Native` and `System.IO.Compression.Native`, the libraries witos builds.
- **The SDK's switches**, pinned with their provenance in `build/runtime/nativeaot-publish.json`. They were captured
  from `Platform.ilc.rsp` of `dotnet publish -r linux-x64 -c Release -p:PublishAot=true -p:InvariantGlobalization=true`
  with the SDK `global.json` pins (10.0.300):
  - 26 switches, each passed as `--feature` and `--runtimeknob`, as the SDK passes them;
  - `System.Diagnostics.Debugger.IsSupported=false`, passed as a feature alone.

  Recapture the list when the SDK changes.

`--systemmodule` is no longer passed, since a publish does not pass it. R1.3's check still holds: `Main` folds to
returning zero.

### The link

`runtime-witos` links the object with clang's driver and the sysroot's options (`Sysroot.DriverOptions`), in the
order `Microsoft.NETCore.Native.Unix.targets` gives:

1. the program;
2. `libSystem.Native.a`;
3. `libbootstrapper.o`, `libRuntime.WorkstationGC.a`, `libeventpipe-disabled.a`, `libRuntime.VxsortDisabled.a` (x64
   alone), `libstandalonegc-disabled.a`, `libaotminipal.a` and `libstdc++compat.a`;
4. `-lpthread -ldl -lm`, which the sysroot's empty libraries answer.

The result is a dynamic executable on musl's `libc.so` and the shared C++ runtime.

### The native libraries

The native build now includes upstream's `libs.native` for witos. `System.Native` needs the GNU declarations of musl
(`struct ucred`, `sched_getaffinity` and the rest), so the native libraries' patch defines `_GNU_SOURCE` for witos as
for Linux and Haiku. It was the one change the libraries needed. The question R1.2b left to R4 is answered here,
because R2 needs `System.Native`. The patch set stays at 17 files.

### What the system layer answers

The runtime and the GC ask the system layer questions it did not answer, or answered wrongly:

- **Memory and limits (`system.c`, new).**
  - `sysinfo` reports the physical memory from the kernel's memory query.
  - `getrlimit(RLIMIT_AS)` (`prlimit64`) reports the data arena that `mmap` reserves in (64 GiB). The GC sizes its
    regions as the smaller of 256 GiB and twice the physical memory, then halves that against `RLIMIT_AS`. Without
    the limit, the GC asked for 256 GiB, which the arena cannot hold. Every other limit, setting a limit and another
    process's limits stay `ENOSYS`.
  - `sched_getaffinity` reports the processors threads run on, as whole words of the mask, as Linux does.
- **The main thread's stack (`memory.c`).** musl's `pthread_getattr_np` measures the main thread's stack by growing
  page after page with `mremap` until the growth fails with something other than `ENOMEM`. With `ENOSYS` it measured
  one page. `mremap` is now `ENOMEM` for growth inside one of the library's mappings or inside the calling thread's
  stack (from `THREAD_QUERY`), and `ENOSYS` otherwise; no mapping grows where it lies, and moving is not implemented.
- **Thread names (`thread.c`).** `prctl(PR_SET_NAME)` and `PR_GET_NAME`, which `pthread_setname_np` and
  `pthread_getname_np` use for the own thread, keep the name in the library's thread record. The kernel knows no
  thread's name, and a new thread inherits its creator's name. NativeAOT's debug runtime asserts that naming succeeds.

### Read-only data is a copy

NativeAOT keeps its GS cookie in `.rodata` (`FEATURE_READONLY_GS_COOKIE`). At startup it makes that page writable,
writes the cookie and makes it read-only again. libwitos's loader mapped every segment that is not writable from the
boot package without a copy, so the `mprotect` failed with `EACCES`.

Now only an executable segment maps from the package. A read-only segment is anonymous memory objects the loader fills,
mapped `READ`, whose mapping keeps the object's rights. This is what the libc's private mapping of a file that does
not execute already was. Code still maps without a copy; data is the process's own.

### compiler-rt's `__clear_cache`

The runtime calls `__clear_cache` to publish code it generates, and on ARM64 the symbol comes from compiler-rt.
`clear_cache.c` joins the compiler-rt pin, compiled unchanged. This program never calls it; see the limits.

### The scenario

`runtime-program` boots the release kernel with the linked program as `/bin/init`, musl's `libc.so` as its dynamic
linker and the shared C++ runtime in `/lib`. The root task must report `/bin/init exited with 0`. `runtime-witos` runs
it on both ISAs after the link. Like `runtime-tryrun`, it is no suite scenario, since the program comes from the
runtime's build on a Linux host.

The `process` scenario's `/bin/init` gains the system layer's new answers, in both suites and on both hosts:

- `sysinfo` and `sysconf(_SC_PHYS_PAGES)`;
- `RLIMIT_AS`, and `ENOSYS` for a limit the libc does not report;
- `sched_getaffinity` against `_SC_NPROCESSORS_ONLN`;
- the main thread's stack from `pthread_getattr_np`;
- a thread's name;
- a read-only page of the program made writable and read back.

## Tests

- **Linux (the container).** `runtime-witos` and `runtime-witos --arch arm64` pass through R2.1:
  - `NativeAOT on witos-x64: tests/Runtime.Witos/Platform.cs ran in the guest as /bin/init and exited with 0`;
  - the same on witos-arm64.
- The layer-2 scenarios pass on both ISAs in the container. The `process` scenario's `/bin/init` reports 73 checks
  on both ISAs.
- **Windows.** `PASS: all 27 kernel integration scenarios` and `PASS: all 21 arm64 foundation scenarios`.
- **Host tests.** 98 pass on Windows and 78 on Linux, and `format-check` is clean.

## Limits kept explicit

- **The program prints nothing.** Its exit code is the evidence: the runtime started, the module initializers ran,
  `Main` returned 0, and the process ended through the runtime's shutdown. Console output needs the class libraries
  above CoreLib, which are not built for witos yet.
- **No acceptance yet.** The M3 acceptance (GC, exceptions, finalization, threads and TLS, waits) is R2.2.
- **Code generation is not ready.** `__clear_cache` executes `DC CVAU` and `IC IVAU` at EL0, which the ARM64 kernel
  does not enable (`SCTLR_EL1.UCI`). Plain memory never executes on WitOS either. Code the runtime would generate at run
  time (thunks, the JIT of R3) needs the double mapping through memory objects that RFC 0015 assigns to R3.
- **Machine-wide sizing.** The GC sizes for the machine's physical memory, not for the process's page quota. Quota
  awareness is R3's `gcenv.unix` work.
- **Harmless failures remain** and stay failures, never pretended answers: `brk` is `ENOMEM` by design, `/proc` and
  `/sys/fs/cgroup` are absent, and `statfs` is `ENOSYS`.
