# D5.1 — The namespace service and the libc's files over it

D5.1 is the first step of D5. Files of mounted volumes reach every process through the libc's ordinary POSIX calls.

The path of a file:

1. The device manager hands its disks to a new NativeAOT service, `/system/Namespace`.
2. The service mounts their volumes through the FAT and ext4 providers of D4.
3. Its endpoint travels to every process in the start message.
4. In each process, the libc sends a path below a mount point to the service over a session channel, while every
   other path stays the boot package's.

This follows the storage document's §21 (a filesystem is a service) and §53–57, and RFC 0008 §12–17 (namespaces and
the existing file APIs). D5.2 puts System.IO over it, and D5.3 loads programs from a volume.

## The path of a disk

- **The device manager** probes its disks as in D3.2–D4.3.
  - Then each disk's resource gives up its block channel without closing it (`ChannelBlockStorage.Detach`).
  - The device manager starts `/system/Namespace` through the process manager, with the grant of a channel to itself.
  - It moves each disk to the service in a `WitNamespaceDisk` message: the device, read-only or not, and the block
    channel in the handle slot. A message marked END follows the last disk.
- **The namespace service** attaches its own window on each block channel; a later `ATTACH` replaces the window, as
  D3.2's protocol allows. It mounts the volumes by an explicit policy until configuration exists:
  - the GPT partition "WitOS ext4" at `/data`;
  - the GPT partition "WitOS FAT" at `/fat`;
  - a disk without a partition table that holds a FAT volume at `/boot`, read-only like its disk.

  The service then answers ready. Its status carries the clients' endpoint: a duplicate with SEND, DUPLICATE and
  TRANSFER of one end of a channel whose other end it receives on.
- **The device manager** forwards that endpoint to the root task in its own ready status.
- **The process manager** (libwitos's `witos_manager_run_services`) keeps the endpoint a service's status carries. It
  gives a duplicate with SEND to every process it starts afterwards, `/bin/init` and everything spawned through it, in
  start message version 5 (`WIT_START_NAMESPACE`).
  - A message holds four handles, so a service that takes a grant does not get the namespace from the manager; it asks
    its creator instead.
  - The libc keeps the endpoint in `WitProcessContext.Namespace`.

## The protocol (`witos/namespace.h`)

- **Connecting.** A client connects once by sending `CONNECT` on the clients' endpoint. In its two handle slots are
  the end of a session channel it made and a duplicate of a memory object of its own: the window, 16 pages.
- **Requests.** From then on the client sends each request on the session and waits for its reply, one at a time.
  Paths, data and listings travel in the window. A path is absolute in the namespace.
- **The operations:**
  - `MOUNTS`, `OPEN` (with the protocol's own flags: read, write, create, exclusive, truncate, directory) and `CLOSE`;
  - `READ`, `WRITE`, `STAT` and `FSTAT`;
  - `LIST`, a directory's entries from an index, as many as the window holds, with the next index;
  - `MKDIR`, `REMOVE` (with `DIRECTORY` for rmdir) and `RENAME` (two paths in the window);
  - `TRUNCATE`, `SYNC` and `READLINK`.
- **Replies** carry an errno value and, where the operation gives one, a stat: kind, permission bits, size, number,
  links, volume, owner, allocation unit, blocks, and the three times in seconds and nanoseconds since 1970 in UTC.

## The service (`src/Services/Namespace`)

- **`MountTable`** resolves a path to its volume and the path within it.
- **`NamespaceSession`** answers each request as POSIX answers it.
  - **Errors.** A filesystem's error maps to one errno value: `ENOENT`, `ENOTDIR`, `EISDIR`, `EEXIST`, `ENOTEMPTY`,
    `ENOSPC`, `EACCES`, `EROFS`, `EBUSY`, `EFBIG`, `EINVAL`, `EOPNOTSUPP`, `EIO`.
  - **mkdir** refuses an existing name (`EEXIST`) and a missing parent (`ENOENT`), unlike `CreateDirectoryAsync`.
  - **Remove** refuses the wrong kind: a directory without `DIRECTORY` is `EISDIR`, a file with it `ENOTDIR`.
  - **Rename** replaces a file with a file and a directory with an empty directory, as POSIX's does. Across volumes it
    is `EXDEV`.
  - **Opened handles.** A stat of a file the session holds open reports the handle's length, as POSIX's stat does
    after a write, even where the provider records the size only when it flushes (FAT).
  - **Defaults.** Entries without POSIX metadata (FAT) report modes 0644 and 0755 (0444 and 0555 read-only), and a
    number hashed from their path.
- **`NamespaceConnection`** serves each client on a thread of its own. When the client closes its session, everything
  it opened is closed.

## The libc (`src/Substrate/libc/namespace.c`, `files.c`)

- **Connecting.** The libc connects at its first path below a mount point and reads the mount points. Each mount
  point's prefix then routes a normalized path to the service; every other path stays the package's, the devices',
  or `/dev/shm`'s.
- **Descriptors.** A descriptor of a volume's file or directory is a remote record holding the service's handle. Its
  duplicates count as references, and the last one closes the handle.
- **The calls:**
  - open with `O_CREAT`, `O_EXCL`, `O_TRUNC` and `O_DIRECTORY` (with `O_APPEND` writing at the size);
  - read, pread, readv, write, pwrite and writev, in transfers of the window;
  - lseek, which asks for the size at `SEEK_END`;
  - fstat, stat and lstat, faccessat and readlink;
  - getdents64 with "." and "..", continued where the caller's buffer ended;
  - mkdir, unlink, rmdir and ftruncate;
  - fsync, which reaches the provider's flush;
  - rename, renameat and renameat2 without flags, newly served (`EXDEV` across volumes, `EROFS` in the package);
  - chdir, fchdir and the `*at` calls from a volume's directories.

## The scenario

- **The package** of `runtime-devices` now holds `/system/Namespace`.
- **The namespace service** mounts `/boot`, `/data` and `/fat`.
- **`/bin/init`** (`tests/User/devices_init.c`) uses the volumes through the libc's POSIX calls, as any program does:
  - On `/data` and `/fat`, it makes, writes, appends to, reads, cuts, lists, renames and removes files and
    directories, and checks each errno value POSIX gives.
  - It reads the loader on `/boot` and is refused a write there (`EROFS`).
  - It leaves `/data/posix-kept.txt`.
- **The host check.** After the boot, the host's `e2fsck` must find the ext4 partition clean and `debugfs` must read
  `/bin/init`'s file.

## Tests

- **`tests/OutWit.OS.Tests`.**
  - The protocol's messages: the C structures' layouts, round trips with a stat's times to the nanosecond before and
    after 1970, a listing's padded entries, disk messages, refused bytes.
  - A session over two FAT volumes in memory:
    - mount points;
    - files created, written, read and stat'ed;
    - a listing in pages of a small window;
    - each POSIX error;
    - a rename that replaces a file;
    - truncate and sync;
    - closing what the session opened.
- **`tests/WitOS.Dev.Tests`.** The data disk's check requires `/bin/init`'s file.

## Results

`runtime-services` passes on both ISAs:

- **Mounts.** The service mounts `/boot` (FAT16, 33,554,432 bytes, read-only), `/data` (ext4 "WITOS EXT4",
  22,020,096 bytes) and `/fat` (FAT12 "WITOS DATA", 8,388,608 bytes).
- **`/bin/init`** passes 46 of 46 POSIX checks.
- **The host check.** After the boot, e2fsck finds the ext4 partition clean and debugfs reads
  `/data/posix-kept.txt`.

## Defects found on the way

- **The service closed its disks.** It received each disk's message in a `using` declaration. Disposing a message
  closes its handles, so the block channel it had just attached closed after the mount. The driver logged that its
  client closed the channel, and the first request got `EBADF` from `CHANNEL_SEND`.
- **No `rmdir` on x64.** musl's `rmdir` calls `SYS_rmdir` where the architecture has it, and the libc had no mapping,
  so it got `ENOSYS`. The libc now maps it to `unlinkat` with `AT_REMOVEDIR`.
- **FAT cannot remove an open file.** The FAT library refuses to remove an open file (`EBUSY`), unlike POSIX, which
  showed when the check left a descriptor open. That limit stays FAT's.

## Limits kept explicit

- **One session per process**, one request at a time under the libc's table lock. A thread blocked on the service
  holds every other file call of the process.
- **No `mmap` of a volume's file** (`ENODEV`). That is D5.2's copy for private mappings and R4.2's memory object for
  shared ones.
- **Rename over an existing entry** removes it first. That is not atomic, unlike POSIX's.
- **flock** locks descriptions alone. Two opens of one volume file do not conflict, since the libc cannot tell they
  name one file.
- **The root directory.** `/`'s listing is the package's; mount points do not appear in it.
- **Fixed mount policy and few disks.** The service mounts by partition name. The device manager moves at most three
  disks before the service starts, since a channel's queue holds four messages.
- **FAT removes no open file** (`EBUSY`), as its library does; ext4 does.
- **No authority below the volume.** Any process may use any mounted volume (§54–56); capabilities over namespaces
  are later work.
