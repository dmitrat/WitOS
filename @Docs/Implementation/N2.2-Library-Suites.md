# N2.2 — The libraries' own test suites

N2.2 completes RFC 0015 §9's gate N2: "NUnit, xUnit, MessagePack, MemoryPack, Math.NET, Roslyn — their own tests in the
guest". N2.1 ran representative tests of the six libraries. N2.2 runs the test suites of their repositories, unchanged,
at the commits their pinned packages were built from.

## The selection (`build/runtime/nuget-suites.json`)

**The repositories.** Each library's repository is pinned at the commit its package names, in its nuspec's repository
element or by its release tag:

| Repository | Package | Commit | SDK |
| --- | --- | --- | --- |
| MessagePack-CSharp | MessagePack 3.1.11 | `242bdad5` | the host's 10.0.300 |
| MemoryPack | MemoryPack 1.21.4 | `0f2fe082` | the host's |
| mathnet-numerics | MathNet.Numerics 5.0.0 | `4435308e` (`v5.0.0`) | 6.0.100 |
| nunit | NUnit 5.0.0 | `110e9112` (`v5.0.0`) | 10.0.401 |
| xunit | xunit.v3 4.0.2 | `0c7aa499` | the host's |
| roslyn | Microsoft.CodeAnalysis.CSharp 5.9.0 | `35d9211b` | 10.0.109 |

A repository whose `global.json` the host's SDK does not satisfy builds with the SDK it names. That SDK is pinned by the
SHA-256 of its linux-x64 archive, which matches the SHA-512 the release metadata publishes. The checkout is shallow,
with the submodules a suite needs (xunit's assertion library), so Nerdbank.GitVersioning is told to read no history
(`NBGV_GitEngine=Disabled`). NuGet's audit is off, as for the runtime tree (R8.1).

**The suites.** Each is a test project built for one framework of its own:

| Library | Suites | Runner |
| --- | --- | --- |
| MessagePack | `MessagePack.Tests` | xunit's console runner 2.9.3 (`tools/net6.0`) |
| MemoryPack | `MemoryPack.Tests` | xunit's console runner |
| Math.NET | `MathNet.Numerics.Tests` | NUnitLite, the project's own program |
| NUnit | `nunit.framework.tests`, `nunit.framework.legacy.tests` | NUnit's `nunitlite-runner` |
| NUnit | `nunitlite.tests` | NUnitLite, the project's own program |
| xUnit | `xunit.v3.assert`, `common`, `core`, `runner.common`, `runner.inproc.console` and `runner.utility` tests | the v3 test project's own in-process runner |
| Roslyn | `Microsoft.CodeAnalysis.UnitTests`, `Microsoft.CodeAnalysis.CSharp.Syntax.UnitTests` | xunit's console runner |

Every runner is in process: WitOS has no `Process.Start`, so VSTest's test host, which runs a suite in a child process,
is not an option. xunit's console runner runs as its own application (`dotnet exec xunit.console.dll Tests.dll`) and
loads the test assembly by its deps.json.

**.NET 10 alone.** The guest has one shared framework, so a suite built for .NET 6, 8 or 9 rolls forward to it
(`dotnet exec --roll-forward Major`). The host runs it the same way. Side by side frameworks are N3.

**Exclusions.** A test leaves both runs only with its reason: `class:` or `method:` and its full name, turned into the
runner's own options (`-noclass`, `-nomethod`, or one NUnit `--where`).

## The run (`RuntimeNuGetSuites`)

1. **Build.** Each repository is fetched under `.tools/nuget-suites` and each suite built with
   `dotnet build -c Release -f <framework>`.
2. **The host.** Each suite runs on the Linux host. Its summary must show no failure, or the command stops: a test
   that fails on Linux too leaves the selection with its reason.
3. **The guest.** The suites' outputs and xunit's console runner are files of the data disk's ext4 volume, under
   `/data/suites`; together they outgrow the boot package's 128 MiB, which stays in memory. The data disk grows to
   hold them (`RuntimeDataDisk`'s size; the volume's inodes follow the file count). The package holds the device
   services, the .NET install and `/etc/apps`. `tests/User/apps_init.c` runs each suite in its directory: a line
   `cd <directory>` of `/etc/apps` names the directory of the commands after it, and apps_init reports it, so the log
   tells whose output follows; each command's exit line gives its duration.
4. **The comparison.** For each suite, the guest must run as many tests as the host, pass as many and fail none.
   NUnit's warnings count as passes: they are its timing assertions (`Warn.Unless` with a maximum time), which the
   emulated processor misses. The counts are compared, not the names, so a test that runs on one side alone must leave
   both: NUnit's tests declared for Linux by `SupportedOSPlatform` or `UnsupportedOSPlatform` ran on the host and were
   skipped in the guest, or the other way round, and are excluded for the platform identity. The report is
   `artifacts/runtime-witos/nuget-suites-<arch>.json`.

5. **Groups.** The suites run for hours in the guest: the run of the fourteen took 5.4 hours of guest time on x64.
   Every suite belongs to a group (`roslyn`, `roslyn-syntax`, `serialization-numerics`, `test-frameworks`), and
   `runtime-nuget-suites --group <group>` builds, runs and compares that group's suites alone, in one boot. CI's
   `nuget-suites` job runs each group on each ISA after `linux-host`, whose legs upload the .NET install and the services
   they built; `runtime-witos` no longer runs the suites, which would take a leg past GitHub's limit for a job.

## Defects found on the way

Each guest failure that no difference explained had a cause in the platform, and each was fixed:

- **`stat("")` named the current directory.** The libc resolved an empty path to the current directory; Linux answers
  `ENOENT`. .NET's host checks its servicing directory with `stat("")` when `CORE_SERVICING` is unset, saw one, and
  turned on its file existence checks, which refuse xunit's console runner: its deps.json, a netcoreapp1.0 template,
  names Microsoft.CodeAnalysis 1.3.0 files the package never shipped. Every xunit v2 suite ended with
  `ResolverResolveFailure` (exit 140). The libc now answers `ENOENT` for an empty path, `AT_EMPTY_PATH` apart.
- **The GC took the machine's memory for the process's.** Math.NET's suite ended with "Out of memory." after nine
  minutes. A process owned at most 256 MiB, and the GC, which finds no cgroup, sized itself by the physical memory and
  committed past the quota. The root task now gives every process `DOTNET_GCTotalPhysicalMemory`, the GC's own knob for
  a container's limit: the smaller of the process's page quota and the memory free when the system started. The GC
  keeps its heap to 75% of it, and an allocation past the heap is an `OutOfMemoryException` of the test that made it.
- **256 MiB a process was too little.** On Linux, Roslyn's and NUnit's suites peak near 400 MB with the GC's heap
  held to 192 MiB, and a guest process also owns its copies of the volume's assemblies (D5.2). A system layer process
  may own 1 GiB (`WIT_PROCESS_PAGE_CAPACITY` 262144), the scenario's guest has 2 GiB, and the page quota still sizes
  no array but one commit's rollback bitmap.
- **CoreCLR's "Out of memory." was a handle quota.** With the memory raised, MessagePack's suite still ended with
  "Out of memory." after fourteen minutes. A libc trace showed CoreCLR's executable allocator failing to map a chunk of
  its double-mapped memory file, and a kernel trace of the refused `MEMORY_OBJECT_CREATE` read `free handles 0` with
  190 objects charged: the libc holds a handle of every 256 KiB chunk of JIT code, so 256 handles a process could never
  hold the 512 objects the object quota allows. `WIT_PROCESS_HANDLE_CAPACITY` became 1024.
- **The kernel's object table was full.** Roslyn's syntax suite then ended with "Out of memory." after an hour, with
  1.7 GiB free. The kernel trace showed the refused object with the process at 401 objects of its 512, 941 handles of
  1024 and the kernel's table of 1024 full. CoreCLR maps every IL assembly with `MAP_SHARED` (the PAL's
  `MapViewOfFile`), and the namespace service makes an object of each 256 KiB of a volume's file a process maps shared
  (R4.2). The suite's assemblies are 624 such chunks: 156 MiB, with the reference assemblies Roslyn's tests compile
  against. The process held a handle of each beside its own objects. Its reservations numbered 3148 of 4096. The kernel
  now holds 4096 objects, and a process may create 1024, hold 2048 handles and keep 8192 reservations, as many as the
  libc's mapping table. In the run of the fourteen suites the kernel's table held more than 1000 objects at once, the
  namespace service 481 objects of its own (the old quota was 512), a .NET process 931 handles and 3157 reservations.
- **No account database.** `Environment.UserName` threw `IOException`: musl's `getpwuid_r` answers `ENOENT` without
  `/etc/passwd`, which .NET takes for an error, where a missing entry would give an empty name. NUnit writes the user
  into every result, so 90 of its tests failed. The .NET install now carries `/etc/passwd` and `/etc/group` with the one
  account every process runs as, root (uid and gid 0, as the libc reports).
- **Culture data.** xUnit's and NUnit's tests run in `en-US` and `fr-FR`, which invariant mode refuses. R4.3 brought ICU
  for them.

The exclusions, each with its reason in the selection, fall into these kinds:

- **Processes.** xunit's runner utility starts processes (`Process.Start`), and NUnit's test properties read
  `Process.GetCurrentProcess()`; WitOS has neither (Compatibility-Differences: Processes).
- **Platform identity.** NUnit's tests declared for Linux run on the host and are skipped in the guest, or the other
  way round, and one infers Windows from "not Linux".
- **Timing.** Tests that give the emulated processor 10 ms to 2 s, or assert a maximum time: xunit's timeout test,
  NUnit's cancellation and stop tests and its collection performance class.
- **Results that vary on Linux too.** Roslyn's deep-nesting parser tests count the errors reported before
  `EnsureSufficientExecutionStack` refuses to go deeper, which the stack and the tiers of the frames decide; MemoryPack's
  generator diagnostics fail under xunit's console runner, which has not loaded `System.Private.Uri` when the tests
  compile (upstream runs them under VSTest).
- **What the guest's volume does not hold.** NUnit's solution tests read the repository's project files; the guest has
  the suite's build output alone.
- **WitOS's differences.** Roslyn's analyzer loading tests change file modes, which the namespace service does not serve
  (Compatibility-Differences: File modes); its shadow copy test creates a named mutex under `/tmp`; MessagePack's
  `DateTimeOffset` test needs time zone data, which the guest does not have; xunit core's message test expects "N
  threads" where one processor gives "1 thread", as on Linux under `taskset -c 0`.

## Limits kept explicit

- **Slices, not every suite.** Each repository has more test projects. The selection takes the ones that test the
  library a program uses, and leaves out those that test build integration (analyzers, MSBuild tasks, the VSTest
  adapters), Windows or .NET Framework.
- **.NET 10 alone.** Suites built for earlier frameworks roll forward; N3 runs them on their own.
- **No out-of-process runs.** Tests that start a process are left out with Compatibility-Differences' reason.
