# D3.1 — The block storage contract, partitions and a cache

D3.1 is the first half of D3, the block layer of the storage document. It lays down the contract every block device,
partition and cache of WitOS serves, with three providers and a GUID partition table reader, all in `OutWit.OS` and all
tested on the host. D3.2 puts the contract on the virtio driver's channel in the guest.

The storage document's order (§107) runs: the contract, storage in memory, the FAT adapter, the virtio storage, the
persistent filesystem of M5, then GPT. D3.1 takes the contract and the providers that need no device. GPT comes now
rather than eighth because the plan's D3 names it. Nothing of OutWit.Common is copied in (§14–15): D4 reaches
`OutWit.Common.Fat` through an adapter.

## The contract (`OutWit.OS.Storage`)

`IBlockStorage` is the draft of §7, completed.

- **Addressing.** Bytes are addressed by offset, with no shared position (§8). An offset and a length are multiples of
  `Info.RequiredAlignment`, which is at least the logical block.
  - §7 leaves byte offsets against logical block numbers open. Offsets let a filesystem address bytes as it
    computes them, and the alignment rule keeps every request on block boundaries.
- **Asynchronous calls.** `ReadAsync`, `WriteAsync`, `FlushAsync` and `DiscardAsync` are asynchronous. Several
  requests may be outstanding at once (§11–13); a provider that serves one at a time says so in
  `Info.MaxOutstandingRequests`.
- **Flush** is a durability barrier (§45, §48): every write that completed before it is durable when it completes,
  and no later write is ordered before it.
- **`WriteOptions.Durable`** is a write that is durable when it completes (FUA, §47).
- **Discard** is optional (§44). `Info.SupportsDiscard` says whether it reaches the device, and a resource without
  it refuses with `NotSupportedException`.
- **`BlockStorageInfo`** carries the fields of §9. Nothing in it is a filesystem's rule (§10): a block size need not
  be a power of two or lie within 512–4096 bytes.

**`BlockStorageBase`** checks what every resource checks before it serves a request:
- disposal: `ObjectDisposedException`;
- alignment: `ArgumentException`;
- the range and the transfer limit: `ArgumentOutOfRangeException`;
- a write or a discard to a read-only resource: `NotSupportedException`;
- a cancelled request, which goes no further.

A derived resource serves only checked requests.

## The providers

- **`MemoryBlockStorage`** is storage in memory (§107, step 2), the reference the tests and the providers above it
  run on.
- **`PartitionBlockStorage`** is a window of a resource: a partition, whose holder has authority over its range alone
  (§24–25, Inv 11). It does not own the resource and passes a flush through.
- **`CachedBlockStorage`** is a cache that is itself a resource (§35–36), chosen where a medium is slow rather than
  everywhere. It holds the least recently used blocks up to its capacity.
  - Writing through, a write reaches the resource before it completes.
  - Writing back, a write stays dirty in the cache until an eviction, a flush or the cache's end writes it. A flush
    writes the dirty blocks in ascending order, coalescing runs, then flushes the resource, so the barrier of §48
    holds. A durable write goes through at once.
  - It serves one request at a time. It generalizes the idea of `OutWit.Common.Fat`'s `BlockDeviceCached` without
    copying its code.
- **`GptPartitionTable`** reads a GUID partition table (UEFI 2.10, §5.3).
  - The primary header at block 1 is checked whole: its signature, revision and size, its own CRC-32, its place,
    the usable range, and the entry array with its CRC-32.
  - The backup header at the last block serves when the primary fails.
  - Every used entry lies within the usable range, and no two overlap.
  - Each `GptPartition` keeps its GUID, its stable identity apart from its place, and opens as a
    `PartitionBlockStorage`.

## Tests

`tests/OutWit.OS.Tests/Storage` has three parts.
- **Conformance** (§113). The same tests run against four providers: memory, a partition, and the cache writing
  through and writing back. They check that the information is consistent, read after write, a write surviving a
  flush, refusal of unaligned requests and requests beyond the end, read-only refusals, a cancelled request going no
  further, disposal, and sixteen concurrent writes and reads.
- **The cache.** Misses then hits; a write-back write waiting for the flush; a durable write going through; an
  eviction writing a dirty block; the cache's end writing the rest.
- **GPT** on synthetic images that the tests build with their CRCs. Partitions with their names and GUIDs; a
  partition as a window that refuses to go beyond its end; the backup serving when the primary header is corrupt;
  corrupt entries in both tables refused by their CRC-32; overlapping entries refused; a disk without a table
  refused.

64 tests pass in `OutWit.OS.Tests`, which CI runs on both hosts.

## Limits kept explicit

- Byte offsets are 64-bit throughout (§80), but `MemoryBlockStorage` holds at most 2 GiB, as an array does.
- No MBR reader. `OutWit.Common.Fat` reads MBR disks itself, and WitOS's disks are GPT or unpartitioned.
- The cache serves one request at a time and keeps no statistics beyond hits, misses and dirty blocks.
- No device serves the contract yet. That is D3.2: the virtio driver's block protocol over its channel, with writes,
  on a second, writable disk.
