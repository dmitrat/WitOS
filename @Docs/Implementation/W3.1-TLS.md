# W3.1 — TLS: OpenSSL in the system layer, cryptography and HTTPS as on Linux

Plan step W3.1 (phase W, M7; W0 decision 4: a pinned OpenSSL, since the unchanged BCL of the Unix form reaches TLS
through `System.Security.Cryptography.Native.OpenSsl` and nothing else). It closes the two "until W3.1" gaps the
compatibility matrix carried since R4.1 and W2.2: every algorithm beyond the hashes threw
`PlatformNotSupportedException`, and `SslStream` and HTTPS had no provider.

## 1. What was measured

- **What the runtime needs.** The native libraries' build (`src/native/libs/CMakeLists.txt`) adds
  `System.Security.Cryptography.Native` on every Unix but Apple's and Android's; its CMake (`extra_libs.cmake`)
  requires `find_package(OpenSSL)` to succeed and compiles against `OPENSSL_INCLUDE_DIR`; a portable build
  (`FEATURE_DISTRO_AGNOSTIC_SSL`, the default of `build.sh`) links neither library and opens `libssl.so.3` at run time
  through `dlopen` (`opensslshim.c`: the override `DOTNET_OPENSSL_VERSION_OVERRIDE`, then the sonames in turn), binding
  368 required functions and lighting up 92 more by version. The cryptography project takes OpenSSL for every unix
  `TargetPlatformIdentifier` (`UseOpenSsl`; the R4.1 patch had switched witos to the browser's managed set). The root
  store on Unix (`OpenSslCachedSystemStoreProvider`) reads `SSL_CERT_FILE` and every file of `SSL_CERT_DIR`, else every
  file of `/etc/ssl/certs`, parsing every certificate of each, so one bundle file serves and no hashed symbolic links
  are needed (D7 is open). NativeAOT's targets link the shim's static library on every Unix but Apple's and Android's;
  the R2.3b patch had excluded witos.
- **OpenSSL on the musl triples.** OpenSSL 3.5.9, the latest of the long-term support series (support until 2030),
  pinned by the SHA-256 its release publishes. Its `Configure` for `linux-x86_64`, `linux-aarch64` and
  `linux64-riscv64` accepts the pinned clang through `CC`, `CFLAGS` and `LDFLAGS` (`--target`, `--sysroot`, the
  sysroot's resource directory for compiler-rt and the crt objects, lld) and generates four files; the public headers
  (28 of 142 from `.h.in`), the DER tables and the rest are perl templates `make` expands, 40 generated targets, which is
  why the tool drives OpenSSL's own build rather than compiling a list of sources as it does ICU's. Two sources include
  the Linux kernel's headers, which the sysroot does not carry (the sanitized kernel headers serve the C++ runtimes'
  build alone): `crypto/mem_sec.c` (`linux/mman.h`, the secure heap) and `engines/e_afalg.c` (`linux/version.h`, the
  AF_ALG engine) — `no-secure-memory` and `no-afalgeng` leave them out; everything else of 804 crypto, 96 ssl and 209
  provider sources compiles unchanged. Each ISA's build takes under a minute on the Linux host and links `libcrypto.so.3`
  (needing `libc.so`) and `libssl.so.3` (needing both).
- **What VMware and the audit taught about the root store.** Nothing of OpenSSL is in the kernel or the libc: the
  libraries are files of the install under `/usr/lib`, as ICU's, and the bundle a file under `/etc/ssl/certs`.

## 2. The change

- **The pins.** `src/Substrate/openssl.lock.json` (OpenSSL 3.5.9 by SHA-256, Apache-2.0, which `setup` requires the
  tarball's LICENSE.txt to state) and `src/Substrate/cacert.lock.json` (Mozilla's CA bundle as curl's project extracts
  it, the extract of 2026-10-20 by SHA-256, MPL-2.0, which `setup` requires the file's header to state, and at least a
  hundred certificates). `setup` downloads both.
- **`Substrate.OpenSsl`.** Builds the libraries of an architecture under `artifacts/openssl/<arch>` on the Linux host:
  an out-of-tree `Configure` with the release's own options — `shared no-asm no-tests no-docs no-apps no-module
  no-secure-memory no-afalgeng --prefix=/usr --openssldir=/etc/ssl --libdir=lib` — then `make` and OpenSSL's
  `install_dev install_runtime_libs` into a staging directory, once for the pin, the options, the toolchain and the
  sysroot's libc. `runtime-witos` builds it before upstream's native libraries and points `FindOpenSSL` at it through
  `-cmakeargs` (`OPENSSL_INCLUDE_DIR`, `OPENSSL_CRYPTO_LIBRARY`, `OPENSSL_SSL_LIBRARY`), so the sysroot stays the layer-2
  header set it is on both hosts.
- **The runtime's patch set.** The native libraries' witos branch builds `System.Security.Cryptography.Native` (no
  GSSAPI still); the cryptography project's patch leaves, so the unix flavour takes OpenSSL on witos as on every unix;
  NativeAOT's targets link the shim's static library on witos as on Linux. 39 files in `release/10.0`.
- **The install.** `libcrypto.so.3` and `libssl.so.3` in `/usr/lib`, beside ICU's libraries, where the shim's `dlopen`
  finds them (musl's default path); the bundle at `/etc/ssl/certs/ca-certificates.crt`. No `openssl.cnf`: OpenSSL
  runs with its defaults.
- **The checks.** `runtime-system-native`'s "cryptography refused" area becomes "cryptography": RSA with PSS and OAEP,
  ECDSA on P-256, AES-GCM and a self-signed X.509 certificate whose chain builds to itself, under `corerun` with the
  shim and the libraries in its package — and the install's account database, since a chain consults the user's
  Disallowed store under the home directory, which .NET asks `getpwuid_r` for when `HOME` is unset, and
  `PersistedFiles` throws the libc's `ENOENT` as an `IOException` where `/etc/passwd` is absent (the first run's failure;
  the check now reports an exception with its first frames). The compatibility suite gains a Cryptography area (random
  bytes, the hashes and HMAC against published vectors, PBKDF2 against RFC 6070, AES-CBC against NIST SP 800-38A, AES-GCM
  with a tampered byte rejected, RSA with its PEM round trip, ECDSA and ECDH, X.509 made, signed, through PEM and
  PKCS#12, a chain to a custom root and one refused without it, the machine's root store) and four Network checks:
  `TlsEcho` (`SslStream` on both ends of a loopback connection with a certificate of the suite's own, trusted by its
  thumbprint), `HttpsGet` (`HttpClient` over HTTPS against the suite's server serving over TLS), `HttpsRunner` (the
  runner's HTTPS server behind QEMU's `guestfwd` at `10.0.2.100:443`, `Host.NetworkPeer`, with a certificate authority
  made for each boot, `Host.RunnerAuthority`, whose certificate the package carries at
  `/etc/ssl/certs/witos-runner-ca.pem`, so that the guest trusts it through the root store alone, and whose address
  `WITOS_HTTPS_PEER` names in `/etc/environment`; not applicable on the hosts, which have no runner) and `HttpsPublic`,
  the strategy's first network test (§66): `https://example.com/` through the guest's DHCP lease, slirp's forwarder and
  Mozilla's bundle, a failure when the handshake fails and not applicable when the network is unreachable.
- **The records.** `Compatibility-Differences.md`'s Cryptography and Networking rows, `build/compatibility-matrix.json`
  (Cryptography Supported) and the matrix; AGENTS.md describes the cryptography of the Unix form as OpenSSL's. The
  `release/8.0` set (N3) keeps the browser's cryptography, and the same change will not follow for .NET 8, whose support
  ends on 10 November 2026: with the pin's move to .NET 11 the versions side by side become 10 and 11 (the author's
  decision of 2026-10-23).

## 3. What ran

- **The hosts.** `DotNetCompatibilityTests` on Windows: 115 checks, 0 unexpected, `Network.HttpsRunner` not applicable
  without a runner; the tool's suite: 139 passed with the new tests of the pins, the runner's authority and the HTTPS
  peer; CI's `boot`, `boot-arm64`, `windows-publish` and `linux-selftest` jobs green on PR #178.
- **x64** (the container, `runtime-witos`, 6604 s, 26 scenarios): OpenSSL 3.5.9 built for the triple and the shim compiled
  against it; `runtime-system-native` `[R4] cryptography: ok`, `12 areas passed, 0 failed`; the PAL suite's 280 tests,
  CoreCLR's 51 runs, the libraries' 2 projects, the M3 acceptances' 32 runs each; `runtime-compatibility` on four
  processors `116 checks, 3 recorded differences, 0 unexpected, 0 not applicable`: the Cryptography area's 11 checks (the
  root store: 119 certificates, 119 authorities — the bundle's 118 and the runner's), `Network.TlsEcho` over TLS 1.3
  (`TLS_AES_256_GCM_SHA384`, the server saw TLS 1.3), `Network.HttpsGet` (200 over https), `Network.HttpsRunner` (200 from
  `https://10.0.2.100/` through the root store's trust; the runner's server answered one request of the guest) and
  `Network.HttpsPublic` (577 characters from `https://example.com/`); CI's x64 leg green.
- **ARM64** (6798 s, 26 scenarios): the same lines — `[R4] cryptography: ok`, 12 areas; 280 PAL tests, 51 CoreCLR runs
  (258 tests in the groups, 49 process-isolated), 5088 library tests in 2 projects; `116 checks, 0 unexpected`, TLS 1.3
  with the same cipher suite, the runner's server through the root store, the public site's 577 characters, 119
  authorities in the root store. CI's arm64 leg: its first run timed out in `runtime-compatibility` (1800 s) with
  `Network.TlsEcho` reporting no result within 60 s of the guest's time while the monitor's samples showed a thread in a
  loop of user code; the second run passed, and the container's run passed the boot in three and a half minutes — a
  flake to watch, not a difference.
- **riscv64** (6749 s, 25 scenarios: no C# REPL, as C2.5 records): `[R4] cryptography: ok`, 12 areas; 280 PAL tests, 50
  CoreCLR runs (258 and 48), 5076 library tests; `116 checks, 0 unexpected` with the same TLS, HTTPS, runner, public site
  and root store lines; CI's riscv64 leg green.
