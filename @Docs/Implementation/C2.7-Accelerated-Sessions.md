# C2.7 — sessions on the host's hardware virtualization

Plan step C2.7 (phase C), made on 2026-10-18 after the author's first session in the window of C2.4: a session a person
works in runs on the host's hardware virtualization instead of TCG, and the first boot of WitOS on a real processor
found what kept it from starting there.

## 1. Why

Scenarios run under TCG with QEMU's instruction clock (`-icount shift=2`), so that a gate's timing is a function of the
guest's instructions alone. A person typing into PowerShell pays for that: each key makes PSReadLine parse and colour
the line, ask for the cursor's position and, at first, have the JIT compile new paths, and under TCG a key took 7 to 16
seconds to appear in the window. The guest idled between keys; the cost was the emulation. Memory or processors for the
guest would not have helped.

## 2. What the step adds

- **`shell --accel`** (`BootRequest.Accelerated`): QEMU's accelerator of the host — WHPX on Windows, KVM on Linux (where
  `/dev/kvm` exists) — and no instruction clock, for a guest of the host's own ISA (an x64 guest on an x64 host); any
  other combination is refused with the reason. It combines with `--window`, `--image` and `--disk`.
- **The MXCSR mask** (`src/Kernel.Arch.X64/user_cpu_context.c`): the kernel probes the mask FXSAVE reports and refused
  anything beyond 16 bits. AMD processors also report MM (bit 17, the misaligned SSE mode), so the first boot on a real
  AMD processor through WHPX ended with `[PANIC] Invalid hardware MXCSR mask` before the scheduler started. The kernel
  now keeps the low 16 bits, the SSE bits a context may carry, so a context never sets MM and the validation of
  `THREAD_CONTEXT_SET` and `EXCEPTION_CONTINUE` is unchanged. A real machine with an AMD processor, and VMware on one,
  would have met the same panic.
- **No terminal probe in a session** (`TerminalProbe`): the device manager's probe waits 30 seconds for a typed line
  before it answers ready, which held `/bin/init` back in every session; the shell's package carries
  `/etc/witos/session`, and the probe skips itself there, as it never does in a scenario.
- **CI**: a `linux-host` leg may run four hours, since riscv64's took 2 h 25 min at its first run (V2.4).

## 3. What ran

- The release kernel with the mask fixed under WHPX on the Windows host (an AMD processor): `Kernel initialized`,
  the root task's mechanism checks and `[ROOT] exit code 0` in 3.2 seconds from QEMU's start, firmware included.
- The prepared x64 session (C2.4's image with the fixed loader and kernel swapped in) under WHPX with the window: the
  prompt after 52.8 seconds, of which 30 were the terminal probe's wait this step removes; a key's echo in about a tenth
  of a second, where TCG took seconds; `Get-Date` at once.
- The full `runtime-witos --arch x64` with this step (63 minutes in the Linux host's image, every boot passed), then a
  session prepared there and booted on Windows under WHPX with the window: `terminal probe: skipped in a session`, the prompt
  after 26.4 seconds from QEMU's start on a fresh data disk, a listing of `/data/apps/bin` with the 0755 launcher, and
  `exit` stopping the services and the machine.

## 4. What the window needs from a remote desktop

QEMU's GTK and SDL windows take a key's scan code. A remote desktop client that sends characters as Unicode input
(`VK_PACKET`) rather than as scan codes — as some clients do — reaches neither: the keys never get to the guest, as
virtual-key input without a scan code does not (C2.4). A local keyboard, or a client that sends scan codes, types.

## 5. Limits

- Only a guest of the host's ISA: an ARM64 or RISC-V guest on an x64 host stays on TCG.
- The guest's time under acceleration is the host's: nothing of a session is deterministic, and the gates keep TCG.
- WHPX needs Windows' Hypervisor Platform feature, KVM a host with `/dev/kvm`; without them `--accel` is refused.
